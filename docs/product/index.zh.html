主要场景

多源证据审查流水线

该工作流需要长时间运行的工作、并行证据提取、持久化决策、增量重计算和质量测量。

1 · 定义创建一个 owner 范围的项目，包含研究目标、约束和数十到数百个文档或 Web 来源。
2 · 摄取通过可重试的后台任务验证、上传、校验和、解析、去重、版本化、分块、嵌入和索引来源。
3 · 规划将研究目标分解为有界子问题，并持久化暂停、恢复或重放所需的 LangGraph 状态。
4 · 提取并行检索证据，提取结构化声明，保留精确引文和位置，并测量覆盖率。
5 · 对账将声明关系分类为支持、矛盾、重复或仅提及；显示未解决的缺口。
6 · 审查暂停低置信度结论、不可信 Web 证据和 prompt-injection 信号，等待批准、编辑或拒绝决策。
7 · 综合生成证据支撑的报告，然后在来源变更时仅刷新受影响的声明和章节。
8 · 验证运行版本化评估实验并检查 trace、延迟、token 使用、成本、错误、重试和恢复。
故障与恢复合约：提供商超时在策略内重试；中毒的摄取项变为可见的失败任务；不确定的结论暂停等待审查；进程重启从持久化 checkpoint 恢复；跨存储删除持续对账直至每个目标达到终态。

GitHub 联邦登录和租户隐私 OAuth 已上线 + 项目隔离已验证
结果
让用户通过 GitHub 进入，同时每个项目、上传对象、向量、队列消息和 trace 仍限定在拥有它的 Supabase 用户范围内。
当前证据
免费的 GitHub OAuth App 已通过 Supabase Auth 上线。Vercel Production 以只读 email scope 重定向到 GitHub，Supabase 完成回调，浏览器从地址栏移除返回的 token，Render 接受生成的 JWT。GitHub 身份创建/刷新了自己的项目，未列出密码用户的项目，并对其他用户的 Library 收到隐藏的 not-found。十个封闭 auth 测试、21 个前端/文档合约测试、GitHub Actions 运行 30237992253 和已部署的回调均通过。
选定的免费方案
一个免费的 GitHub OAuth App 连接到现有的 Supabase Auth 项目。未添加应用部署：GitHub 认证，Supabase 签发 JWT，Vercel 托管 Web 客户端，Render 仍是唯一的后端部署。Google 仍为可选，将复用相同的边界。
凭据处理
活跃的 Client Secret 仅存在于 GitHub 和 Supabase Authentication → Providers → GitHub 中。一个曾出现在自动化输出中的初始密钥被立即轮换并撤销；替换密钥在浏览器内存中传递后清除。没有 GitHub 凭据存储在 Vercel、Render、源码、终端或应用浏览器存储中。
隔离合约
授权仅使用已验证的 JWT sub UUID，从不使用 email 或 GitHub 用户名。PostgreSQL 将显式 API owner 断言与 RLS 结合。对象键保留在私有存储桶中的 users/{user_id}/projects/{project_id}/documents/{document_id}/… 下，签名 URL 仅在所有权检查后以短过期时间签发。每个 Qdrant upsert/query/delete 都需要 user_id 和 project_id 过滤器。Redis 携带标识符而非源字节；日志和 Langfuse 省略 prompt、文档文本、token 和密钥。
加密边界
TLS 保护传输，托管提供商保护存储的媒体；这不是端到端加密，因为解析、检索和生成需要服务器处理明文。应用级信封加密是后续威胁模型选项，不是当前声明，因为它增加了密钥轮换和 worker 解密复杂性。
剩余验收
上传一个合成文档并证明跨用户 reserve/commit/delete 拒绝、过期签名 URL 失败和零结果跨租户 Qdrant 搜索。还应在已部署环境中测试提供商撤销、会话过期/刷新、直接数据库 RLS 和同邮箱账户关联行为。
