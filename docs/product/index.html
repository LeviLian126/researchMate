Product scope and evidence-review workflow

This page defines the product scope and records its delivery evidence. It describes the primary workflow, current repository behavior, implemented integrations that remain unvalidated, and the deployed evidence required before the public demo can claim reliability.

Product boundary

Audience and success criteria

Primary audience

Recruiters, interviewers, and engineers evaluating AI full-stack design, backend depth, data contracts, reliability, and delivery discipline.

Demo user

A researcher, learner, or analyst who needs to review a large bounded source collection and preserve the evidence behind every conclusion.

Portfolio promise

Every important claim about the system should be inspectable through code, contracts, automated tests, evaluation results, runtime traces, or deployment evidence.

First meaningful success

A reader can understand the architecture quickly, run a grounded workflow, inspect its evidence and trace, and discuss at least one measured engineering trade-off.

Commercial state: this is intentionally not a commercial SaaS. There is no target buyer, price, subscription, payment flow, sales funnel, or revenue objective. Demo usage validates engineering behavior rather than market conversion.

Primary scenario

Multi-source evidence review pipeline

The workflow requires long-running work, parallel evidence extraction, durable decisions, incremental recomputation, and quality measurement.

1 · DefineCreate an owner-scoped project with a research goal, constraints, and tens to hundreds of documents or web sources.
2 · IngestValidate, upload, checksum, parse, deduplicate, version, chunk, embed, and index sources through retryable background jobs.
3 · PlanDecompose the research goal into bounded sub-questions and persist the LangGraph state required to pause, resume, or replay.
4 · ExtractRetrieve evidence in parallel, extract structured claims, preserve exact quotations and locations, and measure coverage.
5 · ReconcileClassify claim relationships as supporting, contradicting, duplicating, or merely mentioning; surface unresolved gaps.
6 · ReviewPause low-confidence conclusions, untrusted web evidence, and prompt-injection signals for an approve, edit, or reject decision.
7 · SynthesizeGenerate an evidence-backed report, then refresh only impacted claims and sections when sources change.
8 · ProveRun versioned evaluation experiments and inspect traces, latency, token use, cost, errors, retries, and recovery.
Failure and recovery contract: a provider timeout retries within policy; a poisoned ingestion item becomes a visible failed job; an uncertain conclusion pauses for review; a process restart resumes from a durable checkpoint; a cross-store deletion is reconciled until every target reaches a terminal state.

Selected free solution
One free GitHub OAuth App connects to the existing Supabase Auth project. No application deployment was added: GitHub authenticates, Supabase issues the JWT, Vercel hosts the web client, and Render remains the only backend deployment. Google remains optional and would reuse the same boundary.
Credential handling
The active Client Secret exists only in GitHub and Supabase Authentication → Providers → GitHub. A first secret that appeared in automation output was immediately rotated and revoked; the replacement was transferred in browser memory and cleared. No GitHub credential is stored in Vercel, Render, source, terminal, or application browser storage.
Isolation contract
Authorization uses only the verified JWT sub UUID, never email or GitHub username. PostgreSQL combines explicit API owner predicates with RLS. Object keys remain under users/{user_id}/projects/{project_id}/documents/{document_id}/… in a private bucket and signed URLs are issued only after ownership checks with short expiry. Every Qdrant upsert/query/delete requires user_id and project_id filters. Redis carries identifiers rather than source bytes; logs and Langfuse omit prompts, document text, tokens, and secrets.
Encryption boundary
TLS protects transit and managed providers protect stored media; this is not end-to-end encryption because parsing, retrieval, and generation require the server to process plaintext. Application-level envelope encryption is a later threat-model option, not a current claim, because it adds key rotation and worker decryption complexity.
Remaining acceptance
Upload a synthetic document and prove cross-user reserve/commit/delete denial, expired signed URL failure, and zero-result cross-tenant Qdrant search. Also test provider revocation, session expiry/refresh, direct database RLS, and same-email account-linking behavior in the deployed environment.
