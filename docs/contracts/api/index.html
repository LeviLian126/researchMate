Request conventions

Authentication, ownership, and errors

Authentication

GET /api/v1/healthz and GET /api/v1/readyz are public for platform probes. Every other REST operation declares HTTP bearer authentication. Local/test mode accepts only named or explicit dev: identities; unknown tokens fail closed. Preview/production requires Supabase JWT mode. On 27 July 2026 password and GitHub OAuth identities authenticated from Vercel to the Live Render API, each completed owner-scoped project create/list/read across a browser refresh, and the GitHub user received a concealed not-found response for the password user's Library. Session expiry/revocation and a direct database RLS denial query remain provider-unvalidated.

Ownership

Handlers resolve a CurrentUser; Store lookups scope resources to that user. A missing resource and another user's resource both return 404 to avoid disclosing identifiers.

Error envelope

Runtime failures use {"error":{"code","message","request_id"}}. Request validation is normalized to VALIDATION_FAILED; the same validated/generated request ID is returned in X-Request-ID.

Federated identity rule. Adding GitHub through Supabase Auth does not change authorization semantics: the verified JWT sub UUID is the only tenant identity. Email address, GitHub login, display name, and provider metadata must never be used as an ownership predicate.
Known OpenAPI/runtime difference. OpenAPI still declares generated HTTPValidationError bodies for some 422 responses while runtime handlers normalize validation to the project error envelope. Ask and Quiz can also return runtime 409 and 429 responses not present in their OpenAPI response maps.

GET /api/v1/readyz — check non-charging dependency readiness
Caller / access
Deployment platform, readiness smoke, or operator. Public; no bearer token and no private payload.
Input
Optional verbose boolean query parameter. Pass ?verbose=true to receive the full component snapshot. In production and preview environments the default is the minimal payload so component state and failure lists are not exposed at the public entrypoint; local and test environments default to verbose for operator iteration.
Success
200 with status:"ready" and environment. When verbose resolves to true the response also includes components (state per non-charging dependency; local/memory dependencies may be not_required) and an empty failed_components list. The minimal non-verbose payload omits components and failed_components entirely.
Failure / semantics
503 with status:"not_ready"; in verbose mode also failed_components with safe component names, never topology details. It executes select 1 for Postgres, verifies the four SDK-owned checkpoint tables, checks fresh worker/dispatcher heartbeats, rejects stale or exhausted outbox work, pings Redis, and reads Qdrant collection metadata. S3-compatible object storage, LLM, and web search remain configuration checks only, so it never spends NVIDIA or Tavily quota.
Current boundary
On 1 August 2026 backend correction c5c89f5 became Live and public liveness plus combined readiness returned HTTP 200; Postgres, Redis, Qdrant collection access, worker/dispatcher heartbeats, outbox state, and checkpoint tables were ready. Authenticated production acceptance passed ordinary chat, text-layer PDF upload/indexing, grounded answer and page citation, Web search, project Quiz generation and refresh recovery through frontend correction ce54452, conversation deletion, and project deletion.
Evidence
routers/health.py · tests/test_runtime_foundation.py · tests/test_http_security_hardening.py · infra/openapi/openapi.yaml
Information-leak reduction
The verbose parameter and the production-mode minimal default were added on 7 August 2026 so the public readiness endpoint no longer leaks dependency topology, component state, or failure lists. Operators and integration tests can opt back in with ?verbose=true; the existing local/test verbose default preserves ergonomic iteration. Coverage lives in tests/test_http_security_hardening.py.

POST /api/v1/documents/{document_id}/complete — verify upload and request ingestion
Caller / access
Document owner.
Input
document_id: UUID. Body may be omitted or null; when present, UploadCompleteRequest accepts optional checksum and extracted text.
Success
202 object containing job_id.
Failure / semantics
404 DOCUMENT_NOT_FOUND; 409 UPLOAD_SIZE_MISMATCH or UPLOAD_TYPE_MISMATCH; 503 object-storage verification failure; 422 validation; auth failures. The memory repository deliberately keeps the synchronous extracted-text fallback. The Postgres repository verifies S3-compatible metadata, then atomically writes the parsing state, pending job, and unique outbox event; a repeated completion returns the existing job. The worker verifies an optional SHA-256 checksum before parsing.
Async / recovery
The outbox dispatcher publishes a deterministic task ID. The Celery consumer uses an expiring Postgres lease, deterministic page/chunk IDs, bounded retry, and explicit ready/failed terminal states. The production text-layer PDF path reached ready and returned a page citation. PDF parsing defaults to low-memory pypdf; scanned PDFs without a text layer terminate with PARSER_TEXT_LAYER_NOT_FOUND and do not invoke Docling automatically.

POST /api/v1/ask — continue a unified conversation
Caller / access
Project owner. Current local quota is 200 Ask requests per user per day.
Input
Strict JSON AskRequest: project UUID, optional conversation UUID, message, and web_enabled. Unknown or retired fields fail validation.
Success
200 AskResponse: conversation and run UUIDs, answer, source summary, citations, trace UUID, and validation status.
Failure / semantics
With no ready documents and Web off, this is ordinary persistent chat and skips embedding, Qdrant, rerank, and citation validation. Ready local documents activate Hybrid RAG; small corpora up to approximately 12,000 tokens use full context, while larger corpora use BM25 plus dense retrieval, RRF, rerank, and an approximately 8,000-token evidence budget. Web adds up to five bounded Tavily results. Uploaded documents still processing return 409 DOCUMENT_PROCESSING. Provider failures are explicit or recorded as degraded deterministic reranking.

Extended contracts

Evidence-review, evaluation, reliability, and MCP operations

The generated OpenAPI now contains 49 REST operations, including personal-chat bootstrap, cross-workspace conversation navigation, conversation-scoped attachments, owner-scoped conversation CRUD, the bounded upload proxy, runtime reranking, and the three-operation answer-feedback review loop. Their route, schema, ownership/role, idempotency, and deterministic repository behavior have code evidence. The feedback workflow is locally verified; its managed migration and production journey remain release evidence, not current proof. MCP is a separate protocol boundary and is not counted as REST.

Shared conventions: bearer authentication; owner/project permission checks in the API; Idempotency-Key on commands; the current error envelope with a request ID; authoritative operation state in Postgres; persisted SSE replay; and Redis as delivery rather than irreplaceable state. Supabase JWT-backed project create/list/read is validated for password and GitHub identities and cross-user API concealment passes. A direct RLS query and distributed delivery are not yet validated.
How to read the rows: request and success shapes describe the implemented route schemas. Local LangGraph, RAGAS, strict-checkpoint serializer, and MCP initialization tests now pass. Failure/recovery and acceptance rows still name distributed-system gates; they are not evidence that a managed checkpoint, provider, queue, or cloud runtime passed.
POST /api/v1/research-runs — start an evidence review implemented contract · runtime unvalidated
Caller / access
Authenticated project owner. The route verifies project, accepted pipeline, and every explicitly selected ready document. Daily and concurrent-run quotas remain unvalidated; the worker enforces the per-run cost ceiling before each model call.
Request
{ project_id: UUID, research_goal: string 20..12000, source_scope: {document_ids?: UUID[], allow_web: boolean}, pipeline_version_id: UUID, review_policy: "strict"|"balanced", max_cost_usd?: decimal }; required Idempotency-Key.
Success / async
202 { run_id, status:"pending", status_url, events_url, created_at }. Postgres commits run and outbox intent before queue publication.
Failure / recovery
404 PROJECT_NOT_FOUND; 409 PIPELINE_NOT_ACCEPTED, SOURCE_DOCUMENT_NOT_READY, SOURCE_SCOPE_EMPTY, or duplicate key with mismatched body; request validation rejects duplicate document IDs. During execution WORKFLOW_BUDGET_EXCEEDED, invalid pipeline configuration, or provider failures produce a durable failed run. A matching command duplicate returns the original operation.
Acceptance
One logical run is created for repeated delivery; owner isolation holds; duplicate task delivery acquires at most one expiring workflow lease; an existing checkpoint resumes without replaying initial input; outbox recovery dispatches after an API crash.
