Interview guide . FastAPI request flow / JWT auth / raw-SQL persistence

Backend interview guide . apps/api

The backend is the FastAPI app under apps/api. It receives an HTTP request, verifies who the caller is, reads from or writes to Postgres with hand-written SQL, and returns a shaped JSON response. This page covers the five topics worth defending in an interview: the request flow, JWT authentication, raw-SQL persistence, fail-closed error handling, and configuration validation.

5 interview topics Raw SQL . no ORM Protocol-based services Pydantic Settings gates

Minimum mental model

What the backend owns, in five lines

Read this first. Every later section assumes you understand the request flow at this level.

What it is

A FastAPI app that exposes REST under /api/v1 and an MCP (Model Context Protocol) surface at /mcp. The app is assembled by create_app() in main.py; the module-level app = create_app() is what the ASGI server loads.

Request flow

Request → attach_request_id middleware (X-Request-ID, security headers, IP rate limit) → router handler → get_current_user → GroundedQueryService.execute → repository + providers → JSONResponse.

Key dependencies

FastAPI + Pydantic v2 + SQLAlchemy Core (no ORM) + psycopg; Qdrant hybrid retrieval; OpenAI SDK talking to NVIDIA NIM; slowapi for per-IP rate limits on /healthz, /me, /mcp.

Worth digging into

(1) FastAPI request flow and dependency injection; (2) Supabase JWT authentication; (3) raw-SQL persistence with manual Pydantic mapping; (4) fail-closed typed error handling; (5) Pydantic Settings production gates.

Topic 1 . FastAPI request flow

How a request enters, gets authenticated, and returns

[Project fact] Every request goes through one middleware, then a router, then a service, then a repository. Dependencies are built once at startup, not per request.

Conclusion first. When a request lands, the first thing that runs is attach_request_id middleware. It assigns a request id (from the X-Request-ID header if valid, otherwise a fresh req_<hex>), attaches security headers, and applies an IP-bucketed rate limit on a few cheap endpoints. After middleware, FastAPI dispatches to a router handler. Routers take two dependency callables — Depends(get_current_user) for the caller identity and Depends(get_store) for the repository. The handler invokes GroundedQueryService.execute(...), which orchestrates retrieval, generation, and persistence, then returns a JSONResponse with X-Request-ID echoed back.

The reason dependencies live on request.app.state is construction cost. S3CompatibleObjectStorage, QdrantHybridStore, RerankCoordinator, and PostgresResearchMateRepository each open network connections or load credentials. Building them per request would be wasteful. So create_app() builds each adapter once and stores it on app.state; the get_* dependency functions just read from state.

Key mechanisms

  • State-resolved dependencies: get_store(request) returns request.app.state.store; the same pattern holds for get_chat_provider, get_hybrid_store, get_reranker, get_object_storage. Adapters are built once in create_app().
  • Request id propagation: The middleware stores the id on request.state.request_id, the global error handler reads it back, and it is set on every response. Every error body carries request_id so a single user report links to one entry in the log search.
  • Per-IP rate limit: slowapi's Limiter gates /api/v1/healthz, /api/v1/readyz, /api/v1/me, and /mcp at 60/minute per IP. The bucket key is researchmate-api:protected so all four paths share one bucket — a client hammering /me also drains its /healthz budget.
  • Security headers: Cache-Control: no-store, X-Content-Type-Options: nosniff, Content-Security-Policy: default-src 'none'; frame-ancestors 'none', Strict-Transport-Security, X-Frame-Options: DENY. Applied on both success and error responses inside the middleware's finally-shaped flow.
  • Optional middleware features: slowapi is wrapped in a try/except ModuleNotFoundError; the MCP SDK the same. Missing optional deps shrink the surface (no rate limit, MCP returns 503) instead of crashing startup.
[Project fact] MCP identity is resolved in the middleware, not in a router. For /mcp requests the middleware itself extracts the Bearer token, calls resolve_bearer_token(token, settings) in a thread (via anyio.to_thread.run_sync), and places an MCPRequestIdentity onto a ContextVar (current_mcp_identity). MCP tool handlers then read the user, repository, and providers off that context — there is no per-tool Depends(get_current_user) on the MCP path.
[Project fact] Middleware execution order. Each request walks a fixed order: (1) the middleware takes a candidate value from the configured request-id header, generates a fresh req_<hex> if it fails the regex, and stores it on request.state; (2) a rate-limit check runs on RATE_LIMITED_PATHS, returning 429 when the bucket is exceeded; (3) only on the /mcp path, it resolves the bearer token and populates the current_mcp_identity ContextVar; (4) it awaits the downstream handler's response; (5) it writes the request id back onto the X-Request-ID response header; (6) it iterates over every configured security header and applies each one to the response.

Interview question trees

Q1. Why build adapters in create_app() instead of per request?

  • └─ What goes wrong if you don't? → Network connections opened on every request; credential parsing per request; cold clients thrash the upstream. [Project fact] Adapters on app.state are reused for the life of the process; the dependency functions just return the cached instance.
  • └─ Cost of this choice? → Restart required to pick up new settings (a @lru_cache on get_settings() also enforces this). Acceptable because Render redeploys rather than live-reloads production.

Q2. Why share one rate-limit bucket across four paths?

  • └─ What would separate buckets buy? → Each path has its own 60/min ceiling. [Reasonable inference] The team made /me and /healthz share one bucket so an attacker hammering the auth edge also burns the health probe — making blast radius visible to monitoring that only watches /healthz.

Q3. What happens when slowapi or the MCP SDK is not installed?

  • └─ [Project fact] Module-level try/except ModuleNotFoundError sets the symbols to None; create_app skips the limiter branch and mounts a stub /mcp handler that returns 503 MCP_RUNTIME_NOT_INSTALLED. Startup never fails on optional deps.

Topic 2 . Authentication

Supabase JWT with a dev-only static-token bypass

[Project fact] get_current_user is the only auth path. Every protected router takes Depends(get_current_user); there is no second auth middleware.

Conclusion first. Authentication needs to answer one question: "Is this caller who they say they are?" The mechanism is a Bearer token in the Authorization header. get_current_user reads the token via HTTPBearer(auto_error=False), resolves it to a CurrentUser, and writes the user's profile row so downstream owned resources always have a foreign key. There are two resolution paths: a static-token dev path keyed by DEV_USERS, and a Supabase path that verifies the JWT against JWKS. The dev path is gated by auth_mode == "development" and allow_dev_auth == True — both flags must be set; flipping AUTH_MODE=development alone does not unlock static credentials.

Key mechanisms

  • Bearer extraction with auto_error=False: A missing or empty token is handled explicitly inside get_current_user as 401 AUTH_REQUIRED. The default auto_error=True would return 403, which is the wrong status — 401 means "please authenticate", 403 means "authenticated but forbidden".
  • Dual-mode resolver: resolve_bearer_token(token, settings) branches on settings.auth_mode: "development" → _development_user, otherwise → _supabase_user.
  • Dev gate: Even in development mode, allow_dev_auth=False logs development_auth_rejected and returns None → 401. The two flags are intentionally separate so a deploy-time typo on AUTH_MODE cannot by itself unlock static tokens.
  • Profile ensure: After identity resolution, repository.ensure_user(user) upserts the profiles row (see insert ... on conflict (id) do update set email = excluded.email, role = excluded.role). Foreign-key constraints on projects, uploads, chunks require a profiles row to exist; ensuring it first means any later write never trips the FK.
[Project fact] Supabase path. PyJWKClient is cached via @lru_cache(maxsize=4) so the JWKS fetch happens once per jwks_url. jwt.decode validates RS256/ES256, aud=authenticated, iss=ACCESS_TOKEN_ISSUER, and requires the claims exp, iat, sub, aud, iss. Role comes from app_metadata.role and is clamped to {"developer","admin"}, otherwise "user" — a caller cannot elevate themselves by editing the JWT.
[Reasonable inference] The two-flag gate exists because operators run preview/production with the env name already set. Without allow_dev_auth as a second switch, a single-line typo on AUTH_MODE would unlock hardcoded bearer tokens in front of real users.
[Project fact] Auth entry flow. Authentication has a single entry point and runs in this order: (1) missing credential → immediately raise 401 AUTH_REQUIRED; (2) take the bearer token out of the credential and trim it; (3) hand the token to the resolver (which branches on settings to the dev path or the Supabase path); (4) resolver returned None → raise 401 INVALID_TOKEN; (5) call ensure_user to upsert the profiles row for the resolved user; (6) return the user to the router.

Interview question trees

Q1. Why two auth modes instead of just Supabase everywhere?

  • └─ What does the dev path buy you that Supabase doesn't? → Local tests and CI run without network or JWKS; deterministic UUIDs (e.g. 00000000-...-000000000001 for dev) let fixtures assert on real ids.
  • └─ How do you keep dev tokens out of prod? → allow_dev_auth defaults to False and is rejected inside validate_security_boundary when app_env is preview/production.

Q2. Why HTTPBearer(auto_error=False) instead of letting it raise 403?

  • └─ Why is 403 wrong for a missing token? → 403 says "we know who you are, but you can't do this"; a missing token means we don't yet know who you are — that's 401. Using raise_api_error(401, "AUTH_REQUIRED", ...) also gives clients one consistent error: {code, message, request_id} body across all auth failures.

Q3. What if JWKS is down or slow?

  • └─ PyJWKClient(cache_keys=True) caches signing keys in memory; the first request after a key rotation blocks on the fetch. [Reasonable inference] The source has no explicit TTL refresh, so a forced rotation could keep 401-ing on the cached old key until the LRU evicts.

Topic 3 . Persistence layer (raw SQL)

Why no ORM: hand-written text() SQL + manual Pydantic mapping

[Project fact] All Postgres access goes through PostgresResearchMateRepository, a class composed of 11 mixins that wrap sqlalchemy.text() calls. Rows are hydrated into Pydantic DTOs by hand.

Conclusion first. The team did not use SQLAlchemy ORM. There is no declarative_base, no Session with model instances, no attribute-style access on row objects. Writes use text("insert into projects ... where exists (select 1 from profiles ...)"); reads use connection.execute(text(...)).mappings().one_or_none() and then ProjectRecord.model_validate(dict(row)). Owner isolation — every where clause repeats and user_id = :user_id — is enforced in SQL, never delegated to a database row-level security (RLS) role on the connection.

The reason to skip ORM is auditability. Every owner-scope filter lives in the diff, not behind a relationship attribute. If an engineer forgets user_id on a query, the missing filter is visible in code review. The trade-off: you give up the ORM's session lifecycle, attribute access on model instances, and lazy-loading — and you take on the work of writing every SQL statement by hand.

Key mechanisms

  • Engine per repository: create_engine with pool_pre_ping; the engine is owned by PostgresRepositoryCore. Transactions come from self._transaction(user), a context manager that yields a Connection and binds the owner id into the call site.
  • Owner scoping in SQL, not RLS: Every query repeats and user_id = :user_id. The earlier "request.jwt.claim.sub" RLS pattern referenced in older docs is not present in the current _postgres_projects.py source.
  • Upsert via on conflict: ensure_user uses insert ... on conflict (id) do update set email = excluded.email, role = excluded.role. ensure_personal_project uses on conflict (user_id) where kind='personal' and deleted_at is null.
  • Manual Pydantic hydration: connection.execute(text(...)).mappings().one() → dict(row) → ProjectRecord.model_validate(dict(row)). The Pydantic model is a DTO (data-transfer object), not a table mirror.
  • Mixin composition: PostgresResearchMateRepository inherits ProjectPersistenceMixin, UploadPersistenceMixin, DocumentLifecycleMixin, RunPersistenceMixin, ... through 11 mixins, with shared helpers from PostgresRepositoryCore (_enum_value, _json, _safe_filename).
[Project fact] Project deletion is a state machine in one transaction. delete_project opens one transaction, runs select status, kind from projects ... for update to take a row lock, refuses kind='personal', transitions status='active' → 'deleting', fails in-flight parse_and_index_document jobs, collects every r2_object_key and qdrant_point_id that needs cleanup, inserts a delete_project job, and enqueues the background deletion task. Re-invoking on a project already in 'deleting' returns the existing job — the row lock serializes concurrent callers.
[Project fact] Project insert execution pattern. The whole write path sits inside a user-scoped transaction: parameter-bound SQL inserts id, user_id, name, kind, expires_at into the projects table; the insert carries a where exists (select 1 from profiles where id = :user_id) guard so a missing profile row silently returns zero rows; the returning clause brings back every column the Pydantic model needs in one round-trip; finally the row dict is hydrated into the DTO through ProjectRecord.model_validate. Every id flows through a bound parameter — never string interpolation.

Three small things in this insert are deliberate: the where exists (select 1 from profiles ...) guard makes a missing profile row cause the insert to silently return zero rows rather than raise an FK error — which is why the auth flow's ensure_user runs first. The ::text-bound :user_id parameter means the id never reaches SQL via string interpolation. And the returning clause lets the insert return exactly the columns the Pydantic model needs, avoiding a second select.

Interview question trees

Q1. Why raw SQL instead of SQLAlchemy ORM?

  • └─ What do you lose? → Session lifecycle, attribute access on instances, lazy-loading. [Reasonable inference] The team chose explicit SQL so every owner-scope filter is auditable in one file and so hand-written queries compose cleanly with the Qdrant + JSON payload mix the Ask path uses.
  • └─ What do you gain? → The SQL in the diff is the SQL that runs at runtime — no generated SQL to trace. Every where user_id = :user_id is a line someone reviewed.

Q2. Why mixin composition instead of one fat class?

  • └─ What breaks with 11 responsibilities in one file? → A 1000+ line file, merge conflicts on every PR. Mixins split by aggregate (Projects, Uploads, Runs, Chunks ...) keep each change scoped to the aggregate that owns it.
  • └─ Cost? → Method resolution order; TYPE_CHECKING stubs like _transaction: Callable[..., AbstractContextManager[Connection]] carry the cross-mixin contract in ProjectPersistenceMixin.

Q3. How is owner isolation enforced?

  • └─ Per-query user_id parameter, never a database role. [Optimization suggestion] A Postgres RLS policy keyed on a per-request role would catch a forgotten user_id filter as a backstop; the team has chosen to rely on code review of explicit SQL.

Q4. What guarantees does select ... for update give the deletion flow?

  • └─ A row lock held to the end of the transaction; concurrent delete_project calls on the same project serialize on that lock. The second caller sees status='deleting' already and short-circuits to returning the existing job.

Topic 4 . Error handling

Fail closed at boundaries, typed domain errors, one global envelope

[Project fact] Errors follow a four-layer shape: provider SDK exceptions → typed domain errors → HTTPException with structured detail → global handler normalizes to {"error": {code, message, request_id}}.

Conclusion first. Imagine the LLM provider throws an OpenAIError mid-request. If the router handler raised that raw, three things would break: the client would see an internal SDK message, the error shape would differ from every other error in the API, and the OpenAPI client would have no schema for it. So the project wraps every provider boundary. generate_answer raises an AnswerGenerationError(code, message, status_code). GroundedQueryService.execute catches it and re-raises as GroundedQueryError(exc.code, exc.message, exc.status_code) from exc. The only sanctioned ways to surface an error in a handler are raise_api_error(status_code, code, message) (for terminal API errors) and raise_grounded_error(code, message, status_code) (for service errors). HTTPException's detail is always {"code": ..., "message": ..., "request_id": ...}.

Key mechanisms

  • AGENTS.md rule: Never bare except Exception: pass. Catch a specific class, log with context, then re-raise a typed domain error. Provider boundaries may catch the broadest SDK exception once and wrap it — but only at the outermost edge.
  • Typed domain error: GroundedQueryError(code, message, status_code) carries a stable string code (e.g. RATE_LIMITED, INVALID_TOKEN, WEB_EVIDENCE_DEGRADED) across both HTTP and MCP transports. The same error code reaches a REST client and an MCP tool caller.
  • Global normalizer: http_exception_handler(request, exc) inspects exc.detail; if it has {code, message, request_id} it passes through, otherwise wraps it as HTTP_ERROR. The request_id is read from request.state so even an unsanctioned HTTPException still gets the request id onto the wire.
  • Validation handler: validation_exception_handler exposes only loc and type from pydantic errors — no raw Python values leak into the 422 body. A request with an invalid UUID returns VALIDATION_FAILED plus the field path, not the value the client sent.
  • Per-request context: attach_request_id middleware generates req_<hex> when the client header is missing or fails ^[A-Za-z0-9._:-]{4,120}$. The id is echoed on every response and every error body.
[Project fact] Boundary example. generate_answer raises AnswerGenerationError; GroundedQueryService.execute catches it and re-raises GroundedQueryError(exc.code, exc.message, exc.status_code) from exc. The original exception is preserved as __cause__ for the traceback; only the typed code/message reach the client.
[Project fact] Handlers may raise in only two sanctioned ways. Terminal API errors (auth failure, rate-limit, not-found) go through a factory that wraps the error as HTTPException(status_code, detail={"code", "message"}); service-layer errors (typed domain errors raised from inside the service orchestration) go through a separate service-level factory that constructs GroundedQueryError(code, message, status_code). Both paths force the error body to carry a stable string code so client retry logic is enum-driven rather than string-match-driven.

Interview question trees

Q1. Why a typed code field on every error?

  • └─ What changes if you rely on HTTP status + message only? → Clients must substring-match messages to tell rate-limit from auth-required. A stable code like RATE_LIMITED makes client retry logic enum-driven and survives copy edits to the message.

Q2. Why from exc when re-raising?

  • └─ What's lost without it? → The traceback chain; the operator loses the underlying SDK exception that caused the domain error. raise GroundedQueryError(...) from exc preserves __cause__ while only the typed code/message reach the wire.

Q3. What's the trade-off of the global envelope?

  • └─ Every error is the same shape, so OpenAPI clients have one schema (ErrorResponse). [Reasonable inference] Cost: handlers cannot return provider-specific fields without breaking the envelope contract.

Topic 5 . Configuration validation

Pydantic Settings + model_validator production gates

[Project fact] Settings(BaseSettings) in config.py declares every env var as a typed field. A mode="after" model validator rejects unsafe combinations before create_app finishes.

Conclusion first. A misconfigured production deploy should fail at startup, not at the first request that exercises the broken path. Settings is validated once by get_settings() (cached via @lru_cache) and shared through app.state.settings. The post-validator enforces three categories of constraints before the app starts serving traffic: (1) cross-field arithmetic (adaptive_dense_weight_min <= adaptive_dense_weight_max; chat_recent + chat_summary <= chat_history); (2) auth and security shape (preview/production must use supabase; allow_dev_auth forbidden in preview/production); (3) production readiness (Postgres repository, REDIS_URL, object storage, NVIDIA LLM, NVIDIA embeddings at dimension 4096, Qdrant URL+key, Tavily, Langfuse).

Key mechanisms

  • Typed fields: app_env: Literal["local","test","preview","production"]; llm_provider: Literal["fake","nvidia"]; secrets are SecretStr so they serialize as ********** and never appear in logs.
  • Range-bound numerics: llm_max_tokens: Field(ge=1, le=32_768); embedding_dimension: Field(ge=128, le=8192). Magic numbers are bound at the field definition, not sprinkled across route handlers.
  • Production block: if app_env in {"preview","production"}: ... raises ValueError for missing DATABASE_URL, REDIS_URL, object storage config, NVIDIA LLM/embeddings, Qdrant config, Tavily, and LANGFUSE_ENABLED=true.
  • Cache: @lru_cache on get_settings() means the post-validator runs at most once per process. Changing env vars requires a redeploy — matching the Render contract where the platform redeploys rather than live-reloads.
[Project fact] The two dev-auth flags must be jointly checked. auth_mode="development" alone does not unlock DEV_USERS; allow_dev_auth=True is required on top. And in preview/production, allow_dev_auth=True raises ValueError. Belt and suspenders.
[Interview extension] Pydantic v2 BaseSettings differs from v1: validators run after env parsing by default; SecretStr serializes as **********; SettingsConfigDict(env_file=".env", extra="ignore") lets unknown env vars not fail the app — useful when containers inject unrelated vars.
[Project fact] The post-validator's production gates. A mode="after" model validator runs after the Settings instance is built and does these checks in order: (1) cross-field arithmetic (dense weight min must not exceed max; chat-history slice components must not exceed the total); (2) auth and security shape (preview and production must use Supabase; allow_dev_auth is rejected in preview/production); (3) production readiness (Postgres, Redis, object storage, NVIDIA LLM, NVIDIA embeddings, Qdrant URL+key, Tavily, Langfuse all present). Any failure raises ValueError so the process fails to start instead of serving real traffic.

Interview question trees

Q1. Why model_validator(mode="after") instead of before?

  • └─ What's the difference? → before operates on raw input (pre-coercion dicts); after runs on the constructed Settings instance with all fields already typed. Cross-field checks like "min <= max" need both values already typed — that's after.

Q2. Why one Settings class with every knob rather than per-module configs?

  • └─ Trade-off? → Single source of truth; one validator covers cross-concern rules (auth-mode + app_env). Cost: any new field touches the central file and triggers a full re-validation. [Reasonable inference] Chosen to keep the production-gate logic in one diffable validator.

Q3. What if ENV_FILE=.env is missing on the deploy host?

  • └─ Fields fall back to defaults; the post-validator catches missing-but-required env (e.g. DATABASE_URL) and raises a precise message. [Project fact] extra="ignore" means unrelated env vars do not crash startup.

Topic 6 . Service layer

GroundedQueryService as a Protocol-orchestrator

[Project fact] GroundedQueryService is the single Ask use-case entry point. It binds six dependencies in __init__ and walks them in a fixed order in execute(). Every adapter it consumes is a Protocol.

Conclusion first. The service layer does not own database mechanics — those are ResearchMateRepository, a Protocol. It does not own LLM mechanics — those are ChatProvider, a Protocol. It does not own reranking — that's RerankCoordinator. What it owns is the order in which they run: prepare context → retrieve → route/rerank → generate → persist → respond. That order is what an interviewer asks about. Because every adapter is a Protocol (structural typing — any object with the right methods satisfies the contract), unit tests can swap a real provider for a fake without touching the service body.

Key mechanisms

  • Protocol boundary: ResearchMateRepository(Protocol) in _store_protocol.py; ChatProvider(Protocol); RerankCoordinator wraps Reranker(Protocol). Any class implementing the methods matches the contract — no inheritance required.
  • One execution method: execute(user, payload: AskRequest) -> AskResponse is the whole use case. A branch on settings.langgraph_research_enabled decides whether the ResearchGraph.run(...) path runs or the inline local/web/rerank path runs.
  • Tool traces per step: Every step builds a ToolCallTrace with tool_name, input_summary, output_summary, status, latency_ms. The traces are persisted alongside the run record so a developer can replay what the service did and why.
  • Quota after success: repository.increment_usage(user, "ask", limit=200) runs only after generate_answer succeeds. The decision matters: provider failures do not consume the caller's daily quota. The quota cap is 200 asks per user per day.
  • Web as augmentation, not hard dependency: _retrieve_web_degraded catches WebEvidenceError, logs web_evidence_degraded, sets strategy="chat", and continues. A Tavily outage downgrades the request to "local-only" but never 500s the caller.
[Project fact] Budget cap before rerank. _route_and_rerank splits candidates into lightweight_candidates (no embedding vector) and rag_candidates (with vector). Lightweight candidates are capped at retrieval_evidence_token_budget // 2 via pack_chunks before the rerank call. Rerank cost is then spent on RAG candidates only — lightweight candidates are cheap and don't need a vector-distance score.
[Project fact] execute orchestration order. The whole Ask use case is one straight line: (1) the conversation builder prepares context; (2) the langgraph_research_enabled flag decides whether the ResearchGraph.run LangGraph path is taken, or the legacy inline local-retrieval + degraded-web + rerank path; (3) an execution plan is built from the chosen strategy; (4) generation runs; (5) only after a successful generation does the quota get incremented (200 asks per user per day, over-limit raises 429 RATE_LIMITED); (6) the run and tool traces are persisted; (7) the response is assembled and returned.

Interview question trees

Q1. Why Protocols instead of ABCs?

  • └─ Trade-off? → Protocols are structural: implement the methods and you match, no inheritance required. ABCs are nominal: subclasses must inherit. [Reasonable inference] Protocol was chosen so the in-memory store, Postgres store, and any future implementation all duck-type to one contract without sharing a base class.
  • └─ Cost? → No runtime enforcement unless @runtime_checkable; mismatches surface at the first call site, not at class definition.

Q2. Why a single execute method instead of splitting it?

  • └─ What would splitting cost? → Cross-cutting concerns (tool traces, runtime_metadata, request_id propagation) would need a parameter object or shared mutable state. Keeping the order in one method makes the orchestration literally linear and readable.

Q3. Why is web retrieval an augmentation instead of a hard dependency?

  • └─ Alternative? → Fail the whole request when Tavily is down. Trade-off: a flaky third party becomes a hard dependency on the Ask path. [Project fact] The chosen path is web_degraded=True + strategy='chat' fallback, so local retrieval still answers.

Q4. Why charge quota only after generation succeeds?

  • └─ A user whose request fails because NVIDIA returned a 500 should not lose one of their 200 daily asks. [Project fact] The increment happens in the line right after generate_answer returns successfully; failures raise before the increment is reached.
