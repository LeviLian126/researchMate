面试指南 . FastAPI 请求流 / JWT 认证 / 原生 SQL 持久化

后端面试指南 . apps/api

后端是 apps/api 下的 FastAPI 应用。它接收一个 HTTP 请求,验证调用者是谁,用写死的手工 SQL 读写 Postgres,再返回一个规整的 JSON 响应。本页覆盖五个面试值得答辩的主题:请求流、JWT 认证、原生 SQL 持久化、fail-closed 错误处理、配置校验。

5 个面试主题 原生 SQL . 无 ORM Protocol 服务 Pydantic Settings 门禁

最小心智模型

后端职责,五条概括

先读这一节。后续每个章节都假设你已经理解这一层的请求流。

它是什么

一个 FastAPI 应用,REST 暴露在 /api/v1,另在 /mcp 提供 MCP (Model Context Protocol) 入口。应用由 main.py 的 create_app() 组装;模块级 app = create_app() 给 ASGI server 加载。

请求流

请求 → attach_request_id 中间件(X-Request-ID、安全头、IP 限流)→ router handler → get_current_user → GroundedQueryService.execute → repository + providers → JSONResponse。

关键依赖

FastAPI + Pydantic v2 + SQLAlchemy Core(无 ORM)+ psycopg; Qdrant 混合检索; OpenAI SDK 调 NVIDIA NIM; slowapi 给 /healthz、/me、/mcp 做 IP 桶限流。

值得深挖的话题

(1) FastAPI 请求流与依赖注入;(2) Supabase JWT 认证;(3) 原生 SQL 持久化 + 手动 Pydantic 映射;(4) fail-closed 类型化错误处理;(5) Pydantic Settings 生产门禁。

主题 1 . FastAPI 请求流

请求如何进入、被认证、再返回

[项目事实] 每个请求都走同一条路径:先一个中间件,再 router,再 service,再 repository。Adapter 在启动时构建一次,不是每请求构建。

结论先行。 请求进来后第一个跑的是 attach_request_id 中间件。它生成或验证 request id(从 X-Request-ID 头取,不合法就生成一个新的 req_<hex>),挂上安全头,并对几个便宜的端点做 IP 桶限流。中间件之后,FastAPI 把请求分发给 router handler。每个 router 通过两个依赖函数取得所需的对象:Depends(get_current_user) 拿调用者身份、Depends(get_store) 拿 repository。Handler 再调 GroundedQueryService.execute(...) 编排检索、生成、持久化,最后返回 JSONResponse 并回写 X-Request-ID。

依赖项放在 request.app.state 上,是出于构造代价的考虑。S3CompatibleObjectStorage、QdrantHybridStore、RerankCoordinator、PostgresResearchMateRepository 都要打开网络连接或读取凭证。每请求构建它们是浪费的。所以 create_app() 把每个 adapter 构建一次放到 app.state 上,get_* 系列依赖函数只是从 state 里读出来。

关键机制

  • State 解析的依赖: get_store(request) 返回 request.app.state.store;get_chat_provider、get_hybrid_store、get_reranker、get_object_storage 同模式。Adapter 在 create_app() 里只构建一次。
  • Request id 透传: 中间件把 id 存到 request.state.request_id,全局错误 handler 读出来,再写回每个响应。每个错误体都带 request_id,用户提交一条 issue 就能在日志里定位到唯一一条请求。
  • 按 IP 限流: slowapi 的 Limiter 给 /api/v1/healthz、/api/v1/readyz、/api/v1/me、/mcp 限到 60/minute per IP。桶 key 是 researchmate-api:protected,四条路径共用一个桶——一个客户端狂打 /me 也会耗光 /healthz 的额度。
  • 安全头: Cache-Control: no-store、X-Content-Type-Options: nosniff、Content-Security-Policy: default-src 'none'; frame-ancestors 'none'、Strict-Transport-Security、X-Frame-Options: DENY。中间件 finally 形状的流里在成功和错误响应上都挂上。
  • 中间件的可选特性: slowapi 包在 try/except ModuleNotFoundError 里,MCP SDK 一样。缺这两个依赖时只是缩小可用面(无限流、MCP 返回 503),不会让启动崩溃。
[项目事实] MCP 身份在中间件里解析,不在 router 里。 对 /mcp 路径,中间件自己抽 Bearer token,在某个线程里调 resolve_bearer_token(token, settings)(通过 anyio.to_thread.run_sync),把 MCPRequestIdentity 放到 ContextVar(current_mcp_identity) 上。MCP 工具 handler 从这个 context 读 user、repository、providers——MCP 路径上没有"每个工具一个 Depends(get_current_user)"。
[项目事实] 中间件执行顺序 每个请求按固定顺序走：(1) 从配置的请求 id 头取候选值，不匹配正则就生成新的 req_<hex>，写入 request.state；(2) 限流检查在 RATE_LIMITED_PATHS 上跑，超额直接 429；(3) 仅对 /mcp 路径，调用令牌解析并把身份放进 current_mcp_identity ContextVar；(4) 等下游 handler 返回响应；(5) 把请求 id 写回 X-Request-ID 响应头；(6) 遍历所有配置好的安全头并逐个挂到响应上。

面试追问树

Q1. 为什么在 create_app() 里构建 adapter,而不是每请求构建?

  • └─ 不这么做会怎样? → 每请求打开网络连接、解析凭证;冷客户端猛冲上游。[项目事实] app.state 上的 adapter 进程生命周期内复用;依赖函数只是返回缓存实例。
  • └─ 这个选择的代价? → 改 env 必须重启(get_settings() 上的 @lru_cache 也强制了这点)。可接受,因为 Render 是重部署而非生产热重载。

Q2. 为什么四条路径共用一个限流桶?

  • └─ 各自一个桶能得到什么? → 每条路径各自一个 60/min 上限。[合理推断] 团队让 /me 和 /healthz 共用同一个桶,是为了攻击者猛打认证端点时也耗光探活桶,让只盯着 /healthz 的监控看到爆炸半径。

Q3. 没装 slowapi 或 MCP SDK 时会怎样?

  • └─ [项目事实] 模块级 try/except ModuleNotFoundError 把符号设为 None;create_app 跳过 limiter 分支,并挂一个返回 503 MCP_RUNTIME_NOT_INSTALLED 的 /mcp 桩 handler。启动永远不会因可选依赖而崩。

主题 2 . 认证

Supabase JWT,加一个仅开发用的静态 token 旁路

[项目事实] get_current_user 是唯一的认证入口。每个受保护的 router 都用 Depends(get_current_user);没有第二个认证中间件。

结论先行。 认证要回答一个问题:"这个调用者是不是他声称的那个人?"机制是 Authorization 头里的一个 Bearer token。get_current_user 通过 HTTPBearer(auto_error=False) 读出 token,把它解析成一个 CurrentUser,并把用户的 profile 行 upsert 进库,让后续 owned 资源一定有外键。解析有两条路径:一条是 DEV_USERS 静态 token 的开发路径,一条是对 JWT 做 JWKS 验签的 Supabase 路径。开发路径的准入条件是 auth_mode == "development" 且 allow_dev_auth == True——两个开关都要满足,单独把 AUTH_MODE=development 翻过来并不会解锁静态凭证。

关键机制

  • 用 auto_error=False 抽 Bearer: token 缺失或空,在 get_current_user 内部以 401 AUTH_REQUIRED 处理。默认的 auto_error=True 会返回 403——状态码语义错了:401 表示"请认证",403 表示"已认证但无权限"。
  • 双模式解析: resolve_bearer_token(token, settings) 按 settings.auth_mode 分支:"development" → _development_user,否则 → _supabase_user。
  • 开发门禁: 即便在开发模式下,allow_dev_auth=False 会记 development_auth_rejected 日志并返回 None → 401。两个开关故意分开,这样部署时误改 AUTH_MODE 不会单独解锁静态 token。
  • Profile 落库: 解析身份后,repository.ensure_user(user) 对 profiles 行做 upsert(见 insert ... on conflict (id) do update set email = excluded.email, role = excluded.role)。projects、uploads、chunks 上的外键约束要求 profiles 行存在;先 ensure 一下,后续写入就永远不会触 FK 报错。
[项目事实] Supabase 路径。 PyJWKClient 经 @lru_cache(maxsize=4) 缓存,JWKS 拉取每个 jwks_url 只发生一次。jwt.decode 校验 RS256/ES256、aud=authenticated、iss=ACCESS_TOKEN_ISSUER,并要求 exp, iat, sub, aud, iss 声明。角色来自 app_metadata.role,被收敛到 {"developer","admin"},否则为 "user"——调用者改不了 JWT 就升不了权。
[合理推断] 两个开关存在,是因为运维跑预览/生产时 env 名本来就设了。没有 allow_dev_auth 作为第二道闸,部署时一行 AUTH_MODE 的笔误就会在真实用户前解锁硬编码的 bearer token。
[项目事实] 认证入口流程。 整套认证就一个入口，按这个顺序执行：(1) 没拿到 credential → 直接抛 401 AUTH_REQUIRED；(2) 取 credential 里的 bearer token 并 trim；(3) 调用令牌解析器（按配置走开发路径或 Supabase 路径）；(4) 解析结果为空 → 抛 401 INVALID_TOKEN；(5) 对解析出的 user 做 ensure_user 把 profiles 行 upsert 进库；(6) 把 user 返回给 router。

面试追问树

Q1. 为什么是双模式而不是只用 Supabase?

  • └─ 开发路径比 Supabase 多得到什么? → 本地测试和 CI 不依赖网络/JWKS;确定性 UUID(如 dev 对应 00000000-...-000000000001)让 fixture 能断言真实 id。
  • └─ 怎么防止开发 token 进生产? → allow_dev_auth 默认 False,且 validate_security_boundary 在 app_env 为 preview/production 时直接拒绝。

Q2. 为什么用 HTTPBearer(auto_error=False) 不让它抛 403?

  • └─ 缺 token 时 403 错在哪? → 403 的意思是"知道你是谁,但不能做";token 缺失意味着"还不知道你是谁"——这是 401。用 raise_api_error(401, "AUTH_REQUIRED", ...) 还让所有认证失败都返回一个统一的 error: {code, message, request_id} 响应体。

Q3. JWKS 挂了或慢怎么办?

  • └─ PyJWKClient(cache_keys=True) 把签名 key 缓存在内存里;key 轮换后的第一次请求会阻塞在拉取上。[合理推断] 源码里没有显式 TTL 刷新,强制轮换时被缓存的旧 key 不匹配会持续 401,直到 LRU 逐出。

主题 3 . 持久层(原生 SQL)

为什么不用 ORM:手写 text() SQL + 手动 Pydantic 映射

[项目事实] 所有 Postgres 访问都经过 PostgresResearchMateRepository——由 11 个 mixin 组合的类,内部包 sqlalchemy.text() 调用。结果行手工装填进 Pydantic DTO。

结论先行。 团队没有用 SQLAlchemy ORM。没有 declarative_base,没有持模型对象的 Session,没有行对象的属性访问。写操作用 text("insert into projects ... where exists (select 1 from profiles ...)");读用 connection.execute(text(...)).mappings().one_or_none(),再 ProjectRecord.model_validate(dict(row))。Owner 隔离——每个 where 子句都重复 and user_id = :user_id——写在 SQL 里,不交给连接级的数据库行级安全(RLS)角色。

不用 ORM 的原因是可审性。每个 owner 范围过滤都在 diff 里,不在关系属性后面。工程师如果忘了 user_id,缺过滤在 code review 里能直接看到。代价:你丢掉了 ORM 的 session 生命周期、实例属性访问、lazy-loading,要自己手写每一条 SQL。

关键机制

  • 每个 repository 一个 engine: create_engine 配 pool_pre_ping;engine 由 PostgresRepositoryCore 持有。事务来自 self._transaction(user)——一个上下文管理器,产出 Connection 并把 owner id 绑到调用点。
  • owner 隔离在 SQL,不在 RLS: 每个查询都重复 and user_id = :user_id。老文档提的 "request.jwt.claim.sub" RLS 模式在当前 _postgres_projects.py 源码中并不存在。
  • 用 on conflict 做 upsert: ensure_user 用 insert ... on conflict (id) do update set email = excluded.email, role = excluded.role。ensure_personal_project 用 on conflict (user_id) where kind='personal' and deleted_at is null。
  • 手动 Pydantic 装填: connection.execute(text(...)).mappings().one() → dict(row) → ProjectRecord.model_validate(dict(row))。Pydantic 模型是 DTO(数据传输对象),不是表的镜像。
  • mixin 组合: PostgresResearchMateRepository 继承 ProjectPersistenceMixin、UploadPersistenceMixin、DocumentLifecycleMixin、RunPersistenceMixin …… 共 11 个 mixin,共享 PostgresRepositoryCore 的 helper(_enum_value、_json、_safe_filename)。
[项目事实] 项目删除是单个事务里的状态机。 delete_project 开一个事务,跑 select status, kind from projects ... for update 取行锁,拒绝 kind='personal',把 status='active' → 'deleting',把在飞的 parse_and_index_document job 置为 failed,收集所有需要清理的 r2_object_key 与 qdrant_point_id,插入一个 delete_project job,再入队后台删除任务。再次调用一个已经 'deleting' 的项目,直接返回已存在的 job——行锁把并发调用串行化。
[项目事实] project insert 执行模式。 整个写路径包在用户级事务里：先用参数化 SQL 把 id, user_id, name, kind, expires_at 插入 projects 表；插入语句带一个 where exists (select 1 from profiles where id = :user_id) 守卫，缺失 profile 就静默返回零行；并通过 returning 子句一次性取回 Pydantic 模型需要的所有列；最后把行字典通过 ProjectRecord.model_validate 装填成 DTO 返回。所有 id 都走绑定参数，不走字符串拼接。

这个 insert 里有三处刻意为之:where exists (select 1 from profiles ...) 守卫让缺失 profile 行时 insert 静默返回零行,而不是抛 FK 异常——这正是认证流先跑 ensure_user 的原因。id 通过 :user_id 绑定参数传给 SQL,从来不走字符串拼接。returning 子句让 insert 直接返回 Pydantic 模型需要的列,省掉第二次 select。

面试追问树

Q1. 为什么用原生 SQL 而不是 SQLAlchemy ORM?

  • └─ 失去什么? → Session 生命周期、实例属性访问、lazy-loading。[合理推断] 团队选了显式 SQL,让每个 owner 范围过滤集中在一个文件里可审,并让手写 SQL 能干净地配合 Ask 路径上 Qdrant + JSON payload 的混合查询。
  • └─ 得到什么? → diff 里的 SQL 就是运行时跑的 SQL——没有生成的 SQL 要追。每个 where user_id = :user_id 都是一行被人 review 过的代码。

Q2. 为什么用 mixin 组合而不是单个大类?

  • └─ 11 个职责塞一个文件会怎样? → 1000+ 行文件,每个 PR 都冲突。按聚合(Projects、Uploads、Runs、Chunks …)切分的 mixin 把每次改动控制在拥有该改动的聚合内。
  • └─ 代价? → 方法解析顺序;TYPE_CHECKING 桩,如 _transaction: Callable[..., AbstractContextManager[Connection]],把跨 mixin 契约写在 ProjectPersistenceMixin 里。

Q3. owner 隔离怎么保证?

  • └─ 每个查询加 user_id 参数,从不依赖数据库角色。[优化建议] 用按请求 role 的 Postgres RLS 策略能兜住漏掉 user_id 过滤的情况;团队选择靠对显式 SQL 的 code review。

Q4. select ... for update 给删除流程什么保证?

  • └─ 行锁持有至事务结束;对同一项目的并发 delete_project 调用在锁上串行。第二个调用看到 status='deleting' 已经更新好,短路返回已存在的 job。

主题 4 . 错误处理

边界 fail-closed、类型化域错误、一个全局信封

[项目事实] 错误遵循四层形态:provider SDK 异常 → 类型化域错误 → 带结构化 detail 的 HTTPException → 全局 handler 规整成 {"error": {code, message, request_id}}。

结论先行。 想象 LLM provider 在请求中途抛了个 OpenAIError。如果 router handler 直接把这个原始异常抛出去,三件事会出问题:客户端看到的是 SDK 内部消息;错误形态和 API 里其他错误不一样;OpenAPI 客户端也没有它的 schema。所以这个项目在每个 provider 边界都做了一层包装。generate_answer 抛 AnswerGenerationError(code, message, status_code)。GroundedQueryService.execute 捕获后以 GroundedQueryError(exc.code, exc.message, exc.status_code) from exc 重抛。Handler 里只允许两种抛错方式:raise_api_error(status_code, code, message)(终态 API 错误)和 raise_grounded_error(code, message, status_code)(服务错误)。HTTPException 的 detail 必须是 {"code": ..., "message": ..., "request_id": ...}。

关键机制

  • AGENTS.md 规则: 禁止裸 except Exception: pass。捕获特定类,带上下文记日志,再抛类型化域错误。Provider 边界最多在最外层捕获一次最宽的 SDK 异常并包起来。
  • 类型化域错误: GroundedQueryError(code, message, status_code) 带稳定的字符串 code(如 RATE_LIMITED、INVALID_TOKEN、WEB_EVIDENCE_DEGRADED),横跨 HTTP 与 MCP 两个传输通道。同一个错误 code 既到达 REST 客户端,也到达 MCP 工具调用方。
  • 全局规整: http_exception_handler(request, exc) 检查 exc.detail;如果含 {code, message, request_id} 就放行,否则包成 HTTP_ERROR。request_id 取自 request.state,即便有人抛了不规范 HTTPException,request id 也照样上得去。
  • 校验 handler: validation_exception_handler 只暴露 pydantic 错误的 loc 和 type——422 响应体不漏客户端发来的原始值。一个无效 UUID 请求返回的是 VALIDATION_FAILED 加字段路径,不是客户端发的那个值。
  • 按请求上下文: attach_request_id 中间件在客户端头缺失或不匹配 ^[A-Za-z0-9._:-]{4,120}$ 时生成 req_<hex>。该 id 在每个响应、每个错误体里都回显。
[项目事实] 边界示例。 generate_answer 抛 AnswerGenerationError;GroundedQueryService.execute 捕获后以 GroundedQueryError(exc.code, exc.message, exc.status_code) from exc 重抛。原始异常作为 __cause__ 保留给 traceback;只有类型化的 code/message 到客户端。
[项目事实] handler 只允许两种抛错方式。 终态 API 错误（如认证失败、限流、找不到资源）通过一个工厂函数包成 HTTPException(status_code, detail={"code", "message"}) 抛出；服务层错误（服务编排内部抛出的 typed 域错误）通过另一条服务级抛出函数构造 GroundedQueryError(code, message, status_code)。两条路径都强制错误体带稳定的 string code，让客户端重试逻辑按枚举驱动而不是字符串匹配。

面试追问树

Q1. 为什么每个错误都要类型化 code?

  • └─ 只用 HTTP status + message 会怎样? → 客户端要 substring 匹配 message 才能区分限流和未认证。稳定的 code(如 RATE_LIMITED)让客户端重试逻辑按枚举驱动,改 message 文案也不会破坏客户端。

Q2. 为什么重抛要用 from exc?

  • └─ 不加会丢什么? → traceback 链;运维丢失导致域错误的底层 SDK 异常。raise GroundedQueryError(...) from exc 保留 __cause__,只有类型化的 code/message 上线。

Q3. 全局信封的取舍?

  • └─ 每个错误同形态,OpenAPI 客户端只要一个 schema(ErrorResponse)。[合理推断] 代价:handler 想返回 provider 特定字段就得破坏信封契约。

主题 5 . 配置校验

Pydantic Settings + model_validator 生产门禁

[项目事实] config.py 中的 Settings(BaseSettings) 把每个 env var 声明为类型化字段。mode="after" 的 model validator 在 create_app 完成前拒绝不安全组合。

结论先行。 一个配置错的 生产部署应该在启动时失败,不应该等到第一个跑出错路径的请求才暴露。Settings 由 get_settings()(经 @lru_cache 缓存)校验一次,通过 app.state.settings 共享。后置 validator 在应用开始服务流量前强制三类约束:(1) 跨字段算术(adaptive_dense_weight_min <= adaptive_dense_weight_max;chat_recent + chat_summary <= chat_history);(2) 认证和安全形态(preview/production 必须用 supabase;allow_dev_auth 在 preview/production 被禁);(3) 生产就绪(Postgres repository、REDIS_URL、object storage、NVIDIA LLM、维度 4096 的 NVIDIA embeddings、Qdrant URL+key、Tavily、Langfuse)。

关键机制

  • 类型化字段: app_env: Literal["local","test","preview","production"];llm_provider: Literal["fake","nvidia"];secret 是 SecretStr,序列化成 **********,日志里不出现。
  • 范围约束数值: llm_max_tokens: Field(ge=1, le=32_768);embedding_dimension: Field(ge=128, le=8192)。魔法数字在字段定义处绑定,不散落到 router handler 里。
  • 生产行: if app_env in {"preview","production"}: ... 对缺失的 DATABASE_URL、REDIS_URL、object storage 配置、NVIDIA LLM/embeddings、Qdrant 配置、Tavily、LANGFUSE_ENABLED=true 都抛 ValueError。
  • 缓存: get_settings() 上的 @lru_cache 意味着后置 validator 每进程最多跑一次。改 env 必须重部署——和 Render 的契约一致(平台重部署,不生产热重载)。
[项目事实] 两个 dev-auth 开关必须联合检查。 仅 auth_mode="development" 不会解锁 DEV_USERS;还要 allow_dev_auth=True。且在 preview/production 下,allow_dev_auth=True 直接抛 ValueError。双重保险。
[面试扩展] Pydantic v2 BaseSettings 与 v1 的差异:validator 默认在 env 解析之后才跑;SecretStr 序列化成 **********;SettingsConfigDict(env_file=".env", extra="ignore") 让未声明的 env var 不让应用崩——容器注入无关变量时有用。
[项目事实] 后置 validator 的生产门禁。 一个 mode="after" 的 model validator 在 Settings 实例化完后依次做这些检查：(1) 跨字段算术（dense 权重 min 不能大于 max；chat history 子项之和不能超出总量）；(2) 认证和安全形态（preview 和 production 必须用 Supabase；allow_dev_auth 在 preview/production 被拒绝）；(3) 生产就绪（Postgres、Redis、对象存储、NVIDIA LLM、NVIDIA embeddings、Qdrant URL+key、Tavily、Langfuse 全部到位）。任意一项不满足就抛 ValueError，让进程启动失败而非暴露给真实流量。

面试追问树

Q1. 为什么用 mode="after" 而不是 before?

  • └─ 区别? → before 操作原始输入(强制前的 dict);after 在所有字段已类型化的 Settings 实例上跑。"min <= max" 这类跨字段检查两个字段都得已类型化——那才是 after。

Q2. 为什么一个 Settings 类塞每个旋钮而不是按模块拆配置?

  • └─ 取舍? → 单一权威源;一个 validator 覆盖跨关注规则(auth-mode + app_env)。代价:加字段就得动中央文件并触发全量重新校验。[合理推断] 这么选是为了把生产门禁逻辑集中在一个可 diff 的 validator 里。

Q3. 如果部署主机没有 ENV_FILE=.env?

  • └─ 字段回退到默认值;后置 validator 捕获"必须但缺失"的 env(如 DATABASE_URL)并抛精准 message。[项目事实] extra="ignore" 让无关 env var 不让启动崩溃。

主题 6 . 服务层

GroundedQueryService 作为 Protocol 编排者

[项目事实] GroundedQueryService 是 Ask 用例的唯一入口。在 __init__ 绑定六个依赖,在 execute() 按固定顺序走一遍。它消费的每个 adapter 都是 Protocol。

结论先行。 服务层不持有数据库机制——那是 ResearchMateRepository,一个 Protocol。不持有 LLM 机制——那是 ChatProvider,一个 Protocol。不持有 rerank——那是 RerankCoordinator。它持有的是它们运行的顺序:准备 context → 检索 → 路由/rerank → 生成 → 持久 → 响应。这个顺序就是面试官要追问的。因为每个 adapter 都是 Protocol(结构化类型——任何方法匹配的对象都满足契约),单测可以用一个 fake 代替真实 provider,不动 service 主体。

关键机制

  • Protocol 边界: ResearchMateRepository(Protocol) 在 _store_protocol.py;ChatProvider(Protocol);RerankCoordinator 包 Reranker(Protocol)。任何实现这些方法的类都满足契约,不用继承。
  • 一个执行方法: execute(user, payload: AskRequest) -> AskResponse 就是整个用例。settings.langgraph_research_enabled 的分支决定走 ResearchGraph.run(...) 路径还是 inline 本地/检索/rerank 路径。
  • 每步一条 tool trace: 每一步构建一个 ToolCallTrace,带 tool_name、input_summary、output_summary、status、latency_ms。trace 与 run 记录一起持久化,开发者可以复盘 service 做了什么、为什么。
  • 成功后扣配额: repository.increment_usage(user, "ask", limit=200) 只在 generate_answer 成功之后执行。这个决定的意义是:provider 失败不消耗调用者的每日配额。配额上限是每个用户每天 200 次 ask。
  • Web 作为增强,不是硬依赖: _retrieve_web_degraded 捕获 WebEvidenceError,记 web_evidence_degraded 日志,把 strategy 设为 "chat" 并继续。Tavily 宕机把请求降到"仅本地",但永远不会对调用方 500。
[项目事实] rerank 前先做预算封顶。 _route_and_rerank 把候选分成 lightweight_candidates(无向量)和 rag_candidates(有向量)。lightweight 候选在 rerank之前经 pack_chunks 封顶到 retrieval_evidence_token_budget // 2。rerank 预算只花在 RAG 候选上——lightweight 候选本来就便宜,不需要一个向量距离分。
[项目事实] execute 的编排顺序。 整个 Ask 用例就是一条直线：(1) 用 conversation builder 准备 context；(2) 看 langgraph_research_enabled 开关，开就走 ResearchGraph.run 这条 LangGraph 编排路径，关就走 inline 本地检索 + Web 降级 + 重排这条旧路径；(3) 用 strategy 构建执行计划；(4) 调用生成；(5) 成功了才扣配额（每天 200 次 ask，超额抛 429 RATE_LIMITED）；(6) 落库 run + trace；(7) 组装响应返回。

面试追问树

Q1. 为什么用 Protocol 而不是 ABC?

  • └─ 取舍? → Protocol 是结构化的:实现方法就满足,不用继承。ABC 是名义的:子类必须继承。[合理推断] 选 Protocol 是让内存 store、Postgres store 与任何未来实现都 duck-type 到同一契约,不必共享基类。
  • └─ 代价? → 没有 @runtime_checkable 就没有运行时强制;不匹配在第一次调用时暴露,不会在类定义时。

Q2. 为什么是单个 execute 方法而不是拆开?

  • └─ 拆开有什么代价? → 横切关注点(tool trace、runtime_metadata、request_id 传播)需要参数对象或共享可变状态。把顺序留在单个方法里让编排字面上线性、可读。

Q3. Web 检索作为增强,为什么?

  • └─ 替代方案? → Tavily 挂了整个请求就失败。取舍:把一个抖动的第三方变成 Ask 路径上的硬依赖。[项目事实] 选定路径是 web_degraded=True + strategy='chat' 回退,本地检索还能回答。

Q4. 为什么配额在生成成功后才扣?

  • └─ 一个因为 NVIDIA 返回 500 而失败的请求,用户不应该从他那每天 200 次 ask 里扣掉一次。[项目事实] increment 写在 generate_answer 成功返回的下一行;失败在它之前抛出,扣不到。
