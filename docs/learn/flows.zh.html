5 条流程 · 功能中心 · 面试级

切面分析 · 五条面试级核心流程

用户在 ResearchMate 里做的事就那么几样：提问、上传论文、等待 AI 生成的报告。本页跟着这些动作走一遍它们在系统里的路径，从 HTTP 请求到数据库落库。每节先用一句话交代"用户做什么、得到什么"，再按节点顺序拆开内部链路、列出关键文件与函数，结尾给一棵小追问树。标记用来区分项目事实、合理推断、面试扩展和优化建议。

流程 1：Ask · 11 节点图 流程 2：证据审查 · 6 节点 worker 图 流程 3：混合 RAG · 5 路径 流程 4：流式 · SSE + token 双层 流程 5：文档摄取 · 上传到任务
失败/拦截/拒绝 决策/分叉 校验/提交 执行/外部调用 中性/无操作

流程 1 · 功能中心 · 端到端

Grounded Ask · 11 节点 ResearchGraph

用户在研究界面输入一个问题，发起 POST /ask。API 先查一次幂等 key（这样重试不会跑第二次），然后把问题交给一个 11 节点的图：圈定有哪些证据可搜、挑一版 wiki 候选、规划查询、跑本地+Web 检索、去重并重排、判断证据够不够、不够就扩大上下文或细化查询、够了就交给生成层出答案。任何外部失败都被记成降级，不会被当成成功掩盖过去。

幂等校验 GroundedQueryService prepare_context select_wiki plan_evidence search_sources merge_evidence rerank_evidence judge_evidence generate Postgres 落库
1

IdempotencyCoordinator.begin()

四态

网络抖动后客户端常常会重试同一个请求。在真正干活之前，routers/ask.py 先拿客户端传来的幂等 key 调用 coordinator.begin()，有四种结果：execute（新 key，或之前 abandon 过 — 继续往下走）、replay（同一个 key 已经成功过，且请求体 hash 匹配 — 直接返回缓存的答案）、mismatch（同一个 key 但请求体不同 → 409 IDEMPOTENCY_KEY_REUSED）、in_progress（同一个 key+body 还在跑 → 409 IDEMPOTENCY_REQUEST_IN_PROGRESS）。[项目事实] hash 用 SHA-256 算 model_dump(mode="json") 并开 sort_keys=True，所以逻辑内容相同的请求体 hash 一致，跟字典顺序无关。

DB: api_idempotency
2

GroundedQueryService.execute()

编排入口

services/grounded_query.py 启动 monotonic 计时器，然后调用 conversations.prepare(user, payload) 把项目、项目里的文档、对应的 chunks、以及一段有界对话历史都加载进来。[项目事实] 如果 settings.langgraph_research_enabled=false，就退回一条旧的内联检索路径。[合理推断] 这个开关保留的目的，是为了让旧路径仍然可以运行，方便和图编排路径对比效果，而不是冷切换。

DB: projects/docs/chunks外部: NVIDIA 摘要
3

prepare_context

决定起步路径

第一个决策是“从哪里开始算”。只有项目 generation 明确相等时，after_prepare() 才选择 Wiki。fresh 且充分的页面可直接回答；需要核验来源的问题展开 raw provenance；Wiki stale 或缺失时进入完整 raw plan。

4

select_wiki

词法候选集

当问题大概率有 wiki 答案时，bm25_candidates() 用 BM25（词重叠）给 wiki chunk 打分，返回一个短名单，数量上限由 settings.wiki_gate_candidate_limit 控制。[项目事实] 设这个上限，是为了避免一个庞大的 wiki 把几百页一股脑塞给 LLM judge，token 预算在检索还没开始前就爆了。

5

plan_evidence

自适应规划

一份检索计划说明：搜什么、怎么搜。AdaptiveQueryPlanner.plan() 以先前的 plan_retrieval() 结果为基础，可选地带入上一轮 judge 的 missing_facets，返回：要跑的 queries、dense 与 lexical 的权重、是否允许用 Web、以及受限的 document scope。[项目事实] 当上一轮做过 refine，refined queries 会通过 model_copy(update=...) 整体覆盖计划里的 queries，而不是合并。

6

search_sources

本地 + 可选 Web

_search_local() 把 plan 的安全权重传给 LocalEvidenceRetriever.retrieve()（详见流程 3）。只有 plan.use_web=true 时 _search_web() 才跑：用第 1 个规划 query 调一次 Tavily，limit 5。[项目事实] Web 失败被捕获，记成 web_degraded=True；本地检索继续跑，不会让整条请求挂掉。

外部: Qdrant + NVIDIA + Tavily
7

merge_evidence

重排前去重

所有本地和 Web 候选先按本地后 Web 顺序拼起来，再按 chunk id 去重，保留第一次出现的位置。把去重放在重排之前，是为了避免同一个 chunk 在不同来源里自相竞争。

8

rerank_evidence

重排回退链

limit_rerank_candidates() 先把池子压到 settings.retrieval_round_candidate_limit，控制重排的成本。然后按 chunk.has_vector 分流：有向量支持的 chunk 走 RerankCoordinator.execute()，没向量的轻量 chunk 跳过重排。[项目事实] rerank provider 通过 get_runtime_rerank_config() 在运行时选择；链条是 QdrantNativeReranker → NvidiaReranker → DeterministicReranker，因此某个 provider 故障会降级成确定性打分，不会直接让请求失败。最后 pack_chunks() 强制 retrieval_evidence_token_budget。

外部: Qdrant 或 NVIDIA
9a

judge_evidence

充分性闸门

重排之后，一个 LLM judge 判断证据够不够。EvidenceSufficiencyService.assess() 返回充分性、置信度、缺失 facets、以及是否降级。然后 after_evidence() 决定去哪：充分就 generate；有轻量证据且没用过 fallback 就 lightweight_fallback；judge 降级或没新证据就 generate；missing_facets 是空列表就 generate；retrieval_round ≥ max_retrieval_rounds 就 generate；否则 refine。[项目事实]

外部: NVIDIA chat
9b

expand_lightweight_context

末位兜底

在放弃之前，图可以把没向量的非 wiki 原始 chunk 在 full_context_token_limit 下打包，置 lightweight_fallback_used=True，回路到 judge_evidence。这个循环有界，不会无限打转。[项目事实]

9c

refine_query

第二轮规划

当 judge 报出 missing facets，planner.refine() 拿这些 facets 和上一轮 plan，返回一份 refined plan，回路到 plan_evidence。refine 次数受 max_retrieval_rounds 约束。[项目事实]

10

generate

交接

在图里 generate() 是个空操作。真正的生成留在 GroundedQueryService：通过 generate_answer() → answering.py build_llm_grounded_answer()。[项目事实] 系统提示里明确把所有 evidence 标成不可信数据，LLM 必须返回 JSON {answer, claims:[{text, evidence_ids}]}；schema 校验失败时只重试一次修复。

外部: NVIDIA chat
11

配额、提交、落库

429 / 重放

配额只在生成成功之后才计数：repository.increment_usage(user, "ask", limit=200)。provider 失败和 429 都不消耗每日 ask 额度 — 系统为交付的价值收费，不为基础设施的瞬态失败收费。超额时抛 429 RATE_LIMITED，同时 coordinator.abandon() 释放幂等记录让用户可以重试。然后 record_run() 在一个事务里写 ask_runs、tool_calls、citations、conversation_messages，RLS 参数已设置。最后 coordinator.complete(response) 把 api_idempotency 翻成 succeeded。[项目事实]

DB: api_usage + 多表

Lightweight → Fallback 完整链路：从摄取到兜底

不是每个文档都值得付 embed + Qdrant 往返的成本。短文档（≤ 4000 tokens）在摄取时跳过向量库，标 has_vector=False。检索时这些 chunk 走 BM25 而非向量搜索；rerank 时被拆出来单独打包；如果 judge 判定证据不足，图会触发一次性 expand_lightweight_context 兜底，把全部原始短文档 chunk 塞进上下文再判一次。整条链路有六个环节，每个环节都有明确的触发条件和预算上限。

环节触发条件操作输出 / 状态变化
1. 摄取判定文档所有分块的 token 总数 ≤ lightweight_document_token_threshold（4000）不把分块写入 Qdrant 向量库（因为全文已能塞进 LLM 上下文，额外生成向量是浪费），只更新 Wiki 索引（轻量关键词检索索引，供 BM25 搜索）分块写入 Postgres，标记 has_vector=False
2. 检索召回候选池中存在 has_vector=False 的分块对每个查询变体跑 BM25 关键词检索，按分块 ID 去重取最高分，上限 rerank_candidate_limitBM25 打分的候选列表，与 RAG 候选合并
3. 图 rerank 拆分重排节点处理合并后的候选按 has_vector 拆为 RAG（有向量）和 lightweight（无向量）两组；只对 RAG 组跑重排器；两者合并打包到 retrieval_evidence_token_budget重排后的 RAG 证据 + lightweight 证据
4. judge 判定证据评估节点运行评估证据充分性，返回置信度、缺失维度、降级标记evidence_sufficient、missing_facets、judge_degraded
5. 路由决策路由节点按优先级检查：充分 → 有轻量且没用过 → 降级/无新证据 → 无缺失维度 → 轮数上限 → refine第 2 条命中时决定走轻量兜底图路由到轻量兜底节点
6. 兜底展开轻量兜底节点执行过滤 has_vector=False 的非 wiki 分块 + 之前重排的证据，去重后打包到 full_context_token_limitlightweight_fallback_used=True，回路到证据评估节点
[项目事实] 一次性触发

after_evidence 检查 not state.get("lightweight_fallback_used")。expand_lightweight_context 执行后立即置 lightweight_fallback_used=True，所以兜底最多触发一次。第二次回到 judge 时，即使证据仍不充分，也不会再进 expand，而是走 generate 或 refine。

[项目事实] has_lightweight_evidence 在每轮规划时设置

每轮规划时，系统检查当前项目范围内是否存在无向量的分块（不含 wiki 分块）。只要有任何一个原始分块没有向量，就标记"存在轻量证据"（has_lightweight_evidence=True），后续路由可以用这个标志决定是否走兜底路径。这个标志在每轮规划时重新计算。

[项目事实] 预算分半保护

lightweight 候选在重排之前就被封顶到 retrieval_evidence_token_budget 的一半。重排预算只花在 RAG 候选上。这样 lightweight 不会挤占重排后的 RAG 证据空间。

[合理推断] 为什么兜底用 full_context_token_limit 而非 retrieval_evidence_token_budget

兜底是最后一搏：不再区分 RAG 和 lightweight，而是把全部可用 chunk 塞进更大的 full_context_token_limit。意图是给 LLM 尽可能多的原始上下文，让生成阶段自行判断相关性。取舍是 token 成本更高，但只在证据不足时触发一次。

追问树 — Lightweight 链路
为什么 lightweight chunk 不送 reranker？
├  reranker 用 embedding 做后期交互打分。lightweight chunk 没有向量（has_vector=False），无法参与 rerank 计算。
└  替代：给 lightweight chunk 也生成向量。但那会失去轻量分支的成本优势 — 短文档全文已塞进 LLM context，不需要 rerank 排序。

如果所有文档都是 lightweight（全项目无向量）会怎样？
├  [项目事实] 全部 lightweight 时，系统不报降级（degraded=False），原因是"整个语料库都是轻量的"，只跑 BM25。图里 has_lightweight_evidence=True，judge 不充分时触发 expand 兜底。
└  这意味着小项目完全不付 Qdrant 成本，但仍能产出有引用的答案。

expand_lightweight_context 为什么只跑一次？
├  [面试扩展] 一次性是循环有界性的体现。如果每次 judge 不充分都触发 expand，图会在 expand → judge → expand 之间无限循环。lightweight_fallback_used 是一个单调递增的布尔标志，保证这个分支最多执行一次。
└  类似模式：refine_query 受 max_retrieval_rounds 约束，也是单调递增的计数器。
为什么按请求编译图，而不是用静态图实例

两个 ask 同一时刻到达，不能共享节点状态。_GraphRuntime 在 run() 里为每个请求编译 11 节点图，闭包捕获请求级数据（用户、项目、chunks、历史），并发请求之间彼此隔离。图受 max_retrieval_rounds 约束，向量库、Web、rerank 等外部失败都被转化成降级元数据，而不是静默成功或终止。

追问树 — Grounded Ask
为什么用 11 节点图而不是单函数调用？
├  这条路径需要条件边（prepare、judge）和有界循环（refine → plan_evidence）。LangGraph 免费提供路由和 checkpointer。
└  手写循环能替代吗？
   ├  能，但要重新实现条件路由和轮次计数。图也为后续的 checkpoint-resume 留了门。

为什么图里 generate 是空操作？
├  图负责有界检索；生成留在应用边界，这样 langgraph_research_enabled=false 仍然能产出答案。
└  取舍：两条执行路径都要维护，直到图开关永久化。

Web 检索被限到 limit=5 且只用第 1 个规划 query，为什么？
├  延迟和 token 成本。Tavily 与 Qdrant 在同一请求里并行；再多 query 会让每轮外部调用翻倍。
└  如何扩展？
   └  [优化建议] 当问题被判为强 Web 倾向时，异步预取 Web，在重排边界再合并。
[项目事实] 配额只计成功

配额在生成成功后通过 increment_usage(limit=200)。provider 失败和 429 都不消耗每日 ask 额度。

[合理推断] 旧的内联路径是评估对照组

langgraph_research_enabled=false 保留了纯函数调用的检索路径。最合理的解释是用来与图编排路径做 A/B 式对照，不是生产降级方案。

流程 2 · 功能中心 · 异步 + 人工审查

证据审查 · 6 节点 worker 图

用户提交一个研究目标，等系统生成一份综合报告。API 用 202 接下请求，写入一行 evidence_runs；随后 Celery worker 跑一个 6 节点图：规划子问题、每个子问题各跑一次检索与抽取、合并批次、暂停等人工审查、接着综合报告并提交。这次暂停是持久化的 — 状态由 checkpointer 存下，所以审查中 worker 重启也不丢，等人工决策到了再恢复。

POST research-runs plan (fan_out) retrieve_and_extract × N reconcile human_review 中断 synthesize validate_and_commit
1

POST /evidence/research-runs

202 + 幂等

前端发请求时，routers/evidence.py create_research_run() 先校验调用方拥有一个有效项目，再用一个 8–160 字符的 Idempotency-Key 调用 evidence.create_research_run()。[项目事实] 接口返回 202 和一个 ResearchRunAccepted 记录；不同步执行任何工作 — 用户拿到一个可以轮询或订阅的句柄，worker 从队列里把任务接走。

DB 写: evidence_runs
2

plan & fan_out

map-reduce

一个研究目标会拆成好几个子问题。build_evidence_graph() 把拓扑串成 plan → (条件 fan_out → retrieve_and_extract) → reconcile → human_review → synthesize → validate_and_commit。[项目事实] fan_out 对每个子问题发出一条 Send("retrieve_and_extract", {question_index, question, ...})。evidence_batches 字段标注为 operator.add，并行批次回来时自动拼接，而不是互相覆盖。

3

retrieve_and_extract × N

每问一条

域钩子 retrieve_and_extract() 针对单个子问题跑一次归属受限的检索和 claim 抽取。[项目事实] 由于每个 Send 都带完整 run 上下文，每个批次都是自包含的，可以并发跑。

外部: 复用流程 3 检索器
4

reconcile

合并 & 去重

多个子问题常常会搜到重复的 claim。域钩子 reconcile() 把所有批次合并成一组干净的 claims 和 relations，供审查步骤使用。[合理推断] 问题之间的重复 claim 的去重和冲突解决就在这一步完成，发生在人工看到提议之前。

5

human_review（interrupt）

人工闸门

当提议的 claim 足够重要，流程会停下来等人审。review_payload() 返回 None 时直接自动批准（低风险增量刷新走这条）；否则 interrupt(proposed) 抛出一个 LangGraph 中断，checkpointer 把它存下来。[项目事实] worker 不把 interrupt 包在 try/except 里 — 注释写着"LangGraph must persist and surface it"。人工决策通过 POST /runs/{run_id}/decisions 的 202 回来。

6

synthesize → validate_and_commit

最终写

synthesize() 产出报告，validate_and_commit() 是终止节点。[项目事实] 图以 END 结束；worker 把 run 标成 succeeded 或 failed，发一个 workflow 级 SSE 事件让任何连着的客户端流干净关闭（见流程 4）。

DB 写: claims/relations/reports

Claim 数据模型：从 chunk 到可审查事实

Claim 是系统从源文档 chunk 中提取的原子事实断言。每条 claim 绑定到服务器控制的证据 ID，带立场（supports/opposes/neutral）和置信度，经人工审查后成为报告的构建块。Claim 不是用户输入的 — 它是 LLM 从有界证据中提取、服务器验证 ID 范围后持久化的结构化事实。

[项目事实] claims 表结构

claims 表（证据审查 schema 迁移中定义）核心字段：text（断言文本）、stance（supports/opposes/neutral）、confidence（0–1）、review_status（pending/accepted/edited/rejected/invalidated）、source_version（来源版本）。唯一约束 (project_id, normalized_key, source_version) 防止同一来源重复提取。

[项目事实] 提取时服务器控制 ID

claim 提取流程给每个 chunk 分配服务器 evidence_id（1–N），LLM 只能引用这些 ID。提取后服务器验证 evidence_id 不超出 allowlist — 超出则抛 EvidenceGenerationError。这防止 LLM 编造不存在的证据引用。

[项目事实] claim 关系图

claim_relations 表存三种有向边：supports、contradicts、duplicates。每条边带独立 confidence 和 rationale_summary。check 约束禁止自环；reconcile 阶段额外拒绝重复边。

[项目事实] owner 隔离在 SQL

claim 列表查询用 where c.project_id = :project_id and c.user_id = :user_id 加 exists (select 1 from projects p where ...) 三层过滤。RLS 策略 claims_owner_select 再加一层 auth.uid() = user_id。

阶段操作输出
提取LLM 从 chunks 提取原子事实，绑定服务器 evidence_idExtractedClaim{text, stance, confidence, evidence_ids}
验证服务器校验 evidence_id 在 allowlist 内通过或抛 EvidenceGenerationError
关联LLM 比较 claims 产出 supports/contradicts/duplicates 边ClaimRelationProposal 批次
审查人工 approve/edit/reject，幂等写回review_status 更新
查询GET /projects/{id}/claims 返回聚合计数ClaimListResponse 含 evidence/support/contradiction/duplicate count
追问树 — Claim 模型
为什么 claim 不直接存原文 chunk？
├  chunk 是原始文本（可能几百字），claim 是从中提取的原子事实断言（一句话）。一个 chunk 可以产出多条 claim。
└  取舍：claim 与 chunk 的关系通过 claim_evidence 表多对多映射，保留溯源但不冗余存储。

为什么 review_status 有 invalidated 而不只是 rejected？
├  [合理推断] rejected 是审查时主动拒绝；invalidated 是来源文档变更或版本过期后系统标记。两者触发路径不同。
└  source_version 字段配合 invalidated_at 时间戳，支持增量刷新时判断哪些 claim 需要重新提取。

claim 关系为什么不合并到 claims 表？
├  [面试扩展] 关系是图结构（多对多），合并到 claims 表会导致重复行或 JSON 数组。独立表支持双向查询（"谁支持这条 claim"和"这条 claim 支持谁"）且可独立索引。
└  替代：用 JSONB 数组存关系。失去关系级索引和约束（如禁止自环的 check）。
为什么用 interrupt() 而不是轮询

人工审查可能花几小时甚至几天，worker 不可能把 run 留在内存里等。interrupt(proposed) 抛一个 LangGraph 信号，checkpointer 存下；worker 内存释放，等 create_human_decision 到了再恢复。另一种做法是 worker 里跑轮询循环 — 那样会一直占着 worker slot 和 DB 读，而且 worker 异常重启会丢状态。[合理推断] 取舍是运维复杂度：run 是持久的，但必须部署 checkpointer（Postgres 或 Redis）并正确处理 resume。

追问树 — 证据审查
为什么图在 build_evidence_graph 里懒构建？
├  from langgraph... import 在函数内并有 try/except ImportError → RuntimeError。API 和单元测试不需要加载 worker 运行时。
└  取舍：首次构建有 import 成本。[优化建议] 若 build 频繁，按 domain 缓存已编译的图。

为什么 fan_out 用 Send 而不是循环节点？
├  Send() 是 LangGraph 的 map-reduce 原语：每个问题成为独立的 state 实例可并发，再由 reconcile reduce。
└  替代：单节点顺序遍历问题。
   └  失去独立问题的并发性，部分失败处理更麻烦。

worker 崩溃后中途审查如何恢复？
├  checkpointer 已持久化 interrupt。在 create_human_decision 时 API 用相同的 thread_id 加 decision 重新调图；LangGraph 从 interrupt 处恢复。
└  重复决策怎么办？
   └  [项目事实] create_decision 要求 Idempotency-Key；重复返回原始 accepted 记录。
[项目事实] 审查可自动批准

若 domain.review_payload(state) 返回 None，审查节点跳过人工，直接发 {"decision": "approve"}。这是低风险增量刷新的路径。

[面试扩展] 异步写幂等

所有改 evidence 的端点（/research-runs、/runs/{id}/decisions、/reports/{id}/refresh、/evaluation-runs、/dev/fault-scenarios）都要求 Idempotency-Key（8–160 字符，^[A-Za-z0-9._:-]{8,160}$）。相同 key + 相同 body → 重放；相同 key + 不同 body → 422。

流程 3 · 功能中心 · 路径系统

混合 RAG · 5 路径 · 加权 RRF

最朴素的 RAG 把每个 query 都按一个固定比例混合向量搜索和关键词搜索。ResearchMate 不这样：plan_retrieval() 先看问题形状和语料规模，从五条路径里选一条，给出 dense 和 lexical 的权重；检索器 LocalEvidenceRetriever.retrieve() 把这份计划翻成一个 Qdrant 混合查询，用 RRF（按排名倒数融合）把 BM25 关键词命中和 dense 向量命中合并。向量库失败时，退到有界的应用内 BM25，并把响应标成 degraded=true，而不是悄悄假装成功。

1

plan_retrieval()

选路径

在碰向量库之前，规划器先决定怎么搜。services/query_planning.py 归一化问题、估算语料 token，产出一份 RetrievalPlan{route, queries, dense_weight, lexical_weight, reason, degraded}。[项目事实] 输出有常量收紧：MAX_QUERY_VARIANTS=3、MAX_QUERY_CHARS=600。正则把问题分到 exact、semantic、expansion 三类触发。

2

Qdrant 混合查询

原生 RRF

BM25 给关键词重叠打分；dense 用 embedding 给语义相似度打分。两个分数不在同一个量纲上，所以系统不直接融合原始分数，而是融合它们的排名 — 这就是 RRF。当 settings.qdrant_native_hybrid_enabled=true 且有 hybrid_store 时，hybrid_store.query(plan=plan) 对每个规划变体建一个 RrfQuery，里面带命名的 bm25 和 dense 预取。[项目事实] dense 和 lexical 的权重被切分到各变体上，复合查询可以扩大召回而不让某一个变体独大。

外部: Qdrant + NVIDIA embed
3

hydration

归属受限

向量库只返回 id 和 payload。要拿到 chunk 的全文，_hydrate_matches() 取 payload.chunk_id 列表，调 repository.get_chunks_by_ids(user, project_id, ids) 拿真实 chunk，保留 provider 的排名并赋 semantic_rank。[项目事实] 这一层就是安全边界：即便 query 构造里有 bug，hydrate 仍然强制按 owner + project 过滤，一个用户读不到别人的 chunk。

4

有界降级

绝不伪造成功

向量库失败时，流程既不会放弃查询，也不会假装它工作正常。三条回退路径每条都带一个稳定的 reason 字符串和 degraded=true：hybrid_store_unconfigured（没配 store → 走应用内 BM25）、legacy_dense_unavailable_application_bm25_used（旧路径 dense 失败）、native_hybrid_unavailable_application_bm25_used（原生路径 dense 失败）。下游 judge 和用户都能看到这次降级。[项目事实]

5

轻量分支

无向量 chunk

不是每个 chunk 都有向量。没有向量的非 wiki chunk（has_vector=false）走 _lightweight_candidates()：对每个查询变体跑 BM25，按 chunk id 去重保留最高分，数量上限 rerank_candidate_limit。[项目事实]

追问树 — 混合 RAG
为什么先路由再检索？
├  单一静态配比无法同时回答"API_KEY 是什么"（exact）和"认证怎么工作"（semantic）。路由后再调 Qdrant 还能在 full_context 够用时避免向量延迟。
└  取舍：路由判错就浪费检索。缓解：full_context 跑 BM25 相关性闸门，绝不返回无关 chunk。

为什么用加权 RRF 而不是融合分数？
├  BM25 和 dense 的分数在不同量纲上，直接融合原始分数会很脆。RRF 只用排名，planner 的权重切分到各变体，任何变体不会独大。
└  某一支返回空怎么办？
   └  RRF 仍工作；缺失排名贡献为 0。向量整体失败由降级路径单独处理。

planner LLM 是可选的，何时用？
├  仅 expanded_hybrid 触发一次有界重写，返回 standalone_query + 至多 2 个变体，由 _ExpansionOutput 校验 schema。其他路径纯正则 — 零 LLM 延迟。
[项目事实] owner 过滤是向量层硬约束

hybrid_store.owner_filter() 对 user_id、project_id、source_type、可选 document_ids 强制 must 条件。即使 query 构造器有 bug 也不会泄露他人向量。双层隔离：Qdrant 硬过滤 + Postgres RLS。

[优化建议] benchmark dense vs lexical 权重

源码只能确认权重数值（0.30/0.70 等），无法确认是否经过调参。建议按路径跑小规模离线评测（recall@K + MRR），用数据解释权重不对称，而不是凭直觉。

流程 4 · 功能中心 · 双层

流式 · SSE workflow 事件 + token 生成

ResearchMate 在两层做流式，服务不同的需求。证据 workflow 层让浏览器盯一个又长又异步的 run：客户端订阅 GET /evidence/runs/{run_id}/events（Server-Sent Events），服务端持续吐存储事件，直到 run 结束或空闲太久，断线重连时按 Last-Event-ID 从上次位置续传。Ask 路径是另一回事：目前 LLM 直接返回完整答案；如果未来换上流式 chat provider，可以在不动 SSE 契约的情况下让推理 token 也流起来。

1

GET /runs/{run_id}/events

StreamingResponse

用户打开一个 run 页面时，浏览器会开一条 SSE 连接。routers/evidence.py stream_run_events() 返回一个 StreamingResponse，media_type 是 text/event-stream，并带上 Cache-Control: no-cache 和 X-Accel-Buffering: no。[项目事实] 后者关闭 nginx 缓冲，每条事件一写就 flush 给客户端，不会攒满一个 buffer 才发。

2

游标解析

Last-Event-ID

连接断了重连时，浏览器会把最后看到的 Last-Event-ID 头发回来。handler 做 after_sequence = max(after_sequence, int(last_event_id))；不是整数就返回 422 INVALID_EVENT_CURSOR。[项目事实] 每条事件都带一个 SSE id: 字段，让浏览器断线重连后从上次看到的位置继续，而不是从头重放。

3

generate()

轮询 + 心跳

异步生成器在客户端还连着且空闲心跳没到 15 次时循环。每轮 evidence.list_run_events(cursor) 返回比游标更新的存储事件，每条事件按 id: <seq>\nevent: <type>\ndata: <json>\n\n 发出。没有新事件时，生成器吐一条 : heartbeat\n\n（SSE 注释，浏览器不当事件处理）并 sleep 1 秒。[项目事实]

4

终止关闭

workflow 完成

当某条事件 status in {succeeded, failed} 且 node_key == "workflow" 时，生成器返回，流关闭。[项目事实] 这避免 run 已经跑完了，流还挂着不关的情况。

5

token 生成层

Ask 路径

Ask 路径是另一个形状。services/query_generation.py generate_answer() 调 answering.py，再调 ChatProvider。[项目事实] 当前 chat provider 返回一个完整的 LLMResult；生成 tool call 记录 latency_ms。[合理推断] 因为 Ask 响应契约是单次 JSON（不分块），未来换上流式 chat provider 把推理 token 也吐给客户端，响应形状不需要改 — citations 还是等生成完再组装。

外部: NVIDIA chat
为什么 SSE 而不是 WebSocket

证据事件只有服务器到客户端一个方向，且都存在 DB 里，需要可续传。SSE 免费：自动重连 + Last-Event-ID，服务端无需维护连接状态，还能穿透那些会破坏 WebSocket 的代理。[合理推断] 15 个空闲心跳的上限约束长尾 run 的资源占用；断线重连从游标恢复，所以这个上限不会丢事件。

追问树 — 流式
为什么 1s 一次轮询而不是 worker 主动推？
├  API 进程持有 SSE 连接；worker 在另一个进程跑。对 evidence.list_run_events 的轮询读是一个简单、RLS 安全的边界。
└  取舍：事件产生到送达最多 1s 延迟。
   └  [优化建议] 加 Postgres LISTEN/NOTIFY → asyncio.Event 唤醒，让循环只在真正空闲时 sleep。

为什么是 15 心跳？
├  15 个周期 × 1s = 15s 宽限。客户端能用最后的 Last-Event-ID 重连。
└  为什么不无限？
   └  长空闲连接占用代理和连接槽。15s 是可调的折中。

Ask 路径能不能也流式吐 token？
├  需要流式 chat provider，并把 AskResponse 契约改成 chunked。目前生成是单次。
└  [优化建议] 加一个可选 ?stream=true 的 Ask 路由，通过 SSE 吐推理 token，最后再统一构造 citations。
[项目事实] 心跳保活

长检索期间，常常几秒都没有真实事件。空闲心跳吐一条 : heartbeat\n\n（SSE 注释），让中间的代理、负载均衡器不关连接。注释前缀让浏览器不当事件弹出。

[面试扩展] 幂等续传

SSE 端点只读，无写入。配合 Last-Event-ID，重连的客户端不会重复副作用。改状态的端点（/decisions）自带幂等 key，这是异步写系统的标准模式。

流程 5 · 功能中心 · 上传到任务

文档摄取 · 预留 → 流式 → 校验 → 任务

用户上传一份 PDF。前端分三个 HTTP 调用走完整流程：先预留文档元数据（POST /documents，返回 id），再通过 API 代理把字节流式传给对象存储（PUT /documents/{id}/content，API 一边校验类型和尺寸一边 spool 到临时文件，再上传到对象存储），最后通知完成（POST /documents/{id}/complete）— 这一步会校验已存对象并把一个 Celery 摄取任务入队，返回 202。用户可以离开页面，解析、切块、embedding、wiki 编译都在后台跑。

预留元数据 PUT 流代理 Spooled 临时文件 对象存储 校验 checksum 入队任务 202 Accepted
1

POST /documents

预留

在传任何字节之前，客户端先声明这份文件：routers/documents.py create_document() 把元数据存下来，绑定 user_id + project_id。[项目事实] 响应是一个 DocumentRecord，状态 201。另一个端点 POST /documents/upload-url 返回一个签名 URL，让客户端绕过代理直接传给 provider（用在代理路径走不通的 CORS 场景）。

DB 写: documents
2

PUT /documents/{id}/content

代理上传

客户端把文件体流式发给 API，API 把它 spool 到一个 SpooledTemporaryFile(max_size=1024*1024)（1 MB 内留内存，超过就滚到磁盘）。同时 API 校验 Content-Type 跟预留的 mime_type 一致（否则 415 MIME_MISMATCH），以及收到的字节跟预留的 size_bytes 一致（否则 409 SIZE_MISMATCH）。超过 MAX_DOCUMENT_UPLOAD_BYTES 或预留 document.size_bytes 的上传会被 413 拒掉。[项目事实]

外部: S3 兼容存储
3

object_storage.upload_stream()

线程卸载

同步的 S3 兼容客户端被包在 await to_thread.run_sync(lambda: object_storage.upload_stream(object_key, source, content_type=mime_type)) 里，这样上传期间 event loop 不会被阻塞。对象 key 形如 users/{uid}/projects/{pid}/documents/{did}/{filename}，按用户和项目做命名空间隔离。失败映射成 503 OBJECT_STORAGE_UNAVAILABLE，能附上 provider 的 code 和 status。[项目事实]

4

POST /documents/{id}/complete

校验 + 入队

字节传完后，客户端调一次 complete。complete_upload() 接收可选的 checksum_sha256 和 extracted_text。它校验已上传的对象存在且匹配：UploadVerificationError → 409；ObjectStorageRequestError → 503；ObjectStorageConfigurationError → 503。成功后 repository.complete_document 返回一个 job；响应是 202 {"job_id", "status"}。[项目事实]

DB 写: documents/jobs
5

Celery 摄取任务

Worker

后台任务解析已上传的对象，切分文本，用 NVIDIA 做 embedding，把 chunk 和向量分别写入 Qdrant 和 Postgres，可选地编译一个 wiki 页（见流程 3 双路径）。[合理推断] 任务通过相同的 job_id 幂等；失败的任务可以重新 complete 触发，不用再传一遍字节。

外部: NVIDIA embed + Qdrant
为什么不直接客户端 → 存储，而要走 API 代理

从浏览器直接把字节传到 S3 能省 API 带宽，但 API 就没机会在存储前校验类型和尺寸了。代理路径可以让 API 在一字节进存储前就校验好 Content-Type、Content-Length、预留尺寸。spooled 临时文件让内存有界 — 小上传留内存，大的滚到磁盘。[合理推断] 签名 URL 路径是为那些 CORS 或公司代理导致直传不可行的客户端准备的，但代理是默认路径。

追问树 — 文档摄取
为什么要三步而不是一次 POST？
├  第 1 步预留元数据，让第 2 步能在存储前校验类型和尺寸。第 3 步通知完成并入队任务。
└  一个端点能做完吗？
   └  能，但 HTTP 连接要扛到解析 + embed 完成。异步任务模型让上传快、摄取有界。

为什么 SpooledTemporaryFile(max_size=1MB)？
├  小上传留内存（快），大的滚到磁盘（内存有界）。1MB 是内存/IO 的折中。
└  [优化建议] 按实测上传尺寸分布 benchmark 这个阈值。

上传怎么幂等？
├  POST /documents/{id}/complete 是写入边界。[项目事实] 它返回的 job 以 job_id 为键；job 本身在支持重试的 Celery 队列里跑。
└  同一 body 被完成两次怎么办？
   └  文档记录单一；第二次 complete 返回已存在的 job 状态。
[项目事实] 上传上限在两层强制

流式过程中累计字节。超过 MAX_DOCUMENT_UPLOAD_BYTES 或预留的 document.size_bytes 都会触发 413 UPLOAD_TOO_LARGE 并停止流。最终尺寸不匹配（即使低于上限）也返回 409 SIZE_MISMATCH。

[面试扩展] MIME 与尺寸前置条件

预留时的 mime_type 与 size_bytes 是早期契约：客户端在预留时承诺上传形状，代理字节级强制执行，避免预留后客户端上传任意内容。
