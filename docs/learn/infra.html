Render / Vercel / Supabase / Qdrant . 4 topics, interview-focused

Infrastructure . interview deep dive

ResearchMate runs four infra pieces that each answer one concrete question. Where do API and worker live after you push code? One Render Free-tier web service, because the Free tier gives exactly one always-on slot. How does the browser reach the API when a corporate proxy mangles *.onrender.com? Vercel rewrites /api/v1/* same-origin, so the browser never sees the onrender host. Where is the source of truth? Supabase Postgres, locked behind RLS and an additive, SHA-256-stamped migration runner. Where do embeddings live? A Qdrant v3 collection with native BM25 + 4096-d dense vectors, filtered by owner on every query.

1 Render Free web service Vercel rewrite bypass 21 SQL migrations + advisory lock Qdrant v3 native hybrid

Tech-stack-centered . Render deployment topology

One Free-tier service runs API + worker from one image

[Project fact] render.yaml declares exactly one type: web service on plan: free, region oregon, runtime docker, command python -m researchmate_worker.render_combined.

Picture what happens after you push code to main: GitHub Actions runs the CI pipeline; if every gate is green, Render notices and rebuilds the Docker image from workers/ai-worker/Dockerfile. The single container the image produces is asked to run render_combined — one Python process that starts the ASGI API server and the Celery worker loop together. There is no second Render service for the worker.

The reason to fuse them is one Free-tier rule: Render's Free plan provides exactly one always-on web service. Paid background workers need a paid tier. So the project puts both jobs into the one slot it gets for free. The cost is in-process contention — when a user request spikes the API, the same process also has to keep the Celery worker responsive — and the Free tier can cold-start or sleep after inactivity. [Reasonable inference] For an MVP-scale project the trade reads as acceptable: zero monthly spend beats clean separation.

Key mechanisms
  • autoDeployTrigger: checksPass — Render waits for the GitHub Actions researchmate-ci run to go green before it picks up a build. CI red = no deploy. [Project fact]
  • buildFilter paths — a push only triggers a rebuild if it touches apps/api/**, workers/ai-worker/**, infra/supabase/migrations/**, the migration or Qdrant provisioner scripts, pyproject.toml or uv.lock. A README-only commit skips deploy. [Project fact]
  • healthCheckPath: /api/v1/healthz — Render probes one cheap liveness route to mark the service up; /api/v1/readyz is the separate route that checks Postgres, Redis and Qdrant. [Reasonable inference]
  • envVarGroup: researchmate-backend — non-secret values (model names, base URLs, toggles like RUN_SCHEMA_MIGRATIONS=1) are checked straight into render.yaml; secrets (DATABASE_URL, REDIS_URL, NVIDIA_API_KEY, Langfuse keys, etc.) are marked sync: false and live only on the Render dashboard. [Project fact]
Why not two services? Free tier = exactly one always-on web service. A second, paid background-worker tier would host the Celery loop separately. For MVP scale the project accepts in-process contention as the cost of zero monthly spend. [Reasonable inference]

Interview question tree

Why is API + worker fused into one Render service?
└─ What does render_combined actually start in-process?
   └─ What happens to worker throughput when the API gets a burst?
Answer: They share one process and one CPU budget. A burst on the API starves the
Celery loop, so worker latency degrades. At scale you split: API stays on the
web service, worker moves to a paid background-worker tier or an external
worker pool, and they share only Redis + Postgres.

Why autoDeployTrigger: checksPass instead of every push to main?
└─ Which CI jobs must pass before Render picks up the build?
   └─ What if a CI job is flaky — does Render wait or skip?
Answer: ci-success (see cicd page) must report success. If CI re-runs the
flaky job and it greens, Render picks up the build. If CI stays red, Render
holds the previous good release. There is no partial deploy.

Function-centered . Vercel + server-side rewrite

Vercel rewrites /api/v1/* same-origin to dodge a corporate proxy

[Project fact] apps/web/next.config.ts defines async rewrites() that, when NODE_ENV !== "development", sends /api/v1/:path* to ${backendOrigin}/api/v1/:path*.

Without the rewrite, the browser would call https://researchmate-backend-dev.onrender.com/api/v1/* directly. The problem: corporate or ISP proxies sometimes intercept that *.onrender.com host and hand the browser an HTML warning page instead of the JSON it expected — health checks break, authenticated calls break, everything looks broken to a user on a corporate laptop even though the backend is healthy.

Vercel's rewrite changes who talks to Render. The browser now calls a same-origin URL on the Vercel host (e.g. research-mate-web.vercel.app/api/v1/*), which the proxy does not intercept. Vercel's server then issues a server-to-server fetch to the Render backend. Because Vercel's servers are not behind the user's corporate proxy, the request reaches Render as JSON, and the response comes back as JSON. This is the single most asked-about infra decision in interviews because it touches CORS, same-origin cookies, and an unexpected deployment-environment constraint at once.

Key mechanisms
  • Dev returns [] — in NODE_ENV=development no rewrite runs, so the local frontend talks straight to http://localhost:8000/api/v1. [Project fact]
  • backendOrigin derivation — NEXT_PUBLIC_API_BASE_URL has its trailing /api/v1 stripped to get the bare origin; the same env is the local fallback. One knob configures both modes. [Project fact]
  • CORS_ALLOWED_ORIGINS — render.yaml pins it to https://research-mate-web.vercel.app. The backend only accepts cross-origin browser calls from that exact origin; a script calling from another origin is rejected. [Project fact]
  • Side benefit — same-origin cookies — because the browser sees only the Vercel origin, cookies do not cross origins, which keeps SameSite defaults from breaking auth. [Reasonable inference]
Trade-off: every API call now adds one Vercel hop (extra latency) and is capped by Vercel function execution time, which can hit long-running uploads. A presigned-S3 upload path was considered earlier and rejected; same-origin proxy is the project's chosen ceiling. [Project fact]

Interview question tree

Why rewrite /api/v1/* through Vercel instead of letting the browser call Render directly?
└─ What does the corporate proxy actually do to *.onrender.com?
   └─ How does server-to-server fetch bypass it where the browser cannot?
Answer: The proxy inspects outbound HTTP and swaps *.onrender.com responses with
an HTML interstitial. The browser is behind the proxy; Vercel's edge is not.
By having Vercel make the call, *.onrender.com never appears on the
user-controlled wire, so the proxy has nothing to intercept.

How does the backend know the request is legitimate?
└─ CORS_ALLOWED_ORIGINS is set to the Vercel origin — what attack does that stop?
   └─ If the proxy intercepts JSON, why does it not intercept the Vercel edge fetch?
Answer: CORS_ALLOWED_ORIGINS stops another site's script from talking to the
backend through the user's cookies. The Vercel fetch is server-to-server and
never traverses the corporate proxy, so the proxy does not get to swap it.

Tech-stack-centered . Supabase Postgres

RLS isolates tenants; migrations are additive, SHA-256 stamped and advisory-locked

[Project fact] Supabase provides managed Postgres at tjdkdganvszqawxspveg.supabase.co; all business tables enforce RLS keyed on auth.uid(); scripts/apply_migrations.py runs migrations under pg_advisory_xact_lock(726_334_129) with SHA-256 checksums.

Postgres is the single source of truth for everything except embeddings. What "single source of truth" buys you: when a worker crashes mid-task, Postgres still holds the agreed state; restart picks up the lease row and continues. There is no second store to reconcile.

Tenant isolation is enforced in the database, not in application code. Supabase auth issues a JWT whose sub claim is the user UUID. Postgres RLS policies compare that claim against a user_id column on each business row; a row whose user_id doesn't match the JWT is refused at the database. [Project fact] Even if the API has a bug that forgets to filter by user, the database refuses to hand back another tenant's row.

Migration mechanics (apply_migrations.py)
  • 21 additive SQL files — sorted by version prefix YYYYMMDDNNNN_*.sql; the validator rejects empty files and any file containing the literal string drop database. [Project fact]
  • pg_advisory_xact_lock(726_334_129) — a hard-coded integer key; two concurrent apply attempts on the same Postgres cannot both proceed. The lock is transaction-scoped, so commit or rollback releases it. [Project fact]
  • SHA-256 ledger — researchmate_schema_migrations(version, checksum_sha256, applied_at). If an already-applied file's hash later changes, the runner raises and aborts. Replay drift cannot sneak through silently. [Project fact]
  • ALLOW_SCHEMA_APPLY=1 — without this env the apply path refuses to run, which is the human approval gate. CI's npm run check:migrations runs --check-files only, no DB write. [Project fact]
  • Idempotent statements — every create table, create index and create policy uses if not exists or a drop policy if exists ... create policy pair, so the same file can be safely re-run within a transaction. [Project fact]
RLS edges to call out outbox_events has no authenticated-user read policy — only the service role can read it, so a misconfigured client JWT cannot leak coordinator rows. pipeline_versions layers developer and admin role policies above plain user-scope. [Project fact]

Interview question tree

Why enforce isolation in Postgres RLS instead of in the API?
└─ What can still go wrong even with RLS on?
   └─ How does auth.uid() map onto the JWT the API sends?
Answer: RLS means a buggy API still cannot leak another tenant's rows — the DB
refuses. The remaining risks are: leaking the service-role key, or shipping a
policy that matches the wrong column. auth.uid() reads the JWT sub claim
(Supabase auth populates it server-side via request headers).

Why pg_advisory_xact_lock with a magic key?
└─ What would happen with two migration runners racing?
   └─ Why advisory lock vs. SELECT ... FOR UPDATE on a sentinel row?
Answer: A sentinel-row lock needs a real row to lock and can be skipped if
someone deletes the row. An advisory lock is keyed on an integer and does not
need a row at all. Transaction scope means the lock dies with the transaction,
so a crashed runner releases the lock on rollback.

How does the SHA-256 checksum protect against replay drift?
└─ What if you legitimately need to edit an applied migration?
   └─ Why are migrations additive and not destructive?
Answer: You never edit an applied file — you ship a new forward migration that
adds the column or undoes the previous behavior. The SHA-256 ledger enforces
that contract: editing an applied file's bytes makes the runner fail. Destructive
ops are rejected up front by the validator so an operator cannot accidentally
DROP TABLE in production.

Tech-stack-centered . Qdrant hybrid retrieval

Native BM25 + dense 4096-d vectors; owner filters on every branch

[Project fact] infra/qdrant/researchmate_chunks.json declares a dense vector (size: 4096, Cosine), an IDF-weighted sparse vector and fusion: rrf; required_filters lists user_id, project_id, source_type.

Text retrieval has two failure modes. A pure keyword search (BM25) misses paraphrase — asking "how do I cancel a lease?" fails to retrieve "termination of tenancy." A pure dense-vector search misses exact rare tokens — a doc that says "CVE-2026-1234" will not surface for "CVE-2026-1234" if the embedding has not seen it. Hybrid retrieval runs both and fuses their rankings.

[Project fact] Qdrant v3 collection researchmate_chunks_v3 lives server-side and carries both retrievers in one collection. A 4096-d dense vector produced by NVIDIA nv-embed-v1 covers paraphrase; a native BM25 sparse vector (qdrant/bm25, modifier: idf) covers exact term match. [Reasonable inference] RRF (Reciprocal Rank Fusion) interleaves the two ranked lists so the project gets the best of each without running a separate rerank step just for the candidate set. (A separate ColBERT rerank collection researchmate_chunks_v2 is wired in afterwards for top candidates only.)

Key mechanisms
  • Named vector config — one collection holds {"dense": VectorParams(4096, COSINE), "bm25": SparseVectorParams(modifier=IDF)}. One query, two retrievers, fused output. [Project fact]
  • Required filter trio — every query must filter by user_id + project_id + source_type. Payload indexes on those plus document_id keep filtered queries fast. [Project fact]
  • Resumable backfill — provision_qdrant_hybrid.py batches BATCH_SIZE=24 chunks, stores a corpus SHA-256 fingerprint in researchmate_vector_migrations, and only re-embeds when the fingerprint changes. Stale points are reconciled by scroll + delete. [Project fact]
  • cloud_inference=True — Qdrant computes the sparse and dense vectors server-side instead of the client shipping them. For BM25 the client sends the raw text and Qdrant builds the sparse vector; for dense Qdrant calls the embedding API. [Reasonable inference]
Magic numbers to justify BATCH_SIZE=24, timeout=180s, BM25 document payload truncated to 1200 chars. [Project fact] Values are pinned constants in provision_qdrant_hybrid.py; [Optimization suggestion] benchmark batch size against Qdrant upsert latency and the NVIDIA embedding API rate limit — no project-level benchmark evidence in the repo.

Interview question tree

Why dense + BM25 fused with RRF, instead of one or the other?
└─ What does dense catch that BM25 misses?
   └─ What does BM25 catch that dense misses?
      └─ Why is IDF weighting on the sparse vector important?
Answer: Dense catches paraphrase and shared intent. BM25 catches exact rare
tokens (CVE IDs, product codes). IDF weighting down-weights common words on the
sparse side, so rare terms surface — without IDF, "the" and "CVE-2026-1234"
would contribute equally.

Why are user_id + project_id required on every query, not optional filters?
└─ What happens if you forget the filter — does Qdrant leak rows?
   └─ Why payload indexes on exactly those four fields, not all?
Answer: Forgetting the filter means a query could match another tenant's chunks.
required_filters in the collection config refuses an unfiltered query at the
client level. Payload indexes are paid storage and build time, so the project
indexes only the fields every query filters on.

How does the backfill stay resumable and never re-embed the same corpus?
└─ What does the corpus fingerprint protect against?
   └─ How are points that exist in Qdrant but not in Postgres reconciled?
Answer: The fingerprint is sha256 over (chunk_id, chunk_text sha256) for the
whole corpus. If the source text changed, the fingerprint changes and the run
re-embeds. Stale points (in Qdrant but not Postgres) are detected by scroll and
deleted before upsert.
