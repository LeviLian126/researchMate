最小心智模型

合约与测试保护什么,一段话讲清

先读这一节。如果你只记住本页 20% 的内容,这就是那 20%。

结论先行。 ResearchMate 是一个由许多独立部分组成的系统:FastAPI 服务端、Celery worker、Next.js 客户端、Postgres 数据库、LLM、向量库。一个请求从一个部分传到另一个部分时,双方必须就"交换的数据长什么样"达成一致。这个一致就是"合约"。本项目把合约写在三个必须保持同步的地方:OpenAPI YAML(一份描述所有端点和 schema 的文件)、Pydantic 模型(服务端用来校验每个请求的 Python 类)、SQL 迁移(数据库的实际表和行级安全策略)。52 个 pytest 文件检查这三层是否一致,以及运行中的代码是否遵守它们。

核心链路

client.ts (类型)
  ↓ 镜像
infra/openapi/openapi.yaml (真相来源,71 schema)
  ↓ 镜像
apps/api/.../schemas/*.py (Pydantic,运行时校验,11 文件)
  ↓ 镜像
infra/supabase/migrations/*.sql (PostgreSQL + RLS,持久化边界)

链路自上而下读,但执行是自下而上:YAML 由脚本从 Pydantic 重新生成,六个测试从磁盘读 SQL 文件,还有一个测试读前端 TypeScript 源码。任何一层的改动如果不匹配其他层,会在部署前让构建失败。

API 合约设计(技术栈中心)

三层镜像:OpenAPI → Pydantic → SQL

同一形状,三个边界。每层保护不同的东西。

结论先行。 一个请求要经过三个地方:发送它的客户端、处理它的服务端、存储它的数据库。如果请求字段的"形状"(类型、长度、允许值)只存在一层,另外两层会慢慢漂移,然后在后面出问题。所以 ResearchMate 把同一个形状维护在三层:OpenAPI YAML 是权威来源,Pydantic 模型复制它做运行时校验,SQL 迁移复制它做列类型和行级安全。一次改动必须传播到三层。六个测试在不运行应用代码的情况下,捕获任何一层的掉队。

每层保护什么

层边界保护对象
infra/openapi/openapi.yaml权威前端编译时类型(通过 apps/web/app/lib/api.ts)
apps/api/.../schemas/*.py请求运行时校验、自动 OpenAPI 文档、响应序列化
infra/supabase/migrations/*.sql持久化列类型、约束、RLS 所有者范围

每层把守一种不同的失败。OpenAPI YAML 把守客户端:TS 类型错了,编译时就失败。Pydantic 模型把守服务端:缺字段的请求在进业务逻辑前就被拒掉。SQL 层把守数据库:即使 service 出 bug 想读别人的行,表上的 RLS 策略也会拒绝。

关键机制

  1. FastAPI 从 Pydantic 派生 OpenAPI — 脚本 check:openapi 从当前 Pydantic 类重新生成 YAML,再和 infra/openapi/openapi.yaml 做 diff。开发者手改了 YAML 却忘了改 Pydantic(或反之),diff 不为空,门禁失败。
  2. 前端类型是本地手写,不靠代码生成 — apps/web/app/lib/api.ts 手工镜像 YAML。项目选手写而非 codegen,是为了前端构建不依赖一个 codegen 步骤。代价是漂移风险;test_frontend_contracts.py 读前端源码,校验前端只调用批准的 route。
  3. SQL 用 RLS 闭环 — test_database_migration_contract.py 用 Path.read_text() 打开 SQL 迁移文件,断言三件事:additive migration 保留既有 schema、RLS policy 覆盖每个 owner-scoped 表、持久化幂等键按 owner 唯一。
[项目事实] OpenAPI 声明 71 个 schema;main.py 把 ErrorResponse 注册为 400/401/403/404/409/422/429/502/503 的响应模型 — 每个错误遵循同一个 {code, message, request_id} envelope。packages/shared 已作为幽灵代码移除;YAML 是唯一的共享真相来源。

测试策略(功能中心)

先写测试再写代码、hermetic、同一 subagent 两个阶段

测试本身就是合约的一部分:它在实现之前写,运行时不碰真实基础设施。

结论先行。 测试按边界组织,不按模块:HTTP 集成、单元 service、worker、workflow,加上 6 个契约源码检视测试。整套是 hermetic 的—不连 PostgreSQL、Qdrant、Redis、LLM。两阶段设计先对着公开合约写测试(黑盒,源码禁看),再由同一 subagent 读源码,针对边界条件收紧测试(白盒)。两个阶段用同一 subagent 省 token,并强制测试断言可观测行为。

边界文件数典型断言

Hermetic 机制

  1. Fake LLM provider — 测试 settings 设 llm_provider="fake";fake 从队列返回脚本化响应。无需 API key、无网络、无 LLM 成本、输出确定。
  2. 内存 store 每个测试重置 — reset_local_store fixture 是 autouse,所以在每个测试前后都跑一次 store.reset()。一个测试无法把状态漏到下一个。
  3. TestClient,不开 socket — fastapi.testclient.TestClient 在同一进程内包住 ASGI app。不绑端口,所以没有网络抖动,也没有启动开销。
  4. 手搭的单元 double — 不用真实 DB 连接,测试传一个 RecordingConnection 捕获 SQL 字符串;不用真实 LLM 队列,传 collections.deque。构建便宜,断言精确。
  5. 源码检视但不执行 — 6 个测试用 Path.read_text() 加正则。它们从不 import 应用,所以不会因为缺依赖失败—只在磁盘上的合约实际变了才失败。
[项目事实] conftest.py 把 apps/api/src 和 workers/ai-worker/src 插入 sys.path — 每个测试隐式依赖它。api_workflow_support.py 共享 HEADERS = {"Authorization": "Bearer dev"} 和 create_ready_document() — 任何需要 ready evidence 的测试都靠它引导。

两阶段合约优先设计

[项目事实] 阶段 1 黑盒:subagent 对着公开合约(route、schema、状态码)写测试,源码禁看。测试反映系统从外面应该怎么表现。阶段 2 白盒:同一 subagent 现在读源码,针对边界条件收紧测试(空输入、超出长度、竞态)。对齐 ISTQB / IEEE 29119 / SOA,它们把合约测试放在结构测试之前。两阶段用同一 subagent 比派两个独立 agent 省 token,阶段 1 的合约意图能带进阶段 2 的源码 review。

Pydantic schema 模式(技术栈中心)

五个让合约在运行时保持诚实的模式

schemas/ 下 11 个文件实现运行时合约。五个模式反复出现。

结论先行。 Pydantic 模型是合约在运行时的具体表现。没有规矩的话,一个枚举字段可能序列化成 TaskType.ANSWER 而不是 "answer",一个凭证字段可能漏进日志,一个数值边界可能在一处硬编码却在另一处漂移。五个模式阻止这些:继承 (str, Enum) 让 wire value 稳定,用 model_validator(mode="after") 校验跨字段规则,配 ConfigDict(use_enum_values=True) 让响应发出字符串,用 SecretStr 包凭证,把每个数值边界作为命名常量放进 schemas/common.py。

模式 1 — (str, Enum) 稳定 wire value

class TaskType(str, Enum):
    ANSWER = "answer"
    QUIZ = "quiz"

class DocumentStatus(str, Enum):
    UPLOADED = "uploaded"; PARSING = "parsing"; PARSED = "parsed"
    INDEXING = "indexing"; READY = "ready"; FAILED = "failed"
    EXPIRED = "expired"; DELETED = "deleted"

[项目事实] 普通 Enum 序列化到 JSON 时,输出可能是 "TaskType.ANSWER"(repr),前端不认。继承 (str, Enum) 让 Python 把成员当成它的字符串值,所以 TaskType.ANSWER 直接序列化成 "answer"。下面的模式 3 是让这在 model_dump() 里也生效的下一步。

模式 2 — model_validator(mode="after") 跨字段规则

class HumanDecisionCreate(BaseModel):
    interrupt_key: str = Field(min_length=1, max_length=160)
    decision: Literal["approve", "edit", "reject"]
    edited_payload: dict[str, Any] | None = None

    @model_validator(mode="after")
    def require_edited_payload(self) -> HumanDecisionCreate:
        if self.decision == "edit" and self.edited_payload is None:
            raise ValueError("edited_payload is required for an edit decision")
        if self.decision != "edit" and self.edited_payload is not None:
            raise ValueError("edited_payload is only valid for an edit decision")
        return self

[项目事实] Pydantic 的字段 validator 一次只查一个字段。但有些规则跨多个字段:这里,如果 decision 是 edit,edited_payload 必须有;如果是别的,edited_payload 必须没有。model_validator(mode="after") 在 Pydantic 解析并类型化完所有字段后才跑,所以函数可以同时读 self.decision 和 self.edited_payload。抛出的 ValueError 变成 422 响应。代码库里其他例子:SourceScope.reject_duplicate_documents 拒绝有歧义的重复 document id;ReportRefreshCreate.require_change 要求至少一个变更文档或强制 section。

模式 3 — ConfigDict(use_enum_values=True)

[项目事实] 模式 1 让枚举在 JSON 编码时变成字符串,但 Pydantic 在你调 model_dump() 时仍然保留枚举成员。没有 use_enum_values=True,dump 出的 dict 是 {"task_type": TaskType.ANSWER} 而不是 {"task_type": "answer"}。在 model config 上设这个,告诉 Pydantic 所有地方都 dump 字符串值。应用在 Citation、ExecutionPlan、GroundedAnswer、AskResponse。

模式 4 — SecretStr + 类型化 Settings

class Settings(BaseSettings):
    nvidia_api_key: SecretStr | None = None
    qdrant_api_key: SecretStr | None = None
    object_storage_secret_access_key: SecretStr | None = None
    llm_temperature: float = Field(default=1.0, ge=0, le=2)
    llm_max_tokens: int = Field(default=16_384, ge=1, le=32_768)

[项目事实] API key 用普通 str 会在 traceback、日志、repr(settings) 里被打出来。SecretStr 包住值,显示 **********;唯一能读出原始 key 的方式是 settings.nvidia_api_key.get_secret_value()。每个可调参数都是带显式 ge/le 边界的 Field—不是裸 default—所以环境变量超范围会响亮地失败,而不是静默错误配置。

模式 5 — 集中化常量,无 magic number

MAX_TEXT_LENGTH = 1200
MAX_MESSAGE_LENGTH = 8000
MAX_ANSWER_LENGTH = 16000
MAX_FALLBACK_REASON_LENGTH = 300
# 然后在 ask.py:
message: str = Field(min_length=1, max_length=MAX_MESSAGE_LENGTH)

[项目事实] 同一个数字必须出现在三个地方—Pydantic 的 Field、SQL 的 CHECK 约束、前端的 maxLength 属性—所以命名一次再 import 是保持它们同步的唯一办法。schemas/common.py 集中了 40+ 个常量:文本边界、snippet 长度、evidence workflow 边界、upload 边界、quiz 边界。AGENTS.md 禁止在 validator 里写 max_length=1200 这样的字面量;必须用常量。

[合理推断] 当合约被三层镜像时,集中化才回报:一个常量流入 Pydantic Field、SQL CHECK 约束、前端 max-length 属性。没有一个统一的名字,三份拷贝会静默漂移—服务端收 1200 字符,DB 在 1000 处截断,前端限 1500。

├  JSON 序列化直接发字符串值;无需自定义 encoder。
└  那为什么还要 use_enum_values=True?

└  "before" 什么时候更好?
   └  需要在类型强转前预处理原始输入时(如重命名字段)。

├  边界要跨 Pydantic、SQL CHECK、前端 max-length 镜像。
└  代价?
   └  间接层;由 AGENTS.md 禁字面量规则缓解。

幂等性(功能中心)

Idempotency-Key:为什么网络重试不能让 LLM 被算两次钱

让有成本的 POST 安全重试的协议。

结论先行。 有些 POST 端点每次跑都耗时间或钱:Ask 请求触发一次 LLM 调用,Quiz 请求触发另一次 LLM 调用,一次 evaluation 跑很多次。如果客户端发了请求,网络在响应回来前超时,客户端不知道服务端到底跑了没有。本能反应是重试—但裸重试让 LLM 跑两次,成本翻倍。Idempotency-Key 协议解决这个:客户端在第一次请求上挂一个随机 key;服务端存住 key、请求体的 hash、响应。带相同 key 和相同 body 的重试,服务端直接返回已存的响应,不再跑。带相同 key 但不同 body 的重试,服务端返回 409 拒绝,因为客户端在试图把一个 key 用在不同的意图上。

请求链路

POST /api/v1/ask
Idempotency-Key: 9f3a...client   (8-160 字符,Ask 可选,evidence 端点必填)
Authorization: Bearer <dev|prod-jwt>

→ Coordinator(user, operation, key, payload)
   ├  state=="execute"  → 执行,然后 complete() 持久化响应快照
   ├  state=="replay"   → 返回已存 JSON(不二次执行)
   ├  state=="mismatch" → IdempotencyError("IDEMPOTENCY_KEY_REUSED") → 409
   └  state=="in_progress" → IdempotencyError("IDEMPOTENCY_REQUEST_IN_PROGRESS") → 409

四个状态覆盖四种情况:execute 是第一次看到这个 key;replay 是带相同 body 的安全重试,返回已存的答案;mismatch 是客户端错误(把 key 用在不同请求上);in_progress 是一个并发相同请求还在跑。

关键机制

  1. Header,不是 body 字段 — routers/ask.py:idempotency_key: str | None = Header(default=None, alias="Idempotency-Key", min_length=8, max_length=160)。quiz.py 和 evidence.py 5 个端点同模式。放 header 让 body 保持干净,便于 hash。
  2. Payload hash 是规范化的 — 两个请求字段相同但顺序不同,必须 hash 成同一个值。request_hash(payload) 用 sort_keys=True, separators=(",",":")(无空格)做 JSON dump,再 SHA-256。字段顺序不会造成假冲突。
  3. 按用户+按操作 scope — begin_idempotent_operation(user, operation, key, payload_hash) 把 key 绑 user_id 和操作名存。一个用户的 "abc123" 不会和另一个用户的 "abc123" 碰撞;一个用于 Ask 的 key 也不能被重放用于 Quiz。
  4. Postgres FOR UPDATE 锁 — evidence_evaluations.py 在事务内对幂等行做 SELECT ... FOR UPDATE。两个相同并发请求都试图抢这行,一个阻塞直到另一个提交,所以它们串行化,而不是都执行。
  5. abandon() 失败时释放 — 操作抛异常时 abandon() 清除预留,让安全重试能再次执行。不这样做,一次瞬态失败会永久占用 key。
[项目事实] 两个不同的错误码:IDEMPOTENCY_KEY_REUSED(同 key 不同 body → 409)和 IDEMPOTENCY_REQUEST_IN_PROGRESS(同 key 同 body 且仍在跑 → 409)。test_api_regressions.py 两者都覆盖:test_idempotency_replays_without_duplicate_messages 和 test_idempotency_key_body_mismatch_returns_conflict。

面试追问树

为什么 key 长度边界是 8-160 字符?
├  够短以便存储/dedupe 索引高效;够长以装下真实 UUID/hex。
└  客户端发 1 字符 key 会怎样?
   └  Header 校验拒绝(min_length=8)→ 422,到不了 coordinator。

为什么要 payload hash 加 key?
├  key 标识意图;hash 验证 body 与首次执行匹配。
└  客户端合法重发同 body 怎么办?
   └  那是重放 — coordinator 返回已存响应,不二次执行。

为什么按用户+按操作 scope?
├  防跨用户 key 碰撞;一个用户的 "abc123" 不能重放另一个的。
└  并发?
   └  事务内 SELECT ... FOR UPDATE 把并发相同请求串行化。

worker 执行中崩溃会怎样?
├  abandon()(或进程退出)释放预留;安全重试可再次执行。
└  风险?
   └  若 complete() 已持久化但响应丢失,重放仍返回已存快照。

覆盖率门禁与生产安全(技术栈中心)

69% 行+分支,CI 强制,合约测试守护

覆盖率是合约,不是指标。低于 69% CI 失败,源码检视测试断言门禁真的在跑。

结论先行。 覆盖率衡量测试实际执行了应用源码的哪些行和分支。npm run test:python 跑 coverage run --branch --source=apps/api/src,workers/.../src -m pytest -q 然后 coverage report --fail-under=69。69% 阈值作用于 API 和 worker 源码根的行+分支。69% 刻意不是 90% 或 100%:测试套优先覆盖合约和边界,而非每个 service 方法的穷举覆盖。另一个源码检视测试读 CI workflow 文件,断言 coverage 步骤在部署前真的跑—有人删了门禁,这个测试就挂。

关键事实

  1. Source 范围 — --source=apps/api/src/researchmate_api,workers/ai-worker/src/researchmate_worker;tests/ 里的测试不计入分子。所以 69% 是"生产源码里有多少被测试执行到"。
  2. 分支覆盖,不只是行 — --branch 强制 if/else 两臂都被覆盖。只看行覆盖会把一个 if 标为已覆盖,只要真分支跑过—哪怕 else 分支(里头可能有 raise)从没执行。
  3. dev 依赖锁版本 — 根 pyproject.toml 锁 coverage>=7.10.0,<8、pytest>=9.0.0,<10;pyright==1.1.390、ruff==0.16.0 做类型 + lint 门禁。
  4. 合约测试守护门禁本身 — test_release_pipeline.py::test_ci_runs_the_full_test_build_contract_and_security_gate 读 CI YAML 文件,断言 coverage 步骤是必跑的。门禁由一个在同一测试套里跑的测试守护。
  5. hermetic 让覆盖率是真 — 没有测试因 "infra 不可用" 被 skip。因为每个测试都用 fake,CI 跑到的每行都能在本地复现。不会出现"CI 覆盖率高但测试套在开发本机跑不起来"的情况。
[项目事实] pre-commit hook(.pre-commit-config.yaml)在每次 commit 前本地跑 ruff、ruff-format、pyright;用 uv run pre-commit install 安装。[合理推断] 69% 阈值刻意不到 90% — 测试套优先覆盖合约 + 边界,而非每个 service 方法的穷举行覆盖,后者维护成本高、边际安全收益低。

面试追问树

为什么是 69% 而不是 90%?
├  测试套优先覆盖合约 + 边界,而非穷举行覆盖。
└  哪些没覆盖?
   └  [项目事实] 当前材料未按模块拆分 31% 的缺口;需要 coverage 报告。

为什么分支而不只行覆盖?
├  行覆盖漏掉 if/else 的假分支;分支强制两臂。
└  代价?
   └  需要更多测试;由 hermetic double 让分支测试便宜来缓解。

怎么知道 CI 真的执行门禁?
├  test_release_pipeline.py 读 CI YAML 断言 coverage 是必跑步骤。
└  有人把门禁删了会怎样?
   └  那个源码检视测试挂 → 构建挂 → 改动无法合入。
