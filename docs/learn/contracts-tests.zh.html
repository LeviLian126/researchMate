合约与测试 · OpenAPI + tests

ResearchMate 测试套件采用 Hermetic、合约优先的验证方式。生成的 OpenAPI 规范定义 71 个 schema，由 Pydantic 模型和前端类型共同镜像。tests/ 下有 47 个 test_*.py 文件，覆盖 HTTP 集成、单元、worker、工作流和源码契约，不依赖云服务。

71 个 OpenAPI schema 47 个 test_*.py 文件 3 个 Python 基础设施文件 + 1 个 INI 配置 7 个 Vitest + 1 个 Playwright 前端测试 三层契约镜像架构 Hermetic · 无外部依赖

技术栈基础

驱动合约与测试的 7 个核心依赖

每张卡片说明该技术的通用职责,以及 ResearchMate 在合约验证中的具体用法。

TypeScript type contracts

生成的 OpenAPI 规范以 71 个 schema 定义权威 API 形状。前端类型位于 apps/web/app/lib/api.ts，后端 Pydantic 模型负责请求边界校验。

Pydantic

Python 数据验证库。后端将每个 TypeScript 合约镜像为 apps/api/src/researchmate_api/schemas/ 下的 Pydantic 模型。Pydantic 在请求边界强制执行字段类型、可选 vs 必填、枚举约束和验证器逻辑。test_project_scaffold.py 验证后端 Pydantic 合约与 OpenAPI 规范定义的请求形状一致。

pytest

Python 测试框架(锁定 9.0+)。pytest.ini 配置 -p no:cacheprovider --basetemp=.pytest-temp 以确保确定性、无缓存的运行。conftest.py 将 API 和 worker 源码路径插入 sys.path。测试函数使用 def test_* 命名,pytest.raises 验证预期失败,pytest.importorskip 处理 SQLAlchemy 等可选依赖。

Vitest

前端单元测试框架,在 apps/web/vitest.config.ts 中配置 jsdom 环境和 v8 coverage provider。7 个测试文件覆盖 API 客户端逻辑、auth gate、展示组件、demo 模式、邮件限流、幂等 intent 和 Supabase session 处理。覆盖率阈值要求 app/lib 和 app/components 达到 40% 行和语句覆盖。

Playwright

浏览器验收测试框架。apps/web/playwright.config.ts 在 demo 模式(NEXT_PUBLIC_DEMO_MODE=true)下对端口 3100 的本地 Next.js dev server 运行测试。1 个 E2E 测试文件(demo-workspace.e2e.ts)验证确定性 client-only demo 运行时。CI 中 retries=2、单 worker;本地运行完全并行。

Hermetic testing

整个 Python 测试套件是 hermetic 的:无真实 PostgreSQL、Qdrant、Redis、LLM 或外部 HTTP 调用。FastAPI TestClient 创建进程内应用,Settings(app_env="test", llm_provider="fake")。autouse reset_local_store fixture 在每个测试前后清除内存 store。源码检视测试从磁盘读取文件,不执行应用代码。

Dependency injection testing

后端通过工厂函数构造所有 managed provider(store、chat provider、hybrid store、reranker),从 app.state 读取。测试通过构造 create_app(settings=Settings(...)) 使用 fake provider 覆盖这些工厂,或使用 monkeypatch 替换模块级函数。reset 保护的 store 之外不修改全局单例。

OpenAPI 规范

API 数据形状的唯一真相来源

生成的 OpenAPI 3.1.0 规范定义 71 个 schema，覆盖所有 API 端点；check:openapi 门禁确保 YAML 与 FastAPI 保持同步。

packages/shared workspace 包已作为未使用的幽灵代码移除(整个仓库中零导入)。所有前端类型现在直接定义在 apps/web/app/lib/api.ts 中。OpenAPI 规范是前端和后端共同镜像的唯一真相来源。

api.ts · 前端类型,逐类型详解

该文件定义了 TypeScript 接口和类型,镜像 OpenAPI 规范。源码中所有注释为英文,类型名和字段名为英文。以下逐个说明每个类型及其用途和关键字段。

1. TaskType (type)

联合类型:"answer" | "quiz"。定义请求代表的任务类型。Task 只决定要做什么,不决定怎么做。Router 检查请求以确定用户是在提问还是生成 quiz。

2. ToolName (type)

8 个工具名的联合类型:query_local_docs、search_web、read_url、crawl_url_optional、rerank_evidence、generate_answer、generate_quiz、save_quiz。后端通过 ExecutionPlan 控制给定请求允许使用哪些工具,强制执行安全边界。

3. ExecutionPlan (interface)

定义一次请求解析后的执行计划。字段:task_type、allowed_tools(ToolName[])、requires_local_docs、requires_web、context_strategy(6 值联合:chat、full_context、hybrid_retrieval、web、hybrid_retrieval_web、quiz)、output_schema(ChatAnswer、GroundedAnswer 或 QuizSet)。

4. SourceSummary (interface)

定义回答顶部的来源计数摘要。字段:local_chunks(number)、web_pages(number)。出现在 GroundedAnswer 和 QuizSet 中。

5. Citation (interface)

定义本地或网络证据引用。字段:id、source_type("local_doc" | "web_page")、document_id?、chunk_id?、page_no?、slide_no?、url?、quote(必填 string)、claim_id?。每个 grounded answer 必须通过此结构引用其来源。

6. GroundedAnswer (interface)

定义可溯源、有证据支撑的回答的结构化输出。字段:sources(SourceSummary)、answer(string)、citations(Citation[])、trace_id(string)、validation_status("passed" | "failed" | "retrying")。AskResponse 继承此 interface。

7. AskResponse (interface, extends GroundedAnswer)

定义 Ask API 响应。新增字段:run_id、conversation_id、rerank_degraded、retrieval_degraded、summary_degraded(均为 boolean)、fallback_reason?。三个 degraded flag 让前端能向用户展示降级通知。

8. QuizQuestion (interface)

定义单个 quiz 题目。字段:id、type("single_choice" | "fill_blank" | "subjective")、question、options?(string[] | null)、answer、explanation、difficulty("easy" | "medium" | "hard")、source_citations(Citation[])。每个题目必须可追溯到来源证据。

9. QuizSet (interface)

定义 quiz 的结构化输出。字段:id、sources(SourceSummary)、questions(QuizQuestion[])。sources 字段镜像 GroundedAnswer,使前端能渲染一致的来源面板。

10. QuizResourceScope (type)

联合类型:"all_ready_documents" | "topic"。定义 quiz 生成的资料选择模式。"all_ready_documents" 使用项目中所有 ready 文档;"topic" 按 topic query 过滤。

11. QuizRequest (interface)

定义 Quiz API 请求。字段:project_id(必填)、prompt?、topic_query?、resource_scope?(QuizResourceScope)、single_choice_count?、fill_blank_count?、subjective_count?。后端为所有可选字段提供合理默认值。

12. QuizCoverage (interface)

定义实际进入生成上下文的资料覆盖情况。字段:documents_available、documents_covered、chunks_selected、truncated(boolean)。让前端显示 quiz 是否覆盖了所有文档或被 token budget 截断。

13. QuizResponse (interface)

定义 Quiz API 响应。字段:quiz_set(QuizSet)、run_id、trace_id、validation_status、coverage(QuizCoverage)。将 quiz payload 与运行时元数据和覆盖诊断结合。

14. QuizHistoryResponse (interface)

定义 quiz 历史响应。字段:project_id、quiz_sets(QuizSet[])。由 quiz 历史端点返回,列出项目之前生成的 quiz 集合。

15. ProjectRecord (interface)

定义项目记录。字段:id、user_id、name、kind("personal" | "workspace")、status("active" | "deleting" | "deleted" | "expired" | string)、expires_at?、created_at、updated_at、deleted_at?。status 联合类型包含 string 逃逸舱以支持前向兼容。

16. DocumentStatus (type)

8 个状态的联合类型:uploaded、parsing、parsed、indexing、ready、failed、expired、deleted。定义文档生命周期状态机。只有 "ready" 文档可作为 quiz 或 answer 的证据。

17. DocumentRecord (interface)

定义所有者范围内的文档标识、规范文件类型与 MIME、大小、生命周期状态、过期时间和时间戳。

18. UploadUrlRequest (interface)

接受 42 种有解析器支持的文件类型。API 创建上传预留前，会同时校验项目/对话范围、文件扩展名、MIME 和 25 MiB 上限。

19. UploadCompleteRequest (interface)

定义上传完成请求，可选字段包括 checksum_sha256，以及最大 1 MiB、只用于本地内存回退的 extracted_text。生产摄入仍会验证并解析私有对象存储中的原文件。

20. UploadUrlResponse (interface)

定义上传地址响应。字段:document_id、upload_url、r2_object_key、expires_in_seconds。前端将文件上传到 upload_url,然后使用 document_id 调用 complete 端点。

21. JobRecord (interface)

定义 job 状态记录。字段:id、user_id、project_id?、document_id?、type(string)、status("pending" | "running" | "succeeded" | "failed" | "cancelled")、progress(number 0-100)、error_message?、created_at、updated_at。

22. DeveloperTrace (interface)

定义用于调试和可观测性的 developer trace 记录。字段:trace_id、user_id、project_id、run_id、execution_plan(ExecutionPlan)、router_reason、retrieved_chunks(Record[])、tool_calls(Record[])、validation_result(Record)、created_at。仅管理员可访问。

23. ErrorResponse (interface)

定义统一错误响应。单个 error 对象包含三个字段:code(机器可读错误码)、message(人类可读消息)、request_id(关联 ID)。每个 API 错误都遵循此结构,实现一致的前端错误处理。

三层契约镜像架构

TypeScript 到 Pydantic 到 SQL

同一数据形状在三层中表达,每层在不同边界强制执行。

Layer 1 · OpenAPI(权威层)infra/openapi/openapi.yaml 包含 71 个生成 schema；check:openapi 门禁验证其与 FastAPI 一致。
Layer 2 · Pydantic(请求边界)apps/api/src/researchmate_api/schemas/ -- 镜像每个 TypeScript interface 的 Python 模型。FastAPI 使用这些模型进行自动请求验证、OpenAPI 生成和响应序列化。字段名完全匹配。
Layer 3 · SQL(持久化边界)infra/supabase/migrations/ -- 带 RLS policy 的 PostgreSQL 表定义。列类型和约束镜像 Pydantic 模型。test_database_migration_contract.py 验证 migration 保留 schema 和 RLS 合约。
为什么要三层? OpenAPI 规范通过本地类型定义给前端编译时安全。Pydantic 给后端运行时验证和自动 OpenAPI 文档。SQL 给数据库结构完整性和 row-level security。对 OpenAPI 规范的修改必须传播到所有三层,契约源码检视测试验证这种一致性。

测试如何强制执行镜像

测试配置详解

3 个 Python 基础设施文件 + 1 个 INI 配置文件

测试基础设施由 conftest.py、api_workflow_fixtures.py、api_workflow_support.py(3 个 Python 文件)和 pytest.ini(1 个 INI 配置文件)组成。它们共同提供导入路径、HTTP client fixture 和确定性测试隔离。

pytest.ini

一个极简的两行配置,禁用 pytest cache provider 并设置本地 base temp 目录。确保测试运行是确定性的,不在仓库外留下产物。

[pytest]
addopts = -p no:cacheprovider --basetemp=.pytest-temp
-p no:cacheprovider 阻止 pytest 写入 .pytest_cache/,避免跨 CI 运行的非确定性行为。--basetemp=.pytest-temp 将所有临时文件重定向到仓库本地目录,已被 gitignore。

conftest.py

将两个源码目录插入 sys.path,使测试模块无需安装即可从 API 和 worker 包导入。这是每个测试隐式依赖的唯一文件。

ROOT = Path(__file__).resolve().parents[1]
API_SRC = ROOT / "apps/api/src"
WORKER_SRC = ROOT / "workers/ai-worker/src"
sys.path.insert(0, str(API_SRC))
sys.path.insert(0, str(WORKER_SRC))

api_workflow_fixtures.py

为 HTTP 集成测试提供两个 pytest fixture。reset_local_store fixture 是 autouse 的,意味着在导入它的每个测试前后运行,清除内存 store。client fixture 使用 fake LLM provider 构建 FastAPI TestClient。

@pytest.fixture(autouse=True)
def reset_local_store() -> Generator[None]:
    store.reset()
    yield
    store.reset()

@pytest.fixture()
def client() -> TestClient:
    return TestClient(create_app(settings=Settings(
        app_env="test", llm_provider="fake"
    )))

Hermetic 测试原则

零外部依赖

整个测试套件是 hermetic 的。没有任何测试需要运行中的 PostgreSQL、Qdrant、Redis、LLM API 或外部 HTTP endpoint。这使得套件快速、确定且可在任何 CI 环境中安全运行。

Fake LLM provider

每个 HTTP 集成测试使用 Settings(app_env="test", llm_provider="fake") 构造 FastAPI app。fake provider 返回确定性、预编排的响应,无任何网络调用。这意味着 Ask 和 Quiz 工作流可以在没有 LLM API key 的情况下端到端测试。

内存 store

后端 store 单例在 app_env="test" 时是内存实现。autouse reset_local_store fixture 在每个测试前后调用 store.reset(),确保测试函数间完全隔离。

TestClient 而非 HTTP server

FastAPI TestClient 在进程内包装 ASGI 应用。不打开 socket,不绑定端口。这消除了网络不稳定性,使测试比真实 HTTP 集成快几个数量级。

源码检视不执行

6 个契约源码检视测试使用 pathlib.Path.read_text() 从磁盘读取文件,用 regex 或字符串匹配解析。它们验证结构合约(文件存在、内容模式、schema 正确性)而不导入或执行任何应用代码。

Unit double

单元测试使用轻量级 double 替代真实基础设施:SimpleNamespace 用于 mock 对象、RecordingConnection 用于在无数据库情况下捕获 SQL 语句、EmptyResult 用于模拟查询响应、collections.deque 用于确定性工作流状态转换。

无真实 PDF 解析模型

test_worker_parsing_unit.py 使用轻量级 pypdf backend 和 703 字节的真实 PDF fixture。Docling 视觉 pipeline(需要 torch)在测试中从不加载。parser 验证文本提取、provenance 序列化和 OOXML 解析,无需重型 ML 依赖。

必须存在的安全依赖

HTTP 限流器仍可作为本地可选适配器，但 MIME 验证属于上传安全边界。对象存储测试必须具备 python-magic/libmagic；检测不可用时直接失败，不再跳过测试或接受无法验证的内容。

Mock 策略

分层隔离模式

测试套件使用经过深思熟虑的分层 mock 策略。每层隔离不同边界,技术选择取决于需要验证什么。

monkeypatch(Python)

pytest 内置 monkeypatch fixture 用于在运行时替换模块级函数和属性。例如 test_mcp_boundary.py monkeypatch build_mcp_server 以抛出 ModuleNotFoundError,模拟缺失的 MCP SDK。test_worker_runtime_bootstrap_unit.py monkeypatch dispatcher 和 heartbeat 函数以避免启动真实进程。

SimpleNamespace

Python types.SimpleNamespace 创建具有任意属性的轻量级 mock 对象。在单元测试中广泛使用,用于模拟 provider 响应、LLM completion 和工作流状态,无需定义完整的 mock 类。例如 test_llm_provider.py 使用 SimpleNamespace 模拟 OpenAI-compatible client 响应对象。

RecordingConnection / EmptyResult

test_evidence_postgres_unit.py 和 test_postgres_repository_contract.py 定义了 RecordingConnection(捕获每条 SQL 语句和参数)和 EmptyResult(从查询返回 None)。这些 double 让测试在不连接 PostgreSQL 的情况下验证 repository 发出正确的 SQL 和参数。

通过 Settings 的 fake provider

不 mock 单个 LLM 调用,而是使用 llm_provider="fake" 构造整个 FastAPI app。这在依赖注入边界将真实 NVIDIA chat provider 替换为确定性 fake,执行完整的请求流程,包括路由、验证和响应序列化。

vi.fn() 和 vi.hoisted()(TypeScript)

前端 Vitest 测试使用 vi.fn() 创建 mock 函数,vi.hoisted() 创建必须在模块导入前可用的 mock。例如 auth-gate.test.tsx hoist Supabase session mock,api.test.ts mock fetch 以在无网络调用的情况下验证 API client 行为。

renderToStaticMarkup

presentation.test.tsx 使用 React renderToStaticMarkup 将组件渲染为 HTML 字符串进行断言。这避免了完整 DOM 测试库的复杂性,同时仍验证组件渲染了预期的可见 chat 和 quiz 状态。

覆盖率配置

Python coverage + 前端 v8 coverage

覆盖率在两个层面配置:Python 测试套件使用 coverage 包(锁定 7.10+),前端使用 Vitest 内置 v8 coverage provider 并强制阈值。

Python 依赖(pyproject.toml)

根 pyproject.toml 将 coverage>=7.10.0,<8 和 pytest>=9.0.0,<10 锁定为 dev 依赖。coverage 包在测试执行期间检测 Python 源码文件,生成行和分支覆盖率报告。CI 门禁 npm run test:python 强制执行 coverage report --fail-under=69,因此 Python 套件必须对 apps/api/src/researchmate_api 和 workers/ai-worker/src/researchmate_worker 保持至少 69% 的合并行与分支覆盖率,push 才可部署。

pytest.ini

禁用 cache provider(-p no:cacheprovider)以防止过期缓存影响覆盖率结果。设置 --basetemp=.pytest-temp 将所有临时测试产物保留在仓库内。

Vitest v8 coverage

apps/web/vitest.config.ts 配置 v8 coverage provider,include: ["app/lib/**/*.ts", "app/components/**/*.{ts,tsx}"],exclude: ["app/**/*.test.{ts,tsx}"]。Reporter:text 和 json-summary。阈值:40% 行和 40% 语句。

覆盖率范围理由

Vitest coverage 包含编排代码(app/lib)和展示代码(app/components),但排除测试文件本身。40% 阈值是有意保守的:确保核心逻辑被测试,而不迫使对每个工具函数写脆弱的测试。coverage-v8 包提供原生 V8 检测。

Playwright trace 保留

apps/web/playwright.config.ts 设置 trace: "retain-on-failure"、screenshot: "only-on-failure" 和 video: "retain-on-failure"。仅在测试失败时生成调试产物,保持 CI 产物存储清洁。

CI 覆盖率强制

test_release_pipeline.py 包含 test_ci_runs_the_full_test_build_contract_and_security_gate,读取 CI 工作流 YAML 并验证完整测试套件(包括覆盖率)在任何部署前作为强制门运行。这使得覆盖率强制成为合约,而非约定。

测试依赖关系图

测试如何连接到源码和基础设施

依赖关系图显示哪些测试文件从哪些源码包导入,以及它们依赖哪些基础设施文件。

conftest.py 到 sys.path每个测试文件依赖 conftest.py,它将 apps/api/src 和 workers/ai-worker/src 插入 sys.path。没有这个,任何测试模块都无法从 researchmate_api 或 researchmate_worker 导入。
HTTP 测试到 api_workflow_support + fixturestest_api_workflow.py 和 test_api_policy_workflow.py 从 api_workflow_support.py 导入 HEADERS、USER_A/B_HEADERS 和 create_ready_document。它们通过 pytest_plugins 激活 api_workflow_fixtures.py 以获取 autouse reset_local_store 和 client fixture。
HTTP 测试到 researchmate_api.main + configtest_evidence_api.py、test_mcp_boundary.py 和 test_runtime_foundation.py 通过直接从 researchmate_api 导入 create_app 和 Settings 构建自己的 TestClient,获得对应用配置的细粒度控制。
单元测试到 researchmate_api.services + schemas单元测试导入特定 service(store、object_storage、persistence.postgres)和 schema(common、document)以验证单个模块。它们使用 SimpleNamespace 和 RecordingConnection double 替代真实基础设施。
Worker 测试到 researchmate_worker 模块Worker 单元测试从 researchmate_worker.outbox、celery_app、ingestion、config、parsing 和 evaluation 模块导入。它们使用 monkeypatch 避免启动 Celery worker 或连接 Redis。
契约测试到 pathlib.Path6 个契约源码检视测试仅依赖文件系统。它们使用 Path.read_text() 读取源码文件、SQL migration、YAML 配置和 Dockerfile,通过字符串匹配和 regex 验证结构合约。
前端测试到 app/libVitest 测试从 ../lib/api(直接在本地定义所有类型)导入类型,测试 app/components 中的组件。Playwright 测试依赖 Next.js dev server 和 demo 模式运行时。
