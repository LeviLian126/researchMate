5 flows · function-centered · interview-grade

Flow analysis · Five interview-grade core flows

A user types a question, uploads a paper, or waits for an AI report. This page walks the five paths those actions take through ResearchMate, from the HTTP request to the database commit. Each section opens with what the user does and what they get back, then steps through the internal nodes in order, names the files and functions that matter, and closes with a short follow-up tree. Markers separate verified facts, inferences, expansion, and improvement ideas.

Flow 1: Ask · 11-node graph Flow 2: Evidence review · 6-node worker graph Flow 3: Hybrid RAG · 5 routes Flow 4: Streaming · SSE + token layers Flow 5: Document ingestion · upload to job

Flow 1 · function-centered · end-to-end

Grounded Ask · 11-node ResearchGraph

A user types a research question and sends POST /ask. The API first checks an idempotency key (so a retry returns the same answer instead of running twice), then hands the question to an 11-node graph that scopes what evidence is available, picks a candidate wiki set, plans queries, runs local + web retrieval, dedups and reranks, judges whether the evidence is enough, optionally expands context or refines the query, and finally hands off to generation. Each external failure is recorded as degradation, never hidden as success.

Idempotency check GroundedQueryService prepare_context select_wiki plan_evidence search_sources merge_evidence rerank_evidence judge_evidence generate Postgres persist
1

IdempotencyCoordinator.begin()

Four states

Before doing any real work, routers/ask.py calls coordinator.begin() with the client's idempotency key. Four outcomes: execute (new key, or an abandoned one — proceed), replay (same key already succeeded and body hashes match — return the cached answer), mismatch (same key but different request body → 409 IDEMPOTENCY_KEY_REUSED), in_progress (same key+body already running → 409 IDEMPOTENCY_REQUEST_IN_PROGRESS). [Project fact] The hash is SHA-256 of model_dump(mode="json") with sort_keys=True, so identical logical payloads hash the same regardless of dict order.

DB: api_idempotency
2

GroundedQueryService.execute()

Orchestration

services/grounded_query.py starts a monotonic timer, then calls conversations.prepare(user, payload) to load the project, its documents, their chunks, and a bounded slice of conversation history. [Project fact] If settings.langgraph_research_enabled is false, it falls back to a legacy inline retrieval path. [Reasonable inference] The flag keeps the legacy path runnable so the team can compare graph-orchestrated vs inline retrieval rather than switching cold.

DB: projects/docs/chunksExternal: NVIDIA summary
3

prepare_context

Pick starting route

The first decision: how to start. graph/graph.py prepare_context() counts estimated tokens across non-wiki chunks, then after_prepare() chooses: chat if no corpus tokens and web is off (answer from history only), select_wiki if there are wiki chunks and web is off, otherwise plan (the full retrieval path). [Project fact] Wiki chunks are never judged as evidence — they are synthetic index entries, not real sources.

4

select_wiki

Lexical shortlist

When the question likely has a wiki answer, bm25_candidates() scores wiki chunks via BM25 (term overlap) and returns a shortlist capped by settings.wiki_gate_candidate_limit. [Project fact] The cap exists so a fat wiki cannot hand hundreds of pages to the LLM judge and blow the token budget before retrieval even starts.

5

plan_evidence

Adaptive plan

A retrieval plan says what to search for and how. AdaptiveQueryPlanner.plan() takes the prior plan_retrieval() result, optionally carries forward missing_facets from a previous judge round, and returns: the queries to run, dense vs lexical weights, a web-allowed flag, and a constrained document scope. [Project fact] When a previous round refined the queries, those refined queries replace the plan's queries wholesale via model_copy(update=...), not a merge.

6

search_sources

Local + optional web

_search_local() calls LocalEvidenceRetriever.retrieve() with the plan's safe weights (see Flow 3). _search_web() runs only if plan.use_web is true; Tavily is queried once with the first planned query, limit 5. [Project fact] Web failure is caught and recorded as web_degraded=True; local retrieval keeps running rather than aborting the whole request.

External: Qdrant + NVIDIA + Tavily
7

merge_evidence

Dedup before rerank

All local then web candidates are concatenated, then deduped by chunk id, keeping the first occurrence. A single rerank boundary exists so the same chunk cannot compete with itself across sources.

8

rerank_evidence

Rerank fallback chain

First, limit_rerank_candidates() caps the pool at settings.retrieval_round_candidate_limit so rerank cost stays bounded. Then candidates are split by chunk.has_vector: RAG-backed chunks go through RerankCoordinator.execute(), while lightweight (no-vector) chunks bypass rerank. [Project fact] Rerank provider is chosen at runtime via get_runtime_rerank_config(); the chain is QdrantNativeReranker → NvidiaReranker → DeterministicReranker, so a provider outage degrades to a deterministic scorer rather than failing the request. Finally pack_chunks() enforces retrieval_evidence_token_budget.

External: Qdrant or NVIDIA
9a

judge_evidence

Sufficiency gate

After rerank, an LLM judge decides whether the evidence is enough. EvidenceSufficiencyService.assess() returns sufficiency, confidence, missing facets, and a degraded flag. Then after_evidence() routes to one of: generate if sufficient; lightweight_fallback if lightweight evidence exists and the fallback hasn't been used; generate if the judge is degraded or no new evidence arrived; generate if missing_facets is empty; generate if retrieval_round ≥ max_retrieval_rounds; otherwise refine. [Project fact]

External: NVIDIA chat
9b

expand_lightweight_context

Last-resort fallback

Before giving up, the graph can pack raw non-wiki non-vector chunks under full_context_token_limit and set lightweight_fallback_used=True, then loop back to judge_evidence. The loop is bounded so it cannot spin forever. [Project fact]

9c

refine_query

Round 2 plan

When the judge signals missing facets, planner.refine() takes those facets and the previous plan, returns a refined plan, and loops back to plan_evidence. Refinement is bounded by max_retrieval_rounds. [Project fact]

10

generate

Hand off

Inside the graph, generate() is a no-op. The actual generation stays in GroundedQueryService via generate_answer() → answering.py build_llm_grounded_answer(). [Project fact] The system prompt marks every evidence text as untrusted data, and the LLM must return JSON {answer, claims:[{text, evidence_ids}]}; on schema failure there is exactly one repair attempt.

External: NVIDIA chat
11

Quota, commit, persist

429 / replay

Quota is checked only after generation succeeds: repository.increment_usage(user, "ask", limit=200). Provider failures and 429s do not consume the daily ask budget — the system charges for delivered value, not transient infrastructure failures. Over the limit raises 429 RATE_LIMITED and coordinator.abandon() releases the idempotency record so the user can retry. record_run() then writes ask_runs, tool_calls, citations, and conversation_messages in one transaction with RLS parameters set. Finally coordinator.complete(response) flips api_idempotency to succeeded. [Project fact]

DB: api_usage + multi-table

Lightweight → Fallback end-to-end chain: from ingestion to last resort

Not every document justifies the cost of embed + Qdrant round-trip. Short documents (≤ 4000 tokens) skip the vector store at ingestion and are marked has_vector=False. At retrieval time these chunks go through BM25 instead of vector search; at rerank they are split out and packed separately; if the judge deems evidence insufficient, the graph triggers a one-shot expand_lightweight_context fallback that packs all raw short-document chunks into context and re-judges. The chain has six stages, each with an explicit trigger condition and budget cap.

[Project fact] One-shot trigger

The routing check inspects not state.get("lightweight_fallback_used"). The fallback node sets lightweight_fallback_used=True immediately, so the fallback fires at most once. On the second pass through the judge, even if evidence is still insufficient, expand is skipped and the graph goes to generate or refine.

[Project fact] has_lightweight_evidence set per plan round

Each plan round, the system scans all raw chunks (excluding wiki chunks) in the owner+project scope and sets has_lightweight_evidence=True if any raw chunk has no vector. This flag is recomputed each plan round.

[Project fact] Budget half-protection

Lightweight candidates are capped to retrieval_evidence_token_budget // 2 before rerank. The rerank budget is spent only on RAG candidates. This prevents lightweight chunks from crowding out reranked RAG evidence.

[Reasonable inference] Why fallback uses full_context_token_limit not retrieval_evidence_token_budget

The fallback is a last resort: it no longer separates RAG from lightweight, but packs all available chunks into the larger full_context_token_limit. The intent is to give the LLM as much raw context as possible and let generation decide relevance. The trade-off is higher token cost, but it only fires once when evidence is insufficient.

Follow-up tree — Lightweight chain
Why aren't lightweight chunks sent to the reranker?
├  The reranker uses embeddings for late-interaction scoring. Lightweight chunks have no vector (has_vector=False), so they cannot participate in rerank computation.
└  Alternative: generate vectors for lightweight chunks too. But that loses the cost advantage of the lightweight branch — short documents already fit entirely in the LLM context and don't need rerank ordering.

What happens if all documents are lightweight (no vectors in the project)?
├  [Project fact] The retrieval layer does not mark all-lightweight corpora as degraded (degraded=False, reason="all_lightweight_corpus"); it runs BM25 only. In the graph has_lightweight_evidence=True, so the judge insufficiency triggers the expand fallback.
└  Small projects pay zero Qdrant cost but still produce cited answers.

Why does the fallback fire only once?
├  [Interview extension] One-shot is a loop-boundedness guarantee. If every judge insufficiency triggered expand, the graph would loop expand → judge → expand forever. lightweight_fallback_used is a monotonic boolean flag that ensures this branch executes at most once.
└  Similar pattern: refine_query is bounded by max_retrieval_rounds, also a monotonically increasing counter.
Why a request-scoped compiled graph — not a static graph instance

Two asks landing at the same instant cannot share node state. _GraphRuntime compiles the 11-node graph inside run() for each request so the node closures capture request-local data (user, project, chunks, history) and concurrent requests stay isolated. The graph is bounded by max_retrieval_rounds, and every external failure (vector store, web, rerank) is converted to degradation metadata rather than a silent success or an abort.

Follow-up tree — Grounded Ask
Why an 11-node graph instead of a single function call?
├  The path needs conditional edges (prepare, judge) and bounded loops (refine → plan_evidence). LangGraph gives routing and a checkpointer for free.
└  Could a hand-rolled loop replace it?
   ├  Yes, but it would re-implement conditional routing and round counting. The graph also opens the door to checkpoint-resume later.

Why is generation a no-op inside the graph?
├  The graph owns bounded retrieval; generation stays at the application boundary so langgraph_research_enabled=false can still produce answers.
└  Trade-off: two execution paths to maintain until the graph flag is permanent.

Web retrieval is bounded to limit=5 and the first planned query only. Why?
├  Latency and token cost. Tavily runs alongside Qdrant in the same request; more queries would double external calls per round.
└  How would you scale this?
   └  [Optimization suggestion] Move web search to an async pre-fetch when the question is classified as web-likely, then merge at the rerank boundary.
[Project fact] Quota counts success only

Quota is incremented after generation succeeds via increment_usage(limit=200). Provider failures and 429s do not consume the daily ask budget.

[Reasonable inference] The legacy inline path is an evaluation control

langgraph_research_enabled=false keeps a function-call retrieval path alive. The most plausible reason is A/B-style comparison against the graph-orchestrated path, not a production fallback.

Flow 2 · function-centered · async + human review

Evidence review · 6-node worker graph

A user submits a research goal and waits for a synthesized report. The API accepts the goal with 202 and writes an evidence_runs row; the Celery worker then runs a 6-node graph: plan the sub-questions, fan out one retrieval-and-extraction call per question, reconcile the batches, pause for a human reviewer, then synthesize the report and commit. The pause is durable — state is persisted by a checkpointer, so the worker can restart mid-review and resume when the human decision arrives.

POST research-runs plan (fan_out) retrieve_and_extract × N reconcile human_review interrupt synthesize validate_and_commit
1

POST /evidence/research-runs

202 + idempotency

routers/evidence.py create_research_run() validates that the caller owns an active project, then calls evidence.create_research_run() with an 8–160 char Idempotency-Key. [Project fact] Returns 202 with the accepted ResearchRunAccepted; no work runs synchronously — the user gets a handle to poll or stream, and the worker picks the run up from the queue.

DB write: evidence_runs
2

plan & fan_out

Map-reduce

A research goal decomposes into several questions. build_evidence_graph() wires the topology plan → (conditional fan_out → retrieve_and_extract) → reconcile → human_review → synthesize → validate_and_commit. [Project fact] fan_out emits one Send("retrieve_and_extract", {question_index, question, ...}) per question. The evidence_batches state field is annotated with operator.add, so when parallel batches come back they are concatenated automatically instead of overwriting each other.

3

retrieve_and_extract × N

Per-question

Domain hook retrieve_and_extract() runs owner-scoped retrieval and claim extraction for one question. [Project fact] Because each Send carries the full run context, every batch is self-contained and batches can run concurrently inside the worker.

External: reuse Flow 3 retriever
4

reconcile

Merge & dedup

Multiple questions often harvest overlapping claims. Domain hook reconcile() merges all batches into a clean set of claims and relations for the review step. [Reasonable inference] Dedup of overlapping claims and conflict resolution between questions happen here, before a human reviewer sees the proposed output.

5

human_review (interrupt)

Human gate

When the proposed claims matter enough, the flow pauses for a human. If review_payload() returns None the review node auto-approves (path for low-risk incremental refreshes). Otherwise interrupt(proposed) raises a LangGraph interrupt that the checkpointer persists. [Project fact] The worker does NOT wrap interrupt in try/except — the comment says "LangGraph must persist and surface it." The human decision comes back as a 202 from POST /runs/{run_id}/decisions.

6

synthesize → validate_and_commit

Final write

synthesize() produces the report; validate_and_commit() is the terminal node. [Project fact] The graph ends with END; the worker marks the run succeeded or failed and emits a workflow-level SSE event so any connected client stream closes cleanly (see Flow 4).

DB write: claims/relations/reports

Claim data model: from chunk to reviewable fact

A claim is an atomic factual assertion extracted by the LLM from source document chunks. Each claim is bound to server-controlled evidence IDs, carries a stance (supports/opposes/neutral) and confidence score, and becomes a report building block after human review. Claims are not user-authored — they are structured facts extracted from bounded evidence, validated for ID range by the server, and persisted for review.

[Project fact] claims table structure

The claims table (defined in the evidence review schema migration) core fields: text (assertion text), stance (supports/opposes/neutral), confidence (0–1), review_status (pending/accepted/edited/rejected/invalidated), source_version (source version). Unique constraint (project_id, normalized_key, source_version) prevents duplicate extraction from the same source.

[Project fact] Server-controlled IDs at extraction

The claim extraction flow assigns each chunk a server evidence_id (1–N); the LLM can only reference these IDs. After extraction the server validates every evidence_id stays within the allowlist — out-of-range IDs raise EvidenceGenerationError. This prevents the LLM from inventing non-existent evidence references.

[Project fact] Claim relation graph

The claim_relations table stores three directed edge types: supports, contradicts, duplicates. Each edge carries its own confidence and rationale_summary. A check constraint forbids self-loops; the reconcile stage additionally rejects duplicate edges.

[Project fact] Owner isolation in SQL

The claim list query uses where c.project_id = :project_id and c.user_id = :user_id plus exists (select 1 from projects p where ...) for triple filtering. The RLS policy claims_owner_select adds a further auth.uid() = user_id layer.

Follow-up tree — Claim model
Why doesn't a claim store the original chunk text?
├  A chunk is raw text (potentially hundreds of words); a claim is an atomic factual assertion extracted from it (one sentence). One chunk can produce multiple claims.
└  Trade-off: the claim-to-chunk mapping lives in the claim_evidence join table (many-to-many), preserving provenance without redundant storage.

Why does review_status have invalidated separately from rejected?
├  [Reasonable inference] rejected is an active human review decision; invalidated is a system mark when the source document changes or its version expires. The two have different trigger paths.
└  The source_version field, together with the invalidated_at timestamp, lets incremental refreshes decide which claims need re-extraction.

Why aren't claim relations merged into the claims table?
├  [Interview extension] Relations are a graph structure (many-to-many). Merging them into claims would produce duplicate rows or JSON arrays. A separate table supports bidirectional queries ("who supports this claim" and "what does this claim support") with independent indexing.
└  Alternative: store relations as a JSONB array. Loses relation-level indexing and constraints (e.g., the self-loop check constraint).
Why interrupt() instead of polling

A human review can take hours or days. The worker cannot hold the run in memory while waiting. interrupt(proposed) raises a LangGraph signal that the checkpointer stores; worker memory is released, and the run resumes only when create_human_decision arrives. The alternative — a polling loop inside the worker — would burn worker slots and DB reads the whole time, and an unclean worker restart would lose state. [Reasonable inference] The trade-off is operational complexity: the run is durable, but you must deploy the checkpointer (Postgres or Redis) and handle resume correctly.

Follow-up tree — Evidence review
Why is the graph built lazily inside build_evidence_graph?
├  from langgraph... import lives inside the function with a try/except ImportError → RuntimeError. API and unit tests do not need the worker runtime loaded.
└  Trade-off: import cost on first build. [Optimization suggestion] Cache the compiled graph per domain if builds become hot.

Why fan_out with Send instead of a loop node?
├  Send() is LangGraph's map-reduce primitive: each question becomes a separate state instance that can run concurrently, then reconcile reduces them.
└  Alternative: one node iterates questions sequentially.
   └  Loses parallelism for independent questions and complicates partial-failure handling.

How does resume work after a worker crash mid-review?
├  The checkpointer persisted the interrupt. On create_human_decision the API re-invokes the graph with the same thread_id and the decision; LangGraph resumes from the interrupt.
└  What if decisions arrive twice?
   └  [Project fact] create_decision requires an Idempotency-Key; a duplicate returns the original accepted record.
[Project fact] Review can auto-approve

If domain.review_payload(state) returns None, the review node skips the human and emits {"decision": "approve"}. This is the path for low-risk incremental refreshes.

[Interview extension] Idempotency on async writes

Every mutating evidence endpoint (/research-runs, /runs/{id}/decisions, /reports/{id}/refresh, /evaluation-runs, /dev/fault-scenarios) requires Idempotency-Key (8–160 chars, ^[A-Za-z0-9._:-]{8,160}$). Same key + same body → replay; same key + different body → 422.

Flow 3 · function-centered · routing system

Hybrid RAG · 5 routes · weighted RRF

A naive RAG runs every query as one fixed blend of vector + keyword search. ResearchMate does not: plan_retrieval() looks at the question shape and corpus size, picks one of five routes, and emits a plan with dense and lexical weights. The retriever (LocalEvidenceRetriever.retrieve()) turns that plan into a Qdrant hybrid query that fuses BM25 keyword matches with dense vector matches via RRF (reciprocal rank fusion). If the vector store fails, a bounded in-app BM25 takes over and the response carries degraded=true rather than failing silently.

1

plan_retrieval()

Choose route

Before touching the vector store, the planner decides how to search. services/query_planning.py normalizes the question, estimates corpus tokens, and emits a RetrievalPlan{route, queries, dense_weight, lexical_weight, reason, degraded}. [Project fact] Constants bound the output: MAX_QUERY_VARIANTS=3, MAX_QUERY_CHARS=600. Regexes classify the question into exact, semantic, or expansion triggers.

2

Qdrant hybrid query

Native RRF

BM25 scores keyword overlap; dense scores semantic similarity via embeddings. Their raw scores live on different scales, so the system fuses them by rank instead: this is RRF. When settings.qdrant_native_hybrid_enabled is on and a hybrid_store exists, hybrid_store.query(plan=plan) builds one RrfQuery per planned variant, with named bm25 and dense prefetches. [Project fact] Dense and lexical weights are divided across variants, so a compound query can broaden recall without any one variant dominating.

External: Qdrant + NVIDIA embed
3

Hydrate candidates

Owner-scoped

The vector store returns only ids and payloads. To get full chunk text the system calls _hydrate_matches(), which takes the payload.chunk_id list and fetches real chunks via repository.get_chunks_by_ids(user, project_id, ids), preserving provider rank and assigning semantic_rank. [Project fact] This call is the security boundary: even if the query builder has a bug, hydrate still enforces owner + project filtering, so one user cannot read another user's chunks.

4

Bounded degradation

Never invent success

When the vector store fails, the flow does not abandon the query or pretend it worked. Three fallback paths each carry a stable reason string and degraded=true: hybrid_store_unconfigured (no store set up → fall back to in-app BM25), legacy_dense_unavailable_application_bm25_used (dense query failed on the legacy path), native_hybrid_unavailable_application_bm25_used (dense query failed on the native path). The downstream judge and the user both see the degradation. [Project fact]

5

Lightweight branch

No-vector chunks

Not every chunk has a vector. Non-wiki chunks without one (has_vector=false) go through _lightweight_candidates(): BM25 is run over each query variant, results are deduped by chunk id keeping the max score, and the pool is capped at rerank_candidate_limit. [Project fact]

Follow-up tree — Hybrid RAG
Why route before retrieval?
├  One static blend cannot answer both "what does API_KEY mean" (exact) and "how does auth work" (semantic). Routing before the Qdrant call also avoids vector latency when full_context is sufficient.
└  Trade-off: a misjudged route is wasted retrieval. Mitigation: full_context runs a BM25 relevance gate so it never returns irrelevant chunks.

Why weighted RRF instead of fused scores?
├  BM25 and dense scores live on different scales; fusing raw scores is brittle. RRF uses ranks, and the planner's weights divide across query variants so no variant dominates.
└  What if one branch returns nothing?
   └  RRF still works; missing ranks contribute zero. The degraded path handles complete vector failure separately.

The planner LLM is optional. When does it run?
├  Only expanded_hybrid triggers one bounded rewrite call returning standalone_query + up to two variants, schema-validated by _ExpansionOutput. Other routes are regex-only — zero LLM latency.
[Project fact] Owner filter is a vector-layer hard constraint

hybrid_store.owner_filter() enforces must conditions on user_id, project_id, source_type, optional document_ids. Even a buggy query builder cannot leak another user's vectors. Dual-layer isolation: Qdrant hard filter + Postgres RLS.

[Optimization suggestion] Benchmark dense vs lexical weights

Source only confirms the weight values (0.30/0.70, 0.70/0.30, 0.50/0.50, 0.55/0.45). Whether they were tuned is not verifiable from source. A small offline eval (recall@K + MRR) per route would justify the asymmetry instead of relying on intuition.

Flow 4 · function-centered · dual-layer

Streaming · SSE workflow events + token generation

ResearchMate streams at two layers serving different needs. The Evidence workflow layer lets a browser watch a long, asynchronous run: it subscribes to GET /evidence/runs/{run_id}/events (Server-Sent Events), the server yields stored events until the run finishes or stays idle too long, and reconnection resumes from the last seen event via Last-Event-ID. The Ask path is separate: the LLM returns a complete answer at once today; a future streaming chat provider would surface reasoning tokens without touching the SSE contract.

1

GET /runs/{run_id}/events

StreamingResponse

When a user opens a run page, the browser opens an SSE connection. routers/evidence.py stream_run_events() returns a StreamingResponse with media_type="text/event-stream" and headers Cache-Control: no-cache and X-Accel-Buffering: no. [Project fact] The latter disables nginx buffering so each event flushes to the client as soon as it is written, not held until a buffer fills.

2

Cursor resolution

Last-Event-ID

If a connection dropped and the browser reconnects, it sends the last Last-Event-ID header. The handler does after_sequence = max(after_sequence, int(last_event_id)); an invalid integer returns 422 INVALID_EVENT_CURSOR. [Project fact] Each event carries an SSE id: field, which lets the browser reconnect and resume from the last seen event instead of replaying everything.

3

generate()

Poll + heartbeat

The async generator loops while the client is connected and idle cycles stay below 15. On each iteration evidence.list_run_events(cursor) returns any stored events newer than the cursor; each is emitted as id: <seq>\nevent: <type>\ndata: <json>\n\n. When there are no new events, the generator emits : heartbeat\n\n (an SSE comment the browser does not surface as an event) and sleeps 1s. [Project fact]

4

Terminal close

Workflow done

When an event has status in {succeeded, failed} AND node_key == "workflow", the generator returns and the stream closes. [Project fact] This prevents dangling idle streams left open after a run already finished.

5

Token generation layer

Ask path

The Ask path is a different shape. services/query_generation.py generate_answer() calls answering.py, which calls ChatProvider. [Project fact] The current chat provider returns a complete LLMResult; the generation tool call records latency_ms. [Reasonable inference] Because the Ask response contract is JSON-once (not chunked), swapping in a streaming chat provider later would surface reasoning tokens to the client without changing the response shape — the citations are still built after generation completes.

External: NVIDIA chat
Why SSE over WebSocket for evidence events

Evidence events are server-to-client only, persisted in the DB, and resume-safe. SSE gives automatic reconnection + Last-Event-ID for free, requires no server-side connection state, and works through proxies that mangle WebSockets. [Reasonable inference] The 15-idle-cycle cap bounds resource use on long-tail runs; reconnects resume from the cursor so the cap does not lose events.

Follow-up tree — Streaming
Why poll every 1s instead of push from the worker?
├  The API process owns the SSE connection; the worker runs in a separate process. The polling read against evidence.list_run_events is a simple, RLS-safe boundary.
└  Trade-off: up to 1s latency between event creation and delivery.
   └  [Optimization suggestion] Add a Postgres LISTEN/NOTIFY → asyncio.Event wake so the loop only sleeps when truly idle.

Why 15 idle cycles?
├  15 cycles × 1s = 15s grace before the stream closes. The client can reconnect with the last Last-Event-ID.
└  Why not infinite?
   └  Long idle streams hold proxy connections and connection slots. 15s is a tunable compromise.

Could the Ask path stream tokens too?
├  It requires a streaming chat provider and changing the AskResponse contract to chunked. Today generation is single-shot.
└  [Optimization suggestion] Add an opt-in ?stream=true Ask route that emits reasoning tokens via SSE while still building citations at the end.
[Project fact] Heartbeats keep the connection alive

During a long retrieval step, no real events arrive for several seconds. An idle cycle emits : heartbeat\n\n (SSE comment) so intermediaries (proxies, load balancers) do not close the connection. The comment prefix means the browser does not surface it as an event.

[Interview extension] Idempotent resumption

The SSE endpoint is read-only; no writes. Combined with Last-Event-ID, a reconnecting client cannot duplicate side effects. Mutating endpoints (/decisions) carry their own idempotency keys, the standard pattern for async-write systems.

Flow 5 · function-centered · upload to job

Document ingestion · reserve → stream → verify → job

A user uploads a PDF. The frontend makes three HTTP calls: first reserve the document metadata (POST /documents, returns an id); then stream the bytes through the API as a proxy (PUT /documents/{id}/content, the API validates type and size while spooling to a temp file, then uploads to object storage); then signal completion (POST /documents/{id}/complete), which verifies the stored object and enqueues a Celery ingestion job, returning 202. The user can navigate away — parsing, chunking, embedding, and wiki compilation all run in the background.

Proxy upload

The client streams the file body to the API, which spools it into a SpooledTemporaryFile(max_size=1024*1024) (1 MB in memory, then rolls to disk). The API validates Content-Type matches the reserved mime_type (else 415 MIME_MISMATCH) and that the bytes received match the reserved size_bytes (else 409 SIZE_MISMATCH). Uploads larger than MAX_DOCUMENT_UPLOAD_BYTES or the reserved document.size_bytes are rejected with 413. [Project fact]

object_storage.upload_stream()

Thread offload

The synchronous S3-compatible client is wrapped in await to_thread.run_sync(lambda: object_storage.upload_stream(object_key, source, content_type=mime_type)) so the event loop is not blocked during the upload. The object key shape is users/{uid}/projects/{pid}/documents/{did}/{filename}, so objects are namespaced per user and project. Failures map to 503 OBJECT_STORAGE_UNAVAILABLE with the provider code + status when present. [Project fact]

After the bytes are uploaded, the client calls complete. complete_upload() accepts an optional checksum_sha256 and extracted_text. It verifies the uploaded object exists and matches: UploadVerificationError → 409; ObjectStorageRequestError → 503; ObjectStorageConfigurationError → 503. Worker

The background job parses the uploaded object, chunks the text, embeds via NVIDIA, upserts chunks and vectors into Qdrant + Postgres, and optionally compiles a wiki page (see Flow 3 dual-path). [Reasonable inference] The job is idempotent via the same job_id; a failed job can be retried by reissuing complete without uploading again.

Why stream through the API instead of direct client → storage

Sending bytes directly to S3 from the browser saves API bandwidth, but gives the API no chance to enforce type and size before storage. The proxy path validates Content-Type, Content-Length, and reserved size before a single byte hits storage. The spooled temp file keeps memory bounded — small uploads stay in memory, large ones roll to disk. [Reasonable inference] The signed URL path exists for clients where CORS or a corporate proxy makes direct upload impractical, but the proxy is the default.

Follow-up tree — Document ingestion
Why a three-step flow instead of one POST?
├  Step 1 reserves metadata so step 2 can validate type and size before storage. Step 3 signals completion and enqueues the job.
└  Could one endpoint do all three?
   └  Yes, but you would hold the HTTP connection through parsing + embedding. The async job model keeps uploads fast and ingestion bounded.

Why SpooledTemporaryFile(max_size=1MB)?
├  Small uploads stay in memory (fast); large ones roll to disk (bounded memory). The 1 MB threshold is a memory/IO trade-off.
└  [Optimization suggestion] Benchmark this threshold against the measured upload size distribution.

How is the upload made idempotent?
├  POST /documents/{id}/complete is the mutating boundary. [Project fact] It returns a job record keyed by job_id; the job itself runs on a Celery queue that supports retry.
└  What if the same body is completed twice?
   └  The document record is single; the second complete returns the existing job status.
[Project fact] Bounded upload size is enforced at two levels

During streaming the request byte count is tracked. If it exceeds MAX_DOCUMENT_UPLOAD_BYTES OR the reserved document.size_bytes, the API returns 413 UPLOAD_TOO_LARGE and stops the stream. A final size mismatch (even under the cap) returns 409 SIZE_MISMATCH.

[Interview extension] MIME and size preconditions

The reserved mime_type and size_bytes act as an early contract: the client commits to the upload shape at reserve time, and the proxy enforces it byte-for-byte. This prevents a client from uploading arbitrary bytes after reservation.
