Render / Vercel / Supabase / Qdrant . 4 个主题，面试导向

基础设施 . 面试深挖

ResearchMate 的四个基础设施决策各回答一个具体问题。你 push 代码后 API 和 worker 跑在哪？一个 Render Free 档位的 web service，因为 Free 档位只给一个常驻槽。当企业代理把 *.onrender.com 的响应打掉时浏览器怎么访问 API？Vercel 把 /api/v1/* 做 same-origin rewrite，让浏览器看到的请求里根本不出现 onrender 主机。事实来源在哪？Supabase Postgres，被 RLS、增量迁移和 SHA-256 摘要的迁移 runner 关住。embedding 放哪？一个 Qdrant v3 collection，同时承载 native BM25 与 4096 维 dense 向量，每次查询都按 owner 过滤。

1 个 Render Free web service Vercel rewrite 绕过代理 21 条 SQL 迁移 + advisory lock Qdrant v3 native hybrid

技术栈中心 . Render 部署拓扑

一个 Free 档位 service 用同一镜像跑 API + worker

[项目事实] render.yaml 只声明一个 type: web service：plan: free，region oregon，runtime docker，命令 python -m researchmate_worker.render_combined。

先还原场景：你把代码 push 到 main，GitHub Actions 跑 CI；如果全绿，Render 注意到这次推送，按 workers/ai-worker/Dockerfile 重新构建镜像。生成的容器被要求执行 render_combined —— 这是一个 Python 进程，同时启动 ASGI API server 和 Celery worker 循环。不存在为 worker 单独开 Render 的情况。

合并的原因来自 Free 档位的一条规则：Free 档只提供「一个常驻 web service」。要给 worker 单开 Render background worker service，必须升级到付费档。所以项目把两套职责塞进它能免费拿到的那个唯一槽里。代价是进程内争用 —— 用户请求高峰打 API 时，同进程还要保持 Celery worker 响应 —— 还有 Free 档在空闲后会冷启动或睡眠。[合理推断] 对 MVP 规模的项目，零月费收益大于干净拆分的收益，所以接受这种代价。

关键机制
  • autoDeployTrigger: checksPass — Render 在 GitHub Actions researchmate-ci 跑绿之后才会拾取一次构建。CI 红，不部署。[项目事实]
  • buildFilter paths — 只有改动触及 apps/api/**、workers/ai-worker/**、infra/supabase/migrations/**、迁移或 Qdrant provisioner 脚本、pyproject.toml 或 uv.lock 时才触发重建。纯 README 改动跳过部署。[项目事实]
  • healthCheckPath: /api/v1/healthz — Render 探活一条便宜的 liveness 路由判断服务存活；/api/v1/readyz 是另一条路由，专门检查 Postgres、Redis、Qdrant 的就绪。[合理推断]
  • envVarGroup: researchmate-backend — 非敏感值（模型名、base URL、RUN_SCHEMA_MIGRATIONS=1 之类的开关）直接写在 render.yaml 里；secret（DATABASE_URL、REDIS_URL、NVIDIA_API_KEY、Langfuse keys 等）标 sync: false，只在 Render dashboard 维护。[项目事实]
为什么不拆两个 service？ Free 档 = 一个常驻 web service。把 Celery worker 单独放 Render background worker 是付费档。对 MVP 规模项目，把进程内争用当作零月费的代价接受。[合理推断]

面试追问树

为什么 API 和 worker 合并进同一个 Render service？
└─ render_combined 实际在进程里启动了什么？
   └─ API 被突发流量打中时，worker 吞吐会怎样？
答：两者共用一个进程和一个 CPU 预算。API 被打爆时，Celery 循环被饿住，
worker 延迟退化。规模到了就该拆：API 留在 web service，worker 搬到付费
background-worker 档或外部 worker 池，两者只共享 Redis + Postgres。

为什么 autoDeployTrigger 设为 checksPass 而不是每次推送到 main？
└─ 哪些 CI job 必须通过 Render 才会拾取此次构建？
   └─ 某个 CI job 不稳定，Render 是等待还是跳过？
答：必须 ci-success（见 cicd 页）报告 success。CI 把不稳定的 job 重跑，
跑绿 Render 才拾取；保持红则 Render 不动上一个好版本。不存在部分部署。

功能中心 . Vercel + 服务端 rewrite

Vercel 把 /api/v1/* 做 same-origin rewrite，绕开企业代理

[项目事实] apps/web/next.config.ts 定义 async rewrites()：当 NODE_ENV !== "development" 时把 /api/v1/:path* 转发到 ${backendOrigin}/api/v1/:path*。

如果不做 rewrite，浏览器会直接请求 https://researchmate-backend-dev.onrender.com/api/v1/*。问题来了：企业或 ISP 代理有时会拦截这个 *.onrender.com 主机，把响应换成 HTML 警告页而不是浏览器要的 JSON —— 连未鉴权的 health 检查都坏，鉴权调用也坏。用户在公司笔记本上看到「全站挂了」，但后端其实健康。

Vercel rewrite 改变的是「谁去跟 Render 说话」。浏览器请求的是 Vercel 主域的 same-origin URL（例如 research-mate-web.vercel.app/api/v1/*），代理不会拦这个域。Vercel 服务端再做一次 server-to-server fetch 到 Render。因为 Vercel 服务器不在用户公司代理后面，请求以 JSON 形态抵达 Render，响应也以 JSON 形态回来。面试里这条最容易被反复追问，因为它同时涉及 CORS、same-origin cookie、和一个少见的部署环境约束。

关键机制
  • Dev 返回 [] — 在 NODE_ENV=development 不跑 rewrite，本地前端直连 http://localhost:8000/api/v1。[项目事实]
  • backendOrigin 推导 — 从 NEXT_PUBLIC_API_BASE_URL 去掉末尾的 /api/v1 得到裸 origin；同一 env 同时作为本地 fallback。一个开关管两种模式。[项目事实]
  • CORS_ALLOWED_ORIGINS — render.yaml 把它钉成 https://research-mate-web.vercel.app。后端只接受来自这个确切 origin 的浏览器跨域调用；其他 origin 上的脚本想调进来会被拒。[项目事实]
  • 附带收益 — same-origin cookie — 浏览器只看到 Vercel origin，cookie 不跨域，SameSite 默认值就不会破坏登录态。[合理推断]
权衡：每次 API 调用现在多一跳 Vercel hop（多一跳时延），还受 Vercel 函数执行时长上限约束，长时上传可能撞顶。之前评估过 presigned-S3 上传方案并被否决；same-origin proxy 是项目选择的方案。[项目事实]

面试追问树

为什么通过 Vercel rewrite /api/v1/* 而不是让浏览器直连 Render？
└─ 企业代理究竟对 *.onrender.com 做了什么？
   └─ 为什么 server-to-server 的 fetch 能绕开它，浏览器不能？
答：代理检查对外 HTTP，把 *.onrender.com 的响应换成 HTML 中间页。浏览器
在代理后面；Vercel edge 不在。让 Vercel 发起这次调用，*.onrender.com
不出现用户可控制的链路上，代理没东西可拦。

后端怎么判断这个请求是合法的？
└─ CORS_ALLOWED_ORIGINS 设成 Vercel origin 防的是什么攻击？
   └─ 既然代理把 JSON 拦成 HTML，它为什么不会拦 Vercel edge 的 fetch？
答：CORS_ALLOWED_ORIGINS 拦的是另一个站点的脚本借用户 cookie 调后端。
Vercel 的 fetch 是服务端到服务端，不走企业代理，所以代理没机会换包。

技术栈中心 . Supabase Postgres

RLS 切租户；迁移增量、SHA-256 摘要 + advisory lock

[项目事实] Supabase 在 tjdkdganvszqawxspveg.supabase.co 提供托管 Postgres；所有业务表都启用基于 auth.uid() 的 RLS；scripts/apply_migrations.py 在 pg_advisory_xact_lock(726_334_129) + SHA-256 校验下应用迁移。

Postgres 是除 embedding 之外所有数据的事实来源。「事实来源」给你的是：worker 在任务中途崩溃，Postgres 里仍保留双方约定好的状态；重启时按 lease 行继续，不需要和第二个存储对账。

租户隔离在数据库层强制，不在业务代码里。Supabase auth 签发的 JWT，sub 是用户 UUID。Postgres RLS 策略拿它跟每行业务数据的 user_id 列比；user_id 不匹配 JWT 的行，数据库直接拒绝。[项目事实] 哪怕 API 写错忘记按 user 过滤，数据库也不会交出别家租户的行。

迁移机制（apply_migrations.py）
  • 21 个增量 SQL 文件 — 按 YYYYMMDDNNNN_*.sql 前缀排序；校验器拒绝空文件、拒绝含字面字符串 drop database 的文件。[项目事实]
  • pg_advisory_xact_lock(726_334_129) — 一个硬编码整数 key；同一 Postgres 上两个并发 apply 没法同时跑。锁是事务级的，commit 或 rollback 时释放。[项目事实]
  • SHA-256 账本 — researchmate_schema_migrations(version, checksum_sha256, applied_at)。如果已应用文件的 hash 后来变了，runner 抛错中止。重放漂移没法悄悄混过去。[项目事实]
  • ALLOW_SCHEMA_APPLY=1 — 没这个 env，apply 路径拒绝执行，作为人工审批关口。CI 跑的是 npm run check:migrations，即 --check-files，不写库。[项目事实]
  • 幂等语句 — create table、create index 和 create policy 都用 if not exists 或 drop policy if exists ... create policy 配对，所以同一文件能在事务内被安全重放。[项目事实]
RLS 需要提示的边界 outbox_events 没有 authenticated-user 读策略 —— 只有 service role 能读，所以配置错的 client JWT 看不到 coordinator 行。pipeline_versions 在普通 user 之上还叠加 developer 和 admin 角色 policy。[项目事实]

面试追问树

为什么用 Postgres RLS 强制隔离而不是在 API 层做？
└─ RLS 开了之后还有什么可能出问题？
   └─ auth.uid() 怎么映射到 API 发过来的 JWT？
答：RLS 让一个写错的 API 仍无法泄漏别家租户的行 —— 数据库直接拒。剩下
的风险是：service-role key 泄漏，或策略写错列名。auth.uid() 读 JWT 的
sub claim（Supabase auth 经请求头在服务端填进去）。

为什么用 pg_advisory_xact_lock 加一个 magic key？
└─ 两个迁移 runner 竞争会发生什么？
   └─ 为什么用 advisory lock 而不是 SELECT ... FOR UPDATE 锁一个哨兵行？
答：哨兵行锁要先有一行真行可锁，行被删掉就锁不住。advisory lock 按整数
key，不需要真行。事务级意味着锁跟事务一同生死，runner 崩了在 rollback
时自然释放。

SHA-256 摘要怎么防重放漂移？
└─ 如果确实需要改一个已应用过的迁移怎么办？
   └─ 为什么迁移要增量、不允许破坏性操作？
答：永远不改已应用文件 —— 发一条新的前向迁移，加列或撤销上一个行为。SHA-256
账本就是为这件事背书：改已应用文件的字节会让 runner 失败。破坏性操作在
校验器里被先拦掉，运维没法在生产意外 DROP TABLE。

技术栈中心 . Qdrant 混合检索

Native BM25 + 4096 维 dense 向量；每条分支都带 owner 过滤

[项目事实] infra/qdrant/researchmate_chunks.json 声明 dense 向量（size: 4096，Cosine）、IDF 加权 sparse 向量和 fusion: rrf；required_filters 是 user_id、project_id、source_type。

文本检索有两种失败方式。纯关键词检索（BM25）抓不到改写 —— 问「怎么取消租约」检不到「终止租赁」。纯 dense 向量检索抓不到罕见字面 token —— 一份提到「CVE-2026-1234」的文档，对查询「CVE-2026-1234」如果 embedding 没见过就出不来。混合检索两条都跑，再把排名融合。

[项目事实] Qdrant v3 collection researchmate_chunks_v3 在服务端一个 collection 同时承载两套 retriever。一条 4096 维 dense 向量由 NVIDIA nv-embed-v1 产出，覆盖改写；一条 native BM25 sparse 向量（qdrant/bm25，modifier: idf）覆盖精确字面匹配。[合理推断] RRF（Reciprocal Rank Fusion）把两份排名交错合并，让项目在候选阶段就拿到两边长处，不必为了候选集单独加一步 rerank。（候选集出来后另有一个 ColBERT rerank collection researchmate_chunks_v2 只对 top 候选跑。)

关键机制
  • Named vector 配置 — 一个 collection 同时有 {"dense": VectorParams(4096, COSINE), "bm25": SparseVectorParams(modifier=IDF)}。一次查询、两个 retriever、融合输出。[项目事实]
  • 必填过滤三件套 — 每次查询必须按 user_id + project_id + source_type 过滤。这四个字段（含 document_id）上的 payload index 让过滤查询够快。[项目事实]
  • 可恢复 backfill — provision_qdrant_hybrid.py 按 BATCH_SIZE=24 跑，把语料的 SHA-256 fingerprint 写进 researchmate_vector_migrations，只有 fingerprint 变了才重 embed。陈旧点通过 scroll + delete 对账。[项目事实]
  • cloud_inference=True — Qdrant 在服务端算 sparse 和 dense 向量，而不是由客户端把向量传过来。BM25 方面客户端只发原文，Qdrant 自己建 sparse 向量；dense 方面 Qdrant 调 embedding API。[合理推断]
需要解释的 magic number BATCH_SIZE=24、timeout=180s、BM25 文档负载截断到 1200 字符。[项目事实] 这些是 provision_qdrant_hybrid.py 里的固定常量；[优化建议] 应对 batch size 与 Qdrant upsert 时延、NVIDIA embedding API 限流做 benchmark —— 仓库里没有项目级 benchmark 证据。

面试追问树

为什么 dense + BM25 用 RRF 融合，而不是只用一个？
└─ dense 能抓到 BM25 抓不到的什么？
   └─ BM25 能抓到 dense 抓不到的什么？
      └─ sparse 为什么要 IDF 加权？
答：dense 抓改写和共享意图。BM25 抓罕见字面（CVE 编号、产品代码）。IDF 加权
压低 sparse 侧的高频词权重，让罕见词浮上来 —— 不加 IDF，「the」会和
「CVE-2026-1234」贡献相同。

为什么 user_id + project_id 是必填过滤，而不是可选？
└─ 忘记带过滤会怎样——Qdrant 会泄漏行吗？
   └─ 为什么恰好在这四个字段上建 payload index，不是全部？
答：忘带过滤意味着查询可能命中别家租户的 chunk。collection 配置里的
required_filters 在客户端层拒掉未过滤查询。payload index 要占存储和构建
时间，所以项目只给每次查询都过滤的字段建索引。

backfill 怎么可恢复、又不重复 embed 同一份语料？
└─ 语料 fingerprint 防的是什么？
   └─ Qdrant 里存在但 Postgres 里不存在的点是怎么对账的？
答：fingerprint 是整语料 (chunk_id, chunk_text sha256) 的 sha256。源文
变了 fingerprint 就变，那次 run 才重 embed。Qdrant 里有但 Postgres 里没有
的陈旧点通过 scroll 找出来，在 upsert 之前 delete。
