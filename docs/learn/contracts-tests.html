Contracts & Tests · OpenAPI + tests

The ResearchMate test suite is a hermetic, contract-first verification system. The OpenAPI specification (openapi.yaml) defines 65 schemas that mirror across Pydantic models and SQL migrations. The frontend types live locally in apps/web/app/lib/api.ts. The Python test suite contains 36 test_*.py files organized into HTTP integration, unit, worker, workflow, and contract-source-inspection categories. Every test runs without external dependencies, using fake providers, in-memory stores, and source-file inspection. This page walks through every contract type and every test file.

Technology stack fundamentals

7 foundations that power contracts & tests

Each card explains what the technology does in general and how ResearchMate uses it for contract verification.

TypeScript type contracts

The OpenAPI specification at infra/openapi/openapi.yaml defines 65 schemas that serve as the authoritative API data shape. The frontend types are defined locally in apps/web/app/lib/api.ts, mirroring the OpenAPI schemas. The backend mirrors them into Pydantic models. No shared workspace package exists.

Pydantic

Python data-validation library. The backend mirrors every TypeScript contract into Pydantic models under apps/api/src/researchmate_api/schemas/. Pydantic enforces field types, optional vs. required, enum constraints, and validator logic at request boundary. test_project_scaffold.py verifies that backend Pydantic contracts validate the request shape defined by the OpenAPI specification.

pytest

Python test framework (pinned to 9.0+). pytest.ini configures -p no:cacheprovider --basetemp=.pytest-temp for deterministic, cache-free runs. conftest.py inserts API and worker source paths into sys.path. Test functions use plain def test_* naming, pytest.raises for expected failures, and pytest.importorskip for optional dependencies like SQLAlchemy.

Vitest

Frontend unit-test framework configured in apps/web/vitest.config.ts with jsdom environment and v8 coverage provider. Seven test files cover API client logic, auth gate, presentation components, demo mode, email rate limiting, idempotent intents, and Supabase session handling. Coverage thresholds enforce 40% lines and statements across app/lib and app/components.

Playwright

Browser acceptance-test framework. apps/web/playwright.config.ts runs against a local Next.js dev server in demo mode (NEXT_PUBLIC_DEMO_MODE=true) on port 3100. One E2E test file (demo-workspace.e2e.ts) exercises the deterministic client-only demo runtime. CI runs with retries=2 and a single worker; local runs are fully parallel.

Hermetic testing

The entire Python test suite is hermetic: no real PostgreSQL, Qdrant, Redis, LLM, or external HTTP calls. The FastAPI TestClient creates an in-process application with Settings(app_env="test", llm_provider="fake"). An autouse reset_local_store fixture wipes the in-memory store before and after each test. Source-inspection tests read files from disk without executing application code.

Dependency injection testing

The backend constructs all managed providers (store, chat provider, hybrid store, reranker) through factory functions read from app.state. Tests override these factories by constructing create_app(settings=Settings(...)) with the fake provider, or by using monkeypatch to swap module-level functions. No global singletons are mutated outside the reset-protected store.

OpenAPI specification

The single source of truth for API data shapes

The OpenAPI 3.1.0 specification at infra/openapi/openapi.yaml (5729 lines) defines 65 schemas covering every API endpoint. The frontend types in apps/web/app/lib/api.ts mirror these schemas locally. The check:openapi CI gate ensures the YAML stays in sync with the FastAPI runtime.

The packages/shared workspace package was removed as unused ghost code (zero imports across the entire repository). All frontend types are now defined directly in apps/web/app/lib/api.ts. The OpenAPI specification is the single source of truth that both frontend and backend mirror.

api.ts · frontend types, type-by-type

The file defines TypeScript interfaces and types that mirror the OpenAPI specification. Every comment in the source is written in English; the type names and field names are English. Below is each type with its purpose and key fields.

1. TaskType (type)

Union: "answer" | "quiz". Defines what kind of task a request represents. Task only decides what to do, not how. The router inspects the request to determine whether the user is asking a question or generating a quiz.

2. ToolName (type)

Union of 8 tool names: query_local_docs, search_web, read_url, crawl_url_optional, rerank_evidence, generate_answer, generate_quiz, save_quiz. The backend uses ExecutionPlan to control which tools are allowed for a given request, enforcing the security boundary.

3. ExecutionPlan (interface)

Defines the parsed execution plan for one request. Fields: task_type, allowed_tools (ToolName[]), requires_local_docs, requires_web, context_strategy (6-value union: chat, full_context, hybrid_retrieval, web, hybrid_retrieval_web, quiz), output_schema (ChatAnswer, GroundedAnswer, or QuizSet).

4. SourceSummary (interface)

Defines the source count summary shown at the top of an answer. Fields: local_chunks (number), web_pages (number). Appears in GroundedAnswer and QuizSet.

5. Citation (interface)

Defines a local or web evidence citation. Fields: id, source_type ("local_doc" | "web_page"), document_id?, chunk_id?, page_no?, slide_no?, url?, quote (required string), claim_id?. Every grounded answer must cite its sources through this structure.

6. GroundedAnswer (interface)

Defines the structured output for a traceable, evidence-backed answer. Fields: sources (SourceSummary), answer (string), citations (Citation[]), trace_id (string), validation_status ("passed" | "failed" | "retrying"). AskResponse extends this interface.

7. AskResponse (interface, extends GroundedAnswer)

Defines the Ask API response. Adds: run_id, conversation_id, rerank_degraded, retrieval_degraded, summary_degraded (all boolean), fallback_reason?. The three degraded flags let the frontend surface degradation notices to the user.

8. QuizQuestion (interface)

Defines a single quiz question. Fields: id, type ("single_choice" | "fill_blank" | "subjective"), question, options? (string[] | null), answer, explanation, difficulty ("easy" | "medium" | "hard"), source_citations (Citation[]). Every question must trace back to source evidence.

9. QuizSet (interface)

Defines the structured output for a quiz. Fields: id, sources (SourceSummary), questions (QuizQuestion[]). The sources field mirrors GroundedAnswer so the frontend can render consistent source panels.

10. QuizResourceScope (type)

Union: "all_ready_documents" | "topic". Defines the resource selection mode for quiz generation. "all_ready_documents" uses every ready document in the project; "topic" filters by a topic query.

11. QuizRequest (interface)

Defines the Quiz API request. Fields: project_id (required), prompt?, topic_query?, resource_scope? (QuizResourceScope), single_choice_count?, fill_blank_count?, subjective_count?. The backend provides sensible defaults for all optional fields.

12. QuizCoverage (interface)

Defines the actual resource coverage that entered the generation context. Fields: documents_available, documents_covered, chunks_selected, truncated (boolean). Lets the frontend show whether the quiz covered all documents or was truncated by token budget.

13. QuizResponse (interface)

Defines the Quiz API response. Fields: quiz_set (QuizSet), run_id, trace_id, validation_status, coverage (QuizCoverage). Combines the quiz payload with runtime metadata and coverage diagnostics.

14. QuizHistoryResponse (interface)

Defines the quiz history response. Fields: project_id, quiz_sets (QuizSet[]). Returned by the quiz history endpoint to list previously generated quiz sets for a project.

15. ProjectRecord (interface)

Defines a project record. Fields: id, user_id, name, kind ("personal" | "workspace"), status ("active" | "deleting" | "deleted" | "expired" | string), expires_at?, created_at, updated_at, deleted_at?. The status union includes a string escape hatch for forward compatibility.

16. DocumentStatus (type)

Union of 8 statuses: uploaded, parsing, parsed, indexing, ready, failed, expired, deleted. Defines the document lifecycle state machine. Only "ready" documents can serve as quiz or answer evidence.

17. DocumentRecord (interface)

Defines owner-scoped document identity, canonical file type and MIME, size, lifecycle status, expiry, and timestamps.

18. UploadUrlRequest (interface)

Accepts 42 parser-backed file types. The request binds project/conversation scope, filename extension, MIME, and a 25 MiB size limit before the API creates an upload reservation.

19. UploadCompleteRequest (interface)

Defines the upload completion request. Fields: checksum_sha256?. The production worker parses uploaded files from R2 object storage; no client-side text extraction is accepted.

20. UploadUrlResponse (interface)

Defines the upload URL response. Fields: document_id, upload_url, r2_object_key, expires_in_seconds. The frontend uploads the file to upload_url and then calls the complete endpoint with the document_id.

21. JobRecord (interface)

Defines a job status record. Fields: id, user_id, project_id?, document_id?, type (string), status ("pending" | "running" | "succeeded" | "failed" | "cancelled"), progress (number 0-100), error_message?, created_at, updated_at.

22. DeveloperTrace (interface)

Defines the developer trace record for debugging and observability. Fields: trace_id, user_id, project_id, run_id, execution_plan (ExecutionPlan), router_reason, retrieved_chunks (Record[]), tool_calls (Record[]), validation_result (Record), created_at. Access is admin-only.

23. ErrorResponse (interface)

Defines the unified error response. A single error object with three fields: code (machine-readable error code), message (human-readable message), request_id (correlation ID). Every API error follows this shape, enabling consistent frontend error handling.

Three-layer contract mirroring

TypeScript to Pydantic to SQL

The same data shape is expressed in three layers, each enforcing it at a different boundary.

Layer 1 · OpenAPI (authoritative)infra/openapi/openapi.yaml -- 65 schemas. The CI gate check:openapi verifies it matches the FastAPI runtime. The frontend mirrors these in apps/web/app/lib/api.ts. This is the single source of truth that the other two layers must mirror.
Layer 2 · Pydantic (request boundary)apps/api/src/researchmate_api/schemas/ -- Python models that mirror every TypeScript interface. FastAPI uses these for automatic request validation, OpenAPI generation, and response serialization. Field names match exactly.
Layer 3 · SQL (persistence boundary)infra/supabase/migrations/ -- PostgreSQL table definitions with RLS policies. Column types and constraints mirror the Pydantic models. test_database_migration_contract.py verifies that migrations preserve schema and RLS contracts.
Why three layers? The OpenAPI spec gives the frontend compile-time safety via local type definitions. Pydantic gives the backend runtime validation and automatic OpenAPI docs. SQL gives the database structural integrity and row-level security. A change to the OpenAPI spec must propagate to all three layers, and the contract-source-inspection tests verify this consistency.

Contract consistency guarantees

How tests enforce the mirror

Six contract-source-inspection tests verify that the three layers stay in sync without running application code.

Frontend to API contract

test_frontend_contracts.py reads frontend source files and verifies that the frontend calls only approved API routes from the OpenAPI spec. It checks that MVP pages exist, that the frontend does not reference backend secret names, and that it does not call model providers directly.

Shared to Pydantic contract

test_project_scaffold.py includes test_shared_contracts_define_unified_chat_outputs and test_backend_pydantic_contracts_validate_request_shape, which verify that the OpenAPI schemas and backend Pydantic models agree on request and response shapes.

SQL to schema contract

test_database_migration_contract.py reads migration SQL files and verifies that additive migrations preserve schema, RLS, and idempotency contracts. It checks that all planned tables are defined, that RLS policies close initial gaps, and that durable run and evaluation idempotency keys are unique per owner.

Postgres to repository contract

test_release_safety_contracts.py verifies that Qdrant rerank projection indexes every filter field, that evaluation budget and fault audit migrations are fail-closed, and that workflow claim versions are serialized and incremented.

OpenAPI to route contract

test_project_scaffold.py includes test_openapi_contract_declares_mvp_routes, verifying that the generated OpenAPI spec declares all MVP routes. test_evidence_api.py includes test_evidence_routes_are_exposed_in_generated_openapi.

Docs to source contract

test_project_scaffold.py includes tests that verify docs local links resolve, docs use English HTML without parallel markdown, docs separate current truth from archived plans, and database and API docs reconcile complete source contracts.

Test configuration

3 Python infrastructure files + 1 INI config

The test infrastructure consists of conftest.py, api_workflow_fixtures.py, api_workflow_support.py (3 Python files), and pytest.ini (1 INI configuration file). Together they provide import paths, HTTP client fixtures, and deterministic test isolation.

pytest.ini

A minimal two-line configuration that disables the pytest cache provider and sets a local base temp directory. This ensures test runs are deterministic and do not leave artifacts outside the repository.

[pytest]
addopts = -p no:cacheprovider --basetemp=.pytest-temp
-p no:cacheprovider prevents pytest from writing .pytest_cache/, which could cause non-deterministic behavior across CI runs. --basetemp=.pytest-temp redirects all temporary files to a repository-local directory that is gitignored.

conftest.py

Inserts two source directories into sys.path so that test modules can import from both the API and worker packages without installation. This is the only file that every test implicitly depends on.

ROOT = Path(__file__).resolve().parents[1]
API_SRC = ROOT / "apps/api/src"
WORKER_SRC = ROOT / "workers/ai-worker/src"
sys.path.insert(0, str(API_SRC))
sys.path.insert(0, str(WORKER_SRC))

api_workflow_fixtures.py

Provides two pytest fixtures for HTTP integration tests. The reset_local_store fixture is autouse, meaning it runs before and after every test that imports it, wiping the in-memory store. The client fixture builds a FastAPI TestClient with the fake LLM provider.

@pytest.fixture(autouse=True)
def reset_local_store() -> Generator[None]:
    store.reset()
    yield
    store.reset()

@pytest.fixture()
def client() -> TestClient:
    return TestClient(create_app(settings=Settings(
        app_env="test", llm_provider="fake"
    )))

Hermetic testing principle

Zero external dependencies

The entire test suite is hermetic. No test requires a running PostgreSQL, Qdrant, Redis, LLM API, or external HTTP endpoint. This makes the suite fast, deterministic, and safe to run in any CI environment.

Fake LLM provider

Every HTTP integration test constructs the FastAPI app with Settings(app_env="test", llm_provider="fake"). The fake provider returns deterministic, pre-scripted responses without any network call. This means Ask and Quiz workflows can be tested end-to-end without an LLM API key.

In-memory store

The backend store singleton is an in-memory implementation when app_env="test". The autouse reset_local_store fixture calls store.reset() before and after each test, ensuring complete isolation between test functions.

TestClient instead of HTTP server

FastAPI TestClient wraps the ASGI application in-process. No socket is opened, no port is bound. This eliminates network flakiness and makes tests orders of magnitude faster than a real HTTP integration.

Source inspection without execution

Six contract-source-inspection tests read files from disk using pathlib.Path.read_text() and parse them with regex or string matching. They verify structural contracts (file existence, content patterns, schema correctness) without importing or executing any application code.

Unit doubles

Unit tests use lightweight doubles instead of real infrastructure: SimpleNamespace for mock objects, RecordingConnection to capture SQL statements without a database, EmptyResult to simulate query responses, and collections.deque for deterministic workflow state transitions.

No real PDF parsing models

test_worker_parsing_unit.py uses the lightweight pypdf backend and a 703-byte real PDF fixture. Docling visual pipeline (which requires torch) is never loaded in tests. The parser verifies text extraction, provenance serialization, and OOXML parsing without heavy ML dependencies.

Optional dep skipif pattern

Tests that exercise optional adapters (the slowapi limiter, the python-magic MIME verifier) skip gracefully rather than fail when the dependency is absent. The pattern: a module-level try: import slowapi ... _HAS_SLOWAPI = True except ModuleNotFoundError: _HAS_SLOWAPI = False guard sets a boolean, and the affected assertions are decorated with @pytest.mark.skipif(not _HAS_SLOWAPI, reason="slowapi not installed") (and the matching not _HAS_MAGIC for python-magic). The constant-level tests in test_http_security_hardening.py always run; only the limiter-enforcement tests skip. The MIME matcher tests in test_object_storage.py always run; only the mismatch-rejecting assertion skips when libmagic is unavailable, and the verifier fails open in production rather than blocking legitimate traffic.

Hermetic + optional together: The HTTP-security and object-storage tests keep the suite hermetic even when the optional dep is installed: test_http_security_hardening.py uses Settings(app_env="local", auth_mode="development") against an in-process TestClient, and test_object_storage.py uses a FakeS3Client with fetched_bytes fixtures rather than real S3. The optional dep only changes whether the limiter middleware or libmagic detection runs — the assertions still do not touch any external service.

Mock strategy

Layered isolation patterns

The test suite uses a deliberate, layered mock strategy. Each layer isolates a different boundary, and the choice of technique depends on what needs to be verified.

monkeypatch (Python)

pytest built-in monkeypatch fixture is used to swap module-level functions and attributes at runtime. For example, test_mcp_boundary.py monkeypatches build_mcp_server to raise ModuleNotFoundError, simulating a missing MCP SDK. test_worker_runtime_bootstrap_unit.py monkeypatches dispatcher and heartbeat functions to avoid starting real processes.

SimpleNamespace

Python types.SimpleNamespace creates lightweight mock objects with arbitrary attributes. Used extensively in unit tests to simulate provider responses, LLM completions, and workflow state without defining full mock classes. For example, test_llm_provider.py uses SimpleNamespace to simulate the OpenAI-compatible client response object.

RecordingConnection / EmptyResult

test_evidence_postgres_unit.py and test_postgres_repository_contract.py define RecordingConnection (captures every SQL statement and parameters) and EmptyResult (returns None from queries). These doubles let tests verify that the repository issues correct SQL with correct parameters without connecting to PostgreSQL.

Fake provider via Settings

Instead of mocking individual LLM calls, the suite constructs the entire FastAPI app with llm_provider="fake". This swaps the real NVIDIA chat provider for a deterministic fake at the dependency-injection boundary, exercising the full request flow including routing, validation, and response serialization.

vi.fn() and vi.hoisted() (TypeScript)

Frontend Vitest tests use vi.fn() for mock functions and vi.hoisted() for mocks that must be available before module imports. For example, auth-gate.test.tsx hoists Supabase session mocks, and api.test.ts mocks fetch to verify API client behavior without network calls.

renderToStaticMarkup

presentation.test.tsx uses React renderToStaticMarkup to render components to HTML strings for assertion. This avoids the complexity of a full DOM testing library while still verifying that components render the expected visible chat and quiz states.

Coverage configuration

Python coverage + frontend v8 coverage

Coverage is configured at two levels: the Python test suite uses the coverage package (pinned 7.10+), and the frontend uses Vitest built-in v8 coverage provider with threshold enforcement.

Python dependencies (pyproject.toml)

The root pyproject.toml pins coverage>=7.10.0,<8 and pytest>=9.0.0,<10 as dev dependencies. The coverage package instruments Python source files during test execution and produces line and branch reports. The CI gate npm run test:python enforces coverage report --fail-under=69, so the Python suite must keep at least 69% combined line and branch coverage across apps/api/src/researchmate_api and workers/ai-worker/src/researchmate_worker for a push to be deployable.

pytest.ini

Disables the cache provider (-p no:cacheprovider) to prevent stale cache from affecting coverage results. Sets --basetemp=.pytest-temp to keep all temporary test artifacts inside the repository.

Vitest v8 coverage

apps/web/vitest.config.ts configures the v8 coverage provider with include: ["app/lib/**/*.ts", "app/components/**/*.{ts,tsx}"] and exclude: ["app/**/*.test.{ts,tsx}"]. Reporters: text and json-summary. Thresholds: 40% lines and 40% statements.

Coverage scope rationale

The Vitest coverage includes orchestration code (app/lib) and presentation code (app/components) but excludes test files themselves. The 40% threshold is intentionally modest: it ensures that core logic is tested without forcing brittle tests on every utility function. The coverage-v8 package provides native V8 instrumentation.

Playwright trace retention

apps/web/playwright.config.ts sets trace: "retain-on-failure", screenshot: "only-on-failure", and video: "retain-on-failure". This produces debugging artifacts only when a test fails, keeping the CI artifact store clean.

CI coverage enforcement

test_release_pipeline.py includes test_ci_runs_the_full_test_build_contract_and_security_gate, which reads the CI workflow YAML and verifies that the full test suite (including coverage) runs as a mandatory gate before any deployment. This makes coverage enforcement a contract, not a convention.
