Minimum mental model

What contracts & tests protect, in one paragraph

Read this first. If you only remember 20% of the page, this is the 20%.

Conclusion first. ResearchMate is a system with many independent parts: a FastAPI server, a Celery worker, a Next.js client, a Postgres database, an LLM, and a vector store. When a request crosses from one part to another, both sides must agree on the shape of the data they exchange. That agreement is the “contract.” This project writes the contract in three places that must stay in sync: the OpenAPI YAML (a single file describing every endpoint and schema), the Pydantic models (Python classes the server uses to validate every request), and the SQL migrations (the actual database tables and row-level security policies). 52 pytest files check that these three layers agree, and that the running code respects them.

Core link

  ↓ mirrors
infra/openapi/openapi.yaml (source of truth, 71 schemas)
  ↓ mirrors
apps/api/.../schemas/*.py (Pydantic, runtime validation, 11 files)
  ↓ mirrors
infra/supabase/migrations/*.sql (PostgreSQL + RLS, persistence boundary)

The chain reads top-down but is enforced bottom-up: the YAML is regenerated from Pydantic by a script, six tests read the SQL files off disk, and one test reads the frontend TypeScript source. A change in any layer that does not match the others fails the build before it reaches deploy.

API contract design (tech-stack-centered)

Three-layer mirror: OpenAPI → Pydantic → SQL

Same shape, three boundaries. Each layer protects a different thing.

Conclusion first. A request touches three places: the client that sends it, the server that handles it, and the database that stores it. If the “shape” of a request field (its type, length, allowed values) lives in only one layer, the other two layers drift and break later. So ResearchMate keeps one shape in three layers: the OpenAPI YAML is the authoritative source, Pydantic models copy it for runtime validation, and SQL migrations copy it for column types and row-level security. A change must travel to all three. Six tests catch any layer that falls behind without running application code.

What each layer protects

LayerBoundaryProtects
infra/openapi/openapi.yamlAuthoritativeFrontend compile-time types via apps/web/app/lib/api.ts
apps/api/.../schemas/*.pyRequestRuntime validation, auto OpenAPI docs, response serialization
infra/supabase/migrations/*.sqlPersistenceColumn types, constraints, RLS owner-scoping

Each layer guards a different failure. The OpenAPI YAML guards the client: if a TS type is wrong, the build fails at compile time. The Pydantic models guard the server: a request missing a required field is rejected before any business logic runs. The SQL layer guards the database: even if a service has a bug that tries to read another user’s row, the RLS policy on the table rejects it.

Key mechanisms

  1. FastAPI derives OpenAPI from Pydantic — the script check:openapi regenerates the YAML from the current Pydantic classes and diffs it against infra/openapi/openapi.yaml. If a developer edits the YAML by hand and forgets to update the Pydantic class (or vice versa), the diff is non-empty and the gate fails.
  2. Frontend types are local, not generated — apps/web/app/lib/api.ts hand-mirrors the YAML. The project chose hand-writing over codegen so the frontend build is not coupled to a code-generation step. The cost is drift risk; test_frontend_contracts.py reads the frontend source and verifies it only calls approved routes.
  3. SQL closes the loop with RLS — test_database_migration_contract.py opens the SQL migration files with Path.read_text() and asserts three things: additive migrations preserve existing schema, RLS policies cover every owner-scoped table, and stored idempotency keys are unique per owner.
[Project fact] OpenAPI declares 71 schemas; main.py registers ErrorResponse as the model for 400/401/403/404/409/422/429/502/503 — every error follows the same {code, message, request_id} envelope. packages/shared was removed as ghost code; the YAML is the only shared source.

Interview follow-up tree

Why three layers instead of just Pydantic?
├  Pydantic protects the request boundary; SQL protects persistence; OpenAPI protects the client.
└  What breaks if you collapse two layers?
   └  Collapsing Pydantic + SQL means no DB-level owner scoping; a service bug bypasses RLS.

How is drift caught?
├  check:openapi regenerates YAML and diffs; 6 contract tests read files from disk.
└  Do these tests execute application code?
   └  No — they use pathlib.Path.read_text() + regex, no import, no server.

Why hand-write frontend types instead of codegen?
├  Local types give compile-time safety without a build step tied to the API.
└  Cost?
   └  Manual drift risk; mitigated by test_frontend_contracts.py reading frontend source.

Test strategy (function-centered)

Test before code, hermetic, one subagent two phases

A test is part of the contract: it is written before the implementation, and it runs without touching real infrastructure.

Conclusion first. Tests are organized by boundary, not by module: HTTP integration, unit services, worker, workflow, and six contract-source-inspection tests. The whole suite is hermetic — no PostgreSQL, Qdrant, Redis, or LLM is contacted. The two-phase design writes the test against the public contract first (black-box, source forbidden), then the same subagent reviews source and tightens the tests for boundary conditions (white-box). One subagent for both phases saves tokens and forces tests to assert observable behavior.

Test surface (52 files, by boundary)

BoundaryFilesTypical assertion
HTTP integration7status code, JSON shape, idempotency replay
Unit (services)16SQL issued to RecordingConnection, evidence allowlist
Worker unit7Celery task registration, heartbeat, retry backoff
Workflow unit2LangGraph review→commit arc via deque

Hermetic mechanisms

  1. Fake LLM provider — the test settings set llm_provider="fake"; the fake returns scripted responses from a queue. No API key, no network, no LLM cost, deterministic output.
  2. In-memory store reset every test — the reset_local_store fixture is autouse, so it runs before and after every test and calls store.reset(). One test cannot leak state into the next.
  3. TestClient, no socket — fastapi.testclient.TestClient wraps the ASGI app in the same process. No port is bound, so there is no network flake and no startup cost.
  4. Hand-built doubles for unit tests — instead of a real DB connection, tests pass a RecordingConnection that captures SQL strings; instead of a real LLM queue, they pass collections.deque. Cheap to build, exact assertions.
  5. Source inspection without execution — six tests use Path.read_text() plus regex. They never import the app, so they cannot fail because a dependency is missing; they only fail when the actual contract on disk changes.
[Project fact] conftest.py inserts apps/api/src and workers/ai-worker/src into sys.path — every test depends on it implicitly. api_workflow_support.py shares HEADERS = {"Authorization": "Bearer dev"} and create_ready_document(), the bootstrap helper for any test needing ready evidence.

Two-phase contract-first design

[Project fact] Phase 1 is black-box: the subagent writes tests against the public contract (routes, schemas, status codes) with source forbidden. The test reflects how the system should behave from the outside. Phase 2 is white-box: the same subagent now reads source and tightens the tests for boundary conditions (empty input, overflow length, race conditions). Aligned with ISTQB / IEEE 29119 / SOA which place contract testing before structural testing. Using one subagent for both phases saves tokens compared to dispatching two separate agents, and the contract intent from phase 1 carries into phase 2’s source review.

Interview follow-up tree

Why hermetic instead of testcontainers?
├  Speed + determinism in CI; no port flake, no LLM cost, no Qdrant boot.
└  What is the cost?
   └  Doubles can drift from real adapters; mitigated by RecordingConnection assertions on actual SQL strings.

Why same subagent for both phases?
├  Phase 1 context (contract intent) carries into phase 2 (source review).
└  Risk?
   └  Anchoring bias; mitigated by requiring source-confirmed facts in phase 2.

How are source-inspection tests not brittle?
├  They assert structural contracts (file exists, RLS clause present, route declared).
└  When do they break?
   └  On additive schema or route changes — which is exactly when you want a gate failure.

Pydantic schema patterns (tech-stack-centered)

Five patterns that keep the contract honest at runtime

Eleven schema files in schemas/ implement the runtime contract. Five patterns recur.

Conclusion first. A Pydantic model is the runtime expression of the contract. Without discipline, an enum field can serialize as TaskType.ANSWER instead of "answer", a credentials field can leak into logs, or a numeric bound can be hard-coded in one place and drift in another. Five patterns stop these: inherit (str, Enum) for stable wire values, use model_validator(mode="after") for cross-field rules, set ConfigDict(use_enum_values=True) so responses emit strings, wrap credentials in SecretStr, and put every numeric bound in schemas/common.py as a named constant.

Pattern 1 — (str, Enum) for stable wire values

class TaskType(str, Enum):
    ANSWER = "answer"
    QUIZ = "quiz"

class DocumentStatus(str, Enum):
    UPLOADED = "uploaded"; PARSING = "parsing"; PARSED = "parsed"
    INDEXING = "indexing"; READY = "ready"; FAILED = "failed"
    EXPIRED = "expired"; DELETED = "deleted"

[Project fact] When a plain Enum is serialized to JSON, the output can be "TaskType.ANSWER" (the repr), which the frontend does not expect. Inheriting (str, Enum) makes Python treat the member as its string value, so TaskType.ANSWER serializes directly as "answer". Pattern 3 below adds the second step that makes this work in model_dump() too.

Pattern 2 — model_validator(mode="after") for cross-field rules

class HumanDecisionCreate(BaseModel):
    interrupt_key: str = Field(min_length=1, max_length=160)
    decision: Literal["approve", "edit", "reject"]
    edited_payload: dict[str, Any] | None = None

    @model_validator(mode="after")
    def require_edited_payload(self) -> HumanDecisionCreate:
        if self.decision == "edit" and self.edited_payload is None:
            raise ValueError("edited_payload is required for an edit decision")
        if self.decision != "edit" and self.edited_payload is not None:
            raise ValueError("edited_payload is only valid for an edit decision")
        return self

[Project fact] Pydantic field validators check one field at a time. But some rules span multiple fields: here, if decision is edit, then edited_payload must be present, and if decision is anything else, edited_payload must be absent. A model_validator(mode="after") runs after Pydantic has parsed and typed every field, so the function can read self.decision and self.edited_payload together. The raised ValueError becomes a 422 response. Other examples in the codebase: SourceScope.reject_duplicate_documents rejects ambiguous duplicate document IDs; ReportRefreshCreate.require_change requires at least one changed document or a forced section.

Pattern 3 — ConfigDict(use_enum_values=True)

[Project fact] Pattern 1 makes the enum stringify at JSON encoding time, but Pydantic still keeps the enum member when you call model_dump(). Without use_enum_values=True, the dumped dict contains {"task_type": TaskType.ANSWER} rather than {"task_type": "answer"}. Setting it on the model config tells Pydantic to dump the string value everywhere. Applied on Citation, ExecutionPlan, GroundedAnswer, AskResponse.

Pattern 4 — SecretStr + typed Settings

class Settings(BaseSettings):
    nvidia_api_key: SecretStr | None = None
    qdrant_api_key: SecretStr | None = None
    object_storage_secret_access_key: SecretStr | None = None
    llm_temperature: float = Field(default=1.0, ge=0, le=2)
    llm_max_tokens: int = Field(default=16_384, ge=1, le=32_768)

[Project fact] A plain str for an API key would be printed in tracebacks, in logs, and in repr(settings). SecretStr wraps the value and shows ********** instead; the only way to read the raw key is settings.nvidia_api_key.get_secret_value(). Every tunable parameter is a Field with explicit ge/le bounds — not a bare default — so an env var outside the range fails loudly instead of producing a silent misconfiguration.

Pattern 5 — Centralized constants, no magic numbers

MAX_TEXT_LENGTH = 1200
MAX_MESSAGE_LENGTH = 8000
MAX_ANSWER_LENGTH = 16000
MAX_FALLBACK_REASON_LENGTH = 300
# Then in ask.py:
message: str = Field(min_length=1, max_length=MAX_MESSAGE_LENGTH)

[Project fact] schemas/common.py centralizes more than 40 constants: text bounds, snippet sizes, evidence workflow bounds, upload bounds, quiz bounds. The same number must appear in three places — the Pydantic Field, the SQL CHECK constraint, and the frontend maxLength attribute — so naming it once and importing it is the only way to keep them in sync. AGENTS.md forbids literals like max_length=1200 in validators; the constant is mandated.

[Reasonable inference] Centralization pays off when the contract is mirrored three places: one constant flows into Pydantic Field, the SQL CHECK constraint, and the frontend max-length attribute. Without a single name, the three copies drift silently — the server accepts 1200 chars, the DB truncates at 1000, the frontend caps at 1500.

Interview follow-up tree

Why (str, Enum) instead of plain Enum?
├  JSON serialization emits the string value directly; no custom encoder.
└  Why use_enum_values=True on top of that?
   └  Without it, Pydantic returns the Enum member, not the string, in model_dump().

Why model_validator(mode="after") instead of "before"?
├  After-validation runs once fields are typed; easier to reason about typed self.
└  When would "before" be better?
   └  When you need to preprocess raw input before type coercion (e.g., rename a field).

Why centralized constants in common.py?
├  Bounds mirror across Pydantic, SQL CHECK, and frontend max-length.
└  Trade-off?
   └  Indirection; mitigated by the AGENTS.md rule banning literals in validators.

Idempotency (function-centered)

Idempotency-Key: why a network retry must not double-charge

The protocol that makes cost-bearing POSTs safe to retry.

Conclusion first. Some POST endpoints cost time or money each time they run: an Ask request triggers an LLM call, a Quiz request triggers another LLM call, an evaluation runs many. If the client sends the request and the network times out before the response arrives, the client does not know whether the server ran it. The natural reflex is to retry — but naively retrying runs the LLM twice and doubles the cost. The Idempotency-Key protocol solves this: the client attaches a random key to the first request; the server stores the key, the request body’s hash, and the response. On a retry with the same key and same body, the server returns the saved response without re-running. On a retry with the same key but a different body, the server rejects with 409, because the client is trying to reuse a key for a different intent.

Request link

POST /api/v1/ask
Idempotency-Key: 9f3a...client   (8-160 chars, optional on Ask, required on evidence endpoints)
Authorization: Bearer <dev|prod-jwt>

→ Coordinator(user, operation, key, payload)
   ├  state=="execute"  → run, then complete() persists response snapshot
   ├  state=="replay"   → return saved JSON (no second execution)
   ├  state=="mismatch" → IdempotencyError("IDEMPOTENCY_KEY_REUSED") → 409
   └  state=="in_progress" → IdempotencyError("IDEMPOTENCY_REQUEST_IN_PROGRESS") → 409

Four states cover four situations: execute is the first time the key is seen; replay is a safe retry with the same body, returning the saved answer; mismatch is a client error (reusing a key for a different request); in_progress is a concurrent identical request that is still running.

Key mechanisms

  1. Header, not body field — routers/ask.py: idempotency_key: str | None = Header(default=None, alias="Idempotency-Key", min_length=8, max_length=160). Same pattern on quiz.py and 5 endpoints in evidence.py. Putting it in a header keeps the body clean for hashing.
  2. Payload hash is canonical — two requests with the same fields in different order must hash to the same value. request_hash(payload) JSON-dumps with sort_keys=True, separators=(",",":") (no whitespace), then SHA-256. Field order cannot cause a false mismatch.
  3. Per-user, per-operation scoping — begin_idempotent_operation(user, operation, key, payload_hash) stores the key against user_id and the operation name. One user’s "abc123" cannot collide with another user’s "abc123", and a key used for an Ask cannot be replayed for a Quiz.
  4. Postgres FOR UPDATE lock — evidence_evaluations.py runs SELECT ... FOR UPDATE on the idempotency row inside the transaction. Two identical concurrent requests both try to claim the row; one blocks until the other commits, so they serialize rather than both execute.
  5. abandon() releases on failure — if the operation throws, abandon() clears the reservation so a safe retry can run again. Without this, a transient failure would permanently occupy the key.
[Project fact] Two distinct error codes: IDEMPOTENCY_KEY_REUSED (same key, different body → 409) and IDEMPOTENCY_REQUEST_IN_PROGRESS (same key, same body, still running → 409). test_api_regressions.py covers both: test_idempotency_replays_without_duplicate_messages and test_idempotency_key_body_mismatch_returns_conflict.

Interview follow-up tree

Why 8-160 char length bound on the key?
├  Short enough to store/dedupe index efficiently; long enough to be a real UUID/hex.
└  What if a client sends a 1-char key?
   └  Header validation rejects it (min_length=8) → 422 before reaching the coordinator.

Why payload hash AND key?
├  Key identifies the intent; hash verifies the body matches the first execution.
└  What if the client legitimately wants to resend the same body?
   └  That is a replay — coordinator returns the saved response, no second execution.

Why per-user+per-operation scoping?
├  Prevents cross-user key collision; one user's "abc123" cannot replay another's.
└  Concurrency?
   └  SELECT ... FOR UPDATE inside the transaction serializes concurrent identical requests.

What happens if the worker crashes mid-execution?
├  abandon() (or process exit) releases the reservation; a safe retry can execute again.
└  Risk?
   └  If complete() was already persisted but the response was lost, replay still returns the saved snapshot.

Coverage gate & production safety (tech-stack-centered)

69% line+branch, CI-enforced, contract-tested

Coverage is a contract, not a metric. CI fails the build below 69%, and a source-inspection test verifies the gate runs.

Conclusion first. Coverage measures which lines and branches of the application source are actually executed by the tests. npm run test:python runs coverage run --branch --source=apps/api/src,workers/.../src -m pytest -q then coverage report --fail-under=69. The 69% threshold applies to line plus branch coverage of the API and worker source roots. 69% is deliberately not 90% or 100%: the suite prioritizes contract and boundary tests over exhaustive coverage of every service method. A separate source-inspection test reads the CI workflow file and asserts the coverage step actually runs before deploy — if someone removes the gate, that test fails.

Key facts

  1. Source scope — --source=apps/api/src/researchmate_api,workers/ai-worker/src/researchmate_worker; tests in tests/ are not counted in the numerator. So the 69% is “of the production source, how much is exercised by tests.”
  2. Branch coverage, not just lines — --branch forces both arms of if/else to be exercised. Line-only coverage would mark an if as covered if the true branch ran, even if the else branch (which might contain raise) never executed.
  3. Dev dependencies pinned — coverage>=7.10.0,<8, pytest>=9.0.0,<10 in root pyproject.toml; pyright==1.1.390, ruff==0.16.0 for type and lint gates.
  4. Contract test verifies the gate itself — test_release_pipeline.py::test_ci_runs_the_full_test_build_contract_and_security_gate reads the CI YAML file and asserts the coverage step is mandatory. The gate is guarded by a test that runs in the same suite.
  5. Hermetic keeps coverage real — no test is skipped for “infra unavailable.” Because every test uses fakes, every line executed in CI is reproducible locally. There is no scenario where coverage is high in CI but the suite does not run on a developer laptop.
[Project fact] Pre-commit hooks (.pre-commit-config.yaml) run ruff, ruff-format, and pyright locally before each commit; install with uv run pre-commit install. [Reasonable inference] The 69% threshold is intentionally below 90% — the suite prioritizes contract + boundary tests over exhaustive line coverage of every service method, which would require high maintenance for low marginal safety.
