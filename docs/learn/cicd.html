CI/CD . interview deep dive

After you push, CI does four things in parallel: runs Python tests with a 69% coverage gate, builds the frontend and runs its unit tests plus a dependency audit, runs Playwright end-to-end browser tests, and scans the Docker image for HIGH/CRITICAL CVEs. A fifth aggregator job, named ci-success, only goes green when all four are green; Render's deploy gate waits on that single job. Below: the pipeline's shape and the ci-success sentinel; pre-commit's ruff + pyright hooks reusing the locked uv environment; the SQL migration runner's advisory lock and SHA-256 ledger; and the 69% coverage threshold wired into npm run check:all.

Function-centered . GitHub Actions pipeline

Four parallel quality gates aggregated by a ci-success sentinel

In plain language: after a push, CI runs 4 things; Render deploys only after all 4 + ci-success go green
  • python-quality — Python tests + 69% coverage gate + ruff lint + pyright type-check + OpenAPI drift detection + migration file validation. When you add an API endpoint, CI catches if the committed OpenAPI spec and the rendered one diverge.
  • web-quality — Frontend production build + unit tests + npm audit dependency scan. When you bump a package, CI builds, runs unit tests, and blocks on a moderate-or-worse vulnerability in prod deps.
  • browser-e2e — Playwright runs end-to-end browser flows; on failure uploads the report artifact with 7-day retention for triage. When you change the login flow, CI verifies the whole user path in a real browser.
  • container-quality — lint the Dockerfile with hadolint, build the image with layer cache, scan with trivy for HIGH/CRITICAL CVEs. When you change the Dockerfile, CI scans the produced image for known CVEs.
  • ci-success — aggregator sentinel: runs if: always() after all four and asserts each result equals success. Render's checksPass deploy gate reads this job. One red gate anywhere = no deploy.

[Project fact] .github/workflows/ci.yml triggers on PR and on push to main / develop. concurrency: cancel-in-progress: true kills stale runs of the same branch. The four jobs above run in parallel; ci-success has needs: [all four] and if: always().

The pipeline is the single source of truth for release readiness — Render's autoDeployTrigger: checksPass waits on exactly these checks. The key design move: instead of letting GitHub implicitly reject the workflow when any job fails, the project runs an explicit aggregator job that asserts test "$RESULT" = success on each downstream job's result. Why this matters: GitHub's implicit "needs" treats continue-on-error: true jobs as non-blocking, so a sibling job that fails softly would slip past a default gate. The explicit assertions make the gate single, named, inspectable, and immune to soft failures.

Job-by-job (what each gate actually checks)
  • python-quality — npm run test:python (69% coverage gate), npm run check:types (pyright basic), npm run check:lint + check:openapi + check:migrations; install uses uv sync --frozen --all-packages --group dev. timeout 35 min. [Project fact]
  • web-quality — npm ci --no-audit --no-fund, npm run test:web, npm run check:web (production build), npm run check:audit (npm audit --omit=dev --audit-level=moderate). timeout 20 min. [Project fact]
  • browser-e2e — npx playwright install --with-deps chromium then npm run test:e2e; on failure uploads apps/web/playwright-report artifact (7-day retention). timeout 20 min. [Project fact]
  • container-quality — hadolint --ignore DL3008 on workers/ai-worker/Dockerfile, docker build-push-action with load: true, push: false + GHA cache, then aquasec/trivy:0.73.0 image --exit-code 1 --ignore-unfixed --severity HIGH,CRITICAL. timeout 25 min. [Project fact]
  • ci-success — if: always(), needs: [python-quality, web-quality, browser-e2e, container-quality]; runs four literal test "$X_RESULT" = success assertions. [Project fact]

python-quality — Python tests, types, lint, contracts

What it runs (5 steps, 35-min timeout):

  1. uv sync --frozen --all-packages --group dev — install locked Python deps. --frozen means uv.lock is the oracle; if the lockfile does not match pyproject.toml, the step fails. No silent resolution.
  2. npm run test:python — coverage run --branch --source=apps/api/src,workers/ai-worker/src -m pytest -q && coverage report --fail-under=69. Runs every test in tests/, measures branch coverage across both packages, and blocks if total coverage drops below 69%.
  3. npm run check:types — npx --yes pyright@1.1.390. Static type analysis in basic mode. Catches None-dereference risks, wrong argument types, and missing return annotations before runtime.
  4. npm run check:lint — ruff check apps/api/src workers/ai-worker/src tests. Lints all three trees with ruff 0.16.0 rules (UP, F, E, I, etc.). Any autofix-able violation that was not fixed locally fails the step.
  5. npm run check:openapi && npm run check:migrations — OpenAPI drift check: renders the FastAPI spec and compares it byte-for-byte with infra/openapi/openapi.yaml. Migration file check: validates every SQL file has a unique version prefix, is non-empty, and contains no drop database.

Principle: This job is the contract gate. Tests verify behavior; pyright verifies type safety; ruff verifies style consistency; OpenAPI check verifies the public API contract has not silently drifted; migration check verifies the database schema files are structurally valid. Together they form the "does the code do what it claims" gate that every other job depends on.

web-quality — Build, unit tests, dependency audit

What it runs (4 steps, 20-min timeout):

  1. npm ci --no-audit --no-fund — install from package-lock.json exactly. ci (not install) refuses to write the lockfile; if package.json and lockfile disagree, the step fails. --no-audit --no-fund skips the npm registry telemetry to save ~10s.
  2. npm run test:web — npm --workspace @researchmate/web run test. Runs Vitest unit tests for the frontend workspace. Tests cover component rendering, hook logic, and utility functions.
  3. npm run check:web — npm --workspace @researchmate/web run build. Full Next.js production build. If TypeScript compilation fails or a page has an import error, the build fails. This is the strongest signal that the frontend compiles cleanly.
  4. npm run check:audit — npm audit --omit=dev --audit-level=moderate. Scans production dependencies for known CVEs. --omit=dev skips devDependencies (not shipped). --audit-level=moderate means a moderate-or-worse CVE in a prod dep fails the step.

Principle: Build + test + audit. The build catches TypeScript and import errors that unit tests might miss (a component can be wrong but still importable). The audit catches supply-chain risk: a transitive dependency with a known vulnerability should block the release, not be discovered after deploy.

browser-e2e — Playwright browser acceptance test

What it runs (4 steps, 20-min timeout):

  1. npm ci --no-audit --no-fund — install web deps (same as web-quality).
  2. npx playwright install --with-deps chromium — download Chromium + OS-level browser dependencies (fonts, libs). Pinned to the Playwright version in package-lock.json.
  3. npm run test:e2e — starts a Next.js dev server on 127.0.0.1:3100 with NEXT_PUBLIC_DEMO_MODE=true, then runs apps/web/e2e/demo-workspace.e2e.ts against it.
  4. On failure only: uploads apps/web/playwright-report as a 7-day artifact (HTML report + traces + screenshots + video).

What the test actually checks in the browser:

The single test (demo-workspace.e2e.ts) exercises a complete user journey in a real Chromium instance. It does not stub the DOM — it clicks, types, drags, and reads rendered HTML. [Project fact]

  • Console + runtime error monitoring — listens to page.on("console") and page.on("pageerror") throughout the entire test. Any console error or uncaught exception makes the test fail at the end, even if the assertion that triggered it passed.
  • Network isolation — listens to every page.on("request") and records any request whose hostname is not 127.0.0.1. The test asserts externalRequests === [] at the end. This proves the demo mode does not accidentally call cloud APIs, LLM providers, or external CDNs.
  • Healthz mock — intercepts **/api/v1/healthz and returns {"status":"ok"}. The app's health check passes without a real backend.
  • Chat journey — navigates to /app?new=1, asserts the heading "What can I help with?" is visible, types a research question, clicks "Send message", then asserts the user's message and the AI's response (containing "retrieval is useful when evidence is relevant") both appear.
  • Citation drill-down — asserts a citation "1. Project source, page 3" is visible, clicks it, and asserts a detail panel with "Grounding and explicit source attribution" opens. Also asserts the URL changed to include ?conversation= (deep linking works).
  • Sidebar resize — finds the sidebar by ARIA role complementary (not by CSS class), finds the resize handle by ARIA role separator, drags it 72px, and polls until the sidebar width exceeds the original by 40px. This tests interactive layout, not just static rendering.
  • Project creation — clicks "New project", fills the name "E2E evidence workspace", clicks "Create", and asserts the URL matches /app/projects/[^/]+/chat?new=1 and the heading "Chat in E2E evidence workspace" appears.
  • Quiz generation — clicks "Quiz", asserts the quiz panel (ARIA role complementary, name "Project quiz") is visible, clicks "Generate quiz", and asserts a quiz question containing "What makes a retrieved conclusion defensible" appears.

Principles:

  • Deterministic demo mode — NEXT_PUBLIC_DEMO_MODE=true makes the app serve pre-baked responses without any backend, LLM provider, or credentials. The test is reproducible: no flaky API calls, no rate limits, no cost. [Project fact]
  • Accessibility-first assertions — every element is found by ARIA role and accessible name (getByRole("complementary", { name: "Workspace navigation" })), not by CSS class or test ID. This means the test validates semantic HTML structure. If a developer removes an aria-label, the test breaks — catching accessibility regressions for free. [Project fact]
  • Browser error as test failure — the test does not just check "did the right text appear." It checks "did the browser stay clean the entire time." A console error from a lazy-loaded component that renders after the assertion still fails the test. [Reasonable inference]
  • CI-specific Playwright config — in CI: forbidOnly: true (no test.only escapes), 2 retries, 1 worker (serial, no parallel browser instances), HTML reporter for artifact upload, trace/screenshot/video retained on failure. [Project fact]

container-quality — Dockerfile lint, image build, CVE scan

What it runs (3 steps, 25-min timeout):

  1. hadolint --ignore DL3008 — lints workers/ai-worker/Dockerfile via the official hadolint Docker image. DL3008 (pin apt package versions) is suppressed because the base image python:3.13-slim manages its own apt versions. Other rules (DL3005 --no-install-recommends, DL3059 no --chown on COPY) still apply.
  2. docker build-push-action with load: true, push: false — builds the image locally (does not push to a registry). Uses GHA layer cache (cache-from: type=gha, cache-to: type=gha,mode=max) so repeated builds reuse layers. The image is tagged researchmate-render:ci.
  3. trivy image --exit-code 1 --ignore-unfixed --severity HIGH,CRITICAL — scans the built image's layer filesystem for known CVEs in installed system packages and Python packages. --ignore-unfixed skips CVEs that have no upstream fix yet (reduces noise). --exit-code 1 means any HIGH or CRITICAL CVE with a fix available fails the step.

Principle: The Dockerfile is the exact artifact that Render deploys. Linting it catches Dockerfile anti-patterns (missing --no-install-recommends, running as root, large layer waste). Building it proves the image compiles. Scanning it catches known vulnerabilities in the OS-level and Python-level packages before they reach production. The scan uses --ignore-unfixed because flagging unfixable CVEs creates alert fatigue without actionable remediation.

ci-success — the aggregator sentinel

What it runs (1 step, no timeout pressure):

  1. Four literal test "$X_RESULT" = success assertions, one per upstream job. If any returns non-zero (i.e., any job's result is not success), the step fails and ci-success goes red.

Principle: GitHub's needs graph treats continue-on-error: true jobs as non-blocking — a soft-fail sibling would not block downstream needs. The explicit assertions bypass this: ci-success runs if: always() (so it runs even if siblings fail) and checks each result literally. Render's autoDeployTrigger: checksPass reads this single job's conclusion. One red gate anywhere = no deploy.

On-demand workflows — evaluation gate and recovery benchmark

Beyond ci.yml, the repo has two workflow_dispatch workflows that run on manual trigger, not on push. [Project fact]

  • evaluation-release-gate — triggered with an evaluation_run_id input. Calls scripts/check_evaluation_gate.py, which fetches the evaluation run's aggregate result from the dev API, checks six conditions (status=succeeded, summary.complete, execution_succeeded, quality_passed, no regression, pipeline_code_sha matches), and compares three metric thresholds (evidence_recall ≥ 0.80, retrieval_mrr ≥ 0.50, retrieval_ndcg ≥ 0.80). The gate step uses continue-on-error: true so the artifact upload always runs; a final test "$GATE_OUTCOME" = success step enforces the decision. [Project fact]
  • langgraph-recovery-benchmark — triggered with a trials input (default 1000). Spins up a postgres:16 service container, runs scripts/measure_langgraph_recovery.py which forks child processes that write LangGraph checkpoints, kill the process, and attempt recovery. Asserts the recovery rate's 95% confidence interval lower bound is ≥ 99.5%. [Project fact]
Risks worth naming (1) The evaluation-release-gate workflow uses continue-on-error: true on its gate step — gh run watch misreports that step as failed even when the workflow conclusion is success; read gh run view --json conclusion instead. (2) cancel-in-progress: true is keyed on github.ref, so two PRs run in parallel and only same-branch pushes kill each other. [Reasonable inference]

Interview question tree

Why an explicit ci-success job instead of letting GitHub reject on any failed job?
└─ What partial-failure scenario does `if: always()` guard against?
   └─ How does Render's checksPass actually consume this job's result?
Answer: A sibling job with `continue-on-error: true` would not fail a default
`needs` graph, because GitHub treats soft-fail as success. ci-success runs after
all four (`if: always()`), asserts each `result == success` literally, and
exposes a single job whose status Render can pin on. Render reads that job's
conclusion, not the workflow's.

Why split into exactly four parallel jobs instead of one big job?
└─ What does each job's isolation buy (cache, runner, timeout)?
   └─ Why is container-quality (trivy + hadolint) a separate gate?
Answer: Parallel jobs have separate runners, so a slow Python test does not
block web build. Caches stay per-stack (uv vs npm). Timeouts are tuned per
job. container-quality is separate because it produces a Docker image that
every later prod restart depends on, so scanning it standalone catches CVEs
even before code tests run.

How does cancel-in-progress avoid wasted CI spend?
└─ What is the concurrency group keyed on, and what does that mean for two open PRs?
   └─ What happens to an already-running workflow when you force-push to the same branch?
Answer: Group keyed on `github.ref`. Two PRs run in parallel (different refs);
a new push to the same branch cancels the previous run on that branch. Saves
minutes when you push a fix while the previous run is still mid-flight.

Tech-stack-centered . Pre-commit hooks

ruff + pyright reuse the locked uv environment, plus hygiene hooks

[Project fact] .pre-commit-config.yaml has three repos: pre-commit-hooks v5.0.0 (merge-conflict, EOF, YAML/TOML, trailing-whitespace), ruff-pre-commit v0.16.0 (lint + autofix, format check), and a local pyright hook. Every Python hook uses language: system to reuse the uv-managed Python environment.

The point of pre-commit is not "run a linter" — it's to shift left the exact same pinned tool versions that CI runs. Imagine a contributor whose pre-commit hook succeeds locally, pushes, and the CI lint step unexpectedly fails because their laptop has a newer ruff that flags rules CI's older ruff does not. That drift is what the project eliminates. Because ruff (0.16.0) and pyright (1.1.390) are pinned in uv.lock, and the hooks run via language: system (which calls the uv-managed Python directly instead of pre-commit building a fresh venv), local and CI use literal bit-identical tool versions.

Key mechanisms
  • ruff: check --force-exclude --fix, files: \.py$, pass_filenames: false. Autofix is on; if a fix rewrites a file, pre-commit marks the commit failed and the author re-stages. [Project fact]
  • ruff-format: --check only — formatting is not auto-applied at commit time; you must run ruff format yourself. Strictly catches drift. [Project fact]
  • pyright local hook, entry pyright, pass_filenames: false, no file filter; reads root pyproject.toml with typeCheckingMode = "basic". Same invocation as CI's npm run check:types. [Project fact]
  • Hygiene hooks — check-merge-conflict --assume-in-merge, end-of-file-fixer, check-yaml --allow-multiple-documents, check-toml, trailing-whitespace. [Project fact]
Gotcha to flag hooks that auto-fix files cause the commit to fail with the message "files were modified by this hook." That is not a real error — re-stage the fixed files and retry the commit. Forgetting this trips up new contributors. [Reasonable inference]

Interview question tree

Why `language: system` instead of pre-commit's default managed virtualenv?
└─ What does it gain that a pre-commit-managed env cannot?
   └─ How does that coupling with uv.lock reduce CI/local drift?
Answer: A pre-commit-managed env builds its own ruff/pyright, so the local
version can drift from uv.lock. `language: system` calls the uv-managed
Python, which is pinned to exactly the bytes CI installs via `uv sync --frozen`.

Why is ruff-format check-only at commit time when ruff --fix is on?
└─ What is the trade-off between autofix and check-only?
   └─ How would you enforce format on commit if you wanted to?
Answer: autofix rewrites unsafe rules automatically (less friction, but you
can commit changes you didn't review). format check-only refuses to apply
and forces the author to run `ruff format` themselves, which guarantees they
look at the diff. To enforce apply-on-commit, swap `--check` for nothing and
re-stage on the hook's modified-file failure.

What does `pass_filenames: false` buy in the ruff hook?
└─ Why not let pre-commit pass only the changed files to ruff?
   └─ What goes wrong with --force-exclude in that case?
Answer: The hook calls ruff on the whole target tree regardless of changed
files. Pre-commit passing only changed files means a rename or move can let
a no-longer-passed file slip un-linted. Whole-tree invocation keeps ruff's
--force-exclude semantics predictable.

Function-centered . Database migration strategy

Additive SQL files, SHA-256 ledger, advisory lock, idempotent statements

[Project fact] scripts/apply_migrations.py enforces unique version prefixes, rejects empty files and drop database, then (when ALLOW_SCHEMA_APPLY=1) acquires pg_advisory_xact_lock(726_334_129) and applies unapplied files in order, stamping each with a SHA-256 into researchmate_schema_migrations.

Picture the danger: an operator runs a script that alters a tenant table in production while another instance of the same script runs at the same time, racing the schema into an inconsistent state. Or worse: someone edits a migration file that already ran in prod, thinking the change will pick up cleanly — instead the prod DB and the migration ledger no longer agree on what was applied.

The migration runner stacks four defenses so re-running against a live database is safe. First, the apply path acquires a transaction-scoped advisory lock; two apply attempts cannot both proceed. Second, the researchmate_schema_migrations table records each applied file's SHA-256; an already-applied file whose bytes later changed raises RuntimeError and aborts. Third, the validator bans empty files and the literal string drop database. Fourth, the SQL itself is written idempotently with if not exists / drop policy if exists ... create policy, so re-running a file in a transaction never double-applies.

Key mechanisms
  • pg_advisory_xact_lock(726_334_129) — transaction-scoped; any concurrent apply on the same Postgres is blocked until the first commits or rolls back. The integer is a hardcoded magic number in apply_migrations.py. [Project fact]
  • researchmate_schema_migrations — (version text primary key, checksum_sha256 text not null, applied_at timestamptz); created with create table if not exists inside the same transaction. If applied.get(name) != sha256(source), raise RuntimeError and abort. [Project fact]
  • --check-files vs --apply — --check-files is the CI-only validation (no DB access); --apply requires ALLOW_SCHEMA_APPLY=1 and DATABASE_URL, which is the human approval gate. CI runs npm run check:migrations = --check-files. [Project fact]
  • Idempotent SQL style — every create table / create index / create policy uses if not exists or a drop policy if exists ... create policy pair; example: 202608010010_api_idempotency.sql creates api_idempotency with PK (user_id, operation, idempotency_key) and a state-machine CHECK constraint. [Project fact]
Why additive only The validator rejects drop database and empty files, but does not block alter table drop column. The project's actual discipline is forward-only migrations: any change to an existing column ships as a new migration file rather than editing one that already ran. The SHA-256 ledger is the enforcement mechanism: editing an applied file's bytes fails the runner. [Reasonable inference]

Interview question tree

Why an advisory lock instead of a row lock on a migrations table?
└─ What does transaction-scoped mean for the lock's lifecycle?
   └─ What would a `SELECT ... FOR UPDATE` on a sentinel row change?
Answer: A sentinel-row lock needs a real row; deleting it skips the lock.
Advisory locks are keyed on an integer and need no row. Transaction-scoped means
the lock dies with the transaction — commit or rollback releases it, so a
crashed runner cleans up automatically via rollback.

How does the SHA-256 checksum protect against drift?
└─ What does the runner do if an applied file's content changes?
   └─ If you legitimately need to fix an applied migration, what is the project's process?
Answer: Raise and abort. The process is never edit an applied file — write a
new forward migration that adds the column or undoes the prior behavior. Editing
in place would silently desync prod from the committed file list.

Why split --check-files (CI) and --apply (operator) into two modes?
└─ What does ALLOW_SCHEMA_APPLY=1 specifically guard against?
   └─ Could a CI job ever run --apply by mistake?
Answer: --check-files reads file bytes only; --apply opens a database
connection and writes schema. ALLOW_SCHEMA_APPLY=1 forces a human to set the
env explicitly before any DB write can happen, which blocks a CI job
(inheriting no such env) from touching prod. CI runs --check-files; only the
operator with prod secrets can run --apply.

Tech-stack-centered . Coverage gate & check:all

69% threshold wired into npm run check:all

[Project fact] package.json defines test:python as uv run --frozen coverage run --branch --source=apps/api/src/researchmate_api,workers/ai-worker/src/researchmate_worker -m pytest -q && uv run --frozen coverage report --fail-under=69; check:all chains test, lint, types, openapi, migrations, web build, and audit.

Coverage is a number between 0 and 100 that says "of the lines or branches your tests could have exercised, what fraction actually ran during the test suite." A 100% number means every line and every branch of every if ran at least once during tests. The project pins a 69% floor. When coverage drifts below 69%, coverage report --fail-under=69 exits non-zero and the python-quality CI step fails.

Why 69% in particular? [Project fact] The number is a literal in package.json, not derivable from a benchmark. [Reasonable inference] It reflects the achievable coverage on the current code surface when branches (not just lines) are counted — the project uses --branch, so partial branches count as uncovered. A partial branch is an if x: A else: B where tests only took one of A or B; the missing side is counted uncovered.

check:all composition
  • test = test:python && test:web — Python (with the 69% gate) and web workspace tests must both pass. [Project fact]
  • check:lint = uv run --frozen ruff check apps/api/src workers/ai-worker/src tests. [Project fact]
  • check:types = npx --yes pyright@1.1.390 — version pinned to match pre-commit. [Project fact]
  • check:openapi = uv run --frozen python scripts/export_openapi.py --check — rendered OpenAPI must match the committed infra/openapi/openapi.yaml; drift fails. [Project fact]
  • check:migrations = uv run --frozen python scripts/apply_migrations.py --check-files — CI-safe file validation only, no DB write. [Project fact]
[Optimization suggestion] The 69% threshold is project-specific and not benchmarked. Consider running coverage report --skip-covered in dev to surface the most valuable gaps, and raising the floor in 1–2 point increments as coverage grows rather than resetting after a regression.

Interview question tree

Why branch coverage (--branch) instead of line coverage?
└─ What does a partial branch count as — covered or uncovered?
   └─ Why is 69% a believable number instead of 100%?
Answer: A partial branch has one side untested; --branch counts that side as
uncovered. 100% is unrealistic on a real codebase because some branches are
defensive-only (error paths, framework stubs) and never fire in tests. 69% is
the project's current measurable floor, not an aspirational target.

Why wire the OpenAPI --check into check:all?
└─ What kind of drift would it catch that tests would not?
   └─ When would you legitimately want to skip it?
Answer: It catches drift between the committed OpenAPI spec and what
FastAPI would render. Tests rarely exercise every endpoint shape; an author
can change a response model, tests still pass, and the public contract has
silently broken. Skip only during a known, intentional contract migration
that ships in the same PR.

Why is the same ruff and pyright pinned in three places (uv.lock, .pre-commit, CI npx)?
└─ What failure mode does each pin defend against?
   └─ What goes wrong if CI's pyright version drifts ahead of pre-commit's?
Answer: CI npx pins `pyright@1.1.390` so a fresh CI runner without uv cache
still gets the exact version. uv.lock pins the same for local installs.
.pre-commit pins via the same uv environment. If CI drifts ahead, a hook can
pass locally and CI fails — exactly the drift the design exists to prevent.
