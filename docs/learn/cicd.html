CI/CD . Pipeline & deployment

ResearchMate ships through a five-job GitHub Actions pipeline that gates every push and pull request, two multi-stage Dockerfiles that produce hardened container images, and a single Render Free service that auto-deploys when CI checks pass. This page walks through every configuration file that defines the build, test, scan, and deploy lifecycle.

Technology stack fundamentals

7 tools that define the build and deploy lifecycle

Each card explains what the tool does in general and how ResearchMate uses it specifically.

CI/CD

Continuous Integration / Continuous Deployment is the practice of automatically testing, building, scanning, and deploying every code change through a reproducible pipeline. ResearchMate treats CI as the single source of truth for release readiness: no commit reaches production unless all five gate jobs pass and the ci-success aggregator confirms every result equals success.

GitHub Actions

Workflow automation platform triggered on push to main or develop and on every pull request. The researchmate-ci workflow uses a concurrency group with cancel-in-progress to kill stale runs, pins every action to a major version, and runs five jobs with explicit timeout-minutes ranging from 20 to 35 minutes. The ci-success job uses if: always() with needs to aggregate all four quality gates.

Docker

Containerization engine producing reproducible runtime images. Both Dockerfiles use multi-stage builds with a pinned uv stage and python:3.13-slim base. Layered COPY directives separate dependency manifests from source code to maximize build-cache hits. The API image runs as a non-root user (uid 10001); the worker image adds system libraries and pre-downloads Docling models. CI validates both with hadolint and Trivy.

Render

Cloud deployment platform hosting the combined backend-plus-worker service as a single Free-tier Docker web service in the Oregon region. render.yaml declares one envVarGroups block with 48 entries (37 with values, 11 sync:false secrets), an autoDeployTrigger of checksPass, and a buildFilter that limits rebuilds to relevant path patterns. The healthCheckPath /api/v1/readyz confirms runtime readiness.

Vercel

Frontend deployment platform for the Next.js 16.3.0 web application in apps/web. Vercel builds and serves the production frontend independently from the backend. CORS_ALLOWED_ORIGINS in render.yaml is set to the Vercel origin so the API accepts browser requests from the deployed frontend.

uv

Python package manager and project manager by Astral, pinned to version 0.12.1 in both CI and Dockerfiles. uv resolves the monorepo workspace (apps/api + workers/ai-worker), installs locked dependencies via uv.lock with the --frozen flag, and supports --all-packages for installing every workspace member in one command. The setup-uv action enables caching in CI for faster runs.

npm workspaces

JavaScript monorepo management with npm 11.6.0 declared via packageManager in the root package.json. The workspaces array includes apps/web. CI runs npm install --no-audit --no-fund to install the full workspace tree, and the package-lock.json lockfile guarantees reproducible JavaScript dependency resolution across local and CI environments.

CI/CD workflow

From commit to production: five quality flows and deployment elevation chain

Every push to main/develop and every pull request follows the same gate chain. State transitions follow the planned → ready → executed → verified four-state model: the first four parallel gate Jobs verify the source artifact in the ready phase, and the ci-success aggregation gate confirms all succeeded in the verified phase. Only after the aggregation gate passes does Render's autoDeployTrigger: checksPass trigger the production deployment elevation—establishing a hard dependency between CI green light and production deployment.

Why this topology works

Four independent quality flows run in parallel instead of sequentially, compressing wall-clock time from 100 minutes to 35 minutes (the longest path). The ci-success aggregation gate uses if: always() to ensure explicit result reporting even when upstream fails, rather than silently skipping. Render's checksPass establishes a hard dependency between CI green light and production deployment — a green build does not mean it has been elevated; only the aggregation gate passing triggers deployment. buildFilter restricts rebuilds to relevant path changes, preventing pure documentation changes from triggering unnecessary backend rebuilds.

Dockerfile . API

apps/api/Dockerfile . two-stage, non-root, health-checked

The API Dockerfile produces a slim production image that runs uvicorn behind Render's managed proxy. It prioritizes cache efficiency, least-privilege execution, and built-in health verification.

Multi-stage build

Stage 1 copies the uv and uvx binaries from ghcr.io/astral-sh/uv:0.12.1. Stage 2 builds the runtime on python:3.13-slim. The uv binary is copied as a static asset, so the final image carries no build toolchain.

Non-root user

Creates a dedicated group researchmate (gid 10001) and user (uid 10001) with --no-create-home --shell /usr/sbin/nologin. The USER 10001:10001 directive ensures the process never runs as root inside the container.

Layered COPY

Dependency manifests are copied before source code: pyproject.toml uv.lock first, then apps/api/pyproject.toml and workers/ai-worker/pyproject.toml, then apps/api source. This ordering lets Docker cache the uv sync layer and invalidate it only when dependencies change.

uv sync

uv sync --frozen --no-dev --package researchmate-api installs exactly the locked production dependencies for the API workspace member, skipping dev tools and refusing lockfile drift.

HEALTHCHECK

--interval=30s --timeout=5s --start-period=20s --retries=3 calls python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/api/v1/healthz', timeout=3)". Three consecutive failures mark the container unhealthy.

CMD (shell form)

sh -c "exec python -m uvicorn researchmate_api.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 2 --proxy-headers". Shell form is required so Render's runtime PORT value expands safely. The --proxy-headers flag trusts Render's load-balancer X-Forwarded-* headers.

FROM ghcr.io/astral-sh/uv:0.12.1 AS uv FROM python:3.13-slim AS runtime COPY --from=uv /uv /uvx /bin/ RUN groupadd --gid 10001 researchmate \ && useradd --uid 10001 --gid researchmate --no-create-home --shell /usr/sbin/nologin researchmate COPY pyproject.toml uv.lock /app/ COPY apps/api/pyproject.toml /app/apps/api/pyproject.toml COPY workers/ai-worker/pyproject.toml /app/workers/ai-worker/pyproject.toml COPY apps/api /app/apps/api RUN uv sync --frozen --no-dev --package researchmate-api USER 10001:10001 EXPOSE 8000 HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \ CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/api/v1/healthz', timeout=3)"] CMD ["sh", "-c", "exec python -m uvicorn researchmate_api.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 2 --proxy-headers"]

Dockerfile . Worker

workers/ai-worker/Dockerfile . three-stage, system deps, role switching

The worker Dockerfile builds the CPU-only combined backend-plus-worker runtime used by Render's Free tier. It adds system libraries for Docling, pre-downloads ML models, and switches between dispatcher and worker roles via an environment variable.

Three stages

Stage 1 (uv) copies the uv binary. Stage 2 (dependencies) installs system packages and Python dependencies on python:3.13-slim. Stage 3 (runtime) extends dependencies to download Docling models and set ownership, keeping the model artifacts in a separate cacheable layer.

System dependencies

apt-get install --yes --no-install-recommends libgl1 libglib2.0-0 provides the shared libraries that Docling and OpenCV require for PDF rendering and image processing. The apt cache is cleaned immediately to minimize image size.

Docling models

docling-tools models download layout tableformer rapidocr -o /opt/docling/models pre-fetches three model bundles into DOCLING_ARTIFACTS_PATH=/opt/docling/models. chown -R researchmate:researchmate /opt/docling ensures the non-root user can read them at runtime.

--all-packages

uv sync --frozen --no-dev --all-packages installs every workspace member (researchmate-api + researchmate-worker) in one resolved graph. This is required because Render runs the combined runtime via python -m researchmate_worker.render_combined, which imports both packages.

Role switching

The CMD inspects RESEARCHMATE_PROCESS_ROLE. When set to dispatcher, it runs exec researchmate-dispatch-outbox. Otherwise it starts a Celery worker consuming 5 queues (ingestion, deletion, workflow, evaluation, reliability) with --concurrency=2.

torch CPU index

The worker pyproject.toml pins torch==2.13.0+cpu and torchvision==0.28.0+cpu via [tool.uv.sources] pointing to the pytorch-cpu index. This avoids pulling CUDA drivers on Free-tier hosts that have no GPU.

FROM ghcr.io/astral-sh/uv:0.12.1 AS uv FROM python:3.13-slim AS dependencies COPY --from=uv /uv /uvx /bin/ RUN apt-get update \ && apt-get install --yes --no-install-recommends libgl1 libglib2.0-0 \ && rm -rf /var/lib/apt/lists/* COPY pyproject.toml uv.lock /app/ COPY apps/api /app/apps/api COPY workers/ai-worker /app/workers/ai-worker RUN uv sync --frozen --no-dev --all-packages FROM dependencies AS runtime RUN docling-tools models download layout tableformer rapidocr -o /opt/docling/models \ && chown -R researchmate:researchmate /opt/docling USER 10001:10001 CMD ["sh", "-c", "if [ \"${RESEARCHMATE_PROCESS_ROLE:-worker}\" = dispatcher ]; then exec researchmate-dispatch-outbox; \ else exec python -m celery -A researchmate_worker.celery_app:celery_app worker --loglevel=INFO \ --queues=ingestion,deletion,workflow,evaluation,reliability --concurrency=2; fi"]

Dependency management

Dual-lock strategy across Python and JavaScript

ResearchMate manages dependencies with two independent lockfiles: uv.lock for the Python workspace and package-lock.json for the npm workspace. Both are committed to the repository and used with --frozen flags in CI and Docker to guarantee reproducible installs.

Root package.json

Declares packageManager: npm@11.6.0 and workspaces: ["apps/web"]. Defines 17 scripts including test:python, test:web, test:e2e, check:lint, check:openapi, check:migrations, check:web, check:audit, and the umbrella check:all. The private flag prevents accidental npm publish.

Root pyproject.toml

Declares the uv workspace (members = ["apps/api", "workers/ai-worker"]) and the dev dependency group: coverage>=7.10.0,<8, httpx2>=2.5.0,<3, pre-commit>=4.2.0,<5, pytest>=9.0.0,<10, pyyaml>=6.0.0,<7, ruff==0.16.0. A dedicated pytorch-cpu index is declared for torch CPU wheels. The pinned pyright==1.1.390 is no longer in this dev group: npm run check:types now invokes npx --yes pyright@1.1.390. A new [tool.pyright] section configures the project-wide type checker with typeCheckingMode = "basic", venvPath = ".", venv = ".venv", pythonVersion = "3.13", and include/exclude path lists.

apps/api/pyproject.toml

17 production dependencies including FastAPI, Pydantic, SQLAlchemy, psycopg, PyJWT, qdrant-client, redis, boto3, OpenAI SDK, Langfuse, and four OpenTelemetry packages (opentelemetry-api, opentelemetry-exporter-otlp-proto-http, opentelemetry-instrumentation-fastapi, opentelemetry-sdk). Ruff is configured with line-length=100 and ignores B008 and BLE001.

workers/ai-worker/pyproject.toml

18 production dependencies including Celery[redis], Docling (pinned 2.111.0), LangGraph, RAGAS 0.4.3, torch 2.13.0+cpu, torchvision 0.28.0+cpu, and pypdf. Declares the researchmate-dispatch-outbox console script. Sources torch and torchvision from the pytorch-cpu index.

apps/web/package.json

Next.js 16.3.0 with React, 10 Radix UI primitives, Tailwind CSS 4, lucide-react, and class-variance-authority. Dev tools: Vitest 4 with coverage-v8, Playwright 1.62, TypeScript 6.0.3, jsdom. The type: module flag enables ESM.

Dual-lock strategy

uv.lock pins the complete Python dependency graph (including transitive deps and the pytorch-cpu index). package-lock.json pins the npm workspace tree. CI and Dockerfiles use --frozen (uv) and npm install (reads lockfile by default). Neither lockfile is edited manually; both are regenerated by their respective package managers.

Quality gates & AI guidance

Two new root-level files codify the local quality and code-generation gates. The new .pre-commit-config.yaml installs three hook groups through the locked uv environment (language: system): built-in checks (merge-conflict, end-of-file-fixer, check-yaml, check-toml, trailing-whitespace), ruff with --fix + ruff-format --check on apps/api/src workers/ai-worker/src tests, and a local pyright hook that reuses the [tool.pyright] config. The new root AGENTS.md file orients AI coding tools (CodeAgentCLI, Cursor, Copilot, Codex) to ResearchMate's standards: from __future__ import annotations on every module, full type hints, snake_case/PascalCase/SCREAMING_SNAKE_CASE naming, fail-closed error handling at boundaries, English-only comments, no unjustified typing.Any, domain constants instead of magic numbers, and the npm run check:* gate commands.
