Wiki-guided Hybrid RAG / MCP / LangGraph

AI agent stack . Retrieval, Protocol, Orchestration

ResearchMate's AI agent stack is a cohesive subsystem spanning the FastAPI backend and the Celery worker. Four foundations compose it: a Wiki-guided Hybrid RAG retriever that compiles LLM-structured Wiki pages as a first retrieval layer; a routed Hybrid RAG retriever that chooses among five observable routes before fused retrieval and dual rerank; an MCP server that exposes six tools and three resources over Streamable HTTP under the same bearer auth as REST; and a LangGraph evidence workflow that orchestrates a six-node stateful graph with parallel fan-out, PostgreSQL checkpointing, and human-in-the-loop review. This page goes file-by-file through every component, decision tree, and integration seam.

Technology stack fundamentals

Three foundations of the AI agent stack

Each card explains what the technology does in general and how ResearchMate uses it specifically.

Routed Hybrid RAG

Retrieval-augmented generation with an observable five-route planner. query_planning.py classifies each question into FULL_CONTEXT, EXACT, SEMANTIC, HYBRID, or EXPANDED_HYBRID before any vector search runs. Qdrant native BM25 + dense branches feed weighted RRF fusion in qdrant_hybrid_query.py. A three-provider rerank coordinator (QdrantNativeReranker → NvidiaReranker → DeterministicReranker) in rerank.py applies late-interaction reranking with deterministic fallback.

MCP

Model Context Protocol server built on FastMCP. mcp_server.py exposes six tools (list_projects, search_project, search_conversation, ask_grounded, get_run_trace, run_evaluation) and three resources (project://{project_id}/documents, conversation://{conversation_id}/documents, run://{run_id}) over stateless Streamable HTTP, authenticated by the same bearer middleware as REST. The SDK is optional — when absent, /mcp returns 503 MCP_RUNTIME_NOT_INSTALLED.

LangGraph

Stateful graph orchestration library. evidence_graph.py builds a six-node StateGraph (plan, retrieve_and_extract, reconcile, human_review, synthesize, validate_and_commit) with conditional fan-out via Send. Checkpoints persist to PostgreSQL via PostgresSaver with JsonPlusSerializer(pickle_fallback=False). The interrupt() primitive pauses for human review without try/except wrapping, and the Celery run_workflow task resumes via Command(resume=...).

Routed retrieval

Routed Hybrid RAG . five routes, RRF fusion, dual rerank

The retrieval pipeline is not a single vector search. A deterministic planner classifies the question first, then Qdrant fuses sparse and dense branches with weighted RRF, and a three-provider rerank coordinator applies late-interaction scoring before context packing.

Five-route decision tree

The RetrievalRoute StrEnum in apps/api/src/researchmate_api/services/query_planning.py names each observable policy. plan_retrieval() evaluates the decision tree in order — the first match wins:

#RouteDense / LexicalTriggerReason field
1FULL_CONTEXT0.0 / 0.0corpus_tokens <= full_context_limit (default 12000)entire_authorized_corpus_fits
2EXPANDED_HYBRID0.55 / 0.45Pronoun/reference pattern + conversation history, or multiple ?/？ marksconversation_or_compound_query_expanded
3EXACT0.30 / 0.70_EXACT_PATTERN matches: quoted text, uppercase identifiers, numeric tokensidentifier_quote_or_numeric_constraint
4SEMANTIC0.70 / 0.30_SEMANTIC_PATTERN matches: why, how, explain, 为什么, 原理, 机制conceptual_or_explanatory_intent
5HYBRID0.50 / 0.50Fallback when no prior pattern matchesbalanced_default
Why five routes? Small relevant corpora benefit from full context (no vector search needed); larger corpora need explicit routing so exact identifiers do not lose to embeddings and paraphrases do not lose to lexical mismatch. The planner is deterministic — only EXPANDED_HYBRID calls the LLM, and only when conversation references or compound questions genuinely need rewriting.

Expansion via bounded LLM call

When EXPANDED_HYBRID triggers, _expanded_plan() sends the last four conversation messages plus the current question to the chat provider with a system prompt asking for a standalone query and up to two alternative search formulations. The response is validated by the _ExpansionOutput pydantic model (standalone_query + variants, extra="forbid"). If the provider is unconfigured or returns invalid JSON, _degraded_expansion() preserves the original query with degraded=True. Constants: MAX_QUERY_VARIANTS = 3, MAX_QUERY_CHARS = 600.

Qdrant native hybrid query . RRF fusion

execute_hybrid_query() in apps/api/src/researchmate_api/services/qdrant_hybrid_query.py fuses sparse and dense branches per query variant:

BM25 sparse branchQdrant native sparse/BM25 model with Prefetch sub-query per variant
Dense branchNVIDIA embedding vector with Prefetch sub-query per variant
RRF fusionQdrant Reciprocal Rank Fusion with per-branch weights derived from plan.dense_weight and plan.lexical_weight divided by the number of query variants. Branch limit = max(limit * 3, 20).

Owner-scoped payload filters (user_id, project_id, source_type) are applied on every prefetch and final query. When qdrant_native_hybrid_enabled is False, the system falls back to application-level BM25 (bm25_candidates() in retrieval.py) with CJK bigram tokenization, title boosting, and exact-match bonus, fused by fuse_candidates() with RRF k=60.

Dual rerank coordinator . three providers

RerankCoordinator in apps/api/src/researchmate_api/services/rerank.py chains three rerankers with explicit degradation:

ProviderImplementationMechanismFallback target
QdrantNativeRerankerQdrant late-interaction model in a dedicated rerank collectionrerank_query() on the rerank collection with multi vector typeNVIDIA
NvidiaRerankerNVIDIA ranking API (/v1/ranking)HTTP POST with passages, returns ranked indicesDeterministic
DeterministicRerankerLocal tie-breakingSorts by (score, has_lexical_rank, -lexical_rank)—

The execute() method accepts provider as "auto" | "qdrant" | "nvidia" | "deterministic". In "auto" mode it tries Qdrant first, then NVIDIA, then deterministic. WEB_PAGE source-type candidates skip the Qdrant reranker (it only handles LOCAL_DOC). The provider is selected at runtime from the database via repository.get_runtime_rerank_config() (called in grounded_query.py).

Wiki-guided Hybrid RAG

LLM Wiki compilation . three-layer retrieval architecture

ResearchMate now adds an LLM-compiled structured Wiki layer as the first retrieval tier. When a document is ingested, a WikiCompiler synthesizes a concise overview page that captures section headings, key concepts, and relationships; each Wiki page carries structured references back to source chunks. At query time, the planner checks whether Wiki candidates exist before routing — if they do and the route is FULL_CONTEXT or SEMANTIC, Qdrant is skipped entirely and Wiki chunks are returned directly (score=1.0, reason="wiki_first_routing"). EXACT queries still flow through the full RAG pipeline; HYBRID and EXPANDED_HYBRID run dual-path parallel with a 50/50 budget split.

Wiki compilation modes

Short-document mode (≤4000 tokens)

Documents below the WIKI_COMPILE_TOKEN_THRESHOLD boundary get a full Wiki compilation: the LLM produces a single WikiPage that replaces original chunks in retrieval results (has_vector=false). The compiled Wiki preserves all factual content in a condensed structured format.

Long-document overview (>4000 tokens)

Larger documents trigger compile_overview(): the LLM generates a high-level overview page sampled to WIKI_OVERVIEW_MAX_INPUT_TOKENS = 6000 token budget. The overview Wikipedia page is appended alongside Qdrant RAG blocks (has_vector=false for overview, has_vector=true for RAG blocks). This keeps the overview compact while preserving deep evidence from the full RAG pipeline.

Wiki-first routing decision tree

The router in query_planning.py checks for Wiki candidates after determining the route. The decision logic:

FULL_CONTEXT or SEMANTIC + Wiki existsSkip Qdrant entirely; return Wiki chunks with score=1.0 and reason="wiki_first_routing". No vector search cost.
EXACT queryFull RAG pipeline regardless of Wiki presence — exact identifier matching takes priority. Wiki chunks are appended but scored 0.0.
HYBRID or EXPANDED_HYBRIDDual-path parallel: 50% token budget to Wiki chunks, 50% to Qdrant RAG. Results merged via weighted RRF.
No Wiki or compilation failedGraceful degradation — fall through to standard RAG pipeline as if Wiki layer never existed.

Structured references for traceability

Every WikiPage dataclass carries a references: list[dict] field where each entry contains {document_id, section_title, page_no, chunk_id}. The wiki_pages_to_chunks() helper converts these into ChunkEntry-compatible metadata with a wiki_references key, so every citation in the final answer can be traced back through the Wiki page to the exact source location within the S3-stored PDF or PPTX.

Graceful degradation contract

Wiki compilation failure fallback: If the LLM provider is misconfigured, returns invalid JSON, or times out, WikiCompiler.compile() catches the exception and returns [] (no Wiki candidates). The downstream router sees an empty wiki list and falls through to standard Qdrant RAG without any behavioral change. The Wiki layer is an optimization, not a correctness requirement.

Wiki-first routing strategy

Wiki-first routing

When Wiki candidates exist AND query route is FULL_CONTEXT or SEMANTIC, skip Qdrant entirely and return Wiki chunks (score=1.0, reason="wiki_first_routing"). EXACT queries still go through full RAG pipeline.

Graceful degradation

Wiki compilation failure is non-blocking — system falls back to original RAG blocks without error propagation.

Structured references: Each WikiPage carries a references: list[dict[str, object]] field mapping back to source evidence with {document_id, section_title, page_no, chunk_id}. This enables traceability from synthesized Wiki knowledge back to raw source fragments while maintaining a clean separation between navigation aids and proof-bearing evidence.

Model Context Protocol

MCP server . Streamable HTTP gateway

The MCP server exposes the same domain services as REST, behind the same bearer auth, so IDEs and agents become a second real consumer without duplicating logic.

Transport and mount

build_mcp_server() in apps/api/src/researchmate_api/mcp_server.py creates a FastMCP("ResearchMate") instance with stateless_http=True, json_response=True, and streamable_http_path="/". The ASGI app is mounted at /mcp in main.py (app.mount("/mcp", mcp_asgi)). The MCP SDK is an optional dependency — when absent, the /mcp endpoint returns 503 MCP_RUNTIME_NOT_INSTALLED.

Authentication . MCPRequestIdentity ContextVar

Authentication happens at the FastAPI middleware layer in main.py, not inside the MCP server. Every request to /mcp or /mcp/* must carry a Bearer token. The middleware calls resolve_bearer_token() (Supabase OAuth in production, static credentials in development) and sets a ContextVar[MCPRequestIdentity] named current_mcp_identity with the full authenticated context:

@dataclass(frozen=True)
class MCPRequestIdentity:
    user: CurrentUser
    repository: ResearchMateRepository
    evidence: EvidenceRepository
    chat_provider: ChatProvider | None
    hybrid_store: QdrantHybridStore | None
    web_search: TavilyWebSearchProvider | None
    settings: Settings
    reranker: RerankCoordinator

Each tool calls _identity() to retrieve this context, raising PermissionError("AUTH_REQUIRED") if absent. The /mcp path is included in RATE_LIMITED_PATHS for IP-based rate limiting at 60 requests/minute.

LangGraph evidence workflow

LangGraph . six-node stateful graph with HITL

The evidence review workflow is a bounded state graph that plans sub-questions, retrieves and extracts evidence in parallel, reconciles claims, pauses for human review, synthesizes a report, and validates before committing.

State schema . EvidenceWorkflowState

The EvidenceWorkflowState TypedDict in workers/ai-worker/src/researchmate_worker/evidence_graph.py defines checkpoint-safe state exchanged by nodes:

FieldTypePurpose

run_kindstrevidence_review or report_refresh
base_report_id, impacted_section_keys, changed_document_idsstr / list[str]Report refresh scope
questions, question_index, questionlist[str] / int / strPlanned sub-questions and current fan-out index
evidence_batchesAnnotated[list[dict], operator.add]Accumulator — parallel batches merged via operator.add

Graph topology

build_evidence_graph(domain, checkpointer) assembles the StateGraph and compiles it with a checkpointer:

START → planCreates provider-backed research questions from the research goal, or preserves section keys for report refresh
plan → fan-out → retrieve_and_extractfan_out() returns one Send("retrieve_and_extract", {...}) per question — parallel execution with full context plus per-question question_index and question
retrieve_and_extract → reconcileRetrieves evidence from Qdrant (+ optional Tavily web search), loads chunks, extracts claims via LLM. Batches merge into evidence_batches via operator.add. Reconcile derives claim relationships (agreement/contradiction) without changing evidence.
reconcile → human_reviewThe review() wrapper calls domain.review_payload(state). If None, auto-approves. Otherwise calls interrupt(proposed) — the checkpoint persists and the graph pauses.
human_review → synthesizeOn resume, domain.apply_decision() processes the human decision (approve/edit/reject). Synthesize builds a ReportProposal from reviewed claims via synthesize_report() LLM call.
synthesize → validate_and_commit → ENDValidates all claims have evidence (chunk_ids), then atomically commits the report to the database within one transaction.

Human-in-the-Loop . interrupt and resume

The review() node is the critical HITL boundary. It calls domain.review_payload(state) which flags low-confidence claims (score < 0.75) or suspicious sources. If review is needed, it calls interrupt(proposed) from langgraph.types — this persists the checkpoint and pauses the graph. The comment in source is explicit: "Never wrap interrupt in try/except; LangGraph must persist and surface it."

When the human submits a decision (approve, edit, reject), the Celery run_workflow task in tasks.py resumes the graph via Command(resume=resume_value). The domain.apply_decision() method processes the decision and the graph continues to synthesize.

Checkpointing . PostgresSaver

Checkpoints persist to PostgreSQL via PostgresSaver with JsonPlusSerializer(pickle_fallback=False). Thread IDs are the workflow run_id. This means a paused workflow survives worker restarts — the checkpoint is in the database, not in process memory. The pickle_fallback=False setting ensures no arbitrary deserialization, keeping the boundary safe.

Domain protocol and composition

The EvidenceWorkflowDomain Protocol defines the seven methods the graph calls: plan, retrieve_and_extract, reconcile, review_payload, apply_decision, synthesize, validate_and_commit. The implementation is split across:

WorkflowExecutionMixin

workflow_execution.py — implements all seven node methods as a mixin. plan() creates provider-backed questions. retrieve_and_extract() queries Qdrant with owner-scoped filters. reconcile() derives relationships. validate_and_commit() commits atomically.

SqlEvidenceWorkflowDomain

workflow_runtime.py — composes the core domain with WorkflowExecutionMixin and overrides synthesize() to build the ReportProposal via synthesize_report() LLM call.

Quality feedback loop

Evaluation Lab . real retrieval ablations and reviewed Bad Cases

The evaluation path changes execution policy, not just labels. It also turns explicit user feedback into reviewed relevance judgments without trusting client-supplied evidence.

Pipeline modeDense weightSparse weightPurpose
dense_only1.00.0Skips lexical prefetch to isolate semantic-vector retrieval.
sparse_only0.01.0Skips embedding and dense prefetch to isolate lexical retrieval.
hybridRoute-dependentRoute-dependentUses the production query planner and weighted dual-channel fusion.
Ranking metrics

evidence_recall measures whether expected chunks appear within the retrieved set. Reciprocal rank records the first relevant position; binary NDCG rewards placing all judged-relevant chunks near the top. When a case has no expected evidence, ranking metrics remain unscored instead of manufacturing a zero.

Baseline comparison

Each durable run stores the effective pipeline configuration, retrieval channel weights, per-case results, aggregates, and the preceding successful baseline summary. The Engineering UI presents candidate and baseline together, including explicit regressions and execution failures.

Feedback capture

Thumb feedback is keyed to a successful owned Ask run. The API reconstructs the question, answer, citations, and retrieved candidates from persisted server state; the browser cannot forge those snapshots.

Bad Case promotion

A developer reviews negative feedback, selects expected chunks only from server-recorded local-document candidates, and atomically creates the next frozen Answer feedback regressions dataset version. The same advisory-lock transaction creates a pending evaluation for the latest accepted pipeline and appends evaluation.run.requested, so historical cases rerun automatically with evidence recall, citation precision, and faithfulness. Web candidates remain visible but cannot enter the local-document replay dataset.

Current evidence boundary: metric logic, retrieval branch selection, feedback ownership, immutable promotion, UI rendering, and the release-gate script have local automated evidence. A populated managed-provider comparison and a production promotion remain unclaimed.
