Reading path

1. How to use this guide

Lead with the scene, then explain the order. If you are new to the project, open the docs one level at a time — each page assumes the previous one built a model you can use.

Each learning page is structured the same way: a hero lede gives the one-sentence pitch and key file counts; sections open with a conclusion paragraph and then expand; every page ends with an interview question tree with answers attached, not bare questions. Read top-to-bottom on a first pass — the structure is designed so a single page gives you a model you can apply, not a list of facts to memorize.

Recommended order for a 0-foundation reader

If you are new to ResearchMate or to the stack itself, read in this order. The project-structure page gives you the map of where things live; backend, worker, and AI-stack pages deepen the three layers you saw on that map; contracts-tests and infra verify the contracts and the deployment; flows ties the layers together end-to-end. Read cross-cutting flows last — it makes sense only once you can name each layer from memory.

Module relationships

2. How the eight modules fit together

The map shows the dependency edges between learning modules. The core shape is a fan: a request enters through the Frontend, hits the Backend, splits inline (Ask) or queued (ingestion + evidence) into the Worker, and the AI stack modules run inside both.

Think of the project as a fan with one handle and three ribs. The handle is the Frontend — it only talks to the backend over HTTP. The three ribs are the Backend, the Worker, and the AI stack that lives inside both. Frontend and Worker do not talk directly: the Backend writes an outbox row in Supabase, the Worker polls it, and results come back through Supabase — not through HTTP. Every other module (Infrastructure, CI/CD, Contracts & tests, Cross-cutting flows, Project structure) supports how the four ribs are built and verified, not how they call each other.

Three edges that carry the architecture

EdgeWhat crossesWhere to read
Frontend → Backend (HTTP, same-origin proxy)Chat composer messages, file upload, idempotency-key headers; Vercel rewrite proxies to Render to avoid corporate proxy interceptionFrontend + Backend
Backend → Worker (Outbox, not direct call)Tasks for ingestion and evidence review; one DB transaction writes business data + outbox_events; worker polls and enqueuesWorker + Cross-cutting flows
Backend + Worker → AI providers (NVIDIA NIM, Qdrant, Tavily)LLM calls, embedding calls, hybrid retrieval, rerank; same adapters used by both Ask (inline) and Evidence (queued)AI stack + Backend + Worker
[Reasonable inference] The most-asked architecture question is "why does the Frontend not call the Worker directly?" The answer is on the Backend → Worker edge: an HTTP call would race against the database commit, and if the API crashes between the DB write and the task dispatch, the task is lost. The Outbox pattern fixes this — task and business data commit together, the task becomes reliable because it is just a database row.

Interview question trees

Why does the Frontend proxy through Vercel rewrites instead of calling Render directly?
├─ [Project fact] Vercel rewrite proxies the API request through the frontend host
└─ Why is that needed?
   └─ Corporate/ISP proxy interception of *.onrender.com serves HTML instead of JSON; the rewrite uses the Vercel domain which the proxy permits

Why is the outbox pattern on the Backend → Worker edge?
├─ Direct task.delay() races the DB transaction
├─ If the API crashes after commit but before dispatch, the task is lost
└─ [Project fact] Outbox writes business row + outbox_events row in one transaction; the dispatcher polls and enqueues — task becomes durable as long as Postgres is up

High-frequency interview points

3. Cheat sheet: the points that come up most

Five points cover roughly 80% of the deep-dive questions on this project. Each names the page where the full explanation lives.

PointOne-line answerFull page
Why hybrid retrieval (BM25 + dense) instead of one method?BM25 catches keyword-style queries; dense catches paraphrase queries; RRF fuses the ranked lists into one top-KAI stack
Why is rerank budgeted before invocation?Bypass candidates from full-text or keyword paths are cheap; running rerank on a huge pile wastes tokens, so candidates are split by type and budget-capped before rerank sees themAI stack
Why the outbox, not task.delay()?The API commits business data + outbox_events in one transaction; the dispatcher polls; if the API crashes, the task is still in PostgresWorker + Cross-cutting
Why idempotency on the Ask request?Network timeout may push the client to retry; same Idempotency-Key replays without re-calling the LLM — saves tokens and prevents duplicate runsBackend
Why one Render container for API + worker?Render Free tier = one sleeping service; render_combined runs both in one process; trade-off is no independent scalingProject structure
[Project fact] None of these answers reference fabricated metrics. The project does not publish QPS, recall, or latency numbers; in an interview, say what the source confirms and mark the rest as [Reasonable inference] or [Optimization suggestion].

Interview question trees

What is the cheapest path through an Ask request?
├─ Idempotency replay → return cached response, no LLM call
└─ [Project fact] IdempotencyCoordinator.begin() checks the key before execute()

What is the worst-case path?
├─ Extended-hybrid retrieval → rerank → LLM with one repair retry
└─ Where are the latency sinks?
   └─ [Project fact] NVIDIA embedding (4096-dim) + Qdrant hybrid query + NVIDIA LLM; rerank is gated by a budget cap before invocation

How do you keep long workflows from being killed mid-execution?
├─ [Project fact] Celery soft_time_limit + task_acks_late; SoftTimeLimitExceeded has an explicit handler ahead of except Exception
└─ [Interview extension] Why can't soft timeout interrupt a blocking C call?
   └─ Raises only between Python bytecodes; boto3/C-extension calls ignore it; only SIGKILL is a hard backstop
