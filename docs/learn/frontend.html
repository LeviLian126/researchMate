Frontend interview study

Users open a Next.js page, log in through Supabase, ask a question, and watch the AI answer stream in one chunk at a time. This page cuts the 54-file inventory to the 5 topics an interviewer is most likely to drill: how the browser actually reaches the backend through a proxy, how the AI answer streams over fetch+ReadableStream, how App Router organizes pages, how React state survives page switches and races, and how CSP blocks injected scripts.

Next.js 16.3.0 · App Router · Turbopack React 19 · "use client" + hooks Supabase Auth · HttpOnly cookie Tailwind CSS v4.3.3 · shadcn/ui

Topic 1 · Proxy bypass

Server-side rewrite to bypass corporate proxy interception

When a user opens the chat page, the browser must call the backend. The backend lives on Render at *.onrender.com, which is a different origin from the frontend on Vercel. Normally the browser would make a cross-origin request directly. This project instead routes the call through Next.js so the browser only ever sees its own origin, and Vercel makes the real server-to-server hop.

Problem [Project fact]

Some corporate or ISP proxies sit between the user and the internet. When they see a browser request to *.onrender.com, they sometimes return an HTML warning page instead of JSON. The browser then tries response.json(), parsing fails, and the UI shows an unknown client error.

Mechanism [Project fact]

next.config.ts declares async rewrites() with one rule: source: "/api/v1/:path*" → destination: ${backendOrigin}/api/v1/:path*. backendOrigin is NEXT_PUBLIC_API_BASE_URL with the /api/v1 suffix stripped. In NODE_ENV=development the function returns [], so the browser calls http://localhost:8000/api/v1 directly with no rewrite.

Why same-origin wins

When the browser sees only its own origin, the proxy has no cross-origin rule to match, so it never intercepts. Vercel's edge reaches Render through a server-to-server network path that no corporate proxy sits on.

Trade-off

Every byte of API traffic now flows through Vercel's edge function instead of going straight from browser to backend. [Reasonable inference] This adds one network hop and bounds throughput by the Vercel function. The cost is acceptable because the project is single-tenant and the heaviest payload (SSE events) is streamed, not buffered.

Alternatives considered and rejected [Reasonable inference]: A pre-signed upload URL or a directly CORS-enabled backend were rejected for the chat path. The API needs the bearer token in the Authorization header; enabling CORS would also re-expose the backend origin to the corporate proxy.
Q1: Why not let the browser call Render directly?
→ A proxy on the path returns HTML, not JSON. response.json() throws and the UI shows "unknown client error".
Q2: Why is rewrites() declared async?
→ The function must return an array; the async form allows reading environment variables at build or request time. It reads NEXT_PUBLIC_API_BASE_URL when the config is evaluated.
Q3: What breaks if Vercel's edge goes down?
→ All API and SSE traffic fails. [Interview extension] The frontend has no direct-to-Render fallback; describeApiError maps 5xx to "provider unavailable" and the user can retry.

Topic 2 · API client and streaming

fetch + manual SSE parsing, no EventSource, AbortSignal cancellation

When the user submits a question, the backend creates a "run" that may take 20+ seconds. The user cannot stare at a spinner for that long. The project streams progress events from the backend so the UI can show node-by-node updates. The browser's built-in EventSource API cannot send custom headers, so the project streams by reading a fetch response body through a ReadableStream reader.

apiFetch<T>

Called for every JSON request. Builds a Headers object, sets Content-Type: application/json when a body is present, and sets Authorization: Bearer ${token} by calling getAccessToken(). Calls fetch. Always reads response.json() (with .catch(() => ({})) for non-JSON error bodies so a parse error never masks the real HTTP failure), then either throws an ApiError built by toApiError or returns the typed body. [Project fact]

streamRunEvents

Called with a runId, an afterSequence cursor, an onEvent callback, and an AbortSignal. Fetches /runs/${runId}/events?after_sequence=N with Accept: text/event-stream and the bearer header. Gets response.body.getReader(), decodes raw bytes with TextDecoder into a string buffer. Splits the buffer on "\n\n" because the SSE spec separates events with a blank line; frames.pop() keeps the last partial chunk in buffer so the next decode does not cut a frame in half. For each complete frame, finds the line starting with "data: " and JSON.parses the slice from offset 6. Malformed frames are swallowed by try/catch so one bad provider event does not kill the whole stream. [Project fact]

getAccessToken

In local dev returns getDevToken() (reads localStorage.researchmate_token or falls back to "dev"). In production calls getSupabaseSession() which restores the session from an HttpOnly cookie route. If no session exists, throws ApiError(401, AUTH_REQUIRED). If Supabase refresh fails, throws 503 AUTH_PROVIDER_UNAVAILABLE. [Project fact]

describeApiError

Maps an ApiError to a user-facing {title, detail, kind} triple: 401→auth, 403→permission, 409→conflict, 429→limit, 5xx→provider, default→validation. Drives StateNotice styling across AuthGate, ConversationThread, and Library. [Project fact]

Why not use the browser's EventSource [project fact + reasonable inference]

The browser EventSource API can connect to a URL and receive SSE events automatically, but it cannot set custom request headers. This project's event endpoint requires Authorization: Bearer; without it the backend returns 401. So the project must use fetch + ReadableStream reader and parse SSE frames manually. The trade-off is reimplementing reconnection logic; the current code does not auto-reconnect and relies on the polling fallback below as the backstop.

Polling fallback: The Research page runs a parallel setTimeout(3000) poll of GET /runs/${run_id} while the run is in running or waiting_human state. If the SSE stream dies, canonical run status still recovers through polling. [Project fact]
Q1: Why split the buffer on "\n\n"?
→ SSE spec separates events with a blank line. pop() keeps the partial tail in the buffer so the next decode(value, {stream:true}) does not cut a frame mid-flight.
Q2: How is a malformed JSON frame handled?
→ try/catch swallows it silently. Design choice: one bad provider frame must not break a long-running stream. Trade-off: a structurally broken stream shows no visible error; the polling fallback is the last line of defense.
Q3: How does the client cancel a stream?
→ The caller passes an AbortController().signal and fetch propagates the abort. [Optimization suggestion] The Research page currently creates an AbortController with no abort() call on unmount; a useEffect cleanup should call controller.abort() to stop streaming when the page is left.

Topic 3 · App Router

Next.js 16 App Router: how a URL becomes a page

When the user types a URL, Next.js maps the path to files on disk and decides what runs on the server versus the browser. Server-side concerns (the root HTML layout, security headers, the rewrites config, the per-request nonce) live at the framework edge so they run before any React tree renders. Per-page state and interactivity are isolated to client islands marked "use client" at the top of the file.

Stack [Project fact]

Next.js 16.3.0, React 19.2.8, App Router, Turbopack bundler, static export to Vercel. reactStrictMode: true. distDir is overridable via NEXT_DIST_DIR so the E2E build can use .next-e2e and not collide with the dev build.

File conventions used

Nested layouts: app/layout.tsx (root, sets the nonce context), app/app/layout.tsx (authed shell wrapping AuthGate and AppSidebar), app/app/projects/[projectId]/* (project-scoped pages). Page files colocate with their components in app/components/. No Server Actions or data Route Handlers for business data — all data goes through apiFetch. Only two cookie Route Handlers exist (POST /api/auth/session to write, GET /api/auth/session/get to read session). [Project fact]

Client islands

Heavy interactive pages such as research/page.tsx and the chat workspace start with "use client". The root layout and middleware stay server-side so the nonce and static CSP can be injected before any HTML streams to the browser. [Reasonable inference]

Path alias

tsconfig.json maps @/* → ./app/*, so @/components/ui/button resolves into the in-repo shadcn/ui copy instead of an npm package. [Project fact]

Why App Router over Pages Router [Reasonable inference]: Server-side rewrites(), static headers() config, and per-request middleware all require App Router's request pipeline. Migrating back to Pages Router would force a custom Node server and lose Vercel's edge deployment.
Q1: Where does the auth token live?
→ In an HttpOnly cookie, written by the POST /api/auth/session Route Handler and read by GET /api/auth/session/get. Session tokens never reach localStorage. [Project fact]
Q2: Why two cookie Route Handlers instead of cookies() in middleware?
→ [Reasonable inference] Middleware runs on every request including static assets; writing cookies there adds latency on hot paths. Two narrow handlers concentrate the write cost where sessions actually rotate.
Q3: What renders while a page waits on apiFetch?
→ The client page renders its skeleton or empty state first; a useEffect then resolves apiFetch and calls setState. There is no RSC data streaming — data pages are pure client islands.

Topic 4 · State and race protection

useChatWorkspace: hooks-only state plus four race guards

When the user types a question and presses send, three things race: the optimistic UI must show the message immediately, the network request must not fire twice if the user double-clicks, and the response must not land on the wrong conversation if the user switches tabs mid-flight. There is no Redux or Zustand; a single useChatWorkspace custom hook owns all chat state and four independent guards that handle these races. The Research page mirrors the same shape with a smaller state set.

State shape [Project fact]

16 useState variables: conversationId, messages, message, webEnabled, historyLoading, sending, slowResponse, error, documents, uploading, quizOpen, quizPrompt, quiz, quizLoading, degradedNotice, resolvedProject. State is grouped by concern (chat, upload, quiz), not flattened globally.

Refs for guards [Project fact]

8 useRef values: fileInput, threadEnd, loadGeneration, askIntent, quizIntent, quizHistoryLoadedFor, askInFlight, quizInFlight. Refs are chosen over state deliberately — guards mutate them but must not trigger re-renders.

Effects [Project fact]

useEffect covers: bootstrap personal project, load conversation (with a generation guard), auto-scroll, a slowResponse 10s timer, document status polling every 2s, and quiz history load. Each effect takes an active flag or increments a generation counter in cleanup so a stale async result is discarded.

Idempotent intent [Project fact]

resolveIntentKey from idempotent-intent.ts builds a JSON fingerprint of the request params. If the fingerprint is unchanged, the prior Idempotency-Key is reused; if it changed, a new prefix-uuid key is minted. So a retry-after-failure resends the same key, while a brand-new question gets a new one — the backend can dedupe retries without losing distinct questions.

Four race patterns [Project fact]

(1) Generation counter: cleanup runs ++loadGeneration.current; the response checks generation !== loadGeneration.current and bails if stale. (2) In-flight flag: askInFlight.current = true blocks a second submitQuestion while the first is pending. (3) Active flag: let active = true is flipped to false in cleanup so late-arriving work is ignored when the component has moved on. (4) Intent fingerprint: makes a retry reuse the same idempotency key instead of minting a new one.

Inter-component communication [Project fact]

No React Context. Uses window.dispatchEvent(new Event("researchmate:sidebar-refresh")) and "researchmate:sources-refresh". The sidebar subscribes via addEventListener and unsubscribes in cleanup. Trade-off: this is an implicit contract — a typo in the event name fails silently.

Q1: Why a generation counter instead of just aborting the request?
→ Abort cancels the HTTP transport. The counter also protects against the response arriving after the component has already moved on. It is a logical-staleness guard, not a transport cancellation.
Q2: Why no global store?
→ One chat page owns the state; cross-page sync happens through the event bus. [Reasonable inference] A global store would pay bundle-size and indirection cost for a state graph that is already small and scoped to one page.
Q3: What happens if two submitQuestion calls race?
→ askInFlight.current blocks the second. If the first fails, the optimistic message is removed, the draft is restored, and the user retries with the same Idempotency-Key so the backend dedupes.

Topic 5 · CSP + auth boundary

Per-request nonce, explicit connect-src allow-list, HttpOnly session

Content Security Policy is a browser defense: it tells the browser which scripts, styles, and network destinations are allowed to run on the page. If an attacker injects a <script> tag through user input, the browser refuses to run it because it did not come from a trusted source. This project uses three layers: a static CSP in next.config.ts, a per-request nonce injected by middleware.ts to replace 'unsafe-inline', and a shared allow-list in csp-origins.ts.

Static CSP [Project fact]

buildStaticCsp() joins 11 directives: default-src 'self'; script-src 'self' (+ 'unsafe-eval' in dev); style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; font-src 'self' data:; connect-src 'self' <allow-list> (+ dev localhost); object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; worker-src 'self' blob:.

Nonce mechanism [Project fact]

middleware.ts runs on every page and API route (matcher skips _next/static, _next/image, favicon.ico, icon.svg). It calls crypto.randomUUID().replaceAll("-","") to produce a 32-hex nonce, forwards it to the React tree via the x-researchmate-nonce request header so layout and components can attach it to inline scripts, and sets the runtime CSP via buildNonceCsp(nonce). Each request gets a new nonce, so a stolen nonce from one request cannot be reused later.

connect-src allow-list [Project fact]

allowedConnectOrigins contains exactly two entries: safeOrigin(NEXT_PUBLIC_SUPABASE_URL) and safeOrigin(BACKEND_API_BASE). Provider endpoints (NVIDIA, Tavily, Langfuse) are deliberately absent — those calls happen server-to-server on the FastAPI worker where CSP does not apply, so they never need to be in the browser bundle.

Auth boundary [Project fact]

Session tokens live in an HttpOnly cookie; the browser's JavaScript cannot read it directly. Two Route Handlers write and read the cookie. getSupabaseSession refreshes the token 60s before expiry. The browser Authorization: Bearer header is the only place the token enters JS-readable memory, and only inside a fetch call.

SEC-4 / SEC-5 history [Project fact]: An earlier CSP had a permissive https: wildcard in connect-src and a static 'unsafe-inline' in script-src. Both have been removed. The wildcard was replaced by the explicit two-entry allow-list; 'unsafe-inline' was replaced by the per-request nonce.
Q1: Why a nonce instead of a hash-based policy?
→ Hash policies require knowing inline script contents at build time. Next.js pages emit inline scripts whose contents depend on runtime data; a per-request nonce is the pragmatic match.
Q2: Why is style-src still 'unsafe-inline'?
→ [Project fact] Tailwind and shadcn/ui rely on inline styles for variants and theming. Trade-off accepted: script injection is the higher-risk surface; with object-src 'none' and frame-ancestors 'none' in place, style injection is lower risk.
Q3: What stops an XSS from calling fetch to the API?
→ CSP cannot stop a script that already runs on the page from calling same-origin. Defense is layered: no inline scripts without a nonce, no provider endpoints in the bundle, and the session token never reaches JS-readable storage so an XSS cannot exfiltrate a refresh token.
