Frontend module deep dive

apps/web is the ResearchMate Next.js frontend application, deployed on Vercel. It contains 50 source files (excluding config and assets), covering page routes, React components, API client, authentication logic, and E2E tests. This page analyzes every file's purpose, key logic, and dependencies, and traces the complete journey of an Ask request from the browser to the backend through a slice perspective.

Tech stack fundamentals

Core technology stack

apps/web uses the following 7 core technologies, each chosen for a specific project scenario. The fact cards below describe version, purpose, and actual usage in the project.

Next.js 16.3.0

React full-stack framework using the App Router file-based routing system. Statically exported and deployed on Vercel, with next.config.ts rewrites proxying /api/v1/* requests to the Render backend, bypassing corporate proxy interception of cross-origin requests. reactStrictMode enabled, Turbopack bundler. distDir overridable via NEXT_DIST_DIR env var (E2E uses .next-e2e).

React

UI library, heavily using Client Components ("use client"). State managed through hooks (useState, useEffect, useRef, useMemo, useCallback) without Redux or Zustand. Components are layered into container (ChatWorkspace), presentation (ConversationThread, ChatComposer), and UI primitives (ui/*).

Tailwind CSS v4.3.3

Utility-first CSS framework, integrated via the @tailwindcss/postcss plugin. globals.css uses @import "tailwindcss" and @theme inline to define design tokens (CSS variables), supporting light/dark themes and prefers-reduced-motion. Components use the cn() utility to merge Tailwind class names.

shadcn/ui

Customizable component system built on Radix UI primitives. apps/web includes 15 ui/ components, depending on 9 @radix-ui packages. Components use class-variance-authority (cva) for variants and tailwind-merge for class deduplication. Not an npm package but source files copied into the project.

Vitest 4.1.10

Unit testing framework using jsdom environment to simulate the browser. Coverage collected via @vitest/coverage-v8, covering app/lib/**/*.ts and app/components/**/*.{ts,tsx}, with a 40% baseline (lines/statements). Test files live alongside source (.test.ts suffix), totaling 7 test files.

Playwright 1.62.1

E2E testing framework using only Chromium. The webServer config starts a demo-mode Next.js on 127.0.0.1:3100, with test files in e2e/. Validates the complete user journey: send a message, view citations, create a project, generate a quiz, while checking for zero browser errors and zero external requests.

Supabase Auth

Authentication service supporting GitHub OAuth and email/password. supabase.ts implements browser-side session management from scratch (no @supabase/supabase-js dependency), including JWT decoding, refresh token rotation, HttpOnly cookie persistence (via /api/auth/session POST + /api/auth/session/get GET routes — session tokens never reach localStorage), and OAuth redirect recovery. The AuthGate component guards all protected routes.

File-by-file analysis

Page route files

Next.js App Router uses filesystem routing: folder names map to URL segments, layout.tsx and page.tsx are special files. Below is a file-by-file analysis of each route's purpose.

app/layout.tsx

Root layout, the HTML shell for the entire application. Exports a metadata object (title/description), imports globals.css design system, and sets <html lang="en" data-scroll-behavior="smooth">. Every route's children is wrapped in this layout. This is the only layout file that does not use "use client".

app/page.tsx

Home page (/), a client component. Wraps an AuthenticatedRedirect component in AuthGate: authenticated users are redirected via router.replace("/app") directly to the workspace, while unauthenticated users see the AuthGate sign-in panel. Displays a "Opening your workspace..." status with a Loader2 spinner.

app/app/layout.tsx

Protected application layout, wrapping all /app/* routes. Wraps AppSidebar + content area in AuthGate. The sidebar is wrapped in Suspense with a 260px-wide empty aside fallback. The layout is flex h-[100dvh] with the sidebar fixed on the left and the content area filling the remaining space with flex-1.

app/app/page.tsx

Personal chat route (/app), a client component. Wraps ChatWorkspace (without projectId) in Suspense, with a "Starting chat" skeleton fallback. Suspense is required because ChatWorkspace internally uses useSearchParams to read the conversation and new URL parameters.

projects/[projectId]/page.tsx

Project root route, a server component. Receives params: Promise<{ projectId: string }> (Next.js 16 async params) and directly redirects to /app/projects/${projectId}/chat. Ensures each project has a single canonical entry route.

projects/[projectId]/chat/page.tsx

Project chat route, a client component. Reads projectId via useParams, loads the project name via apiFetch, then renders ChatWorkspace with projectId, projectName, and projectMode=true. An outer Suspense handles the useParams async boundary.

projects/[projectId]/library/page.tsx

Source library page, one of the most feature-rich routes. Supports file upload (drag + select), manual text fallback, document list search, and document deletion (with confirmation + async job polling). Uses ProjectNav for top navigation, displays document status with Badge components (ready/uploading/parsing/failed), and polls every 2 seconds while documents are processing.

projects/[projectId]/quiz/page.tsx

Legacy quiz route, a server component. Directly redirects to /app/projects/${projectId}/chat?quiz=1. Quiz functionality has migrated from a standalone page to the ProjectQuizDrawer on the chat page; this route is retained for backward compatibility.

projects/[projectId]/labs/page.tsx

Engineering labs page, role-restricted. Checks session.user.role via getSupabaseSession for developer or admin. Contains three panels: evaluation runs (select dataset + pipeline + metrics), reliability metrics (run_count, success_rate, p95, cost), and fault injection exercises (llm_timeout, qdrant_unavailable, etc., 10-second limit).

dev/layout.tsx

Developer route layout, wrapping all /dev/* routes in AuthGate. Ensures developer tool pages require authentication, but does not perform role checks here (role enforcement is at the backend API layer).

dev/traces/[traceId]/page.tsx

Developer trace viewer, a client component. Loads an execution trace via apiFetch<DeveloperTrace> and displays execution_plan, validation_result, retrieved_chunks, and tool_calls as JSON pre blocks. API keys, OAuth tokens, and other sensitive data are filtered on the backend.

Component layer

Business components

apps/web has 10 business components (excluding 15 ui/ primitives), divided into container, presentation, and navigation components. Below is a Props count, responsibility, and key logic analysis for each.

chat-workspace.tsx — Chat container (composition root, 3 Props)

Container component that composes state logic (useChatWorkspace) with presentation components (ConversationThread, ChatComposer, ProjectQuizDrawer). Only 3 Props: projectId?, projectName?, projectMode?. When projectMode is true, renders a project toolbar (New chat / Quiz / Sources buttons) and the Quiz drawer. Personal chat passes no Props; the Hook bootstraps itself.

use-chat-workspace.ts — State hook (core orchestration)

Custom hook, the most complex module in the frontend. Receives { suppliedProjectId?, projectMode }, manages 16 useState, 8 useRef, 5 useEffect, and 1 useMemo. Returns 25+ fields and methods. Core responsibilities: conversation loading (with generation race protection), message sending (optimistic update + idempotency key + intent fingerprint), file upload (signed URL flow), quiz generation (idempotent + history loading), event bus (researchmate:sidebar-refresh).

chat-composer.tsx — Input area (13 Props)

Presentation component rendering the file upload button, message input, web search toggle, and send button. Props count: 13. documents, projectMode, uploading, fileInput (RefObject), message, webEnabled, sending, historyLoading, hasReadyAttachments, onUpload, onSubmit, onMessageChange, onWebEnabledChange. Enter key submits (Shift+Enter for newline), maxLength 8000, file type restricted to .pdf/.docx/.pptx. Uses lucide-react Paperclip, ArrowUp, Globe, Loader2 icons.

conversation-thread.tsx — Conversation thread (11 Props)

Presentation component rendering the message list, citations, loading states, and error notices. Props count: 11. messages, historyLoading, sending, slowResponse, error, degradedNotice, projectMode, projectName, threadEnd (RefObject), onDismissError, onSelectPrompt. Empty conversations show 3 starter prompts (EMPTY_PROMPTS). Citations are collapsible via details, supporting local_doc and web_page source types. The "thinking" animation uses three CSS-animated dots (rm-thinking keyframe). slowResponse shows "Still working" after 10 seconds.

app-sidebar.tsx — Navigation sidebar

Client component managing project lists, conversation lists, and their CRUD. Uses usePathname + useSearchParams to identify the active item. Features: create project (Dialog form), rename conversation (PATCH), delete conversation (with confirmation state), delete project (async job polling, up to 20 attempts, 1.5s each). Desktop collapsible (72px / 260px), mobile uses Sheet component. Refreshes via researchmate:sidebar-refresh event bus. Uses requestGeneration ref to prevent race conditions.

auth-gate.tsx — Auth guard (5 states)

Client component guarding all protected routes. 5 states: loading (restoring session), signed_out (GitHub sign-in panel), signed_in (renders children + session bar), misconfigured (Supabase not configured), error (session recovery failed). Local development passes through directly (isLocalDevelopment()). Demo mode shows a static banner then passes through. Calls warmApi() on mount to pre-warm the API health check, reducing first-request latency.

project-quiz-drawer.tsx — Quiz drawer (7 Props)

Presentation component, fixed-positioned on the right (max 430px). Props: prompt, quiz, loading, onPromptChange, onSubmit, onClose, onReset. Two modes: without quiz, shows a generation form (Textarea + default 3 single-choice + 2 fill-blank + 2 subjective); with quiz, displays each question in a collapsible details (question/options/answer/explanation). Copy reads "Uses available indexed project resources" to avoid overpromising coverage.

project-nav.tsx — In-project navigation

Client component rendering the project top navigation bar. Props: projectId, current ("chat" | "library" | "evidence" | "quiz" | "labs"). Loads the project name via apiFetch and displays Chat / Sources / Quiz links (Quiz links to chat?quiz=1). The current page is marked with aria-current="page" and a highlighted style.

state-notice.tsx — Notice component

Presentation component rendering categorized recovery notices. Props: state (title, detail, kind), action? (ReactNode). When kind is error or provider, role="alert"; otherwise role="status". Reused across AuthGate, ConversationThread, and the Library page, ensuring consistent error/status notice styling.

brand-logo.tsx — Brand logo

Presentation component using next/image to render researchmate-logo-mark.png. Props: withName (default false). Logo area 36x36px, unoptimized + priority. When withName is true, also renders the "ResearchMate" wordmark. aria-hidden="true" hides the decorative image.

Lib layer

Lib modules

app/lib/ contains 6 modules that form the frontend's core infrastructure: API transport, authentication, demo runtime, idempotency coordination, utility functions, and rate limiting. Below is an analysis of exported functions and types for each.

api.ts

API client + type contracts, the frontend mirror of the backend contract. Exports 30+ TypeScript interfaces and 8 core functions. apiFetch<T>: unified fetch wrapper injecting Authorization header and Content-Type, throwing ApiError on error. getAccessToken: resolves bearer token (local dev or Supabase session). describeApiError: maps HTTP status codes to user-friendly messages (401→auth, 403→permission, 429→limit, 5xx→provider). streamRunEvents: consumes SSE event streams, parsing data: lines by splitting on \n\n. idempotencyKey: generates prefix-uuid format keys. warmApi: single best-effort /healthz pre-warm request. API_BASE is /api/v1 (same-origin rewrite) in production, NEXT_PUBLIC_API_BASE_URL locally.

supabase.ts

Browser-side Supabase Auth implementation, not depending on @supabase/supabase-js SDK. Implements 5 core functions: getSupabaseSession (restore/refresh session), onAuthStateChange (subscribe), signInWithGitHub (OAuth redirect), signOut (logout + cleanup), signInWithPassword / signUpWithPassword / sendMagicLink (email flows). Session persisted to an HttpOnly cookie via POST /api/auth/session (set/clear) and GET /api/auth/session/get (read) — SEC-3 hardening: tokens never touch localStorage or any JavaScript-readable storage. Auto-refreshed 60 seconds before expiry (refresh skew). JWT email/role decoded via identityFromAccessToken (base64 payload). workspaceRedirect enforces redirect URLs stay within /app paths, preventing open redirects. SupabaseAuthError preserves provider status and code.

demo.ts

Deterministic browser demo runtime, enabled via NEXT_PUBLIC_DEMO_MODE=true. When isPublicDemo() is true, apiFetch delegates to demoFetch. demoFetch implements the complete API subset: project CRUD, conversation CRUD, message lists, document upload-url/complete, ask, quiz, pipeline-versions, research-runs, evaluation-runs, reliability, traces, fault-scenarios. All data stored in module-level variables (projects, documents, chatMessages, quizSets), with no network requests sent. demoRunEvents emits 2 deterministic events (retrieve + report_published).

idempotent-intent.ts

Idempotent intent tracker ensuring failed retries reuse the same Idempotency-Key. Exports IntentKeyState interface (fingerprint + key) and 2 functions. resolveIntentKey: returns the existing key if the fingerprint is unchanged, otherwise creates a new one. The fingerprint is the JSON serialization of request parameters. clearCompletedIntent: clears the intent for a successful request. Used with api.ts's idempotencyKey in use-chat-workspace.ts's submitQuestion and generateQuiz.

utils.ts

Utility module exporting only cn(...inputs: ClassValue[]). Combines clsx (conditional class names) and tailwind-merge (deduplicating conflicting Tailwind classes), forming the class name merging foundation for all shadcn/ui and business components. For example, cn("px-2 py-1", condition && "bg-accent") → "px-2 py-1 bg-accent".

auth-email-rate-limit.ts

Browser-side email rate-limit guard mirroring Supabase's per-user cooldown. Exports AUTH_EMAIL_COOLDOWN_MS (60 seconds) and 2 functions. remainingEmailCooldown: computes remaining seconds. nextEmailCooldown: computes the next allowed timestamp. Ensures the frontend does not send duplicate magic link or confirmation email requests within the cooldown window.

API request slice

The 6-step frontend journey of an Ask request

From the user pressing send to receiving a cited answer, the request passes through 6 steps on the frontend. Each step involves different files; the proof-chain below shows the complete flow.

1. Form submitchat-composer.tsx: user types a message → Enter or click send → onSubmit(event) → calls workspace.submitQuestion. Send button disabled when !message.trim() || sending || historyLoading.
2. Hook orchestrationuse-chat-workspace.ts: submitQuestion builds a fingerprint (JSON.stringify of request params) → resolveIntentKey reuses or creates an idempotency key → adds an optimistic user message → setSending(true) → calls apiFetch<AskResponse>("/ask", ...) with the Idempotency-Key header.
3. Token resolutionapi.ts: apiFetch calls getAccessToken() → local dev returns getDevToken() (localStorage dev token only) → production calls getSupabaseSession() which reads the HttpOnly session cookie via GET /api/auth/session/get, returning a JWT access_token → injects Authorization: Bearer ${token} header. Session tokens never reach localStorage (SEC-3).
4. Session checksupabase.ts: getSupabaseSession loads the session from the HttpOnly cookie → if within 60 seconds of expiry, calls refreshSession (trades refresh_token for a new access_token, then re-writes the cookie via POST /api/auth/session) → returns a valid session or null (triggering a 401 error).
5. HTTP requestfetch: POST ${API_BASE}/ask, body contains project_id, conversation_id, message, web_enabled. API_BASE is /api/v1 (same-origin rewrite to Render) in production, http://localhost:8000/api/v1 locally. Demo mode delegates to demoFetch.
6. Response handlinguse-chat-workspace.ts: parses AskResponse (answer, citations, conversation_id, degraded flags) → replaces optimistic message + adds assistant message → setConversationId → router.replace updates URL → dispatchEvent("researchmate:sidebar-refresh") → on failure, removes optimistic message + restores draft + displays error.
Race protection: The askInFlight.current ref prevents concurrent duplicate submissions. If the request fails, the optimistic message is removed, the draft is restored to the input, and the user can retry while resolveIntentKey reuses the same Idempotency-Key (fingerprint unchanged).

State management

React Hooks and race protection

apps/web does not use Redux/Zustand or other external state libraries; all state is managed through React Hooks. Below is an analysis of each Hook's usage patterns and the project's race protection mechanisms.

useState (16+ state variables)

use-chat-workspace.ts is the densest: conversationId, messages, message, webEnabled, historyLoading, sending, slowResponse, error, documents, uploading, quizOpen, quizPrompt, quiz, quizLoading, degradedNotice, resolvedProject. app-sidebar.tsx has another 12: collapsed, mobileOpen, projects, conversations, personalProjectId, creatingProject, and more.

useEffect (5+ side effects)

use-chat-workspace.ts: (1) bootstrap personal project; (2) load conversation (generation race protection); (3) auto-scroll to bottom; (4) slowResponse 10s timer; (5) document processing status polling (2s interval); (6) quiz history loading. Each effect has an active flag or cleanup to prevent memory leaks.

useRef (8 refs)

fileInput (file input reference), threadEnd (scroll anchor), loadGeneration (conversation load race counter), askIntent/quizIntent (idempotent intent state), quizHistoryLoadedFor (prevents duplicate quiz history loading), askInFlight/quizInFlight (prevents concurrent duplicate requests). app-sidebar has requestGeneration.

useMemo (3 usages)

readyAttachments: filters documents with status==="ready". personalConversations: filters personal project conversations. activeProjectConversations: filters current project conversations. Avoids recomputing filter results on every render.

useCallback (1 usage)

app-sidebar.tsx's loadNavigation: parallel-loads project list + conversation list + personal project. Uses requestGeneration ref to reject stale concurrent responses. Must be useCallback as a useEffect dependency to avoid infinite re-renders.

Custom hook

useChatWorkspace is the only custom hook, encapsulating all chat workspace state and actions. Receives { suppliedProjectId?, projectMode }, returns 25+ fields. Completely separates state logic from presentation components, making ChatWorkspace a pure composition root.

Event bus

Uses window.dispatchEvent(new Event("researchmate:sidebar-refresh")) and "researchmate:sources-refresh" for inter-component communication. When a message is sent or a file is uploaded, a sidebar refresh is triggered to update the conversation list. The sidebar subscribes via window.addEventListener and unsubscribes in useEffect cleanup. No React Context or global store is used.

Race protection (4 patterns)

(1) Generation counter: loadGeneration.current / requestGeneration.current, incremented per request, checked on response arrival. (2) In-flight flag: askInFlight.current / quizInFlight.current, prevents concurrent submissions. (3) Active flag: let active = true, set to false in cleanup. (4) Intent fingerprint: resolveIntentKey ensures identical params reuse the idempotency key.

File upload slice

The 3-step file upload flow

After a user selects a PDF/DOCX/PPTX file, it goes through 3 steps to complete upload and indexing. Uses a signed URL pattern: the frontend first requests an upload URL, PUTs directly to object storage, then notifies the backend to complete.

1. File selectionchat-composer.tsx: <input type="file" accept=".pdf,.docx,.pptx" multiple> onChange → calls onUpload(event) → passed to workspace.uploadFiles. Shows a Loader2 spinner during upload. The Library page also supports drag-and-drop (onDrop).
2. Upload orchestrationuse-chat-workspace.ts: uploadFiles → validates file extension (/\.(pdf|docx|pptx)$/i) → fileTypeFromName + mimeForFileType resolve type → apiFetch POST /documents/upload-url gets a signed URL → fetch PUT uploads directly to R2 → apiFetch POST /documents/{id}/complete notifies the backend.
3. State refreshuse-chat-workspace.ts: project mode dispatches "researchmate:sources-refresh" event → personal mode setDocuments refreshes the document list → if documents are still processing, starts a 2-second polling timer until all documents become ready/failed. The Library page similarly polls loadDocuments.
Signed URL pattern: The frontend does not relay file binary data through the backend but PUTs directly to an R2 presigned URL. This reduces backend bandwidth pressure but requires R2 CORS configuration to allow browser PUT requests.

Configuration files

Build and test configuration

The apps/web root directory has 6 configuration files controlling Next.js build, TypeScript type checking, PostCSS/Tailwind, Vitest unit tests, and Playwright E2E tests.

next.config.ts

Demo mode isolation

E2E enables demo.ts's deterministic runtime via NEXT_PUBLIC_DEMO_MODE=true. All API requests are handled by demoFetch in-browser, sending no network requests to the backend. Playwright's page.on("request") listener verifies no requests go to hosts other than 127.0.0.1.

Separate build directory

E2E uses the NEXT_DIST_DIR=.next-e2e environment variable, directing Next.js build output to .next-e2e/ instead of .next/. This avoids conflicts between E2E tests and the development server or production build, enabling parallel execution.
