Project Structure . Interview deep dive

When you clone ResearchMate, you get one repository with three independently-deployable apps: a Next.js frontend, a FastAPI backend, and a Python worker. The four interview beats are: why the repo is split the way it is, how the API stacks four layers, why the worker lives as its own package, and why tests sit at the top level instead of inside each app.

100 API .py files 46 worker .py files 52 test files 21 SQL migrations

[Project fact] Three apps in one repo, two package managers

1. What you see when you open the repo

Lead with the scene, then name each dir's job. The top level is small on purpose — it exists to point at three deployables and the shared test suite that crosses them.

Open the project root and you see seven top-level directories. Each one maps to a clear job: apps/web is the Next.js frontend that users see in the browser; apps/api is the FastAPI backend that answers HTTP requests (100 Python files); workers/ai-worker is a separate Python package that runs long jobs like document ingestion and evidence review (46 Python files); tests/ holds 52 pytest suites that test both Python packages from one place; infra/ holds declarative config (SQL migrations, Qdrant collection specs, OpenAPI spec); scripts/ is one-off provisioning tools; docs/ is the HTML-first documentation you are reading now.

Why one repo instead of three

The three apps need to stay in sync: API routers change a request shape, the frontend must follow, and the worker must keep writing compatible rows. Putting them in one repo means one git pull moves all three together, and one pull request can touch API + worker + tests in the same diff. Splitting them would mean a router change requires three PRs across three repos plus a version bump dance.

Why two package managers, not one

The frontend is JavaScript; the API and worker are Python. There is no one tool that handles both well. So the project uses two workspace-native tools: npm workspaces for the JS side and uv workspace for the Python side. Each does one job well — npm gives Vercel native detection for deploys, and uv produces one uv.lock parity with the production Docker image.

The cost is no independent scaling: when traffic grows you split the worker into its own Render Background Worker, keep the shared uv.lock, and give up that single-process simplicity.

[Project fact] routers → services → schemas → persistence

2. Inside the API: four layers and one graph

The interview beat is why each layer exists and what crosses the boundary. Don't memorize filenames — name the layer job, then why it cannot collapse into the next.

A FastAPI app could put SQL queries right inside the route handler, and small apps do. This project does not, because the handler is the only place that talks HTTP and the SQL is the only place that talks Postgres — collapse them and the route becomes untestable without a database, and the SQL becomes untestable without an HTTP client. The project splits the API into four layers: routers receive HTTP; services hold business logic; persistence talks to Postgres; schemas validate the data shapes that cross between them. One extra package — graph/ — holds the LangGraph state machine that drives the grounded Ask and Evidence flows.

Layered request flow (Ask endpoint)

3. Inside the worker: why it is its own package

A separate worker package is not a styling choice. It reflects that the worker has its own deploy, its own runtime concerns (long-running, restartable, killable), and its own dependency on Celery + LangGraph — none of which belong in the API's request/response loop.

The worker is a separate package (workers/ai-worker, package name researchmate_worker) because its runtime profile is opposite to the API's. The API answers in milliseconds and is killed if a request takes too long; the worker runs jobs that take minutes (PDF parsing, chunking, vector indexing, evidence review) and must survive crashes — it restarts, retries, and is killable without losing work. Bundling the worker into the API package would let an import from the API accidentally pull Celery into a request path; keeping them separate forces every cross-boundary call to go through a real task queue.

Interview question trees

Why is the API and worker connected via an outbox, not direct task.delay()?
├─ What problem does the outbox solve?
│  └─ [Project fact] API writes outbox_events row + business data in one DB transaction; the dispatcher polls and enqueues; avoids the "DB committed but task lost" race
└─ What happens if the dispatcher enqueues the same task twice?
   └─ [Project fact] ingestion and evidence tasks are idempotent on document_id / run_id; replay is safe

How are long-running workflows protected from being killed mid-execution?
├─ [Project fact] Celery soft_time_limit + task_acks_late; SoftTimeLimitExceeded has an explicit handler ahead of except Exception (the broad catch would swallow it otherwise)
└─ [Interview extension] Why can't Celery's soft timeout interrupt a blocking C call?
   └─ Soft timeout raises between Python bytecodes; boto3 / C-extension calls ignore it; only SIGKILL is a hard backstop

[Project fact] Top-level tests + declarative infra

4. Why tests live at the top, and where infra lives

Tests at the top level and infra in declarative files are the two structural choices that survive scaling. Both come from the same principle: the repo layout should tell you what is deployed and what is verified, not what one developer happened to organize first.

Tests live at the top level (tests/, 52 pytest files), not inside each app's directory. The reason is that the most important tests cross the boundary between the API and the worker — a document upload triggers an outbox row, which the worker consumes, which writes back evidence that the next Ask reads. Putting these tests inside apps/api would force them to import the worker package across a workspace boundary; putting them at the top lets them import both researchmate_api and researchmate_worker cleanly. One test:python command from the repo root runs all 52 files with a 69% coverage gate.

Infra is declarative-only — everything that runs in production is defined in files you can read here. Three things to know: 21 SQL migrations in infra/supabase/migrations/ own the database schema; render.yaml owns the deploy (one Render Free web service, Docker, health check on /api/v1/healthz, ~48 env vars); scripts/ owns one-off provisioning tools that run on container start or on demand.
