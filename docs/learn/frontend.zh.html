主题 1 · 代理旁路

服务端 rewrite:绕过企业代理对跨域请求的拦截

用户打开聊天页时,浏览器必须调后端。后端在 Render 的 *.onrender.com,和前端在 Vercel 上的源不是同一个。正常情况下浏览器会直接发跨域请求。本项目把请求改走 Next.js,让浏览器只看到自己的源,由 Vercel 服务端发起真正的 server-to-server 跳。

问题 [项目事实]

有些企业或 ISP 代理坐在用户和互联网之间。它们看到浏览器直连 *.onrender.com 时,有时会返回一个 HTML 警告页而不是 JSON。浏览器接着去做 response.json() 解析失败,UI 就显示 unknown client error。

机制 [项目事实]

next.config.ts 声明了一个 async rewrites(),只配一条规则:source: "/api/v1/:path*" → destination: ${backendOrigin}/api/v1/:path*。backendOrigin 是把 NEXT_PUBLIC_API_BASE_URL 的 /api/v1 后缀剥掉得到。NODE_ENV=development 时函数返回 [],浏览器直连 http://localhost:8000/api/v1,不走 rewrite。

同源为何能赢

当浏览器只看到自己的源时,代理没有跨域规则可匹配,根本不会拦截。Vercel 的边缘节点到 Render 走的是纯服务端网络,企业代理不在路径上。

代价

所有 API 流量都要经 Vercel 边缘函数中转,不能浏览器直连后端。[合理推断] 这样多了一跳网络,吞吐受 Vercel 函数边界限制。代价可以接受,因为项目是单租户,而且最重的 SSE 是流式的,不是一次性缓冲。

被否决的替代方案 [合理推断]: 预签名直传 URL 或直接开 CORS 的后端方案在 chat 路径上被否决。API 需要把 bearer token 放进 Authorization header;开 CORS 还会把后端域名重新暴露给企业代理。
Q1: 为什么不让浏览器直连 Render?
→ 路径上的代理会返回 HTML 而不是 JSON,response.json() 抛错,UI 显示 "unknown client error"。
Q2: rewrites() 为什么声明成 async?
→ 函数必须返回数组;async 形式可以在构建或请求时读环境变量。它在 config 求值时读 NEXT_PUBLIC_API_BASE_URL。
Q3: Vercel 边缘挂了会怎样?
→ 所有 API 和 SSE 流量都失败。[面试扩展] 前端没有直连 Render 的回退;describeApiError 把 5xx 映射为 "provider unavailable",用户可以重试。

主题 2 · API 客户端与流式

fetch + 手写 SSE 解析,无 EventSource,AbortSignal 取消

用户提一个问题后,后端会创建一个 "run",可能要跑 20+ 秒。用户没法盯着 spinner 等这么久。项目把 run 的进度事件流式推给前端,UI 就能按节点逐条更新。浏览器自带的 EventSource API 不能设自定义 header,所以项目用 fetch 响应体的 ReadableStream reader 读流。

apiFetch<T>

所有 JSON 请求都走它。建一个 Headers,body 存在时设 Content-Type: application/json,并通过 getAccessToken() 设 Authorization: Bearer ${token}。调用 fetch。总是 response.json()(带 .catch(() => ({})) 兜底非 JSON 错误体,保证解析错误不会盖过真正的 HTTP 失败),然后通过 toApiError 抛 ApiError 或返回类型化 body。[项目事实]

streamRunEvents

接收一个 runId、一个 afterSequence 游标、一个 onEvent 回调和一个 AbortSignal。请求 /runs/${runId}/events?after_sequence=N,带 Accept: text/event-stream 和 bearer header。取 response.body.getReader(),用 TextDecoder 把原始字节解码进字符串 buffer。按 "\n\n" 切分 buffer(SSE 规范用空行分隔事件);frames.pop() 把最后那块不完整的留在 buffer 里,下一次解码不会把帧切到一半。对每个完整帧,找到以 "data: " 开头的行,从偏移 6 处 JSON.parse 它。异常帧被 try/catch 静默吞掉,一个坏 provider 事件不会拖死整条流。[项目事实]

getAccessToken

本地开发返回 getDevToken()(读 localStorage.researchmate_token,没有就降级回 "dev")。生产调用 getSupabaseSession(),从 HttpOnly cookie 路由恢复 session。无 session 抛 ApiError(401, AUTH_REQUIRED);Supabase 刷新失败抛 503 AUTH_PROVIDER_UNAVAILABLE。[项目事实]

describeApiError

把 ApiError 映射成面向用户的 {title, detail, kind} 三元组:401→auth,403→permission,409→conflict,429→limit,5xx→provider,默认→validation。驱动 AuthGate、ConversationThread、Library 里的 StateNotice 样式。[项目事实]

为什么不用浏览器自带的 EventSource [项目事实 + 合理推断]

浏览器 EventSource API 可以连一个 URL 自动收 SSE 事件,但它不能设自定义请求头。本项目的事件端点要求 Authorization: Bearer,没有这头后端会返 401。所以项目必须用 fetch + ReadableStream reader,自己解析 SSE 帧。代价是要自己实现重连;当前代码不自动重连,靠下面的轮询兜底作最后一道防线。

轮询兜底: Research 页在 run 处于 running 或 waiting_human 时,并行跑一个 setTimeout(3000) 轮询 GET /runs/${run_id}。即使 SSE 流死了,canonical run 状态仍能通过轮询恢复。[项目事实]
Q1: 为什么按 "\n\n" 切 buffer?
→ SSE 规范用空行分隔事件。pop() 把最后那块不完整的尾部留在 buffer,下一次 decode(value, {stream:true}) 不会把帧切到一半。
Q2: 异常 JSON 帧怎么处理?
→ try/catch 静默吞掉。设计选择:一条长 run 流里一个坏 provider 帧不该让整条流崩。代价:结构坏掉的流不会报可见错误;轮询兜底是最后一道防线。
Q3: 客户端怎么取消流?
→ 调用方传一个 AbortController().signal,fetch 透传 abort。[优化建议] Research 页目前创建的 AbortController 在 unmount 时没调 abort();应该用 useEffect cleanup 调 controller.abort(),在页面卸载时停止流。

主题 3 · App Router

Next.js 16 App Router:URL 怎么变成页面

用户键入一个 URL 时,Next.js 把路径映射到磁盘上的文件,并决定哪些代码在服务端跑、哪些在浏览器跑。服务端关注点(根 HTML layout、安全 header、rewrites 配置、每请求 nonce)在框架边缘,在任何 React 树渲染之前就跑完。每页状态和交互是孤立的客户端孤岛,在文件顶部用 "use client" 标记。

技术栈 [项目事实]

Next.js 16.3.0、React 19.2.8、App Router、Turbopack、静态导出到 Vercel。reactStrictMode: true。distDir 可由 NEXT_DIST_DIR 覆盖,这样 E2E 构建能用 .next-e2e 不和 dev 构建撞。

用到的文件约定

嵌套 layout:app/layout.tsx(根,设 nonce context)、app/app/layout.tsx(鉴权 shell,包 AuthGate 和 AppSidebar)、app/app/projects/[projectId]/*(项目作用域页)。页面文件和组件同放在 app/components/。无 Server Actions 或数据 Route Handler 处理业务数据 —— 数据全走 apiFetch,只有两个 cookie Route Handler(POST /api/auth/session 写、GET /api/auth/session/get 读 session)。[项目事实]

客户端孤岛

重交互页如 research/page.tsx 和聊天 workspace 以 "use client" 开头。根 layout 和 middleware 留在服务端,这样 nonce 和静态 CSP 可以在任何 HTML 流到浏览器之前注入。[合理推断]

路径别名

tsconfig.json 把 @/* → ./app/* 指向,所以 @/components/ui/button 解析到仓库内的 shadcn/ui 副本,而不是 npm 包。[项目事实]

为什么 App Router 而不是 Pages Router [合理推断]: 服务端 rewrites()、静态 headers() 配置、每请求 middleware 都需要 App Router 的请求管线。迁回 Pages Router 就要自建 Node server,丢掉 Vercel 边缘部署。
Q1: auth token 存在哪?
→ 存在 HttpOnly cookie 里,由 POST /api/auth/session Route Handler 写,GET /api/auth/session/get 读。session token 不进 localStorage。[项目事实]
Q2: 为什么用两个 cookie Route Handler,而不是在 middleware 里写 cookies()?
→ [合理推断] middleware 在每个请求(含静态资源)上跑;在那写 cookie 会在热路径上加延迟。两个窄 Route 把写成本集中到 session 真正轮转的地方。
Q3: 页面等 apiFetch 时渲染什么?
→ 客户端页先渲染骨架或空态,useEffect 再 resolve apiFetch 并 setState。没有 RSC 数据流式 —— 数据页都是纯客户端孤岛。

主题 4 · 状态与竞态保护

useChatWorkspace:仅 hooks 状态 + 四道竞态防线

用户输入问题按发送时,有三件事在赛跑:乐观 UI 要立刻显示这条消息;如果用户双击,网络请求不能发两次;如果用户中途切了会话,响应不能落到错误的会话上。项目没有 Redux 或 Zustand,用一个 useChatWorkspace 自定义 hook 独占所有聊天状态和四道相互独立的竞态守卫。Research 页用更小的状态集镜像同一形态。

状态形态 [项目事实]

16 个 useState:conversationId、messages、message、webEnabled、historyLoading、sending、slowResponse、error、documents、uploading、quizOpen、quizPrompt、quiz、quizLoading、degradedNotice、resolvedProject。按关注点(chat、upload、quiz)分组,不全局扁平化。

守护用 ref [项目事实]

8 个 useRef:fileInput、threadEnd、loadGeneration、askIntent、quizIntent、quizHistoryLoadedFor、askInFlight、quizInFlight。刻意用 ref 不用 state —— 守卫会改它,但决不能触发重渲染。

Effects [项目事实]

useEffect 覆盖:bootstrap 个人 project、load 会话(带 generation 守卫)、自动滚动、slowResponse 10s 定时器、文档状态每 2s 轮询、quiz 历史加载。每个 effect 取一个 active 标志,或在 cleanup 里自增 generation 计数,陈旧异步结果直接丢弃。

幂等 intent [项目事实]

idempotent-intent.ts 的 resolveIntentKey 用请求参数 JSON 指纹。指纹没变 → 复用原 Idempotency-Key;指纹变了 → 铸新 prefix-uuid。所以失败后重试发同一个 key,而新问题发新 key —— 后端可以据此对重试去重,又不会把两次不同问题合并。

四道竞态模式 [项目事实]

(1) generation 计数器:cleanup 里跑 ++loadGeneration.current;响应回来时 generation !== loadGeneration.current 就 bail。(2) 在飞标志:askInFlight.current = true 拦第二个 submitQuestion,第一个没回时不让发。(3) active 标志:let active = true 在 cleanup 时翻 false,组件已经切走时晚到的结果被忽略。(4) intent 指纹:让重试复用同一个幂等 key,不重新签发。

跨组件通信 [项目事实]

无 React Context。用 window.dispatchEvent(new Event("researchmate:sidebar-refresh")) 和 "researchmate:sources-refresh"。sidebar 通过 addEventListener 订阅,cleanup 里退订。代价:这是隐式契约 —— 事件名打错字会静默失败。

Q1: 为什么用 generation 计数器,不直接 abort 请求?
→ abort 取消的是 HTTP 传输。计数器还能拦住"组件已切走后响应才到"的场景。它是逻辑陈旧守卫,不是传输取消。
Q2: 为什么不用全局 store?
→ 单一 chat 页独占状态;跨页同步走事件总线。[合理推断] 全局 store 要为本来小、本就限于一页的状态图付 bundle 和间接成本。
Q3: 两次 submitQuestion 撞车会怎样?
→ askInFlight.current 拦下第二个。第一个失败时乐观消息移除,草稿恢复,用户用同一个 Idempotency-Key 重试,由后端去重。

主题 5 · CSP + 鉴权边界

每请求 nonce、显式 connect-src 白名单、HttpOnly session

内容安全策略(CSP)是一种浏览器防御:它告诉浏览器这个页面允许跑哪些脚本、用什么样式、连哪些域名。如果攻击者通过用户输入注入了一个 <script> 标签,浏览器会拒绝执行,因为它不在可信来源里。本项目分三层:next.config.ts 的静态 CSP 作纵深防御、middleware.ts 注入每请求 nonce 替换掉 'unsafe-inline'、csp-origins.ts 的共享白名单源。

静态 CSP [项目事实]

buildStaticCsp() 拼接 11 条指令:default-src 'self'; script-src 'self'(+ dev 下 'unsafe-eval'); style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; font-src 'self' data:; connect-src 'self' <白名单>(+ dev localhost); object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; worker-src 'self' blob:。

nonce 机制 [项目事实]

middleware.ts 在每页 + API 路由上跑(matcher 跳过 _next/static、_next/image、favicon.ico、icon.svg)。它调 crypto.randomUUID().replaceAll("-","") 生成 32 位 hex nonce,通过 x-researchmate-nonce 请求头转发给 React 树,让 layout 和组件把它附到内联 script,再用 buildNonceCsp(nonce) 设运行时 CSP。每个请求拿一个新 nonce,所以一个请求里的 nonce 被偷走,后面也用不了。

connect-src 白名单 [项目事实]

allowedConnectOrigins 只含两项:safeOrigin(NEXT_PUBLIC_SUPABASE_URL) 和 safeOrigin(BACKEND_API_BASE)。provider 端点(NVIDIA、Tavily、Langfuse)刻意缺席 —— 这些调用都在 FastAPI worker 上 server-to-server,在那 CSP 不生效,所以它们根本不需要进浏览器 bundle。

鉴权边界 [项目事实]

session token 存在 HttpOnly cookie 里,浏览器的 JS 直接读不到。两个 Route Handler 负责写和读 cookie。getSupabaseSession 在过期前 60s 刷新 token。浏览器 Authorization: Bearer header 是 token 唯一触到 JS 可读内存的地方,而且只在一次 fetch 调用里。

SEC-4 / SEC-5 历史 [项目事实]: 早期 CSP 在 connect-src 用过宽容的 https: 通配,在 script-src 用静态 'unsafe-inline'。都已移除:通配换成显式两白名单;'unsafe-inline' 换成每请求 nonce。
Q1: 为什么用 nonce 而不是 hash 策略?
→ hash 策略要构建时知道内联 script 内容。Next.js 页面会发与运行时数据相关的内联 script;每请求 nonce 是更务实的匹配。
Q2: style-src 为什么还是 'unsafe-inline'?
→ [项目事实] Tailwind 和 shadcn/ui 依赖内联 style 来做变体与主题。代价接受:script 注入是更高风险面;有 object-src 'none' 和 frame-ancestors 'none' 兜底时,style 注入风险较低。
Q3: XSS 调 fetch 调 API,什么能拦?
→ CSP 拦不住 —— 一旦 script 在页上跑起来,就能调同源。纵深防御靠分层:无 nonce 不内联 script、provider 端点不进 bundle、session token 永不进 JS 可读存储,使 XSS 无法外泄 refresh token。
