前端模块详解

apps/web 是 ResearchMate 的 Next.js 前端应用,部署在 Vercel。包含 54 个源码文件(不含配置和资源文件),覆盖页面路由、React 组件、API 客户端、认证逻辑和 E2E 测试。本页面逐文件解析每个模块的作用、关键逻辑和依赖关系,并以切片视角追踪一个 Ask 请求从前端到后端的完整旅程。

Next.js 16.3.0 · App Router React · Client Components Tailwind CSS v4.3.3 shadcn/ui · 15 组件 Supabase Auth · GitHub OAuth Vitest 4.1.10 · Playwright 1.62.1

技术栈基础

核心技术栈

apps/web 使用以下 7 项核心技术,每项选择都有明确的项目场景驱动。下方 fact card 逐项说明版本、用途和项目中的实际用法。

Next.js 16.3.0

React 全栈框架,使用 App Router 文件路由系统。静态导出部署在 Vercel,通过 next.config.ts 的 rewrites 将 /api/v1/* 请求代理到 Render 后端,绕过企业代理对跨域请求的拦截。reactStrictMode 开启,使用 Turbopack 构建。distDir 可通过 NEXT_DIST_DIR 环境变量覆盖(E2E 使用 .next-e2e)。

React

UI 库,大量使用 Client Components("use client")。通过 hooks(useState, useEffect, useRef, useMemo, useCallback)管理状态,不使用 Redux 或 Zustand 等外部状态库。组件分为容器组件(ChatWorkspace)、展示组件(ConversationThread, ChatComposer)和 UI 原语(ui/*)三层。

Tailwind CSS v4.3.3

原子化 CSS 框架,通过 @tailwindcss/postcss 插件集成。globals.css 使用 @import "tailwindcss" 和 @theme inline 定义设计令牌(CSS 变量),支持 light/dark 双主题和 prefers-reduced-motion。组件使用 cn() 工具函数合并 Tailwind 类名。

shadcn/ui

基于 Radix UI 原语的可定制组件系统。apps/web 包含 15 个 ui/ 组件,依赖 9 个 @radix-ui 包。组件使用 class-variance-authority(cva)定义变体,通过 tailwind-merge 去重冲突的类名。不是 npm 包,而是复制到项目中的源码文件。

Vitest 4.1.10

单元测试框架,使用 jsdom 环境模拟浏览器。通过 @vitest/coverage-v8 收集覆盖率,覆盖 app/lib/**/*.ts 和 app/components/**/*.{ts,tsx},覆盖率基线 40%(lines/statements)。测试文件与源码同目录(.test.ts 后缀),共 11 个测试文件:7 个组件测试(app-sidebar、auth-gate、evaluation-report、feedback-workflow、presentation、project-nav、use-chat-workspace)与 4 个 lib 测试(api、demo、idempotent-intent、supabase)。

Playwright 1.62.1

E2E 测试框架,仅使用 Chromium。通过 webServer 配置在 127.0.0.1:3100 启动 demo 模式 Next.js,测试文件在 e2e/ 目录。验证完整用户旅程:发消息、看引用、建项目、生成 quiz,同时检查无浏览器错误和外部请求。

Supabase Auth

认证服务,支持 GitHub OAuth 和邮箱密码。supabase.ts 自实现浏览器端 session 管理(不依赖 @supabase/supabase-js),包括 JWT 解码、refresh token 轮转、HttpOnly cookie 持久化(通过 POST /api/auth/session 写入 + GET /api/auth/session/get 读取 —— session token 不再进入 localStorage)和 OAuth 重定向恢复。AuthGate 组件守卫所有受保护路由。

逐文件详解

页面路由文件

Next.js App Router 使用文件系统路由:文件夹名映射为 URL 段,layout.tsx 和 page.tsx 是特殊文件。下方逐个解析每个路由文件的作用。

app/layout.tsx

根布局(root layout),是整个应用的 HTML 外壳。导出 metadata 对象(title/description),导入 globals.css 设计系统,设置 <html lang="en" data-scroll-behavior="smooth">。每个路由的 children 都被包裹在这个布局中。这是唯一一个不使用 "use client" 的布局文件。

app/page.tsx

首页(/),客户端组件。用 AuthGate 包裹一个 AuthenticatedRedirect 组件:已认证用户通过 router.replace("/app") 直接跳转到工作区,未认证用户看到 AuthGate 的登录面板。展示一个带 Loader2 旋转动画的 "Opening your workspace..." 状态。

app/app/layout.tsx

受保护应用布局,包裹所有 /app/* 路由。用 AuthGate 包裹 AppSidebar + 内容区域。Sidebar 用 Suspense 包裹,fallback 是一个 260px 宽的空 aside。整体布局是 flex h-[100dvh],Sidebar 左侧固定,内容区域 flex-1 填充剩余空间。

app/app/page.tsx

个人聊天路由(/app),客户端组件。用 Suspense 包裹 ChatWorkspace(不传 projectId),fallback 是一个 "Starting chat" 骨架屏。Suspense 是必需的,因为 ChatWorkspace 内部使用 useSearchParams 读取 URL 中的 conversation 和 new 参数。

projects/[projectId]/page.tsx

项目根路由,服务端组件。接收 params: Promise<{ projectId: string }>(Next.js 16 的 async params),直接 redirect 到 /app/projects/${projectId}/chat。确保每个项目只有一个规范入口路由。

projects/[projectId]/chat/page.tsx

项目聊天路由,客户端组件。用 useParams 读取 projectId,通过 apiFetch 加载项目名称,然后渲染 ChatWorkspace 并传入 projectId、projectName 和 projectMode=true。外层 Suspense 处理 useParams 的异步边界。

projects/[projectId]/library/page.tsx

来源库页面,功能最丰富的路由之一。支持文件上传(拖拽 + 选择)、手动文本回退、文档列表搜索、文档删除(带确认 + 异步 job 轮询)。使用 ProjectNav 顶部导航,文档状态用 Badge 组件展示(ready/uploading/parsing/failed 等),处理中状态每 2 秒轮询刷新。

projects/[projectId]/quiz/page.tsx

Quiz 旧路由,服务端组件。直接 redirect 到 /app/projects/${projectId}/chat?quiz=1。Quiz 功能已从独立页面迁移到 chat 页面的 ProjectQuizDrawer 抽屉,此路由保留向后兼容。

projects/[projectId]/labs/page.tsx

工程实验室页面,角色受限。通过 getSupabaseSession 检查 session.user.role 是否为 developer 或 admin。包含三个面板:评估运行(选择 dataset + pipeline + metrics)、可靠性指标(run_count, success_rate, p95, cost)、故障注入练习(llm_timeout, qdrant_unavailable 等,10 秒限时)。

dev/layout.tsx

开发者路由布局,用 AuthGate 包裹所有 /dev/* 路由。确保开发者工具页面也需要认证,但不像 labs 那样做角色检查(角色检查在后端 API 层执行)。

dev/traces/[traceId]/page.tsx

开发者追踪查看器,客户端组件。通过 apiFetch<DeveloperTrace> 加载执行追踪,以 JSON pre 块展示 execution_plan、validation_result、retrieved_chunks 和 tool_calls。API 密钥、OAuth 令牌等敏感数据在后端已被过滤。

组件层详解

业务组件

apps/web 有 10 个业务组件(不含 15 个 ui/ 原语),分为容器组件、展示组件和导航组件。下方逐个解析 Props 数量、职责和关键逻辑。

chat-workspace.tsx — 聊天容器(组合根,3 Props)

容器组件,将状态逻辑(useChatWorkspace)与展示组件(ConversationThread, ChatComposer, ProjectQuizDrawer)组合。Props 仅 3 个:projectId?, projectName?, projectMode?。projectMode 为 true 时渲染项目工具栏(New chat / Quiz / Sources 按钮)和 Quiz 抽屉。个人聊天不传任何 Props,由 Hook 自行 bootstrap。

use-chat-workspace.ts — 状态 Hook(核心编排)

自定义 Hook,是前端最复杂的模块。接收 { suppliedProjectId?, projectMode },管理 16 个 useState、8 个 useRef、5 个 useEffect、1 个 useMemo。返回 25+ 个字段和方法。核心职责:对话加载(带 generation 竞态保护)、消息发送(乐观更新 + 幂等键 + intent 指纹)、文件上传(signed URL 流程)、Quiz 生成(幂等 + 历史加载)、事件总线(researchmate:sidebar-refresh)。

chat-composer.tsx — 输入区(13 Props)

展示组件负责文件上传、消息输入、Web 搜索开关和发送。Props 数量：13。Enter 提交，Shift+Enter 换行。共享上传契约接受 42 种文档、表格、文本/数据、Notebook 和源码格式。

conversation-thread.tsx — 对话线程(11 Props)

展示组件,渲染消息列表、引用、加载状态和错误通知。Props 数量:11。messages, historyLoading, sending, slowResponse, error, degradedNotice, projectMode, projectName, threadEnd(RefObject), onDismissError, onSelectPrompt。空对话时展示 3 个引导提示(EMPTY_PROMPTS)。引用以 details 折叠展示,支持 local_doc 和 web_page 两种 source_type。"thinking" 动画用三个 CSS 动画圆点(rm-thinking keyframe)。slowResponse 10 秒后展示 "Still working" 提示。

app-sidebar.tsx — 导航侧边栏

客户端组件,管理项目列表、对话列表和它们的 CRUD。使用 usePathname + useSearchParams 识别当前活跃项。功能:新建项目(Dialog 表单)、重命名对话(PATCH)、删除对话(带确认状态)、删除项目(异步 job 轮询,最多 20 次,每次 1.5 秒)。桌面端可折叠(72px / 260px),移动端用 Sheet 组件。通过 researchmate:sidebar-refresh 事件总线触发刷新。使用 requestGeneration ref 防止竞态。

auth-gate.tsx — 认证守卫(5 状态)

客户端组件,守卫所有受保护路由。5 种状态:loading(恢复 session)、signed_out(展示 GitHub 登录面板)、signed_in(渲染 children + session bar)、misconfigured(Supabase 未配置)、error(session 恢复失败)。本地开发直接放行(isLocalDevelopment())。Demo 模式展示静态横幅后放行。挂载时调用 warmApi() 预热 API 健康检查,降低首次请求延迟。

project-quiz-drawer.tsx — Quiz 抽屉(7 Props)

展示组件,固定定位在右侧(最大 430px)。Props: prompt, quiz, loading, onPromptChange, onSubmit, onClose, onReset。两种模式:无 quiz 时展示生成表单(Textarea + 默认 3 单选 + 2 填空 + 2 主观);有 quiz 时以 details 折叠展示每道题(题目/选项/答案/解释)。文案 "Uses available indexed project resources" 避免过度承诺资源覆盖率。

project-nav.tsx — 项目内导航

客户端组件,渲染项目顶部导航栏。Props: projectId, current("chat" | "library" | "evidence" | "quiz" | "labs")。通过 apiFetch 加载项目名称,展示 Chat / Sources / Quiz 三个链接(Quiz 链接到 chat?quiz=1)。当前页面用 aria-current="page" 和高亮样式标记。

state-notice.tsx — 通知组件

展示组件,渲染带分类的恢复通知。Props: state(title, detail, kind), action?(ReactNode)。kind 为 error 或 provider 时 role="alert",其他为 role="status"。在 AuthGate、ConversationThread、Library 页面中复用,确保错误/状态通知风格一致。

brand-logo.tsx — 品牌 logo

展示组件,使用 next/image 渲染 researchmate-logo-mark.png。Props: withName(默认 false)。logo 区域 36x36px,unoptimized + priority。withName 为 true 时额外渲染 "ResearchMate" 文字。aria-hidden="true" 隐藏装饰性图片。

lib 层详解

lib 模块

app/lib/ 包含 6 个模块,是前端的核心基础设施:API 传输、认证、demo 运行时、幂等协调、工具函数和限流。下方逐个解析导出的函数和类型。

api.ts

API 客户端 + 类型契约,是前后端契约的前端镜像。导出 30+ 个 TypeScript interface 和 8 个核心函数。apiFetch<T>:统一 fetch 封装,注入 Authorization header 和 Content-Type,错误时抛 ApiError。getAccessToken:解析 bearer token(本地 dev 或 Supabase session)。describeApiError:将 HTTP 状态码映射为用户友好消息(401→auth, 403→permission, 429→limit, 5xx→provider)。streamRunEvents:消费 SSE 事件流,按 \n\n 分帧解析 data: 行。idempotencyKey:生成 prefix-uuid 格式的幂等键。warmApi:单次 best-effort /healthz 预热请求。API_BASE 在生产环境为 /api/v1(同源 rewrite),本地为 NEXT_PUBLIC_API_BASE_URL。

supabase.ts

浏览器端 Supabase Auth 实现,不依赖 @supabase/supabase-js SDK。自实现 5 个核心函数:getSupabaseSession(恢复/刷新 session)、onAuthStateChange(订阅)、signInWithGitHub(OAuth 跳转)、signOut(登出 + 清理)、signInWithPassword / signUpWithPassword / sendMagicLink(邮箱流程)。session 通过 POST /api/auth/session 写入/清除、GET /api/auth/session/get 读取 HttpOnly cookie —— SEC-3 加固:token 永不进入 localStorage 或任何 JS 可读存储。过期前 60 秒自动刷新(refresh skew)。JWT 的 email/role 通过 identityFromAccessToken 解码 base64 payload。workspaceRedirect 强制重定向 URL 必须在 /app 路径下,防止开放重定向。SupabaseAuthError 保留 provider status 和 code。

demo.ts

确定性浏览器 demo 运行时,通过 NEXT_PUBLIC_DEMO_MODE=true 启用。当 isPublicDemo() 为 true 时,apiFetch 委托给 demoFetch。demoFetch 实现了完整 API 子集:项目 CRUD、对话 CRUD、消息列表、文档上传-url/complete、ask、quiz、pipeline-versions、research-runs、evaluation-runs、reliability、traces、fault-scenarios。所有数据存储在模块级变量中(projects, documents, chatMessages, quizSets),不发送任何网络请求。demoRunEvents 发射 2 个确定性事件(retrieve + report_published)。

idempotent-intent.ts

幂等 intent 跟踪器,确保失败重试复用同一个 Idempotency-Key。导出 IntentKeyState 接口(fingerprint + key)和 2 个函数。resolveIntentKey:如果 fingerprint 未变则返回现有 key,否则创建新 key。fingerprint 是请求参数的 JSON 序列化。clearCompletedIntent:成功的请求清除对应的 intent。与 api.ts 的 idempotencyKey 配合使用,在 use-chat-workspace.ts 的 submitQuestion 和 generateQuiz 中应用。

utils.ts

工具函数模块,仅导出 cn(...inputs: ClassValue[])。组合 clsx(条件类名)和 tailwind-merge(去重冲突的 Tailwind 类),是所有 shadcn/ui 组件和业务组件的类名合并基础。例如 cn("px-2 py-1", condition && "bg-accent") → "px-2 py-1 bg-accent"。

auth-email-rate-limit.ts

浏览器端邮件限流守卫,镜像 Supabase 的 per-user 冷却时间。导出 AUTH_EMAIL_COOLDOWN_MS(60 秒)和 2 个函数。remainingEmailCooldown:计算剩余秒数。nextEmailCooldown:计算下次允许时间戳。确保前端不会在冷却期内重复发送 magic link 或确认邮件请求。

API 请求切片

一个 Ask 请求的 6 步前端旅程

从用户按下发送按钮到收到带引用的回答,请求在前端经过 6 个步骤。每步涉及不同文件,下方 proof-chain 展示完整流转。

1. 表单提交chat-composer.tsx:用户输入消息 → Enter 或点击发送 → onSubmit(event) → 调用 workspace.submitQuestion。发送按钮在 !message.trim() || sending || historyLoading 时禁用。
2. Hook 编排use-chat-workspace.ts:submitQuestion 构建 fingerprint(JSON.stringify 请求参数)→ resolveIntentKey 复用或创建幂等键 → 添加乐观用户消息 → setSending(true) → 调用 apiFetch<AskResponse>("/ask", ...) 并传入 Idempotency-Key header。
3. Token 解析api.ts:apiFetch 调用 getAccessToken() → 本地 dev 返回 getDevToken()(仅开发用的 localStorage token)→ 生产环境调用 getSupabaseSession(),后者通过 GET /api/auth/session/get 读取 HttpOnly cookie 中的 JWT access_token → 注入 Authorization: Bearer ${token} header。Session token 永不进入 localStorage(SEC-3)。
4. Session 检查supabase.ts:getSupabaseSession 从 HttpOnly cookie 加载 session → 如果距过期不足 60 秒则调用 refreshSession(用 refresh_token 换新 access_token,再通过 POST /api/auth/session 重新写入 cookie)→ 返回有效 session 或 null(触发 401 错误)。
5. HTTP 请求fetch: POST ${API_BASE}/ask,body 包含 project_id, conversation_id, message, web_enabled。API_BASE 在生产环境是 /api/v1(同源 rewrite 到 Render),本地是 http://localhost:8000/api/v1。Demo 模式委托给 demoFetch。
6. 响应处理use-chat-workspace.ts:解析 AskResponse(answer, citations, conversation_id, degraded flags)→ 替换乐观消息 + 添加 assistant 消息 → setConversationId → router.replace 更新 URL → dispatchEvent("researchmate:sidebar-refresh") → 失败时移除乐观消息 + 恢复草稿 + 展示错误。
竞态保护:askInFlight.current ref 防止并发重复提交。如果请求失败,乐观消息被移除,草稿恢复到输入框,用户可以重试且 resolveIntentKey 会复用同一个 Idempotency-Key(fingerprint 未变)。

状态管理

React Hooks 与竞态保护

apps/web 不使用 Redux/Zustand 等外部状态库,全部通过 React Hooks 管理状态。下方解析各 Hook 的使用模式和项目特有的竞态保护机制。

useState(16+ 状态变量)

use-chat-workspace.ts 管理最密集:conversationId, messages, message, webEnabled, historyLoading, sending, slowResponse, error, documents, uploading, quizOpen, quizPrompt, quiz, quizLoading, degradedNotice, resolvedProject。app-sidebar.tsx 另有 collapsed, mobileOpen, projects, conversations, personalProjectId, creatingProject 等 12 个。

useEffect(5+ 副作用)

use-chat-workspace.ts:(1) bootstrap 个人项目;(2) 加载对话(generation 竞态保护);(3) 自动滚动到底部;(4) slowResponse 10 秒定时器;(5) 文档处理状态轮询(2 秒间隔);(6) Quiz 历史加载。每个 effect 都有 active 标志或 cleanup 防止内存泄漏。

useRef(8 个 ref)

fileInput(文件输入引用), threadEnd(滚动锚点), loadGeneration(对话加载竞态计数器), askIntent/quizIntent(幂等 intent 状态), quizHistoryLoadedFor(防止重复加载 Quiz 历史), askInFlight/quizInFlight(防止并发重复请求)。app-sidebar 另有 requestGeneration。

useMemo(3 处)

readyAttachments:过滤 status==="ready" 的文档。personalConversations:过滤个人项目的对话。activeProjectConversations:过滤当前项目的对话。避免每次渲染重新计算过滤结果。

useCallback(1 处)

app-sidebar.tsx 的 loadNavigation:并行加载项目列表 + 对话列表 + 个人项目。用 requestGeneration ref 拒绝过期的并发响应。作为 useEffect 的依赖项,必须 useCallback 以避免无限重渲染。

自定义 Hook

useChatWorkspace 是唯一自定义 Hook,封装聊天工作区的全部状态和动作。接收 { suppliedProjectId?, projectMode },返回 25+ 个字段。将状态逻辑从展示组件中完全分离,使 ChatWorkspace 成为纯组合根。

事件总线

使用 window.dispatchEvent(new Event("researchmate:sidebar-refresh")) 和 "researchmate:sources-refresh" 在组件间通信。当发送消息或上传文件后,触发 sidebar 刷新以更新对话列表。Sidebar 通过 window.addEventListener 订阅,在 useEffect cleanup 中取消订阅。不使用 React Context 或全局 store。

竞态保护(4 种模式)

(1) Generation counter: loadGeneration.current / requestGeneration.current,每次请求递增,响应到达时检查是否仍为最新。(2) In-flight flag: askInFlight.current / quizInFlight.current,防止并发提交。(3) Active flag: let active = true,cleanup 时设为 false。(4) Intent fingerprint: resolveIntentKey 确保相同参数复用幂等键。

文件上传切片

文件上传的 3 步流程

支持的文件经过三个步骤完成摄取：预留上传、将原始字节 PUT 到对象存储、通知后端解析并建立索引。

1. 文件选择chat-composer.tsx 使用共享的 SUPPORTED_FILE_ACCEPT；Library 页拖拽上传使用同一份格式契约。
2. 上传编排use-chat-workspace.ts 通过 isSupportedFileName() 校验文件；fileTypeFromName() 与 mimeForFileType() 在预留 → PUT → 完成之前生成规范元数据。
3. 状态刷新use-chat-workspace.ts:项目模式 dispatch "researchmate:sources-refresh" 事件 → 个人模式 setDocuments 刷新文档列表 → 如果文档处于处理中状态,启动 2 秒轮询定时器直到所有文档变为 ready/failed。Library 页面同样轮询 loadDocuments。
Signed URL 模式:前端不通过后端中转文件二进制数据,而是直接 PUT 到 R2 对象存储的 presigned URL。这减少了后端带宽压力,但要求 R2 的 CORS 配置允许浏览器的 PUT 请求。

配置文件详解

构建与测试配置

apps/web 根目录有 6 个配置文件,分别控制 Next.js 构建、TypeScript 类型检查、PostCSS/Tailwind、Vitest 单元测试和 Playwright E2E 测试。

next.config.ts

Next.js 构建配置。安全 headers:Content-Security-Policy(default-src 'self';script-src 'self' 由 middleware.ts 注入每请求 nonce,移除静态 'unsafe-inline';connect-src 'self' 加显式 origin 白名单 —— 仅 Supabase URL、API base(后端专属的 NVIDIA/Tavily/Langfuse 按架构设计不进入浏览器 bundle)—— 移除之前的 https: 通配符;+ 开发环境 localhost)、Referrer-Policy、Permissions-Policy(camera/microphone/geolocation 全部禁用)、X-Content-Type-Options: nosniff、X-Frame-Options: DENY。Origin 白名单集中在 app/lib/csp-origins.ts,next.config.ts(静态兜底 CSP)与 middleware.ts(运行时 nonce CSP)共用同一来源。Rewrites:生产环境将 /api/v1/:path* 代理到 Render 后端(backendOrigin/api/v1/:path*),开发环境直接请求本地 API。distDir 可通过 NEXT_DIST_DIR 覆盖。

tsconfig.json

TypeScript 配置。target ES2022,strict true,moduleResolution bundler,jsx react-jsx。路径别名 @/* → ./app/*(使 @/components/ui/button 等导入生效)。include 包含 .next/types 和 .next-e2e/types(Next.js 生成的路由类型)。ignoreDeprecations: "6.0"(TypeScript 6.0 兼容)。

vitest.config.ts

Vitest 配置。environment: jsdom(模拟浏览器 DOM)。resolve.alias: @/ → app/(与 tsconfig paths 一致)。coverage: provider v8,include app/lib/**/*.ts 和 app/components/**/*.{ts,tsx},exclude **/*.test.{ts,tsx}。thresholds: lines/statements 40%(覆盖率基线)。

playwright.config.ts

Playwright E2E 配置。port 3100,baseURL http://127.0.0.1:3100。testMatch **/*.e2e.ts。仅 chromium project。CI 环境:retries 2,workers 1,reporter line + html。webServer:启动 next dev --port 3100,设置 NEXT_PUBLIC_DEMO_MODE=true 和 NEXT_DIST_DIR=.next-e2e(使用独立的构建目录避免与开发服务器冲突)。reuseExistingServer: 非 CI 时复用已运行的服务器。

postcss.config.mjs

PostCSS 配置,仅注册 @tailwindcss/postcss 插件。Tailwind CSS v4 不再使用 tailwind.config.js,而是通过 PostCSS 插件 + CSS 中的 @import "tailwindcss" 和 @theme inline 指令配置。

package.json

包名 @researchmate/web。6 个 scripts:dev, build, start, lint(tsc --noEmit), test(vitest run --coverage), test:e2e(playwright test)。20 个 dependencies(9 个 @radix-ui + next/react/tailwind 等)和 8 个 devDependencies(playwright, vitest, typescript 6.0.3 等)。

E2E 测试

Playwright 端到端测试

apps/web 有 1 个 E2E 测试文件(e2e/demo-workspace.e2e.ts),在 demo 模式下验证完整用户旅程,不依赖任何后端服务或外部 API。

demo-workspace.e2e.ts

测试名称:"completes the deterministic research workspace journey"。验证步骤:(1) 访问 /app?new=1,确认 "What can I help with?" 标题可见且 "Welcome back" 登录面板不存在;(2) 输入消息 "What makes retrieved evidence defensible?" 并发送;(3) 确认用户消息和 assistant 回答可见;(4) 点击引用 "1. Project source, page 3" 展开引用文本;(5) 确认 URL 包含 /app?conversation=;(6) 点击 "New project" 创建项目 "E2E evidence workspace";(7) 确认跳转到项目聊天页面且标题 "Chat in E2E evidence workspace" 可见;(8) 点击 "Quiz" 打开抽屉并生成 quiz;(9) 确认 quiz 题目可见。最后断言 browserErrors 为空(无控制台错误)和 externalRequests 为空(不调用云服务)。mock /api/v1/healthz 返回 { status: "ok" }。

Demo 模式隔离

E2E 通过 NEXT_PUBLIC_DEMO_MODE=true 启用 demo.ts 的确定性运行时。所有 API 请求由 demoFetch 在浏览器内处理,不发送任何网络请求到后端。Playwright 的 page.on("request") 监听器验证没有请求发往 127.0.0.1 以外的主机。

独立构建目录

E2E 使用 NEXT_DIST_DIR=.next-e2e 环境变量,使 E2E 的 Next.js 构建输出到 .next-e2e/ 而非 .next/。这避免了 E2E 测试与开发服务器或生产构建的冲突,可以并行运行。
