模块关系

2. 八个模块怎么咬合

这张图描述学习模块之间的依赖边。核心形状是一把扇子：请求从前端进入，打 Backend，再内联（Ask）或排队（摄入 + 证据）分发到 Worker，而 AI 栈模块两端都跑。

把项目想成一把有一柄三骨的扇子。柄是前端——它只通过 HTTP 跟后端讲话。三根骨是 Backend、Worker 和两端都跑的 AI 栈。前端和 Worker 不直接通话：后端在 Supabase 里写一条 outbox 行，Worker 轮询它，结果通过 Supabase 回来——不经 HTTP。其他模块（基础设施、CI/CD、契约与测试、跨切面、项目结构）支撑这四骨怎么造出来怎么验证，不是它们彼此怎么调用。

承载架构的三条边

边跨过什么去哪读
前端 → 后端（HTTP，同源代理）chat composer 消息、文件上传、Idempotency-Key 头；Vercel rewrite 代理到 Render，避开公司代理拦截前端 + 后端
后端 → Worker（Outbox，非直接调用）摄入与证据评审任务；一个 DB 事务同时写业务数据 + outbox_events；worker 轮询并入队Worker + 跨切面
后端 + Worker → AI provider（NVIDIA NIM、Qdrant、Tavily）LLM 调用、embedding 调用、hybrid 检索、rerank；同一套适配器 Ask（内联）和 Evidence（排队）共用AI 技术栈 + 后端 + Worker
[合理推断] 最常问的架构题："前端为什么不直接调 Worker？"答案就在后端→Worker 那条边上：HTTP 调用会跟数据库事务竞态，API 在写完 DB 到派发任务之间崩溃，任务就丢了。Outbox 模式解决这个——任务和业务数据一起提交，任务变成只是一行 Postgres 行，只要 Postgres 在就可靠。

面试追问树

为什么前端经 Vercel rewrite 代理，而不是直接调 Render？
├─ [项目事实] Vercel rewrite 把 API 请求经前端 host 代理
└─ 为什么需要？
   └─ 公司/ISP 代理对 *.onrender.com 拦截返回 HTML 而非 JSON；rewrite 用 Vercel 域名，代理放行

为什么后端→Worker 边上是 outbox 模式？
├─ 直接 task.delay() 跟 DB 事务竞态
├─ API 在 commit 后 dispatch 前崩溃，任务就丢
└─ [项目事实] Outbox 在一个事务里写业务行 + outbox_events 行；派发器轮询并入队——只要 Postgres 在，任务就在

高频面试点

3. 速查：最常被问到的那几个点

五条覆盖本项目约 80% 的深挖问题。每条都标了完整解释在哪个页面。

点一句话答案完整页
为什么 hybrid 检索（BM25 + dense）而不是单一方法？BM25 抓关键词式查询；dense 抓近义改写式查询；RRF 把两边排名融合成一份 top-KAI 技术栈
为什么 rerank 之前要按预算裁剪？全文或关键词路径出来的 bypass 候选便宜；在一大堆上跑 rerank 浪费 token，所以按类型拆开并预算裁剪后才让 rerank 看到AI 技术栈
为什么用 outbox 而不是 task.delay()？API 在一个事务里同时提交业务数据 + outbox_events；派发器轮询；API 崩了任务仍躺在 Postgres 里Worker + 跨切面
为什么 Ask 请求要做幂等？网络超时可能让客户端重试；同一 Idempotency-Key 重放时不重新调 LLM——省 token 也避免重复 run后端
为什么 API 和 Worker 共用一个 Render 容器？Render Free 档 = 一个睡眠服务；render_combined 一个进程同时跑两端；代价不能独立伸缩项目结构
[项目事实] 这几条答案都不引用编造的指标。项目没有公布 QPS、召回或延迟数字；面试中只说源码能证实的东西，其余标 [合理推断] 或 [优化建议]。

面试追问树

一条 Ask 请求最便宜的路径是什么？
├─ 幂等重放 → 直接返回缓存，不调 LLM
└─ [项目事实] IdempotencyCoordinator.begin() 在 execute() 之前先查 key

最坏情况路径是什么？
├─ 扩展 hybrid 检索 → rerank → LLM 带一次修复重试
└─ 延迟集中在哪？
   └─ [项目事实] NVIDIA embedding（4096 维）+ Qdrant hybrid 查询 + NVIDIA LLM；rerank 触发前已有预算裁剪约束

长运行 workflow 怎么避免被中途杀死？
├─ [项目事实] Celery soft_time_limit + task_acks_late；SoftTimeLimitExceeded 在 except Exception 之前有显式 handler
└─ [面试扩展] 为什么 soft 超时打不断阻塞的 C 调用？
   └─ 只在 Python 字节码之间抛出；boto3 / C 扩展调用无视它；只有 SIGKILL 是硬兜底
