CI/CD . 面试深挖

你 push 之后，CI 并行做四件事：跑 Python 测试带 69% 覆盖率门禁；构建前端并跑单测加依赖审计；跑 Playwright 端到端浏览器测试；扫描 Docker 镜像找 HIGH/CRITICAL 漏洞。第五个聚合 job 名叫 ci-success，只有前四个全绿它才绿；Render 的部署门禁就看这一个 job。下面深挖：流水线结构与 ci-success 哨兵；pre-commit 的 ruff + pyright hook 复用锁定的 uv 环境；SQL 迁移 runner 的 advisory lock 和 SHA-256 账本；以及挂在 npm run check:all 上的 69% 覆盖率门禁。

ci.yml 5 job + ci-success 总计 3 个 workflow --frozen uv + npm ci 双锁 69% 覆盖率门禁 SHA-256 迁移账本

功能中心 . GitHub Actions 流水线

四个并行质量门禁，由 ci-success 哨兵聚合

大白话：push 之后，CI 跑 4 件事；4 件全绿 + ci-success 才允许 Render 部署
  • python-quality — Python 测试 + 69% 覆盖率门禁 + ruff lint + pyright 类型检查 + OpenAPI 漂移检测 + 迁移文件校验。新增一个 API 端点时，CI 检查提交的 OpenAPI spec 与渲染出来的是否一致。
  • web-quality — 前端生产构建 + 单元测试 + npm audit 依赖扫描。升级一个 npm 包时，CI 构建并跑单测，发现 prod 依赖里有中等以上漏洞就拦住。
  • browser-e2e — Playwright 跑端到端浏览器流程，失败上传报告 artifact 留 7 天便于排查。改了登录流程时，CI 在真浏览器里走完整个用户路径。
  • container-quality — hadolint 检查 Dockerfile，带层缓存构建镜像，用 trivy 扫 HIGH/CRITICAL 漏洞。改 Dockerfile 时，CI 扫描生成的镜像找已知 CVE。
  • ci-success — 聚合哨兵：在四条之后用 if: always() 跑，断言每条的 result 都是 success。Render 的 checksPass 部署门禁读这个 job。任何一条红 = 不部署。

[项目事实] .github/workflows/ci.yml 在 PR 和 push 到 main / develop 时触发。concurrency: cancel-in-progress: true 会杀掉同分支的旧 run。上面四个 job 并行跑；ci-success 设了 needs: [四个] 和 if: always()。

这条流水线是发布就绪的唯一事实来源 —— Render 的 autoDeployTrigger: checksPass 等的就是这一组检查。关键设计：不让 GitHub 在任一 job 失败时隐式拒绝整条 workflow，而是显式起一个聚合 job，对每个下游 result 跑 test "$RESULT" = success。为什么这样：GitHub 的隐式 needs 把 continue-on-error: true 的 job 当成不阻断，所以兄弟 job 软失败会从默认门禁里漏过去。显式断言把门禁收成单一、可命名、可检查、且不怕软失败的关卡。

逐 job（每个门禁实际检查什么）
  • python-quality — npm run test:python（69% 覆盖率门禁）、npm run check:types（pyright basic）、npm run check:lint + check:openapi + check:migrations；安装用 uv sync --frozen --all-packages --group dev。timeout 35 min。[项目事实]
  • web-quality — npm ci --no-audit --no-fund、npm run test:web、npm run check:web（生产构建）、npm run check:audit（npm audit --omit=dev --audit-level=moderate）。timeout 20 min。[项目事实]
  • browser-e2e — npx playwright install --with-deps chromium 然后 npm run test:e2e；失败上传 apps/web/playwright-report artifact（保留 7 天）。timeout 20 min。[项目事实]
  • container-quality — 对 workers/ai-worker/Dockerfile 跑 hadolint --ignore DL3008，docker build-push-action 用 load: true, push: false + GHA cache 构建，再跑 aquasec/trivy:0.73.0 image --exit-code 1 --ignore-unfixed --severity HIGH,CRITICAL。timeout 25 min。[项目事实]
  • ci-success — if: always()，needs: [python-quality, web-quality, browser-e2e, container-quality]；跑四条字面 test "$X_RESULT" = success 断言。[项目事实]

python-quality — Python 测试、类型、lint、契约

跑什么（5 步，35 分钟 timeout）：

  1. uv sync --frozen --all-packages --group dev — 安装锁定的 Python 依赖。--frozen 意味着 uv.lock 是唯一事实来源；lockfile 与 pyproject.toml 不匹配就失败，不会偷偷解决。
  2. npm run test:python — coverage run --branch --source=apps/api/src,workers/ai-worker/src -m pytest -q && coverage report --fail-under=69。跑 tests/ 下全部测试，测量两个包的分支覆盖率，总覆盖率低于 69% 就阻断。
  3. npm run check:types — npx --yes pyright@1.1.390。basic 模式静态类型分析。在运行前抓 None 解引用、参数类型错误、缺失返回标注。
  4. npm run check:lint — ruff check apps/api/src workers/ai-worker/src tests。用 ruff 0.16.0 规则（UP、F、E、I 等）lint 三棵树。任何本地未修复的 autofix 违规都会失败。
  5. npm run check:openapi && npm run check:migrations — OpenAPI 漂移检查：渲染 FastAPI spec 并与 infra/openapi/openapi.yaml 逐字节对比。迁移文件检查：校验每个 SQL 文件有唯一版本前缀、非空、且不含 drop database。

原理： 这个 job 是契约门禁。测试验行为；pyright 验类型安全；ruff 验风格一致；OpenAPI 检查验公开 API 契约没偷偷漂移；迁移检查验数据库 schema 文件结构有效。它们合在一起就是"代码是否做到了它声称的"门禁，其他每个 job 都依赖它。

web-quality — 构建、单元测试、依赖审计

跑什么（4 步，20 分钟 timeout）：

  1. npm ci --no-audit --no-fund — 严格按 package-lock.json 安装。ci（不是 install）拒绝写 lockfile；package.json 与 lockfile 不一致就失败。--no-audit --no-fund 跳过 npm registry 遥测省约 10s。
  2. npm run test:web — npm --workspace @researchmate/web run test。跑 Vitest 前端 workspace 单元测试。覆盖组件渲染、hook 逻辑、工具函数。
  3. npm run check:web — npm --workspace @researchmate/web run build。完整 Next.js 生产构建。TypeScript 编译失败或页面 import 错误都会失败。这是前端能否干净编译的最强信号。
  4. npm run check:audit — npm audit --omit=dev --audit-level=moderate。扫描生产依赖的已知 CVE。--omit=dev 跳过 devDependencies（不发布）。--audit-level=moderate 意味着 prod 依赖里有中等以上 CVE 就失败。

原理： 构建 + 测试 + 审计。构建能抓单元测试抓不到的 TypeScript 和 import 错误（一个组件可以错但仍然可 import）。审计抓供应链风险：一个有已知漏洞的传递依赖应该阻断发布，不是部署后才发现。

browser-e2e — Playwright 浏览器验收测试

跑什么（4 步，20 分钟 timeout）：

  1. npm ci --no-audit --no-fund — 安装 web 依赖（同 web-quality）。
  2. npx playwright install --with-deps chromium — 下载 Chromium + OS 级浏览器依赖（字体、库）。版本钉在 package-lock.json 的 Playwright 版本。
  3. npm run test:e2e — 启动 Next.js dev server 在 127.0.0.1:3100，设 NEXT_PUBLIC_DEMO_MODE=true，然后跑 apps/web/e2e/demo-workspace.e2e.ts。
  4. 仅失败时：上传 apps/web/playwright-report 为 7 天 artifact（HTML 报告 + trace + 截图 + 视频）。

测试在浏览器里具体检查什么：

唯一的测试（demo-workspace.e2e.ts）在真实 Chromium 实例里走完一整条用户旅程。它不是 stub DOM — 它点击、输入、拖拽、读渲染后的 HTML。[项目事实]

  • Console + 运行时错误监控 — 全程监听 page.on("console") 和 page.on("pageerror")。任何 console error 或未捕获异常都会在测试末尾判失败，即使触发它的断言已经通过。
  • 网络隔离 — 监听每个 page.on("request")，记录任何 hostname 不是 127.0.0.1 的请求。测试末尾断言 externalRequests === []。这证明 demo 模式不会意外调用云 API、LLM provider 或外部 CDN。
  • Healthz mock — 拦截 **/api/v1/healthz 返回 {"status":"ok"}。应用健康检查在无真实后端时通过。
  • 聊天旅程 — 导航到 /app?new=1，断言标题 "What can I help with?" 可见，输入研究问题，点击 "Send message"，然后断言用户消息和 AI 回复（含 "retrieval is useful when evidence is relevant"）都出现。
  • 引用下钻 — 断言引用 "1. Project source, page 3" 可见，点击它，断言 "Grounding and explicit source attribution" 详情面板打开。还断言 URL 变成含 ?conversation=（深链接生效）。
  • 侧边栏拖拽 — 用 ARIA 角色 complementary（不是 CSS class）找侧边栏，用 ARIA 角色 separator 找拖拽手柄，拖 72px，轮询直到侧边栏宽度超过原始宽度 40px。这测的是交互布局，不是静态渲染。
  • 项目创建 — 点击 "New project"，填名称 "E2E evidence workspace"，点 "Create"，断言 URL 匹配 /app/projects/[^/]+/chat?new=1 且标题 "Chat in E2E evidence workspace" 出现。
  • 测验生成 — 点 "Quiz"，断言测验面板（ARIA 角色 complementary，name "Project quiz"）可见，点 "Generate quiz"，断言含 "What makes a retrieved conclusion defensible" 的问题出现。

原理：

  • 确定性 demo 模式 — NEXT_PUBLIC_DEMO_MODE=true 让应用在没有后端、LLM provider 或凭证的情况下返回预置响应。测试可复现：无 flaky API 调用、无限流、无成本。[项目事实]
  • 无障碍优先断言 — 每个元素都通过 ARIA 角色和可访问名找到（getByRole("complementary", { name: "Workspace navigation" })），不是 CSS class 或 test ID。这意味着测试验证语义 HTML 结构。开发者删掉一个 aria-label 测试就挂 — 顺带抓无障碍回归。[项目事实]
  • 浏览器错误即测试失败 — 测试不只检查"正确文本出现了吗"。它检查"整个过程中浏览器是否保持干净"。懒加载组件在断言后渲染出的 console error 仍然判失败。[合理推断]
  • CI 专用 Playwright 配置 — CI 里：forbidOnly: true（不允许 test.only 逃逸）、2 次重试、1 个 worker（串行，无并行浏览器实例）、HTML reporter 用于 artifact 上传、失败时保留 trace/截图/视频。[项目事实]

container-quality — Dockerfile lint、镜像构建、CVE 扫描

跑什么（3 步，25 分钟 timeout）：

  1. hadolint --ignore DL3008 — 通过官方 hadolint Docker 镜像 lint workers/ai-worker/Dockerfile。DL3008（钉 apt 包版本）被忽略因为基础镜像 python:3.13-slim 自己管 apt 版本。其他规则（DL3005 --no-install-recommends、DL3059 COPY 不带 --chown）仍然生效。
  2. docker build-push-action 用 load: true, push: false — 本地构建镜像（不推 registry）。用 GHA 层缓存（cache-from: type=gha, cache-to: type=gha,mode=max）让重复构建复用层。镜像 tag 为 researchmate-render:ci。
  3. trivy image --exit-code 1 --ignore-unfixed --severity HIGH,CRITICAL — 扫描构建镜像的层文件系统，找已安装系统包和 Python 包的已知 CVE。--ignore-unfixed 跳过上游还没修复的 CVE（减噪）。--exit-code 1 意味着任何有修复可用的 HIGH 或 CRITICAL CVE 都判失败。

原理： Dockerfile 就是 Render 部署的确切产物。lint 它能抓 Dockerfile 反模式（缺 --no-install-recommends、以 root 跑、大层浪费）。构建它证明镜像能编译。扫描它在已知漏洞到达生产前抓 OS 级和 Python 级包的 CVE。扫描用 --ignore-unfixed 因为标记不可修复的 CVE 只会造成告警疲劳却没有可操作的修复。

ci-success — 聚合哨兵

跑什么（1 步，无 timeout 压力）：

  1. 四条字面 test "$X_RESULT" = success 断言，每条上游 job 一条。任何一条返回非零（即任一 job 的 result 不是 success），步骤失败，ci-success 变红。

原理： GitHub 的 needs 图把 continue-on-error: true 的 job 当成不阻断 — 软失败的兄弟 job 不会阻断下游 needs。显式断言绕过这一点：ci-success 用 if: always() 跑（所以即使兄弟失败也跑），逐条字面检查 result。Render 的 autoDeployTrigger: checksPass 读这一个 job 的 conclusion。任何一条红 = 不部署。

按需触发的 workflow — 评测门禁与恢复压测

除了 ci.yml，仓库还有两个 workflow_dispatch workflow，只在手动触发时运行，不在 push 时跑。[项目事实]

  • evaluation-release-gate — 手动输入 evaluation_run_id 触发。调 scripts/check_evaluation_gate.py，从 dev API 拉取评测运行的聚合结果，检查六个条件（status=succeeded、summary.complete、execution_succeeded、quality_passed、无回归、pipeline_code_sha 匹配），并对比三个指标阈值（evidence_recall ≥ 0.80、retrieval_mrr ≥ 0.50、retrieval_ndcg ≥ 0.80）。gate 步骤用 continue-on-error: true 让 artifact 上传总是跑；最后一步 test "$GATE_OUTCOME" = success 强制执行决策。[项目事实]
  • langgraph-recovery-benchmark — 手动输入 trials（默认 1000）触发。启动 postgres:16 service container，跑 scripts/measure_langgraph_recovery.py，该脚本 fork 子进程写 LangGraph checkpoint、杀进程、尝试恢复。断言恢复率的 95% 置信区间下界 ≥ 99.5%。[项目事实]
值得点名的风险（1）evaluation-release-gate workflow 在 gate 步骤上用了 continue-on-error: true —— gh run watch 会把这个步骤误报为 failed，哪怕 workflow 结论是 success；应读 gh run view --json conclusion。（2）cancel-in-progress: true 的并发组以 github.ref 为 key，所以两个 PR 并行跑，只有同分支的 push 会互相 kill。[合理推断]

面试追问树

为什么显式做 ci-success job，而不是让 GitHub 在任一 job 失败时拒绝？
└─ if: always() 防的是哪类部分失败场景？
   └─ Render 的 checksPass 实际怎么消费这个 job 的结论？
答：兄弟 job 上加 `continue-on-error: true` 不会让默认 `needs` 图失败，因为
GitHub 把软失败当成 success。ci-success 在四条之后用 `if: always()` 跑，
逐条 `result == success` 字面断言，让 Render 能挂在一个可命名的 job 上。
Render 读的是这个 job 的 conclusion，不是 workflow 的。

为什么拆成恰好四个并行 job，而不是一条大 job？
└─ 每个 job 的隔离换来了什么（缓存、runner、timeout）？
   └─ container-quality（trivy + hadolint）为什么单列？
答：并行 job 各跑各的 runner，慢的 Python 测试不阻塞前端构建。缓存按
技术栈分开（uv vs npm）。timeout 按 job 调。container-quality 单列
是因为它产出 Docker 镜像，每次生产重启都靠它，所以单独扫 CVE，不等
代码测试跑完。

cancel-in-progress 怎么省 CI 成本？
└─ 并发组的 key 是什么，对两个并开 PR 意味着什么？
   └─ 同分支 force-push 时已经在跑的 workflow 会怎样？
答：并发组以 `github.ref` 为 key。两个 PR 是不同 ref 并行跑；同分支
push 新 commit 会杀掉前一次还在跑的 run，省掉你 push 修正时的多余等待。

技术栈中心 . Pre-commit hooks

ruff + pyright 复用锁定的 uv 环境，外加卫生 hook

[项目事实] .pre-commit-config.yaml 有三个 repo：pre-commit-hooks v5.0.0（merge-conflict、EOF、YAML/TOML、trailing-whitespace）、ruff-pre-commit v0.16.0（lint + autofix、format check）、本地 pyright hook。每个 Python hook 都用 language: system 复用 uv 管理的 Python 环境。

pre-commit 的目的不是「跑 linter」，而是把 CI 跑的那套同样 pin 死的版本左移到本地。设想一个贡献者：本地 hook 过了，push 上去 CI lint 步骤意外挂掉，因为他的笔记本装了更新的 ruff，新 ruff 报了 CI 旧 ruff 不知道的规则。这种漂移项目就靠 pin 死消除。因为 ruff（0.16.0）和 pyright（1.1.390）都在 uv.lock 里钉死，hook 又通过 language: system（直接调被 uv 管理的 Python，而不是让 pre-commit 自己搭一个 venv）跑，本地和 CI 用的是位级别一致的工具版本。

关键机制
  • ruff：check --force-exclude --fix，files: \.py$，pass_filenames: false。autofix 开；如果 fix 改写了文件，pre-commit 把这次提交标记为失败，作者重新 stage。[项目事实]
  • ruff-format：只 --check — 格式不在提交时自动应用，必须自己跑 ruff format。专抓漂移。[项目事实]
  • pyright 本地 hook，entry pyright，pass_filenames: false，不做文件过滤，读根 pyproject.toml，typeCheckingMode = "basic"。调用方式与 CI 的 npm run check:types 一致。[项目事实]
  • 卫生 hook — check-merge-conflict --assume-in-merge、end-of-file-fixer、check-yaml --allow-multiple-documents、check-toml、trailing-whitespace。[项目事实]
需要标注的坑 有 autofix 的 hook 会改写文件，导致 commit 失败并提示 "files were modified by this hook。" 这不是真正的错误 —— 重新 stage 修复后的文件再 retry 一次提交即可。忘了这一步会让新贡献者卡住。[合理推断]

面试追问树

为什么 language: system 而不是 pre-commit 默认的托管 venv？
└─ 它拿到的是 pre-commit 自建 venv 拿不到的什么？
   └─ 这层与 uv.lock 的耦合怎么减少 CI/本地漂移？
答：pre-commit 自建 venv 会自己装一份 ruff/pyright，本地版本可能与
uv.lock 漂移。`language: system` 调的是被 uv 管理的 Python，它和 CI 通过
`uv sync --frozen` 装下来的二进制是同一份字节。

为什么 ruff-format 在提交时 --check 而 ruff --fix 却开？
└─ autofix 与 check-only 之间的权衡是什么？
   └─ 想在提交时强制应用格式，应该怎么做？
答：autofix 会自动改写不安全规则（摩擦小，但你可能没看就提交了）。format
只 check、不应用，逼作者自己跑 `ruff format`，从而保证作者看了一眼 diff。
想要提交时自动应用，把 `--check` 去掉，再在 hook 标记文件被修改时重新
stage。

ruff hook 里 pass_filenames: false 换来什么？
└─ 为什么不让 pre-commit 只把改动文件传给 ruff？
   └─ 那种情况下 --force-exclude 会出什么问题？
答：这个 hook 不管哪些文件变了，都对着整片目标树跑 ruff。pre-commit 只
传改动文件的话，重命名或挪动的文件会从被 lint 的列表里漏出去。整树
调用让 ruff 的 --force-exclude 语义保持可预测。

功能中心 . 数据库迁移策略

增量 SQL 文件、SHA-256 账本、advisory lock、幂等语句

[项目事实] scripts/apply_migrations.py 强制唯一版本前缀、拒绝空文件和 drop database，在 ALLOW_SCHEMA_APPLY=1 时取 pg_advisory_xact_lock(726_334_129)，按顺序应用未应用的文件，并把每个的 SHA-256 写入 researchmate_schema_migrations。

想象危险场景：运维跑一个改生产租户表的脚本，同时另一个同脚本的实例也在跑，两个进程争抢改 schema，结果表结构进入不一致状态。更糟的是有人改一条已经跑过的迁移文件，以为改完能干净地补上 —— 实际上生产库和迁移账本对「跑过什么」已经不一致了。

迁移 runner 叠了四层防护，让对生产库重跑也安全。第一层，apply 路径取一个事务级 advisory lock，两个 apply 没法同时跑。第二层，researchmate_schema_migrations 表给每条已应用文件记 SHA-256，已应用文件的字节后来变了，runner 抛 RuntimeError 中止。第三层，校验器拒掉空文件和字面字符串 drop database。第四层，SQL 自身用 if not exists / drop policy if exists ... create policy 写成幂等，所以同一文件在事务里重放也不会重复应用。

关键机制
  • pg_advisory_xact_lock(726_334_129) — 事务级；同一 Postgres 上任何并发 apply 会被阻塞，直到第一个 commit 或 rollback。这个整数是 apply_migrations.py 里硬编码的 magic number。[项目事实]
  • researchmate_schema_migrations — (version text primary key, checksum_sha256 text not null, applied_at timestamptz)；用 create table if not exists 在同一事务里建。如果 applied.get(name) != sha256(source)，则抛 RuntimeError 并中止。[项目事实]
  • --check-files 与 --apply — --check-files 是 CI-only 校验（不访问 DB）；--apply 要求 ALLOW_SCHEMA_APPLY=1 加 DATABASE_URL，作为人工审批关口。CI 跑的是 npm run check:migrations = --check-files。[项目事实]
  • 幂等 SQL 风格 — create table / create index / create policy 都用 if not exists 或 drop policy if exists ... create policy 配对；例子：202608010010_api_idempotency.sql 建 api_idempotency，主键 (user_id, operation, idempotency_key)，还加一条状态机 CHECK 约束。[项目事实]
为什么只允许增量 validator 拒绝 drop database 和空文件，但并没拦 alter table drop column。项目真实自律是只写前向迁移：任何要改既有列的变更都以新迁移文件发布，而不是改已应用过的那个。SHA-256 账本就是这件事的强制机制：改已应用文件的字节会让 runner 失败。[合理推断]

面试追问树

为什么用 advisory lock 而不是给 migrations 表加行锁？
└─ 事务级意味着锁的生命周期是怎样的？
   └─ 换成 SELECT ... FOR UPDATE 锁一个哨兵行，会改什么？
答：哨兵行锁要先有一行真行可锁；行被删了就锁不住。advisory lock 按
整数 key，不需要真行。事务级意味着锁跟事务一同生死 —— commit 或 rollback
都释放，所以崩溃的 runner 在 rollback 时自然清理。

SHA-256 摘要怎么防漂移？
└─ 如果已应用文件的内容变了，runner 会做什么？
   └─ 真的需要修一个已应用的迁移时，项目的流程是什么？
答：抛错中止。流程是永远不改已应用文件 —— 发一条新的前向迁移，加列或
撤销上一个行为。原地改会让生产偷偷脱离提交上的文件列表。

为什么把 --check-files（CI）和 --apply（运维）拆成两种模式？
└─ ALLOW_SCHEMA_APPLY=1 具体防的是什么？
   └─ CI 有可能误跑 --apply 吗？
答：--check-files 只读文件字节；--apply 打开数据库连接并改 schema。
ALLOW_SCHEMA_APPLY=1 强制人在任何 DB write 之前显式设这个 env，所以一个
没继承该 env 的 CI job 没法碰生产。CI 跑 --check-files，只有持有生产
secret 的运维才能跑 --apply。

技术栈中心 . 覆盖率门禁 & check:all

挂在 npm run check:all 上的 69% 门禁

[项目事实] package.json 把 test:python 定义为 uv run --frozen coverage run --branch --source=apps/api/src/researchmate_api,workers/ai-worker/src/researchmate_worker -m pytest -q && uv run --frozen coverage report --fail-under=69；check:all 串联 test、lint、types、openapi、migrations、web build、audit。

覆盖率是一个 0 到 100 之间的数字，含义是「测试可能跑到的所有行或所有分支里，有多少在测试套件运行时真的跑过了」。100% 意味着每一行、每一个 if 的分支都至少跑过一次。项目把下限钉在 69%。覆盖率掉到 69% 以下时，coverage report --fail-under=69 退出非零，python-quality CI 步骤就挂。

为什么是 69%？ [项目事实] package.json 里的字面值，不是从 benchmark 推出来的。[合理推断] 它反映当前代码面在按分支（不只按行）计数时可达到的覆盖率 —— 项目用 --branch，所以部分分支算未覆盖。部分分支指一个 if x: A else: B 测试只走了 A 或 B 其中一边，没走的那边算未覆盖。

check:all 的组成
  • test = test:python && test:web — Python（带 69% 门禁）和 web workspace 测试都得过。[项目事实]
  • check:lint = uv run --frozen ruff check apps/api/src workers/ai-worker/src tests。[项目事实]
  • check:types = npx --yes pyright@1.1.390 — 版本钉得与 pre-commit 一致。[项目事实]
  • check:openapi = uv run --frozen python scripts/export_openapi.py --check — 渲染出的 OpenAPI 必须等于已提交的 infra/openapi/openapi.yaml；漂移即失败。[项目事实]
  • check:migrations = uv run --frozen python scripts/apply_migrations.py --check-files — CI 安全的文件校验，不写 DB。[项目事实]
[优化建议] 69% 是项目特定值，未做 benchmark。开发态可考虑跑 coverage report --skip-covered 暴露最值得补的空缺，并按 1–2 个点为步长逐步抬高下限，而不是在回退后重置基线。

面试追问树

为什么用 --branch 分支覆盖率而非行覆盖率？
└─ 部分分支算覆盖还是未覆盖？
   └─ 为什么 69% 是可信数字而不是 100%？
答：部分分支的一侧没被测过；--branch 把这侧算未覆盖。100% 在真实代码里
不现实，因为有些分支纯粹是防御性代码（错误路径、框架桩），测试里从不触发。
69% 是项目当前可量化的下限，不是愿景目标。

为什么把 OpenAPI --check 也挂进 check:all？
└─ 它能抓到测试抓不到的哪类漂移？
   └─ 什么时候你会合理地想跳过它？
答：抓的是已提交 OpenAPI spec 与 FastAPI 渲染出的不一致。测试很少覆盖
每个端点的每个形状；作者改了响应模型，测试还能过，但公开契约已经悄悄
破坏。只有在同一次 PR 内有意识地做契约迁移时才跳过。

为什么 ruff 和 pyright 要在三个地方（uv.lock、.pre-commit、CI npx）都 pin 同一版本？
└─ 每个 pin 各防哪类失败？
   └─ CI 的 pyright 漂移到比 pre-commit 新会出什么问题？
答：CI npx 钉 `pyright@1.1.390` 让一台没有 uv 缓存的新 CI runner 也能拿到
精确版本；uv.lock 给本地装同一份；.pre-commit 通过同一 uv 环境跑。CI
漂到前面的话，hook 本地过、CI 挂 —— 正是这个设计要消灭的漂移。
