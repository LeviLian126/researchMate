AI 智能体技术栈 . 检索、协议、编排

ResearchMate 的 AI 智能体技术栈是一个横跨 FastAPI 后端和 Celery worker 的内聚子系统。四大基石构成它：一个 Wiki 引导的混合 RAG 检索器，将 LLM 编译的结构化 Wiki 页面作为第一层检索；一个路由式混合 RAG 检索器，在融合检索和双重重排之前从五条可观测路由中选择；一个 MCP 服务器，在 Streamable HTTP 上以与 REST 相同的 Bearer 认证暴露六个工具和三个资源；以及一个 LangGraph 证据工作流，编排一个六节点有状态图，支持并行扇出、PostgreSQL 检查点和人工审核。本页逐文件讲解每个组件、决策树和集成接缝。

技术栈基础

AI 智能体技术栈的三大基石

每张卡片解释技术的一般作用以及 ResearchMate 的具体用法。

路由式混合 RAG

带可观测五路由规划器的检索增强生成。query_planning.py 在任何向量搜索之前将每个问题分类为 FULL_CONTEXT、EXACT、SEMANTIC、HYBRID 或 EXPANDED_HYBRID。qdrant_hybrid_query.py 中 Qdrant 原生 BM25 + 稠密分支以加权 RRF 融合。rerank.py 中的三提供者重排协调器（QdrantNativeReranker → NvidiaReranker → DeterministicReranker）应用后期交互重排，带确定性兜底。

MCP

基于 FastMCP 的模型上下文协议服务器。mcp_server.py 在无状态 Streamable HTTP 上暴露六个工具（list_projects、search_project、search_conversation、ask_grounded、get_run_trace、run_evaluation）和三个资源（project://{project_id}/documents、conversation://{conversation_id}/documents、run://{run_id}），由与 REST 相同的 Bearer 中间件认证。SDK 是可选依赖 — 缺失时 /mcp 返回 503 MCP_RUNTIME_NOT_INSTALLED。

LangGraph

有状态图编排库。evidence_graph.py 构建六节点 StateGraph（plan、retrieve_and_extract、reconcile、human_review、synthesize、validate_and_commit），通过 Send 实现条件扇出。检查点通过 PostgresSaver 和 JsonPlusSerializer(pickle_fallback=False) 持久化到 PostgreSQL。interrupt() 原语暂停等待人工审核，无需 try/except 包装，Celery run_workflow 任务通过 Command(resume=...) 恢复。

路由式检索

路由式混合 RAG . 五路由、RRF 融合、双重重排

检索管道不是单一的向量搜索。确定性规划器先分类问题，然后 Qdrant 以加权 RRF 融合稀疏和稠密分支，三提供者重排协调器在上下文打包前应用后期交互打分。

五路由决策树

apps/api/src/researchmate_api/services/query_planning.py 中的 RetrievalRoute StrEnum 为每条可观测策略命名。plan_retrieval() 按顺序评估决策树 — 首个匹配胜出：

#路由稠密 / 词法触发条件reason 字段
1FULL_CONTEXT0.0 / 0.0corpus_tokens <= full_context_limit（默认 12000）entire_authorized_corpus_fits
2EXPANDED_HYBRID0.55 / 0.45代词/引用模式 + 对话历史，或多个 ?/？ 标记conversation_or_compound_query_expanded
3EXACT0.30 / 0.70_EXACT_PATTERN 匹配：引号文本、大写标识符、数字标记identifier_quote_or_numeric_constraint
4SEMANTIC0.70 / 0.30_SEMANTIC_PATTERN 匹配：why、how、explain、为什么、原理、机制conceptual_or_explanatory_intent
5HYBRID0.50 / 0.50前面模式均不匹配时的兜底balanced_default
为什么五条路由？小型相关语料库受益于全上下文（无需向量搜索）；更大的语料库需要显式路由，使精确标识符不被嵌入盖过、使意译不被词法失配盖过。规划器是确定性的 — 只有 EXPANDED_HYBRID 调用 LLM，且仅在对话引用或复合问题真正需要改写时。

通过有界 LLM 调用扩展

当 EXPANDED_HYBRID 触发时，_expanded_plan() 将最近四条对话消息加当前问题发送给聊天提供者，系统提示要求返回独立查询和最多两个替代搜索表述。响应由 _ExpansionOutput pydantic 模型验证（standalone_query + variants，extra="forbid"）。如果提供者未配置或返回无效 JSON，_degraded_expansion() 保留原始查询并设置 degraded=True。常量：MAX_QUERY_VARIANTS = 3，MAX_QUERY_CHARS = 600。

Qdrant 原生混合查询 . RRF 融合

apps/api/src/researchmate_api/services/qdrant_hybrid_query.py 中的 execute_hybrid_query() 对每个查询变体融合稀疏和稠密分支：

BM25 稀疏分支Qdrant 原生 sparse/BM25 模型，每个变体一个 Prefetch 子查询
稠密分支NVIDIA 嵌入向量，每个变体一个 Prefetch 子查询
RRF 融合Qdrant 倒数排名融合，分支权重由 plan.dense_weight 和 plan.lexical_weight 除以查询变体数得出。分支限制 = max(limit * 3, 20)。

所有预取和最终查询都应用所有者范围 payload 过滤器（user_id、project_id、source_type）。当 qdrant_native_hybrid_enabled 为 False 时，系统回退到应用层 BM25（retrieval.py 中的 bm25_candidates()），带 CJK 二元分词、标题加权和精确匹配奖励，由 fuse_candidates() 以 RRF k=60 融合。

双重重排协调器 . 三个提供者

apps/api/src/researchmate_api/services/rerank.py 中的 RerankCoordinator 链式调用三个重排器，带显式降级：

提供者实现机制兜底目标
QdrantNativeReranker专用重排集合中的 Qdrant 后期交互模型对重排集合调用 rerank_query()，multi 向量类型NVIDIA
NvidiaRerankerNVIDIA 排序 API（/v1/ranking）HTTP POST 传 passages，返回排序索引确定性
DeterministicReranker本地平局打破按 (score, has_lexical_rank, -lexical_rank) 排序—

execute() 方法接受 provider 为 "auto" | "qdrant" | "nvidia" | "deterministic"。"auto" 模式先试 Qdrant，再 NVIDIA，最后确定性。WEB_PAGE 来源类型候选跳过 Qdrant 重排器（它只处理 LOCAL_DOC）。提供者在运行时从数据库通过 repository.get_runtime_rerank_config()（在 grounded_query.py 中调用）选择。

Wiki 引导的混合 RAG

LLM Wiki 编译 . 三层检索架构

ResearchMate 现在添加 LLM 编译的结构化 Wiki 层作为第一层检索。文档摄取时，WikiCompiler 合成一个简洁的概览页面，捕获章节标题、关键概念和关系；每个 Wiki 页面携带结构化引用回到源分块。查询时，规划器在路由前检查是否存在 Wiki 候选 — 如果存在且路由为 FULL_CONTEXT 或 SEMANTIC，则完全跳过 Qdrant 并直接返回 Wiki 分块（score=1.0，reason="wiki_first_routing"）。EXACT 查询仍流经完整 RAG 管道；HYBRID 和 EXPANDED_HYBRID 以 50/50 预算拆分运行双路并行。

三层架构

层次目的机制证据来源
Wiki 层知识导航的结构化数据摄取时 LLM 编译；每文档缓存概览页面WikiPage 引用 → 源 chunk_id、page_no
RAG 层答案的细粒度证据混合 BM25 + 稠密检索，带 RRF 融合和双重重排带 ChunkEntry 对象的 Qdrant 集合
原始源真相源S3 兼容对象存储（PDF、PPTX、文本文件）boto3 预签名 URL

Wiki 编译模式

短文档模式（≤4000 tokens）

低于 WIKI_COMPILE_TOKEN_THRESHOLD 边界的文档获得完整 Wiki 编译：LLM 生成单个 WikiPage，在检索结果中替换原始分块（has_vector=false）。编译的 Wiki 以压缩结构格式保留所有事实内容。

长文档概览（>4000 tokens）

较大文档触发 compile_overview()：LLM 生成高级概览页面，采样到 WIKI_OVERVIEW_MAX_INPUT_TOKENS = 6000 token 预算。概览 Wiki 页面与 Qdrant RAG 分块一起追加（概览 has_vector=false，RAG 分块 has_vector=true）。这使概览紧凑，同时从完整 RAG 管道保留深度证据。

Wiki 优先路由决策树

query_planning.py 中的路由器在确定路由后检查 Wiki 候选。决策逻辑：

FULL_CONTEXT 或 SEMANTIC + Wiki 存在完全跳过 Qdrant；返回 Wiki 分块，score=1.0，reason="wiki_first_routing"。无向量搜索成本。
EXACT 查询无论 Wiki 是否存在都走完整 RAG 管道 — 精确标识符匹配优先。Wiki 分块被追加但得分 0.0。
HYBRID 或 EXPANDED_HYBRID双路并行：50% token 预算给 Wiki 分块，50% 给 Qdrant RAG。结果通过加权 RRF 合并。
无 Wiki 或编译失败优雅降级 — 回退到标准 RAG 管道，如同 Wiki 层从未存在过。

可追溯性的结构化引用

每个 WikiPage 数据类携带 references: list[dict] 字段，其中每个条目包含 {document_id, section_title, page_no, chunk_id}。wiki_pages_to_chunks() 辅助函数将这些转换为带 wiki_references 键的 ChunkEntry 兼容元数据，因此最终答案中的每个引用都可以通过 Wiki 页面追溯到 S3 存储的 PDF 或 PPTX 中的确切源位置。

优雅降级契约

Wiki 编译失败回退：如果 LLM 提供者配置错误、返回无效 JSON 或超时，WikiCompiler.compile() 捕获异常并返回 []（无 Wiki 候选）。下游路由器看到空的 wiki 列表并回退到标准 Qdrant RAG，没有任何行为变化。Wiki 层是优化，不是正确性要求。

模型上下文协议

MCP 服务器 . Streamable HTTP 网关

MCP 服务器以与 REST 相同的 Bearer 认证暴露相同的领域服务，使 IDE 和智能体成为第二个真实消费者而无需重复逻辑。

传输与挂载

apps/api/src/researchmate_api/mcp_server.py 中的 build_mcp_server() 创建 FastMCP("ResearchMate") 实例，配置 stateless_http=True、json_response=True、streamable_http_path="/"。ASGI 应用在 main.py 中挂载于 /mcp（app.mount("/mcp", mcp_asgi)）。MCP SDK 是可选依赖 — 缺失时 /mcp 端点返回 503 MCP_RUNTIME_NOT_INSTALLED。

认证 . MCPRequestIdentity ContextVar

认证发生在 main.py 的 FastAPI 中间件层，而非 MCP 服务器内部。每个到 /mcp 或 /mcp/* 的请求必须携带 Bearer 令牌。中间件调用 resolve_bearer_token()（生产用 Supabase OAuth，开发用静态凭据）并设置名为 current_mcp_identity 的 ContextVar[MCPRequestIdentity]，携带完整认证上下文：

@dataclass(frozen=True)
class MCPRequestIdentity:
    user: CurrentUser
    repository: ResearchMateRepository
    evidence: EvidenceRepository
    chat_provider: ChatProvider | None
    hybrid_store: QdrantHybridStore | None
    web_search: TavilyWebSearchProvider | None
    settings: Settings
    reranker: RerankCoordinator

每个工具调用 _identity() 获取此上下文，缺失时抛出 PermissionError("AUTH_REQUIRED")。/mcp 路径包含在 RATE_LIMITED_PATHS 中，按 IP 限流 60 次/分钟。

Wiki 引导的混合 RAG . 三层检索架构

Wiki 层位于原始存储和 RAG 检索之间 — LLM 编译的结构化页面为短文档提供导航快捷方式，或为长文档提供概览上下文。

Wiki 优先路由策略

Wiki 优先路由

当 Wiki 候选存在且查询路由为 FULL_CONTEXT 或 SEMANTIC 时，完全跳过 Qdrant 并返回 Wiki 分块（score=1.0, reason="wiki_first_routing"）。EXACT 查询仍走完整 RAG 管道。

优雅降级

Wiki 编译失败是非阻塞的 — 系统回退到原始 RAG 模块，不传播错误。

结构化引用：每个 WikiPage 携带一个 references: list[dict[str, object]] 字段，映射回包含 {document_id, section_title, page_no, chunk_id} 的来源证据。这使得从合成的 Wiki 知识追溯到原始源片段成为可能，同时在导航辅助和承载证据之间保持清晰的分隔。

关键常量和方法

常量

WIKI_OVERVIEW_MAX_INPUT_TOKENS = 6000（在 schemas/common.py 中）防止过长的概览编译。短/长检测的 token 阈值使用相同的 4000-token 边界。

方法

WikiCompiler.compile_overview()、WikiCompiler._sample_for_overview()、wiki_pages_to_chunks()（向元数据添加 wiki_references）、IngestionService._compile_overview_wiki()（在 Qdrant upsert 后对长文档调用）。

图拓扑

build_evidence_graph(domain, checkpointer) 组装 StateGraph 并用检查点器编译：

START → plan从研究目标创建提供者支持的子问题，或为报告刷新保留 section keys
plan → fan-out → retrieve_and_extractfan_out() 对每个问题返回一个 Send("retrieve_and_extract", {...}) — 带完整上下文加每问题 question_index 和 question 的并行执行
retrieve_and_extract → reconcile从 Qdrant 检索证据（+ 可选 Tavily 网络搜索），加载分块，通过 LLM 提取声明。批次通过 operator.add 合并到 evidence_batches。调和派生声明关系（一致/矛盾）而不修改证据。
reconcile → human_reviewreview() 包装器调用 domain.review_payload(state)。如果返回 None 则自动通过。否则调用 interrupt(proposed) — 检查点持久化，图暂停。
human_review → synthesize恢复时 domain.apply_decision() 处理人工决策（approve/edit/reject）。合成通过 synthesize_report() LLM 调用从已审核声明构建 ReportProposal。
synthesize → validate_and_commit → END校验所有声明都有证据（chunk_ids），然后在一个事务内将报告原子提交到数据库。

人工审核 . interrupt 与恢复

review() 节点是关键的 HITL 边界。它调用 domain.review_payload(state)，后者标记低置信度声明（score < 0.75）或可疑来源。如果需要审核，则调用 langgraph.types 中的 interrupt(proposed) — 这会持久化检查点并暂停图。源码注释明确："Never wrap interrupt in try/except; LangGraph must persist and surface it."

当人工提交决策（approve、edit、reject）时，tasks.py 中的 Celery run_workflow 任务通过 Command(resume=resume_value) 恢复图。domain.apply_decision() 方法处理决策，图继续到 synthesize。

检查点 . PostgresSaver

检查点通过 PostgresSaver 和 JsonPlusSerializer(pickle_fallback=False) 持久化到 PostgreSQL。线程 ID 即工作流 run_id。这意味着暂停的工作流在 worker 重启后仍然存活 — 检查点在数据库中，而非进程内存中。pickle_fallback=False 设置确保无任意反序列化，保持边界安全。

领域协议与组合

EvidenceWorkflowDomain Protocol 定义图调用的七个方法：plan、retrieve_and_extract、reconcile、review_payload、apply_decision、synthesize、validate_and_commit。实现分布在：

WorkflowExecutionMixin

workflow_execution.py — 以 mixin 形式实现全部七个节点方法。plan() 创建提供者支持的问题。retrieve_and_extract() 以所有者范围过滤器查询 Qdrant。reconcile() 派生关系。validate_and_commit() 原子提交。

SqlEvidenceWorkflowDomain

workflow_runtime.py — 将核心领域与 WorkflowExecutionMixin 组合，并重写 synthesize() 以通过 synthesize_report() LLM 调用构建 ReportProposal。

排序指标

evidence_recall 衡量预期块是否出现在检索集合中。倒数排名记录第一个相关位置；二元 NDCG 奖励将所有判定相关的块放在接近顶部的位置。当用例没有预期证据时，排序指标保持未评分，而不是制造零值。

每个持久运行存储有效的流水线配置、检索通道权重、每用例结果、聚合和前一个成功的基线摘要。工程 UI 一起呈现候选和基线，包括明确的回归和执行失败。

反馈捕获

拇指反馈键控到成功的拥有 Ask 运行。API 从持久化的服务端状态重建问题、答案、引用和检索候选；浏览器不能伪造这些快照。

Bad Case 提升

开发者审查负面反馈，仅从服务端记录的本地文档候选中选择预期块，并原子创建下一个冻结的 Answer feedback regressions 数据集版本。同一个 Advisory Lock 事务为最新 accepted pipeline 创建 pending evaluation 并写入 evaluation.run.requested，因此历史用例会自动重跑 evidence recall、citation precision 和 faithfulness。Web 候选仍可见，但不能进入本地文档回放数据集。

当前证据边界：指标逻辑、检索分支选择、反馈所有权、不可变提升、UI 渲染和发布门禁脚本具有本地自动化证据。填充的托管提供商比较和生产提升仍然未声明。
