# 挑战与验证

在将规格说明交给 Node02 之前，先对其进行压力测试。从五个风险维度挑战每一条关键断言。如果任一风险为高，则在决定构建之前设计最廉价的测试。

## 何时阅读此文件

在规格说明产出之后，或当用户希望挑战一个已有的产品想法或 PRD 时。

## 五个风险维度

对于每个维度，给出你的推荐评级（LOW、MEDIUM、HIGH 或 UNKNOWN），并附上背后的证据。

### 1. 价值风险：问题是否足够痛？

- 用户今天会花时间或金钱来解决这个问题吗？
- 是否存在行为证据（反复使用、付费、抱怨），还是只有口头声称的需求？
- 应将口头声称的兴趣视为弱于可观察的行为、承诺或付费。

### 2. 触达风险：你能接触到用户吗？

- 第一个用户从哪里来？说出一个具体的渠道，而不是"内容"或"社区"。
- 你是否已有现成的受众、网络或分发优势？

### 3. 可行性风险：你能构建它吗？

- 核心的 API 或依赖是否可靠、可负担，并允许此用途？
- 是否有任何东西必须在承诺之前进行原型验证？
- 延迟、准确性、规模或平台要求对独立开发是否现实？

### 4. 可持续性风险：一个人能维护它吗？

- 运营它每天需要多少人工工作？
- 随着使用量增长，成本和支持负担会如何变化？
- 是否依赖单一供应商或平台，而它可能改变条款？

### 5. 创始人契合度：你会持续做这件事吗？

- 这是一个你愿意维护数年的产品，而不是只构建一次？
- 你在此领域是否有专业知识或不公平优势？

## 验证阶梯

如果任一风险为 HIGH 或 UNKNOWN，选择能产生决策质量证据的最廉价方法：

| 方法 | 成本 | 测试 |
|---|---|---|
| 研究已有证据 | 零 | 市场需求、竞争对手分析 |
| Landing page 或 fake door | 低 | 需求是否存在 |
| Concierge 或人工服务 | 低 | 价值假设、使用意愿 |
| Prototype（一次性代码） | 低到中 | 技术可行性、UI 方向 |
| 付费试点 | 中 | 付费意愿 |
| 窄功能 MVP | 高 | 完整验证 |

当所有风险都为 LOW 时，不需要验证。直接进入 GO。

对于每个需要验证的风险，明确：

- 被测试的假设。
- 所选方法。
- 通过阈值：什么结果确认假设。
- 失败阈值：什么结果拒绝假设。
- 通过后决策：前往 Node02。
- 失败后决策：NO_GO，或修订规格说明并重新质询。

## 最终决策

每份规格说明一个决策：

| 决策 | 条件 | 下一步 |
|---|---|---|
| GO | 五项风险均为 LOW 或 MEDIUM，且最高风险假设已有验证计划或已完成验证 | 前往 Node02 |
| VALIDATE | 一项或多项风险为 HIGH，但可以低成本测试 | 先运行最廉价测试；结果决定 GO 或 NO_GO |
| NO_GO | 某项风险为 HIGH 且无法低成本测试，或证据显示问题不够痛 | 停止；记录原因 |

以下情况不得发出 GO：

- 受众不具备行为上的具体性。
- 核心任务无法用一句话表述。
- 最高风险假设未识别。
- 范围未根据投资预算进行裁剪。

记录决策、置信度（低、中、高）、三条最强的理由，以及什么证据会推翻它。

## 不应做的事

- 不要将注册数、页面浏览量或下载数视为价值的证明，除非它们在因果上代表核心任务已完成。
- 不要因为某维度看起来没问题就跳过它。即使是 LOW 也要显式评级。
- 当更廉价的测试能回答同一问题时，不要推荐构建完整 MVP。
- 不要编造需求证据。如果没有证据，标记为 UNKNOWN 并设计一个测试。
