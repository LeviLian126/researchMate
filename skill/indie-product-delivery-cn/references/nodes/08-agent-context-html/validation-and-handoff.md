# HTML 校验与交付

在生成或刷新项目 HTML 文档集之后使用此清单。只有当新读者无需重读对话或源码树即可区分事实、缺口、契约和决策时，此清单才有意义。

## 工作流程

在写入完成之后依次执行下方的内容、证据和浏览器检查；在交付前修复阻塞项，并声明任何未能执行的检查。

## 内容覆盖

- 确认落地页仍是紧凑的当前快照，凡是涉及产品、交付、架构、数据库、API 或运维的重要细节，都应有清晰的专题页承载，而不是被压缩为浅层摘要。
- 确认全局导航能够到达每个专题页，每个子页面都能链接回当前快照，页面标题不应含混，同一事实不应在页面间漂移。
- 按渲染顺序逐页阅读。移除标题重述、通用引言或结论、重复的小节开头、机械的标签列表，以及一事实一卡片的布局，这些都会迫使读者重新拼凑出本可一句话说清的解释。
- 确认正文使用稳定的项目术语、具体的主语和动作、有源支撑的论断，以及可见的边界。不要把标点、技术词汇、表格或列表本身视为缺陷。

检查每个必需区域都包含有证据支撑的内容或显式的 unknown 状态：

- 项目描述、目标用户/买家/受益人、问题、承诺、首次成功、商业状态，以及定价/权益；
- 能力地图、MVP/MAP 边界、shipped/in-progress/candidate/deferred/unknown 交付状态、验收与验证；
- 前端/后端/数据/集成/运行时流程，含归属、依赖和关键失败/恢复行为；
- 技术决策、数据库实体与字段、API/actions、认证/权限，以及契约凭证；
- 发布/验证状态、风险、阻塞项、决策、证据置信度，以及下一步行动。

对于数据库和 API 页面，将渲染出的台账与已维护的 migration/schema 和 OpenAPI/routes 进行比对。当完整契约可用时，仅抽样少量实体或端点是不够的。

交付前调和覆盖清单：

- 源码能力/状态记录 = 渲染的能力/状态记录 加显式排除项；
- 源码 operations/actions = endpoint/action 索引与详情记录；
- 源码实体及所有有证据的字段 = 数据库实体与字段记录；
- 源码关系、约束、索引和访问策略 = 渲染的完整性/访问记录；
- 源码架构组件、决策、风险和行动 = 渲染的地图或台账。

调查每一处计数差异。除非用户明确要求抽样，否则当页面仅包含 representative、typical、key 或 example 记录时，不得将其描述为完整。

当存在活动页面时，检查它是否从 board 链接而来、是否只包含实质性的历史记录，且不与当前快照矛盾或取代之。

检查缺失的定价、schema、route、部署事实或验证结果是否以 `unknown` 状态可见，并附明确的解决路径。不得静默省略必需类别。

## 证据与安全

- 对每个 `shipped`、`done`、`validated` 或等同声明，向路径、测试、配置、命令结果、已维护契约或授权观测进行核实。
- 对每个 `in-progress`、`partial`、`blocked`、`candidate`、`unknown` 或 `untested` 项，确认其指明了缺口、依赖、决策或下一步行动。
- 检查源标签解释了所链接源码为何重要。对推断与冲突显式标注。
- 在相关凭证达到稳定结果后再同步持久 HTML。将本地、hosted-CI、preview/staging 和生产证据分别标注；不得将一类证据伪装成另一类，也不得把部分容器/构建凭证夸大为完整发布声明。
- 排除凭据、token、个人数据、原始生产 payload、私有 URL 和漏洞利用细节；只保留理解系统所需的契约、风险或控制信息。

## HTML 与浏览器检查

- 直接打开 board，确认其核心内容在 JavaScript 禁用下仍能渲染。
- 确认每个独立 HTML 页面（落地页、子页面和归档页）都恰好包含一个 `<aside class="toc">` TOC 块，并使用统一的标题文本——英文 `On this page` / 中文 `本页目录`——不得出现 `Contents`、`本页导航`、`本页内容` 或 `目录` 等变体，且 TOC 中的每个片段锚点都映射到正文中真实的 `id`。该规则定义在 `visual-interaction-and-accessibility.md` 的 "Page table of contents and navigation consistency" 一节。
- 在桌面、受限桌面、平板和移动宽度下，检查水平溢出、长源码路径（包括在狭窄单元格内堆叠文本的反斜杠风格的 Windows 路径）、密集表格、代码块、粘性导航、details 控件和图。
- 确认长页面使用可折叠的 disclosures，使首屏即可展示当前真相，而不必立即滚动。一次性展开所有 toggle，验证展开后的页面读起来仍是结构化小节，而不是一堆无序文字。
- 用键盘操作目录、筛选器、disclosure 控件、复制控件和架构链接。确认可见焦点、有意义的标签，且无键盘陷阱。
- 检查对比度、超越颜色的状态文本/标记、reduced-motion 行为、语义化标题/地标，以及非文本视觉的标签或替代。
- 当前端由参考站点约束时，在相同视口尺寸下将实现与所选参考原型对照。检查内容宽度、字号/行高、小节节奏、导航、面板几何、边框/圆角、密度、disclosure 行为、断点过渡和焦点/交互状态。仅调色板相似不算通过。
- 检查每个重复组件的每个实例，而非仅看首个示例。包括半宽卡片内的嵌套网格、最长的标题/路径、最密集的表格、每类图，以及筛选/展开状态。拒绝截断文本、重叠标签或箭头、普通卡片出现滚动条，以及页面级水平溢出。

## 交付记录

报告 board 路径、已检查的事实/证据、已执行的验证、高风险 unknown 或冲突，以及推荐的下一步行动。不得声称执行过未实际进行的浏览器验证。

## 把 board 作为产品交付面来验证

运行确定性检查：畸形 HTML、缺失 title 或 language、重复 ID、断开的相对链接、缺失片段、不可访问的图片，以及对不存在资产的引用。然后在环境允许时用真实浏览器打开页面。验证键盘导航、焦点、窄宽与宽版布局、溢出、表格、图、details 控件、筛选器，以及无 JS 阅读路径。

证据质量是独立于标记质量之外的一道关卡。抽样每个状态类别并追溯其归属。确认精确的 commit、CI、部署、migration、计数、日期、提供方和性能论断都得到支撑且范围清晰。一个合规页面仍可能危险地错误——当它把计划变成已完成状态，或把孤立观测变成通用指标时。

交付前，明确已更新的页面、已变更的事实、已执行的检查，以及剩余的 unknown。当 board 是项目的已维护真相源时，应将其纳入与实现相同的变更与验证周期，而不是当作可选的发布美化。

## 检查信息密度与阅读顺序

在页面目标视口下打开，按新读者的路径阅读。页面应在展示次要证据之前先揭示主要状态与决策。密集台账需具备筛选、锚点或分组，以降低检索成本但不隐藏行。图需要标签，以及对它所证明边界的文字说明。

移除不改变读者理解或可执行能力的控件。一张关系清晰的静态页面，往往胜过状态难以链接、打印或检视的交互页面。保留稳定的 URL 和片段目标，以便下一个 agent 在后续任务中能引用精确的证据面。
