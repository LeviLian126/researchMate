## 文档拓扑

按信息职责选择页面边界：

| 面 | 职责 |
| --- | --- |
| current snapshot | 项目身份、已验证的发布边界、商业状态、能力摘要、首要风险、下一步行动、新鲜度与导航 |
| product | 受众、买方、受益者、问题、承诺、场景、首次成功、市场证据、替代方案、分发、定价、信任与非目标 |
| delivery | 完整能力地图、用户旅程、MVP/MAP 边界、验收、实现证据、验证、依赖、负责人、风险与路线图状态 |
| architecture | 前端/后端/数据/集成/任务执行/运行时边界、请求与数据流、归属、失败/恢复与决策 |
| database contracts | 实体地图以及每个有证据的表、重大字段、类型、可空性、默认值、键、约束、索引、租户规则、RLS、生命周期与关系 |
| API contracts | 每个有证据的 endpoint/动作，包含调用方、认证、权限、请求、验证、响应、状态、失败、幂等/异步语义、来源与测试证明 |
| operations and decisions | 环境/发布状态、运行命令、可观测性、安全、成本、阻塞项、风险、决策台账与排序后的行动 |
| activity | 仅限重大历史发布、迁移、事故、安全评审、实验与已批准的里程碑 |

当低体量主题合并可改善阅读时则合并。当单页面会把完整台账藏在概览之后、逼迫过度滚动或把契约细节降为示例时则拆分该主题。保持页面名称描述性并维持导航一致；不要引入模式或客户端路由器。

## Workflow

从最强的可用 Node01/Node02 与仓库证据填充以下章节。摘要可仅保留与决策相关的事实，但数据库与 API 契约台账必须保存范围内每个有证据的字段与操作。

## 覆盖清单

在撰写页面之前构建可计数的清单。这是一道完成边界，而非可选的规划注释。

| 来源面 | 清单单元 |
| --- | --- |
| product and roadmap documents | 范围内每个维护中的能力、需求/故事 ID、验收条件、带状态项、定价/套餐事实、风险与决策 |
| frontend and backend | 每个用户可见路由/界面以及每个重大动作、处理程序、集成、后台任务与授权边界 |
| OpenAPI、route schema 或 action contract | 每个操作加上每个被引用的请求、响应、错误、权限与异步/幂等语义 |
| migrations 与维护中的 schema | 每个表/实体、每个有证据字段、PK/FK、unique/index/check/enum 约束、引用动作、RLS/租户规则与生命周期规则 |
| tests 与 configuration | 用于支撑 shipped、validated、环境、依赖或运营断言的每个结果或设置 |
| architecture 与 decision record | 每个重大组件、边界、交接、失败/恢复路径、所选方案、被拒绝的替代方案与重审触发条件 |

按类别记录预期计数与渲染计数。在完整台账中纳入每个清单项，或记录显式排除及其理由与来源。图示或摘要可放在台账之前，但不能取代台账。

只在完整覆盖存在之后才用示例解释某种模式。若证据体量较大，则跨链接页面拆分或生成紧凑的可展开记录，而不是将其采样压缩为演示样例。

## 证据记录

将此紧凑记录附在重大事实、带状态行、图示与决策上：

| 字段 | 记录 |
| --- | --- |
| status | `shipped`、`in-progress`、`candidate`、`deferred`、`blocked`、`unknown` 或某种验证状态 |
| evidence | 精确的来源路径、测试、配置、迁移、路由、命令结果、维护中的文档或经批准的外部来源 |
| confidence | confirmed、partial、inferred 或 absent |
| gap | 缺失事实、冲突、风险或限制条件 |
| next action | 具体的检查、决策、实现或验证步骤；已知时附负责人 |

## 1. 项目摘要与市场现状 — Node01

将这些事实放在靠近顶部，因为产品范围赋予架构与进度以意义：

| 领域 | 捕获 |
| --- | --- |
| identity | 项目名、简洁描述、生命周期/发布状态，以及已知时的当前负责人 |
| people | 目标用户、买方、受益者、角色、处境与最先可触达的受众/渠道 |
| problem | 当前变通方案/现状、痛点、不作为的代价与切换触发条件 |
| promise | 收窄的结果、价值路径、为何是现在，以及首个可观察的成功时刻 |
| market evidence | 支持与反对证据、置信度、替代方案与最冒险的假设 |
| commercial model | 价格、货币、计费节奏、套餐/权益、试用/限额、支付状态与证据；对猜测的定价显示 `unknown` |
| trust | 隐私、安全、可靠性、迁移、支持、合法性与其他采纳异议 |

当受众、买方与受益者不同时将它们分开保留。保留非目标与被拒绝的范围，因为它们解释了为何某个看似缺失的能力是有意为之的。

## 2. 能力图与交付 — Node01 及实现证据

按用户结果或旅程阶段对能力分组，而不是按仓库文件夹。每个能力使用一行/一卡：

| 字段 | 捕获 |
| --- | --- |
| capability | 面向用户的结果与相关的需求/故事 ID |
| journey | 触发条件、关键状态、首次成功，以及重大时的失败/恢复状态 |
| scope | MVP/MAP、后续 candidate、deferred、rejected 或非目标 |
| delivery | shipped、in-progress、blocked、not-started 或 unknown |
| acceptance | 可观察的成功标准与验证状态 |
| implementation | 负责模块/界面、依赖与证据 |
| risk and action | 具名的缺口/阻塞项、决策触发条件、负责人与下一步行动 |

将 shipped、in-progress、candidate、deferred/rejected 与 unknown 的工作渲染为不同的带标注泳道或时间线。不要仅依赖颜色，也不要把 candidate 工作承诺为已提交的交付。

## 3. 架构与运行时形态 — Node02

绘制从用户意图到持久结果的标注流程。每个节点或边界应说明职责、输入/输出、归属、依赖、证据与重大失败/恢复行为。

仅纳入适用的组件，但显式标记缺失/未知的核心层：

| 层 | 捕获 |
| --- | --- |
| 前端 | 用户界面、客户端状态、路由、渲染，以及客户端不应强制执行的内容 |
| 后端/领域 | 动作/用例、不变量、授权强制执行与模块归属 |
| 数据 | 仓库/存储、持久记录、查询/变更边界、多租户、留存与并发关注 |
| 集成 | 提供方、webhook、导入/导出、契约负责人、超时/重试/对账行为 |
| 工作执行 | 任务、队列、调度、事件生命周期、验收状态、执行器、重试负责人与可见进度 |
| 信任与运行时 | 认证/会话模型、权限、环境/部署边界、可观测性、运行成本与恢复权限 |

对于重大架构选择，展示所选方案、被拒绝的替代方案、理由/证据、后果、成本/可逆性，以及应重开该决策的条件。

## 4. 技术与数据契约 — Node02

### 技术栈台账

列出前端、后端、数据、基础设施、测试、CI/CD、分析/可观测性与第三方组件。对每一个，在有证据时展示版本、职责、存在原因、来源/配置位置、运行成本与退出/重审触发条件。

### 数据库台账

先展示紧凑的实体地图。让每个表/实体可展开，并包含：

| 字段 | 捕获 |
| --- | --- |
| 实体 | 表/集合名、业务用途、负责人与生命周期 |
| 字段契约 | 字段名、类型、可空/必填、默认/生成规则与业务含义 |
| 完整性 | 主/外/唯一键、索引、enum/check 规则、引用行为与迁移证据 |
| 访问 | 租户/用户边界、授权相关性、留存/删除、敏感分类与审计影响 |
| 关系 | 基数、依赖记录、一致性/并发行为与来源证据 |

不要泄露真实秘密值或个人记录。使用字段名与契约语义，而不是生产样本。

### API 与动作台账

展示紧凑的 endpoint/动作索引，并让每条记录可展开：

| 字段 | 捕获 |
| --- | --- |
| 标识 | method/event、path 或 action name、用途、调用方与所属模块 |
| 访问 | authentication、permission/tenant 规则、适用时的 rate/entitlement 规则 |
| 请求 | 必填/可选字段、类型、验证、幂等/关联行为 |
| 响应 | 成功形态/状态、异步验收与进度语义，以及对消费者的影响 |
| 失败 | 错误码/形态、重试/超时行为、安全恢复与用户可见状态 |
| 证明 | 来源路由/处理程序、schema/OpenAPI、契约测试、集成测试或显式缺口 |

## 5. 控制室

以决策就绪的快照收尾：

- 按环境或当前已验证边界的发布与验证状态；
- 首要风险、阻塞项、未知项与冲突证据，附严重程度/后果；
- 重大决策台账：上下文、决策、替代方案、后果、负责人与重审触发条件；
- 排序后的下一步行动，指明受影响的能力/契约与将关闭该项的证据。

就地替换被取代的当前事实。对于重大发布、版本、事故、迁移、安全评审、实验或已批准的里程碑，向链接的活动子页面添加一条紧凑记录：日期/版本、范围、证据、影响与后续事项。活动页仅作为历史背景；当前看板始终保持权威。
