# 代码与测试审查

在依赖运行时结果之前,独立检查变更源码及其真实调用路径。然后判断测试证据能否暴露目标可能失败的重要方式。使用表格聚焦注意力;从变更契约和风险中选择深度,而非将标题作为必填序列。

## 理解变更和调用路径

在评判代码之前,确认变更了什么以及为什么变更。

- 获取 diff:`git diff <base>...HEAD`。从 PR 元数据、CI 配置或远程跟踪分支中确定 base。不要在不检查的情况下默认使用 `main`。
- 从需求、issue 文本、PR 描述或验收标准中恢复意图。commit message 是弱证据;不要将其视为事实来源。
- 扫描无关变更:与需求无关的侧边修改、调试代码(`console.log`、`print`、`debugger`)、临时标志或大量重格式化噪声。将每一项标记为发现;它们会膨胀 diff 并隐藏真正的变更。
- 扫描变更代码中的占位信号:搜索 `TODO`、`FIXME`、`pass`、`return None`、`return True`、`return []`,或函数在不参考输入的情况下返回固定值。将每一项视为可疑,除非契约确实要求 stub。LLM 编写的代码可能具有正确的结构和类型,但决策逻辑缺失。

## 审计 AI 生成代码

LLM 生成的代码有一些仅靠编译和测试无法发现的典型失败模式。对每个变更文件按表格逐项扫描,然后调查在当前系统中适用且可达的候选项。

| 检查项 | 要发现什么 | 为什么是 LLM 特有的 |
| --- | --- | --- |
| 虚构 API | 调用不存在的方法、函数或字段,或使用了与已安装版本不匹配的参数签名 | LLM 会混合不同版本或库的记忆 |
| 占位返回值 | `return None`、`return True`、`pass` 或忽略输入的固定值 | LLM 生成正确的结构但决策逻辑为空 |
| 硬编码数据 | 伪装成真实逻辑的假数据,例如 `return [{"name": "test"}]` | LLM 使用示例数据来"让代码跑起来" |
| 静默降级 | try/except 吞没异常并返回默认值,既不记录日志也不重新抛出 | LLM 偏好"不报错的代码"而非正确的错误处理 |
| 测试削弱 | 删除、跳过或削弱现有测试,或在没有理由的情况下更新 snapshot/golden 文件 | LLM 可能更改断言来让测试通过 |
| 过宽权限 | 默认允许逻辑,缺少租户或所有者范围,无防护的 admin 路由 | LLM 经常跳过多租户隔离 |
| 缺失错误处理 | 无界循环、N+1 查询、无 timeout 或 retry、资源未关闭 | LLM 编写正常路径并跳过资源管理 |
| 虚构依赖 | 导入不存在的包,或假设一个从未定义的配置键 | LLM 记忆中包含过时或虚构的包名 |
| 脱节实现 | 新代码从未从生产 entrypoint、registration、route、job 或 build artifact 触达 | LLM 能实现一个看似可信的孤岛,却不接入系统 |
| 仅表面合理的逻辑 | 类型和控制流看起来完整,但必需的状态转换、持久化写入、权限或副作用从未发生 | 表面连贯性可能掩盖缺失的业务结果 |
| Cargo-cult 抽象 | 不必要的 interface、helper、factory 或泛型 wrapper,遮蔽了一条具体规则及其属主 | 在没有真实 seam 或第二实现的情况下复刻熟悉的模式 |
| 上下文矛盾 | 代码遵循一条记忆中的约定或邻近示例,却与当前仓库契约、config 或依赖版本冲突 | 生成变更可能组合了各自合理但不兼容的上下文 |

对于每个发现,记录:文件、行号、问题、预期行为和严重级别。根据已安装版本和官方文档验证 API 是否存在,而非依赖模型记忆。在将导入标记为虚构之前,先检查该包是否列在 lockfile 中或已安装在 `node_modules` 或虚拟环境中。

## 审查测试策略和强度

通过的测试不能证明代码是正确的。验证测试是否真正测试了契约。

- 测试是执行了目标代码,还是仅验证 mock 调用和固定返回值?一个只断言 `mock.called` 而不检查真实行为的测试是 mock 表演。

从公开契约设计测试——接口签名、schema、验收标准和错误规格——而非从阅读实现出发。镜像代码内部分支的测试共享实现者的假设,无法暴露产生 bug 的盲区。先从契约枚举场景(正常、边界、错误、状态转换、并发、授权),再读代码仅用于确认覆盖缺口。当独立 subagent 编写测试时,只给接口和验收标准,不给实现 diff。

在要求更多测试之前,先构建一个紧凑的风险图。使用目标和公开边界来决定哪些维度能揭示实质性失败。

| 测试维度 | 何时可证伪 |
| --- | --- |
| 正常和边界行为 | 承诺的结果、大小/范围限制、空状态或兼容性边界 |
| schema 和逻辑有效性 | 格式错误的类型、缺失/null/unknown 字段,或有效字段形成无效组合 |
| 授权和滥用 | actor、tenant、object、role、route、method、workflow 顺序或服务端字段可被操纵 |
| 状态、重放和并发 | 步骤可被跳过/重排/重复,交付可被重复,或共享状态可发生竞争 |
| 副作用和不变量 | 持久化、消息、扣费、job、清理、属主或总计与返回结果产生偏离 |
| 资源和依赖失败 | 输入可放大工作量,或 timeout、quota、部分响应、重启和 retry 可破坏或放大影响 |
| property、fuzz、performance、mutation | 示例无法覆盖重要输入空间、parser、不变量、容量声明或断言强度问题 |

优先选择能触达真实契约的最便宜确定性层。仅当更小的测试无法忠实地观察风险时,才升级到集成、浏览器、故障、性能、fuzz 或 mutation 证据。审查中发现任何 bug、绕过、崩溃、race 或病态输入,都应转化为最小化的回归测试或保留的 corpus case,前提是仓库有合适的 seam。

### Bug 修复证据链

对于 bug 修复,以下五个步骤都是必需的。缺少任何一步都会降低结论的可信度。

1. 在 baseline 上复现失败。
2. 添加最小回归测试。
3. 证明该测试在 baseline 上失败。
4. 证明该测试在修复版本上通过。
5. 运行相关回归套件以确认无副作用。

### 测试反模式

将以下任何一项标记为 Major 严重级别:

- 测试之间的共享可变状态或执行顺序依赖。
- 在可以使用条件等待或确定性 fixture 的地方使用任意 `sleep`。
- 完全替换被验证集成行为的 mock。
- 依赖真实外部副作用的测试(实时 API 调用、未清理的真实数据库写入)。
- 未经人工审查语义变更就更新的 snapshot 或 golden 文件。
- 在没有理由的情况下被删除、跳过或断言被削弱的测试。

## 运行静态和 build 门禁

运行仓库自身的命令。不要发明不存在的命令。

按以下顺序发现命令:

1. `AGENTS.md`、`CONTRIBUTING.md`、`README`
2. `Makefile`、`justfile`、`Taskfile.yml`
3. `package.json` scripts、`pyproject.toml`、`tox.ini`、`go.mod`、`Cargo.toml`
4. `.github/workflows`、pre-commit 配置

运行适用于变更交付物的仓库门禁。当多个门禁适用时,优先运行格式检查、lint、类型检查、build,然后是针对性测试,以便让便宜的失败尽早浮现。为每个实际运行的命令记录确切命令及其退出码或结果;不要仅因为它出现在此排序中就运行无关的 build 或完整测试套件。

当没有标准命令时:描述你搜索了什么,提出最小可行命令,并将其标记为 NOT_RUN 直到实际执行。不要猜测一个命令然后报告为通过。

## 需记录的发现

对于每个发现,记录检查了什么、证据、影响和严重级别。将实质性发现汇入 `README.md` 中的结论。静态门禁失败至少为 Major;虚构 API、脱节的核心路径或必需流程上的占位返回值为 Blocker。
