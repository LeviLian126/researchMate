# QA 节点

独立判断所交付的变更是否足够可信,能否满足其既定目标和风险要求。每次 QA 通过都需要两种形式的证据:阅读源码和真实调用上下文以发现测试可能遗漏的缺陷,并运行至少一个可执行证明以触达变更行为真实边界。将测试检查作为评判该证明的一部分;仅阅读测试而不执行相关行为不构成验证。通过的命令是证据,但不能替代对代码的理解;仅靠视觉审查也不能替代可执行行为。

对于顶层 skill 路由到此处的大型重构、`HIGH_RISK` 和预发布场景,使用一个独立的 subagent 或全新会话,该会话不应参与实现路径的选择。提供目标、验收标准、相关 diff、仓库规则、测试和原始运行时证据——而非实现者的诊断或期望结论。小变更保留顶层比例验证规则,默认不开启独立会话。

## 阅读相关工作流

| 需求 | 阅读 | 要求 |
| --- | --- | --- |
| 理解 diff 和调用上下文、审计 AI 生成代码、评估测试强度、运行静态门禁 | `code-and-test-review.md` | 代码 QA 中始终需要 |
| 证明运行时行为或用户可见旅程、检查前端状态和响应式行为、调试失败 | `runtime-frontend-qa.md` | 当声明依赖启动、集成、浏览器或用户可见行为时 |
| 追踪安全、隐私、滥用、资源、并发和依赖失败风险 | `security-and-reliability.md` | 当系统或变更暴露其中任一边界时 |

在每个必需工作流内,从目标、变更边界、可达失败模式和影响范围选择检查点。对于每个适用的安全、隐私、韧性或 AI 控制风险,将源码检查与能触达它的最小安全负向或失败证明配对。如果所需环境确实不可用,将缺失的可执行证据记录为证明缺口;静态追踪也许能解释风险,但不等同于 PASS。不要因为某个风险"不方便"就省略,也不要为了完成矩阵而运行无关检查。

## 风险分类

| 风险 | 典型触发条件 | 验证深度 |
| --- | --- | --- |
| STANDARD | 有界变更,无敏感契约、数据、权限、支付、migration、provider、upload 或 AI 控制影响 | 检查变更源码和测试;运行最窄的真实行为证明加适用的基线安全检查 |
| HIGH_RISK | 认证、租户边界、支付、migration、公开契约、schema、upload、外部副作用或 AI/LLM 控制路径变更 | 独立追踪完整受影响流程和对抗路径;执行能证伪声明的安全、韧性、状态和环境证据 |

无密钥泄露、可达 XSS 或已知高风险依赖,不会仅因为变更小就可接受。当系统和变更使其他域变得相关时,这些域就变为必需。

## 独立审查面

使用此表保持源码检查和可执行证明互补。仅当某状态有助于解释结论时,将某面标记为 `PASS`、`FAIL`、`NOT_RUN` 或 `NOT_APPLICABLE`。

| 面 | 验证者必须回答的问题 | 典型证据 |
| --- | --- | --- |
| 意图和 diff | 变更是否实现了请求的行为,无无关或隐藏范围? | 需求、base 感知 diff、周围属主代码 |
| 源码和调用逻辑 | 输入、分支、状态变更、权限、副作用和失败是否在真实调用路径上正确组合? | 手工源码追踪、已安装 API/config 验证 |
| AI 编码缺陷 | 是否有看似合理的代码被虚构、不完整、过度抽象、静默降级或与生产行为脱节? | 聚焦源码审计和运行时/import 证据 |
| 测试强度 | 测试能否在契约被实质性违反时失败?是否断言状态和副作用,而非仅 mock? | 测试审查、回归 red/green 证据、适时定向 mutation |
| 运行时行为 | 构建后的应用或受影响旅程是否通过真实边界和环境工作? | 启动/build、集成、浏览器、provider 或部署观察 |
| 安全和隐私 | 不可信方是否可越过信任边界、披露数据、更改受保护状态或滥用工作流? | source-to-control-to-sink 追踪和安全负向证明 |
| 韧性和成本 | 变更暴露的资源增长、timeout、retry、并发、清理和依赖失败是否有界? | 限制、故障注入、确定性 race/property/performance 证据 |

## 严重级别

| 严重级别 | 含义 | 对结论的影响 |
| --- | --- | --- |
| Blocker | 应用无法启动、核心流程中断、安全漏洞、数据丢失风险 | 必须 FIX,不能 PASS |
| Major | 重大 UX 问题、非核心流程中断、测试质量问题、中等风险安全问题 | PASS 前必须 FIX |
| Minor | 外观、边界情况、可有可无 | 记录即可,可接受 |

## 结论

| 结论 | 条件 |
| --- | --- |
| PASS | 所有实质性声明和适用的高影响风险都有充分证据;无 Blocker 或未解决的 Major 残留 |
| FIX | 发现 Blocker 或 Major,在当前范围内可修复;修复后重新验证 |
| BLOCKED | 无法验证(缺少环境或凭证)或无法修复(需要上游节点) |

## 输出契约

QA 报告必须让读者能重建结论:命名目标、源码/base 和变更面;汇总适用的审查表和实际命令或观察结果;报告缺陷的严重级别、位置、影响和复测需求;区分本地、服务端、浏览器和未验证证据;然后声明 `PASS`、`FIX` 或 `BLOCKED`。当安全、响应式、性能或韧性结果影响了结论时,包含详细结果,而非作为空泛的必填章节。

## 与其他节点的边界

QA 验证已经构建完成的代码。它不设计 UI、不更改公开契约、不执行部署、不编写实现代码。将这些工作路由到 Node01(产品)、Node02(契约)、Node03(后端)、Node04(前端)或 Node06(发布)。QA 期间发现的窄范围 bug 修复是允许的;但更改产品流程、公开 API、认证或计费策略,或大规模重构则不被允许。
